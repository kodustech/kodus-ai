## Por que este guia é importante

Todo time de engenharia tem um doc de "boas práticas" em algum lugar. O problema é que as sugestões da IDE não o leem, os revisores esquecem os detalhes, e o documento vai perdendo autoridade aos poucos. Este guia transforma seu handbook em guardrails ativos, para que o Kody aplique essas regras em todo pull request e aponte a seção em que o código se desviou.

Vamos usar dois blocos de construção:

- [Kody Rules](/pt-BR/how_to_use/code_review/configs/kody_rules) – cada item da política vira uma verificação em nível de arquivo ou de PR que referencia o handbook.
- [Agentes personalizados](/pt-BR/how_to_use/code_review/custom_agents) – o handbook é vinculado como doc, e cada apontamento cita a regra que aplica.

## Checklist de pré-voo

- Você tem permissão para editar **Code review → Kody Rules**.
- O handbook está no repositório (por exemplo `docs/engineering-standards.md`). Se o seu estiver em outro caminho, ajuste conforme necessário.
- Você sabe quais tópicos devem ser avaliados em nível de arquivo (controllers, configs) e quais em nível de PR (feature flags, narrativas de rollout, arquitetura).

<Callout icon="layers">
  Mantenha o handbook sob controle de versão. Regras e agentes o leem da branch para a qual um pull request aponta, então toda edição passa por um pull request com responsáveis que aprovam.
</Callout>

## Fase 1 – Molde um pacote de políticas amigável para regras

1. Crie ou reutilize um arquivo markdown como `docs/engineering-standards.md`.
2. Organize o conteúdo em itens curtos e verificáveis:

```md
# Engineering Standards

## Error handling
- Never swallow errors.
- Do not log PII or secrets.
- External requests must have a timeout and retry policy.

## Architecture
- No direct cross-module imports from `domain/*` into `web/*`.
- New endpoints must include tracing fields (e.g., requestId) and structured logs.
- Feature flags are mandatory for risky changes.
```

<Tip>
  Torne cada item atômico. Quando uma regra disparar, não deve haver nenhum debate sobre o que precisa mudar.
</Tip>

## Fase 2 – Aponte cada regra para o documento real

Referencie o handbook de verdade em vez de colar trechos em cada instrução.

```text
Use @file:docs/engineering-standards.md (Architecture section) as the policy source.
Only flag code that clearly violates those bullets. If the section is missing, say so.
```

- Troque por outros caminhos de arquivo para pacotes específicos de domínio (por exemplo `@file:docs/mobile.md`).
- Precisa de só um pedaço do arquivo? Acrescente âncoras de linha, como `@file:docs/engineering-standards.md#L40-L72`, para que a regra consuma apenas aquela seção.

<Callout icon="link">
  Uma única referência mantém tudo sincronizado. Atualize o handbook uma vez e cada regra passa a aplicar a versão mais recente.
</Callout>

## Fase 3 – Traduza seções em Kody Rules

Na barra lateral, abra **Code review → Kody Rules**. Na aba **Review Rules**, clique em **New rule** e mapeie cada seção da política para o modo de execução e o path certos.

| Seção da política      | Modo de execução | Exemplo de path                    | Severidade |
| ---------------------- | ---------------- | ---------------------------------- | ---------- |
| Tratamento de erros    | Per file         | `backend/**/*.ts`                  | High       |
| Arquitetura            | Per PR           | não se aplica                      | Critical   |
| Logging e tracing      | Per file         | `web/apps/**/controllers/**/*.ts`  | Medium     |
| Segurança / PII        | Per file         | `**/*`                             | Critical   |

### Exemplo em nível de arquivo

```
Rule name: Enforce tracing fields on new endpoints
Execution mode: Per file
Path: web/apps/**/controllers/**/*.ts
Severity: High
Instructions:
  Compare fileDiff with Architecture → New endpoints in @file:docs/engineering-standards.md.
  Flag handlers that lack requestId tracing AND structured log statements.
  Quote the diff chunk that violates the policy.
```

### Exemplo em nível de PR

```
Rule name: Require feature flags for risky changes
Execution mode: Per PR
Severity: Critical
Instructions:
  Scan pr_files_diff for routes/services/domain files that add major functionality.
  If no feature flag file is touched, cite “Architecture → Feature flags are mandatory” and request the rollout plan.
```

<Info>
  As regras entendem variáveis (`fileDiff` por arquivo, `pr_files_diff` e as outras variáveis `pr_*` por PR) e referências de arquivo. Veja a lista completa no [guia de Kody Rules](/pt-BR/how_to_use/code_review/configs/kody_rules).
</Info>

## Fase 4 – Ou dê o handbook a um agente personalizado

Um agente personalizado lê o handbook como um doc vinculado e precisa citar a regra por trás de cada apontamento. Uma citação que não está no doc na branch de destino é descartada. Os agentes personalizados estão em beta, nos planos Teams e Enterprise e durante o trial; o Kodus self-hosted também precisa de `BETA_FEATURES=true`.

<Steps>
  <Step title="Crie o agente">
    Em **Code review → What to review → Custom agents**, clique em **New agent → Templates → Blank**. Dê a ele o nome **Engineering standards**.
  </Step>
  <Step title="Vincule o handbook">
    Em **Files & knowledge → Skills & docs**, clique em **Add skill or doc → Add by path** e informe `docs/engineering-standards.md`. Um doc é carregado inteiro em cada review, então mantenha-o curto. Um handbook longo funciona melhor como uma skill com arquivos de referência.
  </Step>
  <Step title="Escreva as instruções">
    ```text
    Flag changes that break a rule in docs/engineering-standards.md.
    Quote the rule you apply. Ignore tests and generated code.
    ```
  </Step>
  <Step title="Teste e depois ligue">
    Rode o **Try it** num pull request que quebra uma regra. Cada comentário cita a regra como **Rule** (`docs/engineering-standards.md`) com o item citado.
  </Step>
</Steps>

Veja [Skills, documentação e ferramentas](/pt-BR/how_to_use/code_review/custom_agents_knowledge_and_tools) para os orçamentos e a detecção.

## Fase 5 – Teste, observe e mantenha vivo

<AccordionGroup>
  <Accordion title="Crie um PR de verificação">
    Crie um PR descartável que viole cada seção e deixe o Kody revisá-lo (comente `@kody start-review` se o review não tiver começado). Confira se os comentários inline e de nível de PR citam os itens certos. Rode o agente sob demanda com `@kody -v engineering-standards`.
  </Accordion>
  <Accordion title="Ajuste ruído e severidade">
    Durante o rollout, observe com que frequência cada regra dispara. Restrinja os globs de arquivo, adicione exclusões ou ajuste a severidade até que o sinal atenda às expectativas.
  </Accordion>
  <Accordion title="Atualize docs e regras juntos">
    Sempre que o handbook mudar, atualize o markdown e as regras ou instruções de agente relacionadas no mesmo PR, para que os revisores validem o pipeline inteiro.
  </Accordion>
</AccordionGroup>

## Checklist rápido

- [ ] `docs/engineering-standards.md` existe com itens fáceis de escanear.
- [ ] Toda regra referencia o pacote de políticas com `@file`, então lê o texto mais recente.
- [ ] Kody Rules em nível de arquivo e de PR cobrem suas seções críticas.
- [ ] Opcional: um agente personalizado segue o handbook e o cita.
- [ ] Um PR de dry-run confirmou os comentários inline e o resumo do PR antes do rollout amplo.
