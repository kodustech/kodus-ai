## Por que a conformidade precisa de revisão automatizada

Frameworks de conformidade como SOC2, HIPAA e GDPR exigem práticas de código específicas para tratamento de dados, controle de acesso e registro de auditoria. Revisões manuais pegam algumas violações, mas são inconsistentes, principalmente quando quem revisa não é especialista em segurança.

Este cookbook configura regras que aplicam os requisitos de conformidade em todo PR.

## Passo 1 — Defina suas Memories de conformidade

Comece ensinando à Kody os princípios gerais de conformidade:

```
@kody remember: we are SOC2 compliant. All data access must be logged
with who accessed what, when, and from where.
```

```
@kody remember: PII (personally identifiable information) must never
appear in logs, error messages, or API responses. PII includes:
name, email, phone, address, SSN, date of birth, IP address.
```

```
@kody remember: all data at rest must be encrypted. Database fields
containing PII must use application-level encryption.
```

```
@kody remember: access control follows least privilege principle.
New endpoints default to authenticated + authorized, never public.
```

## Passo 2 — Crie regras de trilha de auditoria

Crie cada regra em **Code review → Kody Rules**: na aba **Review Rules**, clique em **New rule** e preencha os campos como mostrado abaixo.

### Regra de registro de auditoria

```
Rule name: Data mutations must have audit logging
Execution mode: Per file
Path: src/services/**/*.ts, src/repositories/**/*.ts
Severity: Critical
Instructions:
  If fileDiff contains create, update, or delete operations
  on user data or sensitive records, verify that an audit log
  entry is created. Look for calls to auditService.log(),
  AuditLogger, or @Audited decorator.
  Reference @file:src/shared/audit/audit.service.ts for
  the approved audit patterns.
```

### Regra de retenção de dados

```
Rule name: Soft delete required for user data
Execution mode: Per file
Path: src/**/*.ts
Severity: Critical
Instructions:
  Flag any hard delete (DELETE FROM, .delete(), .destroy())
  on tables/collections that contain user data.
  User data must use soft delete (deletedAt timestamp)
  for compliance with data retention policies.
```

## Passo 3 — Crie regras de tratamento de dados

### Prevenção de exposição de PII

```
Rule name: No PII in logs or error responses
Execution mode: Per file
Path: src/**/*.ts
Severity: Critical
Instructions:
  Check fileDiff for logging statements (logger.*, console.*)
  and error response builders that might include PII fields:
  email, name, phone, address, ssn, dateOfBirth, ipAddress.
  These must be redacted or excluded before logging/responding.
```

### Requisito de criptografia

```
Rule name: PII fields must use encryption helpers
Execution mode: Per file
Path: src/entities/**/*.ts, src/models/**/*.ts
Severity: Critical
Instructions:
  If fileDiff adds or modifies entity/model fields that contain
  PII (see list above), verify they use the @Encrypted decorator
  or encryptionService helper. Reference
  @file:src/shared/encryption/encryption.service.ts.
```

## Passo 4 — Crie regras de controle de acesso

```
Rule name: New endpoints must have auth guards
Execution mode: Per PR
Severity: Critical
Instructions:
  Check pr_files_diff for new route definitions or controller
  methods. Every new endpoint must include:
  1. Authentication guard (@UseGuards(AuthGuard))
  2. Authorization decorator (@Roles or @Permissions)
  3. Rate limiting (@Throttle or equivalent)
  If any endpoint is intentionally public, it must have
  an explicit @Public() decorator with a code comment
  explaining why.
```

## Passo 5 — Adicione uma verificação de conformidade em nível de PR

```
Rule name: Compliance impact assessment
Execution mode: Per PR
Severity: High
Instructions:
  If pr_files_diff touches any file in src/entities/,
  src/models/, or database migrations, check whether:
  1. New fields handling PII are documented
  2. Data flow changes are noted in pr_description
  3. Privacy impact is considered
  If the PR adds new data collection, flag it for
  privacy review.
```

## Passo 6 — Configure para aplicação

1. Em **Code review → General → Review feedback**, ative **Request changes on critical issues** (não disponível quando todos os provedores conectados são GitLab). A Kody define o review como Request Changes quando posta um comentário inline Critical, e retira o pedido assim que esses apontamentos são resolvidos
2. Defina todas as regras de conformidade com severidade **Critical**
3. Use herança de regras para aplicar as regras de conformidade em todos os repositórios da organização — crie-as com **Global** selecionado no seletor de escopo

O Request changes segue os comentários inline, então ele é definido por regras **Per file**. Uma regra **Per PR** posta um único comentário no pull request e não o define.

## Checklist

- [ ] As Memories de conformidade ensinam os princípios gerais
- [ ] A regra de registro de auditoria cobre todos os caminhos de mutação de dados
- [ ] A regra de exposição de PII cobre logs e respostas de erro
- [ ] A regra de criptografia cobre as definições de entidade/model
- [ ] A regra de controle de acesso cobre todos os novos endpoints
- [ ] **Request changes on critical issues** está ativado
- [ ] As regras estão no escopo **Global** (toda a organização) para manter a consistência
- [ ] Um PR de teste confirmou que as regras disparam corretamente

Para saber mais sobre a configuração de regras, veja [Kody Rules](/pt-BR/how_to_use/code_review/configs/kody_rules).
