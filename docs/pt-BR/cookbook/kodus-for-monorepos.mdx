## O desafio

Em um monorepo, pacotes diferentes têm padrões diferentes. Seu frontend em React se preocupa com padrões de componentes, seu backend em NestJS se preocupa com injeção de dependência, e suas libs compartilhadas se preocupam com estabilidade de API. Uma revisão única para todos não funciona.

## Visão geral da estratégia

O Kodus suporta três níveis de configuração que se encaixam naturalmente em um monorepo:

| Nível | Aplica-se a | Exemplo |
|-------|-------------|---------|
| **Global** | Todos os repositórios | "Nunca commitar arquivos `.env`" |
| **Repositório** | O monorepo | "Usar conventional commits" |
| **Diretório** | Um pacote específico | "Componentes React devem usar PascalCase" |

## Passo 1 — Mapeie seus pacotes

Identifique as áreas distintas no seu monorepo e as necessidades de revisão de cada uma:

```
monorepo/
├── apps/
│   ├── web/          → React rules, component patterns
│   ├── api/          → NestJS rules, architecture boundaries
│   └── mobile/       → React Native rules
├── libs/
│   ├── shared/       → API stability, breaking change detection
│   └── ui/           → Design system compliance
└── infra/            → Terraform/IaC rules
```

## Passo 2 — Crie escopos de diretório

Escolha o monorepo no seletor de escopo no topo do grupo **Code review**, abra o seletor de novo e escolha **Add directory scope**. Em **Select directories**, escolha uma ou mais pastas de pacote que compartilham as mesmas configurações de revisão e clique em **Add directory scope**. Cada escopo de diretório aparece recuado sob o repositório no seletor — escolha-o para configurá-lo.

Cada escopo de diretório pode ter seus próprios:
- **Kody Rules** (em nível de arquivo e de PR)
- **What to review** (quais categorias habilitar e a severidade mínima para publicar)
- **Custom agents**, somados aos do repositório
- **Ignored files** (em **General**)

Um pull request usa as configurações de um diretório quando toca esse diretório configurado e nenhum outro diretório configurado. Veja [Configurações por diretório](/pt-BR/how_to_use/code_review/configs/directory_level) para saber como um pull request escolhe suas configurações.

## Passo 3 — Escreva regras direcionadas

Em **Code review → Kody Rules**, na aba **Review Rules**, clique em **New rule**. Uma regra criada em um escopo de diretório não tem **Path**, então se aplica a todos os arquivos de um pull request revisado com as configurações daquele escopo de diretório. Um pull request que toca dois ou mais escopos de diretório, ou nenhum, é revisado com as configurações do repositório, e aí as regras de **todos** os escopos de diretório se aplicam a todos os seus arquivos. Escreva as regras de diretório de modo que continuem valendo nesse caso, por exemplo citando a pasta nas instruções. Veja [Herança de regras](/pt-BR/how_to_use/code_review/configs/rules_inheritance). Para direcionar uma parte de um pacote, crie a regra no escopo do repositório com um glob em **Path**.

### Regra de frontend (escopo: o monorepo, com um path)

```
Rule name: React components must use design system tokens
Execution mode: Per file
Path: apps/web/src/components/**/*.tsx
Severity: High
Instructions:
  Check fileDiff for hardcoded colors, spacing, or font sizes.
  Components must import tokens from @file:libs/ui/src/tokens.ts.
  Flag any hex color, pixel value, or font-size not from the token file.
```

### Regra de backend (escopo: o diretório `apps/api/`)

```
Rule name: Domain layer must not import from infrastructure
Execution mode: Per file
Severity: Critical
Instructions:
  In files under apps/api/src/domain, check fileDiff for any import from
  "../infrastructure", "../../infrastructure", or any path containing
  "/infrastructure/". Domain modules must only depend on other
  domain modules and shared interfaces.
```

### Regra de biblioteca compartilhada (escopo: o diretório `libs/shared/`)

```
Rule name: Public API changes require changeset
Execution mode: Per PR
Severity: High
Instructions:
  If pr_files_diff modifies any file in libs/shared/src/index.ts
  or adds/removes exports, check that a changeset file exists
  in the .changeset/ directory. If missing, flag it as a
  potential breaking change without documentation.
```

## Passo 4 — Use Memories para convenções transversais

Algumas convenções valem para tudo. Ensine-as como Memories:

```
@kody remember: in this monorepo, all packages use ESM imports.
CommonJS require() is not allowed anywhere.
```

```
@kody remember: shared libs must maintain backward compatibility.
Any breaking change requires a major version bump and a changeset.
```

## Passo 5 — Defina o limite de severidade por diretório

Pacotes de alto tráfego podem precisar de filtros mais rígidos. Escolha o diretório no seletor de escopo, abra **What to review** e defina **Minimum severity to post**:

- **apps/web/** — **Medium** (o frontend anda rápido)
- **libs/shared/** — **Low/All** (estabilidade importa)
- **infra/** — **High** (menos, mas críticos)

O limite só se aplica às Kody Rules quando **Apply the threshold to Kody Rules** está ativado.

## Passo 6 — Ignore caminhos gerados

Adicione ignores específicos do monorepo para evitar ruído: em **Code review → General → Review scope**, clique em **Edit** em **Ignored files**, ou defina-os no `kodus-config.yml` (lido só quando **Prefer kodus-config.yml settings** está ativado para o repositório):

```yaml
ignorePaths:
  - "**/node_modules/**"
  - "**/dist/**"
  - "**/build/**"
  - "**/*.generated.ts"
  - "**/prisma/migrations/**"
  - "**/coverage/**"
```

## Dicas

- Comece com 2-3 regras por diretório e expanda com base no que seu time realmente aponta nas revisões
- Use herança de regras — regras em nível de organização cobrem segurança, nível de repositório cobre convenções, nível de diretório cobre arquitetura
- Se uma regra dispara com muita frequência em um pacote, mas é válida nos demais, restrinja o **Path** dela ou reescreva-a. **Override and disable for this scope** só marca uma regra herdada como desabilitada na lista; um review ainda a aplica

Para saber mais sobre escopos de diretório, veja [Configurações por diretório](/pt-BR/how_to_use/code_review/configs/directory_level). Para herança de regras, veja [Herança de regras](/pt-BR/how_to_use/code_review/configs/rules_inheritance).
