## Por que um pipeline focado em segurança

O code review genérico pega estilo e bugs. Mas vulnerabilidades de segurança — injeção SQL, segredos hardcoded, padrões de autenticação inseguros — precisam de regras dedicadas que tratem os apontamentos como bloqueios críticos.

Este cookbook configura uma camada de segurança em primeiro lugar por cima do seu review existente.

## Passo 1 — Habilite a análise de segurança

Confirme que a categoria **Security** está ativada em **Code review → What to review**, ou no `kodus-config.yml` (lido só quando **Prefer kodus-config.yml settings** está ativado para o repositório):

```yaml
reviewOptions:
  security: true
```

Isso dá a você as verificações de segurança nativas do Kodus. As regras abaixo acrescentam por cima as políticas de segurança específicas do seu time.

## Passo 2 — Crie regras focadas no OWASP

Crie cada regra em **Code review → Kody Rules**: na aba **Review Rules**, clique em **New rule** e preencha os campos como mostrado abaixo.

### Prevenção de injeção SQL

```
Rule name: No raw SQL queries
Execution mode: Per file
Path: **/*.ts, **/*.js, **/*.py
Severity: Critical
Instructions:
  Flag any use of string concatenation or template literals
  to build SQL queries. Look for patterns like:
  - `query("SELECT ... " + variable)`
  - `query(\`SELECT ... ${variable}\`)`
  - `execute(f"SELECT ... {variable}")`
  Must use parameterized queries or an ORM instead.
```

### Detecção de segredos hardcoded

```
Rule name: No hardcoded secrets or credentials
Execution mode: Per file
Path: **/*
Severity: Critical
Instructions:
  Flag any string that looks like an API key, password,
  token, or secret in fileDiff. Patterns to catch:
  - Variables named *_KEY, *_SECRET, *_TOKEN, *_PASSWORD
    assigned to string literals
  - Strings matching patterns like "sk_live_", "ghp_",
    "AKIA", "Bearer " followed by a long string
  - Connection strings with embedded passwords
  Secrets must come from environment variables or a vault.
```

### Bypass de autenticação

```
Rule name: Auth middleware must not be skipped
Execution mode: Per PR
Severity: Critical
Instructions:
  Check pr_files_diff for any route or controller that
  handles user data without auth middleware. Look for:
  - New routes without @UseGuards, @Authenticated,
    or equivalent decorators
  - Middleware bypass patterns like skipAuth: true
  - Public endpoints that access user-specific data
  Reference @file:src/shared/auth/guards/auth.guard.ts for the
  approved auth patterns.
```

### Prevenção de XSS

```
Rule name: No dangerouslySetInnerHTML without sanitization
Execution mode: Per file
Path: **/*.tsx, **/*.jsx
Severity: Critical
Instructions:
  Flag any use of dangerouslySetInnerHTML in fileDiff.
  If used, verify the input is sanitized with DOMPurify
  or an equivalent library. Unsanitized HTML injection
  is a critical XSS vulnerability.
```

## Passo 3 — Ensine Memories de segurança

Crie convenções persistentes que valem para tudo:

```
@kody remember: all user input must be validated and sanitized
before use. Never trust client-side data.
```

```
@kody remember: all API endpoints that handle sensitive data
must use HTTPS only and include rate limiting.
```

```
@kody remember: error messages must never expose stack traces,
internal paths, or database details to the client.
```

## Passo 4 — Configure para tolerância zero

Para regras de segurança, você quer que os apontamentos críticos bloqueiem e nunca sejam filtrados:

1. Em **Code review → General → Review feedback**, ative **Request changes on critical issues** (não disponível quando todos os provedores conectados são GitLab). O Kody define o review como Request Changes quando posta um comentário inline Critical
2. Defina as regras de segurança com severidade **Critical**
3. Em **Code review → What to review**, deixe **Apply the threshold to Kody Rules** desativado, que é o padrão. As regras então postam em qualquer severidade, seja qual for o **Minimum severity to post**

O Request changes segue os comentários inline, então ele é definido por regras **Per file**. Uma regra **Per PR**, como a do middleware de autenticação, posta um único comentário no pull request e não o define.

## Checklist

- [ ] Categoria **Security** ativada
- [ ] A regra de injeção SQL cobre todo o código que interage com o banco de dados
- [ ] A regra de detecção de segredos cobre todos os tipos de arquivo
- [ ] A regra de bypass de autenticação referencia seus padrões de autenticação reais
- [ ] A regra de XSS cobre todos os arquivos de componentes frontend
- [ ] As Memories de segurança ensinam princípios gerais de codificação segura
- [ ] **Request changes on critical issues** está ativado, e **Apply the threshold to Kody Rules** está desativado
- [ ] Um PR de teste confirmou que as regras disparam corretamente

Para saber mais sobre a configuração de regras, veja [Kody Rules](/pt-BR/how_to_use/code_review/configs/kody_rules).
