Quando o produto está dividido em vários repositórios — por exemplo, um frontend que chama uma API de backend, ou um serviço que depende de um pacote de contratos compartilhados — a revisão de um único repo pode deixar passar quebras na fronteira. **Repositórios vinculados** (*linked repositories*) dão à Kody contexto opcional e sob demanda desses codebases irmãos durante o code review.

> **Requisito de plano:** Repositórios vinculados estão disponíveis nos planos **Teams** e **Enterprise**, e durante o trial. Os planos Free não incluem contexto entre repositórios. O self-hosted precisa de uma licença Enterprise.

Isso é diferente de [compartilhar padrões de codificação entre repositórios](/pt-BR/knowledge_base/how-to-share-standards-across-repositories) (regras e herança no nível da organização). Repositórios vinculados compartilham **contexto de código-fonte** para uma revisão, não regras de revisão.

## O que faz

Para um repositório em revisão, você declara até **3 repositórios vinculados** na mesma organização. Durante a revisão:

1. A Kody primeiro verifica se o diff do PR toca algo com formato de fronteira — uma verificação rápida e fixa, que não custa nada.
2. Se o diff parece tocar uma **superfície de contrato** (DTOs, exports, literais de string, chaves de status, caminhos no formato de API e similares), as ferramentas entre repositórios são habilitadas.
3. Os repos vinculados são **clonados de forma lazy**, só quando a Kody realmente precisa ler ou buscar neles.
4. Os achados continuam **ancorados apenas em linhas do PR em revisão** — o código vinculado é evidência, não um segundo alvo de revisão.

Se nenhum vínculo estiver configurado, o recurso fica totalmente desligado (custo extra zero).

## Configurar no dashboard

Repositórios vinculados são **por repositório**, não globais. A relação é direcional: os vínculos em `frontend` valem só ao revisar PRs em `frontend`.

1. No seletor de escopo no topo do grupo **Code review** na barra lateral, escolha um **repositório específico** (não Global).
2. Abra **Linked repositories** (só aparece no escopo de repositório).
3. Clique em **Add repository** e escolha repos irmãos já conectados à sua organização.
4. Opcionalmente, clique em um vínculo para definir:
   - **Instructions · optional** — dica em texto livre para a Kody (ex.: “API REST que este frontend consome”).
   - **Branch / ref pin · optional** — pin de branch/tag. Deixe vazio para usar a cascata automática de refs (abaixo).
5. Clique em **Save settings**.

Você pode vincular no máximo **3** repositórios. Só repos já conectados à mesma organização são aceitos.

## Configurar no `kodus-config.yml`

Você também pode declarar vínculos no arquivo de configuração do repositório:

```yaml
linkedRepositories:
  - repository: "org/backend-api"
    instructions: "REST API this frontend consumes"
    ref: main   # optional pin; omit for same-branch cascade
```

- `repository` (obrigatório): nome completo de um repo conectado à organização (`owner/repo`).
- `instructions` (opcional): descrição curta do porquê do vínculo.
- `ref` (opcional): fixa uma branch, tag ou commit. Quando omitido, a Kody usa a cascata de refs.

`linkedRepositories: []` vazio significa que o recurso está desligado. O arquivo só é lido quando **Prefer kodus-config.yml settings** (**Code review → General**) está ativado para o repositório, e a lista dele substitui a definida no app web. Veja a [referência das configurações](/pt-BR/how_to_use/code_review/configs/linked_repositories#no-kodus-config-yml).

## Como a ref é escolhida

Para cada repositório vinculado, a Kody tenta as refs nesta ordem e usa a primeira que clonar com sucesso:

1. **Override na descrição do PR** para aquele repo (veja abaixo)
2. **Pin de `ref` na config** (se definido)
3. **PR aberto** no repo vinculado cuja head branch coincide com a head branch do PR
4. O **nome da head branch do PR** no repo vinculado
5. A **branch padrão** do repo vinculado
6. Fallbacks: `main`, depois `master`

Isso mantém alinhado o trabalho multi-repo quando o mesmo nome de branch existe entre serviços, e ainda faz fallback com segurança em PRs comuns.

## Sobrescrever a ref pela descrição do PR

Para uma revisão pontual (por exemplo, revisar contra um PR específico do backend), mencione o repo vinculado no **título ou na descrição** do PR em revisão. Os overrides só se aplicam a repositórios que **já estão vinculados** na config.

Formas suportadas:

| Forma | Significado |
| --- | --- |
| `owner/repo#123` | Usar o head do PR/MR `#123` nesse repo |
| URL de PR/MR | Igual ao anterior, para uma URL em `github.com`, `bitbucket.org`, `dev.azure.com` ou um host com `gitlab` no nome |
| `owner/repo@branch` | Fixar essa branch no repo vinculado |

Exemplos:

```text
Depends on org/backend-api#842
Also needs org/shared-contracts@feature/new-events
```

Mencione cada repositório vinculado uma vez. Com várias menções, um pin `owner/repo@branch` vence uma referência a PR onde quer que apareça, e, entre menções da mesma forma, a última vence. Menções de repos **não** vinculados são ignoradas (não criam novos vínculos).

## Quando o contexto entre repos ativa (boundary gate)

Mesmo com vínculos configurados, a Kody **não** abre sempre os repos irmãos. Um gate barato e determinístico varre as **linhas adicionadas** no diff do PR e só ativa quando encontra **superfície de fronteira**, como:

- Literais de string (segmentos de path, códigos, nomes de eventos etc.)
- Exports (`export function`, types, classes, …)
- Enums / types / interfaces
- Chaves de objeto ou de payload
- Identificadores no estilo de status / state / error-code
- Caminhos de arquivo com cara de contrato (`dto`, `schema`, `api`, `client`, `openapi`, `proto`, …)

Refactors internos que só movem ou reformatam código sem fronteira em geral mantêm o gate desligado — assim os clones e o prompt de fronteira ficam ociosos.

## O que a Kody pode e não pode fazer com repos vinculados

**Pode:**

- Buscar e ler arquivos nos repositórios vinculados quando o gate está ativo
- Usar suas **instructions** para entender a relação
- Citar código vinculado como evidência de apoio em um achado no PR atual

**Não pode / não faz:**

- Publicar comentários de revisão em arquivos que existem só em um repositório vinculado
- Revisar o repo vinculado inteiro como se fosse o PR
- Vincular repositórios de fora da organização ou que não estejam conectados à Kodus
- Usar mais de 3 repositórios vinculados por repo em revisão (no `kodus-config.yml`, as entradas depois da terceira são descartadas)

## O que a revisão mostra

Quando a Kody leu um repositório vinculado, o comentário que ela publica ao fim da revisão inclui **Additional context used:** com o repositório e a ref que ela leu, por exemplo `org/backend-api@main` ou o PR aberto que ela usou. Sem essa linha, nenhum repositório vinculado foi lido. Um vínculo que não pode ser buscado ou que não está conectado à organização é ignorado, e a revisão continua sem ele.

## Setups recomendados

| Cenário | Vincular de | Instructions típicas |
| --- | --- | --- |
| Frontend ↔ backend | Frontend → repo da API de backend | “Contratos de cliente HTTP/REST dos quais esta UI depende” |
| Serviço ↔ contratos compartilhados | Serviço → repo de contracts/package | “Eventos, DTOs e protobufs compartilhados” |
| BFF ↔ vários backends | BFF → até 3 repos de backend | Uma linha curta por fronteira de serviço |

Prefira vínculos **estreitos e direcionais** (o consumidor aponta para o produtor) em vez de ligar cada repo a todos os outros.
