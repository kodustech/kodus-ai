## Onde encontrar

Escolha **Global**, um repositório ou um diretório no seletor de escopo no topo do grupo **Code review** e depois abra **Kody Rules**. Tudo que você cria ou altera na página vale para o escopo escolhido. Veja [Herança de regras](/pt-BR/how_to_use/code_review/configs/rules_inheritance) para saber como os escopos se combinam.

O cabeçalho tem três ações:

- **Configuration**: como regras e memórias são criadas e aprovadas neste escopo.
- **Discovery**: a [Biblioteca de regras](/pt-BR/how_to_use/code_review/configs/rules_library). Exibida na aba **Review Rules**.
- **New rule** (ou **New memory** na aba **Memories**).

## Dois tipos

<Tabs>
  <Tab title="Regras de Review">
    Verificações que rodam durante o code review e reportam violações como sugestões.

    - Regras **Per file** rodam uma vez para cada arquivo alterado e comentam inline.
    - Regras **Per PR** rodam uma vez para o pull request inteiro e postam um único comentário no PR.
    - Cada regra tem uma severidade e pode ser limitada a caminhos.
  </Tab>

  <Tab title="Memórias">
    Conhecimento de fundo que o Kody usa como contexto de alta prioridade nos code reviews e nas conversas com o Kody. Uma memória descreve como o seu codebase funciona; não é uma verificação e não tem severidade.

    - Criadas conversando com o Kody em um comentário de PR, ou com **New memory**.
    - Com escopo para um diretório, um repositório ou a organização inteira.
  </Tab>
</Tabs>

## Criar uma Regra de Review

Na aba **Review Rules**, clique em **New rule** (**Write a rule** quando a lista está vazia).

| Campo | O que faz |
|-------|--------------|
| **Rule name** | Até 300 caracteres. |
| **Execution mode** | **Per file** ou **Per PR**. |
| **Path** | Globs que limitam uma regra **Per file** aos arquivos correspondentes. Separe vários globs com vírgulas; um arquivo que corresponda a qualquer um deles é verificado. Vazio significa todos os arquivos. Não é usado por regras **Per PR** e não é editável no escopo de diretório, onde a regra pertence ao escopo de diretório (veja [Herança de regras](/pt-BR/how_to_use/code_review/configs/rules_inheritance) para saber quando ela vale). |
| **Instructions** | O que o Kody deve verificar e como decidir. Obrigatório. Em uma regra nova você pode **Start with a popular template**. O menu **Variables** insere nomes como `fileDiff` ou `pr_title`, que você pode usar para se referir ao diff e aos detalhes do PR que o Kody vê. |
| **Severity** | **Critical**, **High** (padrão), **Medium** ou **Low**. |
| **Advanced settings** | **Inheritable** (ligado por padrão) e **Code examples**: um **Bad example** e um **Good example**. |

A severidade decide como o finding é rotulado. Se findings abaixo de uma severidade chegam a ser postados é definido em [Severidade mínima](/pt-BR/how_to_use/code_review/configs/suggestion_control#aplicar-o-limite-às-kody-rules).

### O que o Kody vê

- **Per file:** o diff do arquivo, o restante do arquivo quando ele é pequeno o bastante, e o título e a descrição do PR (primeiros 1.000 caracteres).
- **Per PR:** o título e a descrição do PR (primeiros 1.000 caracteres), a lista de arquivos alterados e o diff de cada arquivo. Em PRs muito grandes, os arquivos além do orçamento de diff são listados apenas pelo nome.

O Kody só reporta violações em linhas que o pull request adiciona ou altera. Uma regra cujas instruções citam uma linguagem ("em arquivos Ruby, ...") fica limitada aos arquivos dessa linguagem, que o Kody descobre quando você salva a regra.

### Arquivos de referência em uma regra

Mencione um arquivo pelo caminho nas instruções, por exemplo `@file:docs/architecture.md`, para dar ao Kody o conteúdo dele quando ele julga a regra.

- O Kody encontra as referências a arquivos quando você salva a regra. O status ao lado do editor mostra quando elas foram resolvidas e qualquer arquivo que ele não conseguiu ler.
- Os arquivos são lidos da branch de destino do pull request.
- Use o caminho real no repositório, não um placeholder.

### Exemplos

<Tabs>
  <Tab title="Per file">
    - **Rule name:** Evite operadores de igualdade em condições de término de loop
    - **Path:** `src/**/*.ts`
    - **Severity:** Critical
    - **Instructions:** Usar `==` ou `!=` na condição de um loop pode causar loops infinitos quando o valor exato nunca é atingido.

    **Bad example**

    ```typescript
    // Infinite if the increment is not exactly 1
    for (let i = 0; i != 10; i += 2) {
      console.log(i);
    }
    ```

    **Good example**

    ```typescript
    for (let i = 0; i < 10; i += 2) {
      console.log(i);
    }
    ```
  </Tab>

  <Tab title="Per PR">
    - **Rule name:** Novas rotas precisam ser registradas
    - **Execution mode:** Per PR
    - **Instructions:** Quando o PR adicionar uma rota a um controller, verifique se ela também foi adicionada a `@file:routes.json`.

    Outras coisas que uma regra Per PR pode verificar:

    - A descrição do PR informa o que foi adicionado ou removido.
    - Todo arquivo de service alterado tem um arquivo de teste correspondente no PR.
    - O PR não altera mais do que um número definido de arquivos.
  </Tab>
</Tabs>

## Outras formas de adicionar regras

- **[Biblioteca de regras](/pt-BR/how_to_use/code_review/configs/rules_library):** adicione regras e packs prontos com **Discovery**.
- **[Regras de Repositório](/pt-BR/how_to_use/code_review/configs/repository_rules):** mantenha uma regra por arquivo markdown no seu repositório, em `.kody/rules`.
- **[Fontes globais de regras](/pt-BR/how_to_use/code_review/configs/global_rule_sources):** importe arquivos de regra de um repositório de standards como regras globais.
- **[Geração automática de regras](/pt-BR/how_to_use/code_review/learning/kody_rules_generation):** o Kody rascunha regras a partir dos comentários anteriores dos seus revisores.
- **Em uma thread de review:** peça ao Kody para criar, alterar ou remover uma regra, por exemplo `@kody update this rule to ignore test files`. Regras criadas assim mostram a origem **MCP/Agent** e esperam em **Pending review**.

## A lista de regras

A lista mostra as regras do escopo selecionado mais as herdadas de escopos superiores. Clique em uma linha para abrir a regra em um painel lateral, com **Pause** ou **Resume**, **Edit** (**View** sem permissão de edição) e excluir.

Use a chave de visualização em tabela ou em cards ao lado dos filtros; a escolha fica lembrada no seu navegador. A busca olha títulos, caminhos, instruções e exemplos (pressione `/` para focar nela). Os chips de severidade acima da lista filtram por severidade.

**Filters** permite ordenar por atualização recente, severidade ou nome, mostrar ou ocultar regras herdadas e **Disabled Rules**, e filtrar por origem, por **Has sync errors** (regras cujos arquivos referenciados não puderam ser lidos) ou por **Paused only**.

### Origem

| Origem | De onde a regra veio |
|--------|--------------------------|
| **Manual** | Escrita no app. |
| **Library** | Adicionada da Biblioteca de Regras. |
| **Auto-sync** | Um arquivo de regra em um repositório, mantido em sincronia. |
| **Kody-generated** | Rascunhada a partir de reviews anteriores. |
| **Onboarding** | Sugerida durante o onboarding. |
| **MCP/Agent** | Criada pelas ferramentas MCP do Kodus: pelo Kody em uma thread de review, ou por um cliente MCP. |
| **CLI** | Criada com o Kodus CLI. |
| **Agent file** | Importada de um arquivo de agente de código antes de eles deixarem de virar regras. Congelada. Veja [Instruções para agentes de código](/pt-BR/how_to_use/code_review/configs/rules_file_detection#regras-importadas-de-arquivos-de-agentes-de-código). |

### Status

| Status | Significado |
|--------|---------|
| **Active** | Verificada em todo novo PR. |
| **Paused** | Mantida na lista, pulada em todo PR. |
| **Paused by Kody** | Pausada por **Pause ignored and noisy rules**. |
| **Locked** | Pulada por causa do limite do plano Free (abaixo). |
| **Disabled** | Regra herdada marcada como desativada para este escopo. Um review ainda a aplica; veja [Herança de regras](/pt-BR/how_to_use/code_review/configs/rules_inheritance). |
| **Pending add**, **Pending edit**, **Pending delete** | Uma alteração aguardando em um pull request de [configuração centralizada](/pt-BR/how_to_use/code_review/configs/centralized_config). |

### Ações em lote

Na aba **Review Rules**, marque regras (ou **Select all visible**) para **Pause**, **Resume** ou **Delete** em conjunto. Apenas as regras do escopo atual podem ser selecionadas, não as herdadas.

### Impacto e uso

O painel lateral mostra um bloco **Impact** dos últimos 30 dias: quantas vezes a regra disparou, em quantos pull requests disparou e as sugestões recentes dela. Onde o Cockpit está disponível (planos Teams e Enterprise, e trials), ele também mostra quantas sugestões foram implementadas e o feedback de 👍 e 👎, e a tabela ganha uma coluna **Usage**. Um chip marca as regras que precisam de atenção:

- **Stale:** não disparou nos últimos 30 dias.
- **Ignored:** disparou pelo menos 5 vezes e 20% ou menos das sugestões dela foram implementadas.
- **Noisy:** disparou pelo menos 5 vezes, com pelo menos 3 👎, mais 👎 do que 👍, e um 👎 em pelo menos 10% das sugestões dela.

### Pausar regras ignoradas e ruidosas

Nos planos Teams e Enterprise, **Configuration → Pause ignored and noisy rules** pausa, uma vez por dia, as regras ativas do escopo que ficaram **Ignored** ou **Noisy** nos últimos 30 dias, incluindo regras escritas à mão. Elas mostram **Paused by Kody** com os números por trás. Os admins são notificados e podem usar **Resume** em uma regra a qualquer momento; depois de um resume, só conta o que ela sinalizar dali em diante. Regras gerenciadas por uma [configuração centralizada](/pt-BR/how_to_use/code_review/configs/centralized_config) não são pausadas. Vem desligado por padrão.

## Limites de regras

Organizações no plano **Free** da cloud (ou cuja assinatura foi cancelada ou expirou) e instâncias self-hosted sem uma licença válida rodam no máximo **10 regras ativas** por review, das mais antigas para as mais novas. As 10 contam regras Global, de repositório e de diretório juntas, e as memórias também contam. As regras além do limite ficam na lista como **Locked**, são puladas em todo PR, e um banner na página diz quantas são. Planos pagos da cloud e instâncias self-hosted licenciadas não têm limite.

## Memórias

Uma memória é uma declaração curta que o Kody mantém em mente: como o seu sistema funciona, o que o time já decidiu. As memórias ajudam o Kody a evitar repetir suposições erradas sobre o seu repositório.

- As memórias são adicionadas ao contexto dos code reviews e das conversas com o Kody.
- Quando o Kody está prestes a salvar uma memória, ele confere as existentes e a cria, a pula por ser duplicada, ou atualiza uma memória existente.

### Criar uma memória

**Em um comentário de PR.** Peça ao Kody para lembrar de algo e ele salva:

```
@kody remember: this repo mirrors a third-party API, so some payload fields intentionally stay snake_case.
```

Quando você apenas expõe um contexto ou uma preferência do time, o Kody oferece salvar e espera. Responda `@kody yes` para salvar:

```
@kody in this service, tests usually live next to implementation files rather than in a central test folder.
```

Quando o Kody salva ou atualiza uma memória, ele responde com um link para ela no app.

<Info>
  O Kody não salva instruções transitórias ("corrija isso agora"), conversa de depuração, perguntas, declarações vagas, nem pedidos que valem apenas para uma tarefa ou PR.
</Info>

**No app.** Escolha o escopo, abra a aba **Memories**, clique em **New memory** (**Add a memory** quando a lista está vazia), preencha **Memory name** e **Instructions** e clique em **Create memory**.

### Escopos de memória

| Escopo | Aplica-se a |
|-------|------------|
| **Directory** | Os arquivos de um diretório configurado. Uma memória criada em um comentário de PR também pode ser limitada a um caminho, como `src/components/**`. |
| **Repository** | O repositório inteiro. |
| **Organization** (**Global** no seletor de escopo) | Todos os repositórios da organização. |

## Aprovação

Por padrão, regras geradas a partir de reviews anteriores, regras sugeridas durante o onboarding e memórias que o Kody salva ficam ativas assim que são criadas. Para revisá-las antes, abra **Configuration** e ligue **Kody knowledge approval**.

Com a aprovação ligada, estes itens esperam em **Pending review** até serem aprovados:

- regras geradas a partir de reviews anteriores ou sugeridas durante o onboarding;
- memórias que o Kody salva em uma thread de review;
- regras sincronizadas de arquivos de regra de um repositório. Regras importadas por [Fontes globais de regras](/pt-BR/how_to_use/code_review/configs/global_rule_sources) ficam ativas na hora.

Uma regra criada pelas ferramentas MCP do Kodus, o que inclui uma regra que o Kody cria em uma thread de review, sempre espera em **Pending review**, seja qual for a configuração. Regras que você escreve à mão, adiciona da biblioteca ou cria com a CLI ficam ativas na hora.

### Pending review

Um badge nas abas **Review Rules** e **Memories** mostra a contagem de pendentes. A seção **Pending review** ("Rules and memories awaiting approval.") lista todos juntos, cada um marcado como **Rule**, **Memory** ou **Update**:

- **Regras e memórias novas:** **Approve** para ativar ou **Discard** para rejeitar.
- **Atualizações:** uma alteração proposta em um item existente, mostrada como um diff. **Update existing** a aplica, **Create new instead** mantém o original e adiciona a proposta como um item separado, **Discard** a rejeita.

Selecione vários e use **Bulk actions** (**Approve N**, **Create as new (N)**, **Discard N**) para tratá-los de uma vez.
