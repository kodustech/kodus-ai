<Info>
As Regras do Repositório estão sempre sincronizadas: não há configuração para ativar. Elas são os únicos arquivos de um repositório que viram Kody Rules. Instruções escritas para agentes de código (`CLAUDE.md`, `AGENTS.md`, `.cursor/rules`) são tratadas à parte, veja <a href="/pt-BR/how_to_use/code_review/configs/rules_file_detection">Instruções para Agentes de Código</a>.
</Info>

## Como Usar
Você pode criar Kody Rules personalizadas diretamente no seu repositório colocando arquivos markdown estruturados em diretórios específicos. Isso permite versionar suas regras junto com o código e compartilhá-las com toda a equipe.

<Info>
Arquivos de regras do repositório são importados **verbatim** — sem conversão por LLM. O frontmatter é parseado como está, o corpo markdown vira as instruções da regra exatamente como você escreveu (identificadores, formatação e texto preservados), e os exemplos Bad/Good são importados estruturalmente. Cada arquivo produz uma regra. Um arquivo que não segue o template (sem frontmatter, `title` ou corpo) é ignorado, e a sincronização registra isso no log; nada é gerado a partir dele.
</Info>

### Sincronização
- **Detecção Automática**: As regras do repositório são detectadas e sincronizadas em todo repositório conectado; não há nada para habilitar
- **Importar agora**: No painel **Kody Rules → Configuration** do repositório, **Import rule files now** lê todos os arquivos de regras da branch padrão
- **Aplicação Web**: As regras sincronizadas aparecem na página **Code review → Kody Rules** do repositório, com a origem **Auto-sync** (regras importadas de arquivos de agentes de código antes de pararem de ser convertidas mostram **Agent file**)
- **Atualizações em Tempo Real**: As alterações nos arquivos de regras são sincronizadas quando Pull Requests são mesclados na branch padrão

## Localização dos Arquivos

Coloque seus arquivos de regras em um destes diretórios, na raiz do repositório ou em qualquer subdiretório:
- `.kody/rules/**/*.md`
- `rules/**/*.md`
- `.rules/**` e `docs/coding-standards/**` (apenas arquivos que seguem o template)

## Template de Regra

Cada arquivo de regra deve seguir exatamente esta estrutura de template:

```markdown
---
title: "<nome da regra>"
scope: "file"            # "file" ou "pull-request"
path: []                 # lista de globs. exemplo: ["**/*.ts", "apps/web/**"]
severity_min: "high"     # "low", "medium", "high", "critical"
languages: []            # opcional. ex: ["jsts", "go", "php", "ruby", "java", "csharp", "dart", "kotlin", "rust"]
buckets: []              # opcional. ex: ["style-conventions", "error-handling", "security"]
uuid: ""                 # opcional. use para ID de regra estável
enabled: true            # opcional
---

## Instructions
Descreva o que revisar e como decidir. Seja direto e objetivo.
- Foque nos impactos de segurança, performance e contrato público.
- Forneça preferências ou padrões da equipe quando aplicável.
- Se for uma regra de PR, explique o que considerar no changeset.

## Examples

### Bad example
\`\`\`lang
// cole aqui um breve contra-exemplo que viola a regra
\`\`\`

### Good example  
\`\`\`lang
// cole aqui um breve exemplo que segue a regra
\`\`\`
```
## Campos do Template

### Campos Obrigatórios

Só duas coisas são estritamente obrigatórias: um `title` não vazio e um corpo de regra não vazio.
Um arquivo sem um dos dois é ignorado por completo.

| Campo | Descrição | Valores |
|-------|-------------|---------|
| `title` | Nome da regra exibido na interface | Qualquer string descritiva |

### Campos com valor padrão

Todo o resto é opcional — se omitir, vale o padrão.

| Campo | Descrição | Valores | Padrão |
|-------|-------------|---------|---------|
| `scope` | Escopo de análise da regra | `"file"` ou `"pull-request"` | `"file"` |
| `path` | Caminhos onde a regra se aplica. A regra dispara em arquivos que casem com **qualquer** um dos globs | Array de padrões glob | `**/*` (todos os arquivos) |
| `severity_min` | Nível mínimo de severidade | `"low"`, `"medium"`, `"high"`, `"critical"` | `"medium"` |
| `enabled` | Defina `false` para não importar este arquivo (uma regra já importada não é removida) | boolean | `true` |
| `uuid` | Identificador estável da regra — mantém a mesma regra na plataforma mesmo se o arquivo for renomeado | string | nenhum |
| `languages`, `buckets` | Metadados informativos | — | — |

<Note>
  `severity` é aceito como alias de `severity_min`, já que é um erro fácil de digitar e a
  intenção é inequívoca. Qualquer valor fora dos quatro níveis cai para `"medium"`, e qualquer
  `scope` diferente de `"pull-request"` é tratado como `"file"`.
</Note>

## Exemplos de Regras

### Exemplo de Regra no Nível de Arquivo
```markdown
---
title: "Avoid console.log in production code"
scope: "file"
path: ["src/**/*.ts", "src/**/*.tsx"]
severity_min: "medium"
languages: ["jsts"]
buckets: ["style-conventions"]
enabled: true
---

## Instructions
Check for console.log statements in production TypeScript/JavaScript files.
- Console logs should not appear in production code
- Use proper logging libraries instead
- Allow console.log only in development utilities

## Examples

### Bad example
\`\`\`typescript
function processUser(user: User) {
  console.log('Processing user:', user.id);
  return user.process();
}
\`\`\`

### Good example
\`\`\`typescript
import { logger } from './logger';

function processUser(user: User) {
  logger.info('Processing user:', user.id);
  return user.process();
}
\`\`\`
```

### Exemplo de Regra no Nível de Pull Request
```markdown
---
title: "New API endpoints must have tests"
scope: "pull-request"
path: ["**/*"]
severity_min: "high"
buckets: ["testing"]
enabled: true
---

## Instructions
When new API endpoints are added, ensure corresponding tests are included in the PR.
- Check for new route definitions in controllers
- Verify test files exist for new endpoints
- Ensure both positive and negative test cases

## Examples

### Bad example
Added new endpoint `/api/users/profile` but no test file included in the PR.

### Good example
Added new endpoint `/api/users/profile` with corresponding test file `tests/api/users/profile.test.ts` that covers success and error cases.
```

## Requisitos de Configuração

1. **Criar arquivos de regras**: Coloque arquivos `.md` que seguem o template em `.kody/rules/**` ou `rules/**`. Arquivos em `.rules/**` e `docs/coding-standards/**` que seguem o template também são importados.
2. **Fazer o merge**: Um arquivo de regra sincroniza quando um Pull Request que o adiciona, altera, renomeia ou remove é mesclado na branch padrão. Remover o arquivo remove a regra correspondente.
3. **Arquivos existentes**: Para importar arquivos de regras que já estão na branch padrão, use **Import rule files now** no painel **Kody Rules → Configuration** do repositório.

Novas regras entram ativas, ou em **Pending review** quando **Kody knowledge approval** está ativado.

<Tip>
Adicione `@kody-ignore` em qualquer lugar de um arquivo de regra para mantê-lo no repositório sem sincronizá-lo. A regra existente dele é removida na próxima sincronização.
</Tip>

## Verificando sincronização e avaliação de regras (self-hosted)

Em deployments self-hosted, os logs da API carregam marcadores grep-áveis para debug:

- `[kody-rules-sync]` — sumário por execução de sync: quais arquivos foram importados, pulados (com o motivo) ou removidos.
- `[kody-rules-eval]` — trace de avaliação por arquivo durante um review: exatamente quais regras (uuid + título) foram selecionadas para o prompt de cada arquivo revisado.

```bash
docker logs kodus_api 2>&1 | grep "kody-rules-sync"
docker logs kodus_api 2>&1 | grep "kody-rules-eval"
```

Se uma regra aparece como ativa na UI mas nunca aparece em `[kody-rules-eval]` para os arquivos esperados, verifique o glob do campo **Path** — uma regra só roda em arquivos que casam com o path.

## Limites de regras

Organizações no plano **Free** da cloud (ou cuja assinatura foi cancelada ou expirou) e instâncias self-hosted rodando **sem licença válida** (Community Edition) avaliam no máximo **10 regras ativas** por review (as mais antigas primeiro). Regras além do limite continuam na lista como **Locked** e são puladas em todo PR; um banner em **Code review → Kody Rules** informa quantas estão sendo puladas. Planos pagos da cloud e instâncias self-hosted licenciadas não têm esse limite. Se regras além da 10ª não disparam, esse limite é o motivo.
