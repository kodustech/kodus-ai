<Info>
As Regras do Repositório estão sempre sincronizadas: não há configuração para ativar. Elas são os únicos arquivos de um repositório que viram Kody Rules. Instruções escritas para agentes de código (`CLAUDE.md`, `AGENTS.md`, `.cursor/rules`) são tratadas à parte, veja <a href="/pt-BR/how_to_use/code_review/configs/rules_file_detection">Instruções para agentes de código</a>.
</Info>

## Como funciona

Coloque no seu repositório um arquivo markdown com o template abaixo. O Kody o importa como uma regra, e a regra acompanha o arquivo: edite o arquivo e a regra muda, apague-o e a regra é removida.

Os arquivos são importados **verbatim**, sem conversão por LLM. O frontmatter é lido como está escrito, o corpo markdown vira as instruções da regra exatamente como você escreveu, e os exemplos Bad e Good são importados do corpo. Cada arquivo produz uma regra.

- **Automático:** os arquivos de regras são sincronizados em todo repositório conectado.
- **No merge:** quando um pull request que adiciona, altera, renomeia ou remove um arquivo de regra é mesclado, a regra é criada, atualizada ou removida. Pull requests em um repositório de [configuração centralizada](/pt-BR/how_to_use/code_review/configs/centralized_config) não são sincronizados.
- **Importar agora:** para arquivos que já estão no repositório, abra **Code review → Kody Rules → Configuration** do repositório e clique em **Import rule files now**. Ele lê todos os arquivos de regras da branch padrão.
- **No app:** as regras sincronizadas aparecem na página **Kody Rules** do repositório com a origem **Auto-sync** e o caminho do arquivo como fonte.

Novas regras entram ativas, ou ficam em **Pending review** quando **Kody knowledge approval** está ativado.

O arquivo é a fonte da verdade. O texto, o path, a severidade e o status de uma regra são substituídos a partir do arquivo a cada sincronização, então altere o arquivo em vez da regra no app. Uma regra pausada no app volta a ficar ativa na próxima vez que o arquivo sincroniza.

## Localização dos arquivos

Coloque os arquivos de regras em um destes locais, na raiz do repositório ou em qualquer subdiretório:

- `.kody/rules/`
- `rules/**/*.md`
- `.rules/` e `docs/coding-standards/` (apenas arquivos que seguem o template)

O escopo de uma regra vem do seu `path`, não de onde o arquivo está. Uma regra em `services/billing/.kody/rules/` sem `path` continua valendo para todos os arquivos.

## Template de regra

````markdown
---
title: "<rule name>"
scope: "file"            # "file" or "pull-request"
path: []                 # list of globs. example: ["**/*.ts", "apps/web/**"]
severity_min: "high"     # "low", "medium", "high", "critical"
enabled: true            # optional
---

## Instructions
Describe what to review and how to decide. Be direct and objective.
- Focus on security, performance and public contract impacts.
- Give team preferences or patterns when applicable.
- If it's a PR rule, explain what to consider in the changeset.

## Examples

### Bad example
```lang
// paste here a short counter-example that violates the rule
```

### Good example
```lang
// paste here a short example that follows the rule
```
````

### Campos

Apenas um `title` não vazio e um corpo não vazio são obrigatórios. Um arquivo sem um dos dois é ignorado.

| Campo | Descrição | Valores | Padrão |
|-------|-----------|---------|--------|
| `title` | Nome da regra exibido no app | Qualquer string | obrigatório |
| `scope` | **Per file** ou **Per PR** | `"file"` ou `"pull-request"` | `"file"` |
| `path` | Arquivos aos quais a regra se aplica; ela roda em arquivos que casem com **qualquer** um dos globs. Não é usado por regras `pull-request` | Um glob ou uma lista de globs | `**/*` (todos os arquivos) |
| `severity_min` | A severidade da regra | `"low"`, `"medium"`, `"high"`, `"critical"` | `"medium"` |
| `enabled` | `false` ignora o arquivo. Uma regra já importada dele não é removida | boolean | `true` |

<Note>
  `severity` é aceito como alias de `severity_min`. Um valor fora dos quatro níveis cai para `"medium"`, e qualquer `scope` diferente de `"pull-request"` é tratado como `"file"`. Outras chaves do frontmatter são ignoradas.
</Note>

Os exemplos Bad e Good vêm de headings que contêm "bad" ou "good" (por exemplo `### Bad example`); todo bloco de código cercado sob um heading assim vira um exemplo.

## Exemplos de regras

### Regra no nível de arquivo

````markdown
---
title: "Avoid console.log in production code"
scope: "file"
path: ["src/**/*.ts", "src/**/*.tsx"]
severity_min: "medium"
---

## Instructions
Check for console.log statements in production TypeScript/JavaScript files.
- Console logs should not appear in production code
- Use proper logging libraries instead
- Allow console.log only in development utilities

## Examples

### Bad example
```typescript
function processUser(user: User) {
  console.log('Processing user:', user.id);
  return user.process();
}
```

### Good example
```typescript
import { logger } from './logger';

function processUser(user: User) {
  logger.info('Processing user:', user.id);
  return user.process();
}
```
````

### Regra no nível de pull request

````markdown
---
title: "New API endpoints must have tests"
scope: "pull-request"
severity_min: "high"
---

## Instructions
When new API endpoints are added, ensure corresponding tests are included in the PR.
- Check for new route definitions in controllers
- Verify test files exist for new endpoints
- Ensure both positive and negative test cases

## Examples

### Bad example
Added new endpoint `/api/users/profile` but no test file included in the PR.

### Good example
Added new endpoint `/api/users/profile` with corresponding test file `tests/api/users/profile.test.ts` that covers success and error cases.
````

## Quando um arquivo para de sincronizar

- **O arquivo não segue o template.** Um arquivo sem frontmatter, `title` ou corpo é ignorado. Se uma regra já tinha sido importada dele, a regra mantém o último texto e status, e o painel lateral da regra avisa que o arquivo não sincroniza mais. O aviso some quando o arquivo volta a ser lido.
- **Manter um arquivo fora da sincronização.** Adicione `@kody-ignore` nas primeiras ou nas últimas 10 linhas do arquivo. A regra dele é removida na próxima sincronização.
- **Parar de importar um arquivo.** `enabled: false` faz o arquivo deixar de ser importado. Isso não remove nem pausa uma regra que já existe; apague o arquivo ou use `@kody-ignore` para isso.

## Logs do self-hosted

Em deployments self-hosted, procure nos logs por estes marcadores:

- `[kody-rules-sync]`: um resumo de cada sincronização com os arquivos importados, ignorados (com o motivo) e removidos.
- `[kody-rules-eval]`: durante um review, quais regras (uuid e título) foram selecionadas para os arquivos alterados.

Se uma regra está ativa no app mas nunca aparece em `[kody-rules-eval]` para os arquivos esperados, verifique o **Path** dela: uma regra só roda em arquivos que casam com o seu path.

## Limites de regras

O plano Free e as instâncias self-hosted sem licença rodam no máximo 10 regras ativas, incluindo as regras vindas de arquivos. Veja [limites de regras](/pt-BR/how_to_use/code_review/configs/kody_rules#limites-de-regras).
