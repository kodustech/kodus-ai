---
title: "Configuração centralizada"
description: "Gerencie toda a configuração de code review e as Kody Rules como código em um único repositório. As alterações são sincronizadas automaticamente após cada merge; o rollout é controlado pela UI ou pelo CLI."
---

A configuração centralizada permite manter todas as configurações de code review e todas as Kody Rules em **um único repositório**, em vez de editá-las por repositório na interface web. Cada alteração passa por um pull request nesse repositório, fornecendo histórico de versões, revisão e rollback da sua configuração de revisão.

Use quando você quiser:

- Uma fonte única de verdade para o comportamento das revisões em muitos repositórios.
- Code review como código: histórico, revisão de PR, rollback, validação em CI.
- Kody Rules consistentes (regras de revisão e memórias) em toda a organização.
- Alterações de configuração via CLI ou CI.

## Como Funciona

1. Escolha um repositório para armazenar a configuração centralizada. Ele precisa ser um dos repositórios selecionados no Kodus.
2. Habilite a Configuração Centralizada na UI (**Code review → General** no escopo Global → **Configure centralized config**) e aponte para esse repositório.
3. Escolha um **modo de sincronização inicial**:
   - `pr` — Kodus abre o PR de inicialização com suas configurações e regras efetivas atuais.
   - `manual` — Kodus gera os arquivos; sua equipe faz o download e abre o PR.
4. Após o primeiro merge, todo merge futuro no repositório centralizado propaga automaticamente as alterações para o Kodus.

O Kody não revisa os pull requests do próprio repositório centralizado.

O repositório centralizado espelha a hierarquia de escopos do Kodus (Global → Repositório → Diretório) por meio do seu layout de pastas.

## Estrutura do Repositório

O repositório centralizado usa caminhos de pastas para mapear arquivos a escopos. A estrutura cobre tanto as configurações de revisão (`kodus-config.yml`) quanto as Kody Rules (`.kody-rules/`).

<Note>
O nome do repositório é arbitrário — escolha o que melhor se adapta à sua organização. `kodus-config` é usado abaixo como convenção.
</Note>

```
kodus-config/
├── kodus-config.yml                      ← global settings
├── .kody-rules/
│   ├── review/                           ← global review rules
│   │   └── require-tests-for-endpoints.yml
│   └── memories/                         ← global memories
│       └── logging-convention.yml
│
├── backend-api/                          ← matches a Kodus repository
│   ├── kodus-config.yml                  ← repository-level overrides
│   ├── .kody-rules/
│   │   ├── review/
│   │   │   └── no-raw-sql.yml
│   │   └── memories/
│   │       └── auth-module-layout.yml
│   │
│   └── src%2Fauth/                       ← a directory scope for src/auth
│       ├── kodus-config.yml              ← directory-level overrides
│       └── .kody-rules/
│           ├── review/
│           └── memories/
│
└── frontend-web/
    └── kodus-config.yml
```

Regras:

- Um `kodus-config.yml` na **raiz** do repositório centralizado vale globalmente.
- Uma pasta de primeiro nível com o nome de um repositório do Kodus (por exemplo `backend-api/`) delimita os arquivos dela a esse repositório. No GitLab o nome é o caminho completo, então a pasta é aninhada: `group/project/`.
- Um escopo de diretório é uma pasta dentro da pasta do repositório, nomeada com os caminhos que ela cobre. Escreva cada `/` como `%2F` e junte vários caminhos com `&`: `src%2Fauth`, ou `apps%2Fweb&apps%2Fdocs` para um escopo com duas pastas. Um caminho aninhado mais fundo, como `backend-api/src/auth/`, é ignorado.
- Regras em `.kody-rules/review/` viram **regras de revisão**; regras em `.kody-rules/memories/` viram **memórias**.

Qualquer arquivo sem um escopo correspondente é ignorado na sincronização.

Excluir um arquivo do repositório centralizado remove o que ele definia na próxima sincronização: um arquivo de regra excluído apaga essa regra, e um `kodus-config.yml` excluído que uma sincronização anterior aplicou limpa as configurações desse escopo.

## Arquivos de Configuração

Cada `kodus-config.yml` usa o mesmo schema do `kodus-config.yml` por repositório documentado em [Configurações gerais](/pt-BR/how_to_use/code_review/configs/general). Os campos são aplicados no nível da pasta onde o arquivo está e seguem as regras usuais de herança (veja [Herança de configurações](/pt-BR/how_to_use/code_review/configs/inheritance_overrides)). Diferente do arquivo do próprio repositório, esses arquivos também podem conter `customMessages` (veja [Mensagens personalizadas](/pt-BR/how_to_use/code_review/configs/custom_messages)).

Os [agentes customizados](/pt-BR/how_to_use/code_review/custom_agents), e as skills e docs ligados a eles, não fazem parte da Configuração Centralizada. Eles são configurados no app, e as chaves `customAgents` e `knowledge` nesses arquivos são ignoradas.

Exemplo mínimo:

```yaml
version: 2.0
reviewOptions:
  bug: true
  security: true
  performance: true
  business_logic: true
suggestionControl:
  severityLevelFilter: medium
  applyFiltersToKodyRules: false
ignorePaths:
  - yarn.lock
  - package-lock.json
automatedReviewActive: true
```

## Arquivos de Kody Rules

Cada regra é um único arquivo `.yml` ou `.yaml` em `.kody-rules/review/` (regras padrão) ou `.kody-rules/memories/` (memórias). O nome do arquivo é arbitrário, mas o Kodus liga uma regra ao caminho do arquivo: renomear ou mover um arquivo apaga a regra antiga e cria uma nova na próxima sincronização. `title` e `rule` são obrigatórios; um arquivo que não os tenha ou que falhe na validação é ignorado, a sincronização reporta a falha e não apaga regras removidas até que o arquivo seja corrigido.

Exemplo de regra de revisão (`.kody-rules/review/require-tests-for-endpoints.yml`):

```yaml
title: Require tests for new endpoints
rule: |
  Every new HTTP endpoint handler must include at least one integration test
  that exercises the happy path and one common failure mode.
severity: high
scope: pull-request
path: apps/api/**
examples:
  - snippet: |
      // endpoint added with matching *.spec.ts
    isCorrect: true
  - snippet: |
      // endpoint added with no test file touched in the PR
    isCorrect: false
inheritance:
  inheritable: true
  exclude: []
  include: []
```

Uma regra pausada é escrita com `enabled: false`.

Veja [Visão Geral das Kody Rules](/pt-BR/how_to_use/code_review/configs/kody_rules) para a referência completa de campos e [Herança de regras](/pt-BR/how_to_use/code_review/configs/rules_inheritance) para saber como `inheritance.inheritable`, `exclude` e `include` se comportam.

## Fluxo na UI

Na barra lateral, escolha **Global** no seletor de escopo no topo do grupo **Code review** e depois
abra **Code review → General**:

1. Clique em **Configure centralized config** no cabeçalho da página (abre o diálogo **Centralized Config**).
2. Ative **Enable centralized config**.
3. Selecione o repositório de origem (**Selected repository**).
4. Escolha o **Initial Sync Method**:
   - Automatic (Create PR now)
   - Manual (Sync later)
5. Clique em **Initialize** e confirme o status.

Depois de habilitado, o diálogo mostra o repositório de origem e estes botões:

- **Sync Now** aplica o conteúdo atual do repositório centralizado.
- **Download** salva o pacote de configuração (veja abaixo).
- **Save Changes** salva o que você alterou no diálogo, por exemplo ao desativar **Enable centralized config**.

O repositório de origem não pode ser alterado enquanto estiver habilitado. Para usar outro repositório, desative **Enable centralized config**, clique em **Save Changes** e habilite novamente.

## Comportamento da UI Web Quando Habilitado

O repositório centralizado é a fonte de verdade. A UI web reflete isso:

- As **configurações de code review** nos escopos Global, de repositório e de diretório continuam editáveis na UI web. Cada página mostra um banner — "Centralized config is enabled. Changes on this page are saved immediately and proposed through pull requests in the `<repo>` repository. Synchronization reapplies the configuration from that repository." — com **View active pull request** quando há um aberto. **Save settings** aplica a alteração no Kodus na hora e abre um pull request com a mesma alteração no repositório centralizado. Se esse pull request for fechado sem merge, a próxima sincronização restaura a versão do repositório sobre a configuração salva. Alterações adicionais feitas enquanto esse pull request está aberto são adicionadas a ele. Você também pode editar os arquivos diretamente no repositório centralizado.
- As **Kody Rules** funcionam de outra forma. Criar ou editar uma regra não a altera diretamente: o Kodus abre um pull request no repositório centralizado com a alteração proposta, e a alteração passa a valer quando o pull request recebe merge.

### Regras da UI e regras do repositório coexistem

Habilitar a Configuração Centralizada **não** apaga regras que foram criadas antes na UI web, e o repositório não precisa contê-las. As duas fontes alimentam o mesmo conjunto de regras ativas:

- Regras importadas do repositório centralizado são persistidas com o status `SYNCED`.
- Regras criadas na UI web antes de você habilitar convivem com elas e continuam ativas.
- Na hora da revisão, o Kodus carrega **toda regra ativa** do banco de dados, independentemente da origem. Uma regra que existe só na UI é aplicada exatamente como uma regra que existe só no repositório.
- Regras com status `PENDING_ADD` (criadas pela UI/CLI, ou exportadas pelo `init`, com um PR ainda sem merge) são **excluídas** das revisões até o PR receber merge e o status passar para `SYNCED`. A lista de Kody Rules mostra `PENDING_ADD`, `PENDING_EDIT` e `PENDING_DELETE` como **Pending add**, **Pending edit** e **Pending delete**.
- O `init` com o método `pr` coloca no PR de inicialização toda regra existente que ainda não tem arquivo e a marca como `PENDING_ADD`, então essas regras não rodam nas revisões até esse PR receber merge.

Na prática: se você montar o repositório centralizado à mão e faltar uma regra que você já tinha na UI, essa regra continua rodando — só não fica versionada no repositório. Para colocá-la sob controle de versão, edite-a uma vez na UI (o que abre um PR) ou use o `init` para que o Kodus inclua toda regra existente no PR de inicialização. Não copie o arquivo de uma regra para o repositório à mão enquanto a regra da UI ainda existir: a sincronização associa regras pelo caminho do arquivo, então o arquivo vira uma segunda regra com o mesmo título.

## Estados de Sincronização

Cada regra que vem da Configuração Centralizada acompanha seu ciclo de vida por meio de um status:

| Status | Significado |
|---|---|
| `SYNCED` | A regra no Kodus corresponde ao arquivo no repositório centralizado. |
| `PENDING_ADD` | Uma nova regra foi criada pela UI/CLI e um PR foi aberto; o arquivo ainda não existe na branch padrão. |
| `PENDING_EDIT` | Uma edição foi proposta pela UI/CLI e há um PR aberto; o arquivo existente ainda não foi atualizado. |
| `PENDING_DELETE` | Uma exclusão foi proposta pela UI/CLI e há um PR aberto; o arquivo ainda existe na branch padrão. |

`PENDING_ADD` e `PENDING_EDIT` viram `SYNCED` quando o PR correspondente recebe merge; uma regra `PENDING_DELETE` é apagada. Se o pull request aberto pelo Kodus for fechado sem merge, uma nova regra proposta é rejeitada e uma edição ou exclusão proposta é descartada.

## Baixar o Pacote de Configuração

Clique em **Download** no diálogo **Centralized Config** para obter um ZIP com os arquivos `kodus-config.yml` gerados e a árvore `.kody-rules/` que refletem suas configurações e regras atuais.

Use quando for:

- Auditar a configuração gerada.
- Compartilhar artefatos de setup com outra equipe.
- Manter um backup local antes de um rollout.
- Inicializar o repositório centralizado no modo `manual`.

## Desabilitar a Configuração Centralizada

Desabilitar a Configuração Centralizada limpa o repositório de origem selecionado e devolve todos os repositórios ao comportamento padrão sem centralização (configurações editadas na UI web, `kodus-config.yml` por repositório opcional).

Regras e configurações que já foram sincronizadas permanecem no Kodus — elas não são apagadas ao desabilitar.

## CLI

Use estes comandos para gerenciar a Configuração Centralizada em fluxos de terminal e scripts de CI.

### Requisitos

- Uma chave de equipe com **Allow repository configuration via CLI** ativado (**Organization → CLI keys → Configure**).
- Pelo menos um repositório selecionado no Kodus.

Autentique com:

```bash
kodus auth team-key --key <your-key>
```

### Verificar o Status

```bash
kodus config centralized status
```

### Inicializar a Configuração Centralizada

```bash
kodus config centralized init [owner/repo] --sync-option <pr|manual>
```

Observações:

- `--sync-option` tem `pr` como padrão.
- Use `.` para o repositório do diretório atual.
- Se o repositório for omitido em um terminal interativo, o CLI pede a seleção.
- Em ambientes não interativos, o repositório precisa ser informado.

Exemplos:

```bash
kodus config centralized init kodustech/kodus-config --sync-option pr
kodus config centralized init kodustech/kodus-config --sync-option manual
```

### Executar a Sincronização

```bash
kodus config centralized sync
```

### Desabilitar a Configuração Centralizada

```bash
kodus config centralized disable
```

### Baixar o ZIP de Configuração

```bash
kodus config centralized download --out ./centralized-config.zip
```

Observações:

- `--out` é obrigatório.
- A saída é um pacote ZIP com os arquivos de configuração gerados e a árvore `.kody-rules/`.

### Saída JSON

Todos os comandos de configuração centralizada suportam saída estruturada com `--json`.

```bash
kodus config centralized status --json
kodus config centralized init kodustech/kodus-config --sync-option pr --json
kodus config centralized sync --json
kodus config centralized disable --json
kodus config centralized download --out ./centralized-config.zip --json
```
