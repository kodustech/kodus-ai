O limite de severidade decide **quais** apontamentos da Kody são publicados. Abra **Code review → What to review**; as configurações ficam no card **Minimum severity to post**. Elas podem ser definidas nos escopos Global, Repository e Directory. Veja [Herança de configurações](/pt-BR/how_to_use/code_review/configs/inheritance_overrides).

## Minimum severity to post

A Kody atribui uma severidade a cada apontamento e publica somente os que estão no nível escolhido no slider ou acima dele. O padrão é **Medium**. A Kody continua encontrando problemas de severidade mais baixa; ela só não comenta sobre eles.

| Nível | Apontamentos típicos |
| --- | --- |
| **Low/All** | Inconsistências de manutenção e cosméticas, pequenos trabalhos redundantes, uma linha de log errada ou enganosa. |
| **Medium** (padrão) | Defeitos delimitados: métricas ou mensagens erradas, falhas isoladas de requisição, tratamento comum de entrada inválida, fragilidades de segurança limitadas, falhas de lint ou de CI que só bloqueiam o desenvolvimento. |
| **High** | Um caminho suportado fica inutilizável para entradas válidas, um efeito durável essencial falha, dados são destruídos indevidamente, ou um controle de admissão, como um limite de seats ou de cota, é contornado. |
| **Critical** | Um caminho concreto para contornar a autenticação, administração não autorizada em larga escala, execução de código controlada por um atacante, ou perda sistêmica de trabalho enfileirado. |

<Tip>
  Ruído demais em um PR grande costuma ser problema de severidade, não de volume. Suba para
  **High** antes de tentar qualquer outra coisa — você mantém todo bug real e perde os
  nitpicks. Veja [Como reduzir o ruído na revisão](/pt-BR/knowledge_base/how-to-reduce-code-review-noise).
</Tip>

Os apontamentos das [instruções para agentes de código](/pt-BR/how_to_use/code_review/configs/rules_file_detection) seguem o limite como qualquer outro. Os apontamentos determinísticos (beta) são publicados em qualquer severidade. Um custom agent que define a própria severidade mínima usa essa.

## Aplicar o limite às Kody Rules

Um switch no mesmo card, **desativado por padrão**.

- **Off** — os apontamentos das [Kody Rules](/pt-BR/how_to_use/code_review/configs/kody_rules) **ignoram** o limite de severidade. Uma regra escrita pelo seu time é sempre reportada, qualquer que seja a severidade atribuída.
- **On** — as Kody Rules passam pelo mesmo limite que todos os outros apontamentos.

Deixe desativado, a menos que suas regras gerem mais ruído do que sinal. O sentido de uma Kody Rule é justamente o seu time já ter decidido que aquilo importa.

<Note>
  No `kodus-config.yml`, essas configurações ficam sob `suggestionControl`:

  ```yaml
  suggestionControl:
      severityLevelFilter: 'medium' # low | medium | high | critical
      applyFiltersToKodyRules: false
  ```

  O arquivo só é lido depois que **Prefer kodus-config.yml settings** estiver ativado. Veja
  [General](/pt-BR/how_to_use/code_review/configs/general#prioridade-de-configuração).
</Note>

## Outras formas de cortar ruído

O limite é um instrumento grosseiro. Quando você precisar de algo mais direcionado:

- **Ignored files** — pule código gerado, lockfiles e diretórios vendored. Veja
  [General](/pt-BR/how_to_use/code_review/configs/general#arquivos-ignorados).
- **Categorias** — desative uma categoria inteira, como Performance, com o switch dela em
  [O que revisar](/pt-BR/how_to_use/code_review/configs/what_to_review).
- **Config por diretório** — defina um limite mais rígido ou mais frouxo por pasta em um monorepo. Veja
  [Configurações por diretório](/pt-BR/how_to_use/code_review/configs/directory_level).
- **Kody Rules** — escreva o que o seu time valoriza, para o sinal vir dos seus padrões
  em vez de conselhos genéricos.
