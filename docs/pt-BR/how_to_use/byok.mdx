BYOK (Bring Your Own Key) é a **forma padrão como o Kodus usa LLMs em todos os planos**: Free, Teams e Enterprise. Você conecta suas próprias contas de provedor, adiciona os modelos que quiser e escolhe qual modelo roda cada tarefa. Seu provedor cobra você diretamente pelos tokens, e sua chave é armazenada criptografada e nunca é exibida de volta em texto simples.

O BYOK também funciona no Community self-hosted. Somente [Owners](/pt-BR/how_to_use/workspace_roles) gerenciam credenciais em **AI providers**. No Enterprise, o Kodus também pode rodar os modelos previstos no contrato.

## Como o BYOK funciona

O BYOK é **provider-first**: você conecta um provedor uma vez, adiciona a ele os modelos que quiser e então escolhe qual desses modelos roda cada uma das tarefas da Kody. A conexão fica na página **AI providers** (barra lateral → **AI providers**), que tem duas abas. A escolha de modelos por tarefa fica em **Code review → Routing**, que o botão **Configure routing** no cabeçalho da página abre.

## Conectar um provedor

<Steps>
  <Step title="Abrir AI providers">
    Na barra lateral, abra **AI providers** ([app.kodus.io/byok](https://app.kodus.io/byok)). Em um workspace novo você verá **Connect your first provider**.
  </Step>

  <Step title="Escolher um provedor">
    A grade de provedores é dividida em duas partes:

    - **Providers** — provedores de primeira classe que você conecta apenas com uma chave de API (OpenAI, Anthropic, Google, OpenRouter, Novita, Moonshot, Z.ai…).
    - **Custom** — provedores que você aponta para seu próprio endpoint ou nos quais roda um modelo arbitrário: **OpenAI-compatible**, **Anthropic-compatible**, **Google Vertex AI**, **Amazon Bedrock** e **Azure OpenAI**. Endpoints personalizados vêm marcados com a dica *Custom endpoint*.

    Um provedor que você já conectou exibe **Connected · N models**.
  </Step>

  <Step title="Adicionar um modelo">
    Escolher um provedor abre o formulário de adicionar modelo dele (**Add a … model**). Cole a chave de API uma vez (reutilizada em cada modelo que você adicionar àquele provedor depois) e então escolha o modelo:

    - Se o Kodus listar os modelos do provedor, escolha um na lista. Se o seu não aparecer, escolha **Type model manually** e digite o ID exato do modelo.
    - Caso contrário (endpoints personalizados, self-hosted ou quando chaves de plataforma não estão configuradas), digite o Model ID exato.

    Endpoints personalizados (OpenAI-compatible / Anthropic-compatible) também pedem uma **Base URL** primeiro, e o Azure OpenAI pede um **Resource endpoint**. **OpenAI** mostra uma **Base URL** opcional para o seu próprio proxy ou gateway; deixe vazia para chamar a OpenAI diretamente. Cole a base URL sem o caminho do endpoint (sem `/chat/completions`). Ela deve usar `https://` e resolver para um endereço público.
  </Step>

  <Step title="Ajustar configurações avançadas (opcional)">
    No card **Advanced (optional)**, expanda **Advanced settings**: **Thinking / Reasoning**, **Temperature**, **Max output tokens**, **Max input tokens** e **Max concurrent requests**. Os padrões são sensatos para a maioria dos provedores — veja [Reasoning](/pt-BR/how_to_use/byok/model_settings#reasoning-/-extended-thinking) e [Temperature](/pt-BR/how_to_use/byok/model_settings#temperature) para os campos que o Kodus trava ou oculta por modelo.
  </Step>

  <Step title="Testar e salvar">
    Clique em **Test** para verificar a configuração, ou **Test & save** para rodar o teste e salvar em caso de sucesso. Adicione quantos modelos quiser ao provedor; a chave é colada apenas uma vez.
  </Step>
</Steps>

<Tip>
  **Adicione outro provedor** a qualquer momento pela aba Providers. Cada provedor mantém sua própria chave; habilitar mais modelos em um provedor conectado nunca a pede de novo.
</Tip>

## Teste antes de salvar

O botão **Test** precisa de um modelo escolhido antes. Ele envia uma requisição real mínima a esse modelo, montada do mesmo jeito que uma revisão a monta, com sua chave, base URL, temperature e configuração de reasoning. Um teste que passa significa que essa configuração exata funciona, e um que falha retorna na hora a mensagem do provedor: um Model ID errado, uma chave restrita ou um problema de endpoint. O Google Vertex AI primeiro verifica a service account e depois faz a mesma requisição. O Amazon Bedrock sem um modelo só verifica as credenciais.

O Test também confere seu ajuste contra as regras do próprio modelo e retorna uma mensagem específica em vez de salvar uma configuração que o modelo ignoraria:

- Uma temperature que o modelo ignora ou fixa (veja [Temperature](/pt-BR/how_to_use/byok/model_settings#temperature)).
- Reasoning em **Off** em um modelo que sempre faz reasoning e não pode desabilitá-lo.

Quando o teste passa, mas um override ou nível de reasoning não chegou a nenhum parâmetro da requisição, o resultado traz um aviso dizendo isso.

<Info>
  Como o Test usa o modelo real, um **typo no Model ID é detectado no momento do Test** em vez de na sua primeira revisão: a resposta volta como `Model not found`.
</Info>

## Editar ou remover

Na aba **Providers**, **Edit model** altera as configurações de um modelo, **Edit provider** altera a chave do provedor e **Remove model** (o ícone de lixeira) remove um modelo. Um modelo que ainda é o padrão ou o fallback, está definido para uma tarefa, é usado por um repositório ou diretório, ou está fixado em um agente customizado não pode ser removido. A linha lista onde ele é usado, então altere esses pontos primeiro. Remover seu último modelo desconecta o BYOK: o Kodus usa o LLM definido por variáveis de ambiente, se houver um, e caso contrário para de rodar revisões até você conectar um modelo.

## Routing: qual modelo roda cada tarefa

Abra **Code review → Routing** no escopo **Global** (ou **Configure routing** em **AI providers**). O card **Models** define os padrões da sua organização. Apenas Owners o editam; o routing é flat, então toda tarefa usa o padrão até você escolher outro modelo para ela.

- **Default model**: o único modelo que toda tarefa usa, a menos que seja sobrescrito.
- **Fallback model**: um modelo *diferente* no qual a Kody re-executa uma chamada, uma vez, quando o modelo da tarefa falha: chave inválida ou expirada, sem crédito, acesso negado ou provedor indisponível (após as próprias retentativas dele). Sem um fallback, a revisão falha.
- **Risk assessment model**, **Balanced model** e **Heavy model**: os modelos para a [avaliação de risco](/pt-BR/how_to_use/code_review/configs/risk) e para cada modo de revisão. **Heavy model** está disponível no Teams e no Enterprise. Cada um usa o padrão até você escolher um.
- **Other task models** (expanda): **Kody Rules**, **PR Summary**, **Conversation**, **Business Rules** e **Custom Agents** podem rodar cada um um modelo diferente, por exemplo um mais barato para resumos. Um modelo que não consegue fazer uma dada tarefa fica desabilitado naquela linha, com um tooltip.

Clique em **Save settings** para persistir, ou **Reset** para descartar suas edições. Um painel **Repository overrides** lista os modelos definidos para repositórios individuais, diretórios e agentes customizados. Você define o modelo de um repositório ou diretório com o seletor de escopo em **Routing**; veja [Modos e modelos de revisão](/pt-BR/how_to_use/code_review/configs/routing).

<Note>
  Com um único modelo conectado, o routing fica fixo nele. Conecte um segundo modelo para que o routing faça sentido.
</Note>

## Assinaturas e coding plans

Alguns provedores vendem uma assinatura de taxa fixa, muitas vezes chamada de coding plan, no lugar de, ou junto com, o acesso à API pay-per-token. O Kodus se conecta a uma delas do mesmo jeito que se conecta a qualquer API: com a chave e o endpoint que o plano oferece. Ele nunca faz login com a sua conta no site ou no app de um provedor.

Se um plano pode ser usado assim depende do provedor, e cada um define suas próprias regras. Antes de depender de um:

- **Confira os termos.** Alguns planos permitem o uso apenas nos apps do próprio provedor, ou limitam o uso automatizado. Provedores podem mudar isso a qualquer momento, e o Kodus não consegue verificar isso por você.
- **Confira os limites.** Planos costumam limitar requisições simultâneas, janelas de requisições ou o uso mensal. Defina **Max concurrent requests** de acordo e adicione um **Fallback model** em um provedor diferente para que as revisões não falhem quando um limite for atingido. Veja [Simultaneidade e rate limits](/pt-BR/how_to_use/byok/model_settings#simultaneidade-e-rate-limits).
- **Use o endpoint do próprio plano.** A chave de um plano muitas vezes só funciona no endpoint desse plano, não na API pay-per-token do provedor. [Kimi e GLM](/pt-BR/how_to_use/byok/providers#conectando-kimi-moonshot-e-glm-z-ai) mostram a diferença.

Usar um plano de assinatura é por sua conta e risco. Se o provedor limitar ou encerrar o acesso, as revisões se comportam como em qualquer outra falha de provedor: vão para o **Fallback model** se você definiu um, e falham se não definiu.

## Kodus credits

Se seu workspace no Kodus Cloud tem acesso ao alpha do provedor **Kodus**, acesse **AI providers** e escolha **Kodus** para adicionar um modelo sem chave de API. Adicione saldo pré-pago em **Kodus credits**. O uso é descontado pelo preço por token exibido no modelo. A tela de recarga mostra a taxa da plataforma antes do pagamento.

Use **Configure routing** para escolher as tarefas que o modelo executa. Se o saldo acabar, as revisões que usam modelos do Kodus ficam pausadas até você adicionar créditos. Os modelos que usam suas próprias chaves de provedor continuam funcionando.

## Configurações avançadas

O formulário de cada modelo tem um card opcional **Advanced settings**: reasoning, temperature, limites de saída e entrada e simultaneidade. Os padrões servem para a maioria dos provedores; veja [Configurações do modelo](/pt-BR/how_to_use/byok/model_settings). Duas configurações valem ser conhecidas antes de você precisar delas.

### Custom JSON override

Para uma opção de provedor para a qual o Kodus não tem campo, escolha **Custom** em **Thinking / Reasoning** e cole o JSON. Veja [Custom JSON override](/pt-BR/how_to_use/byok/model_settings#custom-json-override).

### Fixando provedores do OpenRouter

Em um modelo do OpenRouter, **OpenRouter routing** fixa quais provedores upstream o servem. Veja [Fixando provedores do OpenRouter](/pt-BR/how_to_use/byok/providers#fixando-provedores-do-openrouter).

### Estratégia de routing

- Use um **provedor diferente** para o padrão e o fallback (ex.: padrão na Anthropic, fallback no Google). Protege contra indisponibilidades específicas de um provedor.
- Assinaturas com limites de simultaneidade apertados (GLM Coding Plan Lite/Pro, Kimi Code Plan) são configurações ruins sozinhas — combine-as com um fallback pay-per-token para que PRs em pico não fiquem sem atendimento.
- Roteie as tarefas pesadas (revisão de código) para o seu modelo mais forte e as leves (resumos, chat) para um mais barato em **Other task models** em **Code review → Routing**.
