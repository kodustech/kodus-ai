**Kodus Review** タブは、ひとつの問いに答えます。*あなたのチームは Kodus の言うことに基づいて行動しているか？*

デプロイ頻度や PR サイクルタイムといった一般的なデリバリーメトリクスを扱う Productivity タブとは異なり、Kodus Review は Kodus そのものに関するものです。どれだけの提案が実装されたか、どのカテゴリやルールが定着し、あるいは無視されているか、そしてチームがどこで反発しているかを示します。

すべてのチャートとテーブルは、ページ上部の**リポジトリ**フィルターと**期間**フィルターに従います。提案をもとにした数値は、期間内に**クローズ**されたプルリクエストが対象です。レビュー実行の数値（**PRs processed** と **Review processing outcomes**）は、期間内に実行されたレビューが対象です。カテゴリのバーやルールをクリックすると、その背後にある提案を [Suggestions](/ja/how_to_use/cockpit/suggestions) で開けます。リポジトリの行をクリックすると、Cockpit 全体がそのリポジトリにフォーカスされます。

## サマリーカード

| カード | 意味 |
| --- | --- |
| **Implementation rate** | 期間中に送信された提案のうち、チームが実装した割合（%）。下に件数も表示されます |
| **Suggestions sent** | 期間中にクローズされた PR で届けられた提案の数。実装率から除外されたもの（[Not measured](#implementation-rate) を参照）は含まれません |
| **PRs processed** | 期間中に完了したレビュー実行が少なくとも 1 件ある PR の数（成功、失敗、スキップを問いません）と、前の期間からの変化（レビュー実行データがある場合に表示） |
| **Negative vote rate** | リアクションのうち 👎 が占める割合（前の期間との傾向付き）。リアクションが 10 件未満の場合は、割合ではなく実数を表示します |
| **Critical suggestions not yet addressed** | 期間中にクローズされた PR で、届けられたものの未実装の重大な提案。マージされた PR と、マージされずにクローズされた PR の両方を数えますが、カードのフッターには「on merged PRs」と表示されます。実装チェックで判断できなかった提案は数えません。クリックすると **Implementation rate by category** に移動し、どのテーマが無視されているかを確認できます |

レビュー実行データがある場合は、カードの下に **Review processing outcomes** チャートが表示されます。前の期間と比較した **Reviews processed**（すべてのレビュー実行を数えるため、2 回レビューされた PR は 2 回と数えます）と、**Success**、**Error**（エラーで終了した実行を含む）、**Skipped** として終了した実行の週ごとの内訳を示します。横のリストには、各結果の件数、割合、前の期間からのパーセントポイントでの変化が表示されます。

## Implementation rate

中核となるメトリクスです。提案は、PR がクローズされた時点での最終ステータスが **Implemented** または **Partially implemented** であるときに **implemented（実装済み）** として数えられます。

```
Implementation rate = implemented suggestions ÷ sent suggestions
```

スコープのルールは、すべての implementation-rate チャートで共通です。

- 数えられるのは**届けられた（delivered）**提案、つまり実際に PR コメントとして投稿されたものだけです。Kodus がコメント前に除外したドラフトは決して数えられません。
- 提案は **PR がクローズされた週**に帰属します。実装ステータスが確定するのは PR がクローズされた時点だからです。
- 直近の実装チェックが**判断できなかった**提案は、未実装として数えずに実装率から除外されます。これは、モデル呼び出しが失敗した場合、回答が読み取れなかったり不完全だったりした場合、ファイルの変更が大きすぎてモデルに収まらなかった場合、または PR 全体の diff しか得られなかった場合に起こります。週次チャートには除外された件数が表示され、[Suggestions](/ja/how_to_use/cockpit/suggestions) では **Not measured** ステータスで一覧できます。投票と Kody Rule のトリガー数には、届けられたすべての提案が引き続き含まれます。

### 週次推移

週次チャートは推移を示し、トグルで切り替えられます。

- **Overall**：implementation-rate のラインを 1 本表示します。
- **By severity**：重大度（critical / high / medium / low）ごとに 1 本のラインを表示し、重大度の高い提案がより多く実装されているかどうかを確認できます。何も判定されなかった週は、0% ではなく途切れて表示されます。

### カテゴリ別・重大度別

- **Implementation rate by category**：提案カテゴリごとの送信数と実装数を表示します。バーをクリックすると、そのカテゴリで絞り込んだ Suggestions が開きます。
- **Implementation rate by severity**：重大度レベルごとの実装率です。期待されるのは降順のグラデーション（critical が low より多く実装される）です。フラットまたは逆転して見える場合、重大度がチームの判断の指針になっていないことを意味します。

<Warning>
  **重大度チャートの「All / Kodus only」トグルは重要です。** Kody Rule は、Kodus によるリスク評価ではなく、*あなた*がそのルールに設定した重大度を持ちます。両者を混在させるとキャリブレーションの読み取りが歪みます。たとえば、採用率の高い medium の Kody Rule が大量にあると、Kodus が medium を過小評価しているように見えてしまうことがあります。**Kodus only** に切り替えると、Kodus 自身の重大度キャリブレーションを確認できます。提案が 5 件未満のバーは薄く表示され、`*` でマークされます。ひと握りの提案から得られる 0% や 100% は、本当のシグナルではありません。
</Warning>

## ネガティブフィードバック

フィードバックは、Kodus の提案コメントに対する 👍 / 👎 のリアクションから得られます。期間中にクローズされた PR の提案が対象です。

- **Negative vote rate**（サマリーカード）：`👎 ÷ (👍 + 👎)` で、前の期間との傾向付きです。低いほど良好です。
- **Negative feedback (👎)** には 2 つのビューがあります。**By category** はチームが最も反対しているカテゴリを示し（カテゴリをクリックするとその提案が開きます）、**Trend** は 👎 の週ごとの推移を示します。👎 が多いカテゴリは、再調整または無効化の候補です。

## リポジトリ — ヘルス

検索ボックス付きのリポジトリごとのテーブルです。列は **Repository**、**PRs reviewed**（期間中にクローズされた PR のうち、届けられた提案が少なくとも 1 件あるもの）、**Suggestions**、**Impl. rate**、**👍 / 👎**、**Weakest category** です。**Weakest category** は、そのリポジトリで実装率が最も低いカテゴリで、提案が 5 件以上あるカテゴリだけを対象にします。Kodus がどこで定着し、どこで無視されているかを示します。

行をクリックすると、Cockpit 全体がそのリポジトリにフォーカスされます（リポジトリフィルターで選択した場合と同じです）。

## Kody Rules — ヘルス

各 Kody Rule が期間中にどのように機能しているかを示します。列は **Rule**、**Scope**（Global、Repo、Folder）、**Triggers**、**Impl. rate**、**👍 / 👎**、**Status** です。**All / Healthy / Noisy / Ignored / Stale** のピルでテーブルを絞り込み、検索ボックスでルールを名前から探せます。テーブルには組織内のアクティブなルールがすべて表示されます。リポジトリピッカーはトリガー件数を絞り込むため、選択したリポジトリの対象外のルールも **Stale** と表示されることがあります。アクティブなメモリも、ルールのトリガーが発生しないため **Stale** と表示されることがあります。このステータスでルールを残すか判断する前に、ルールのスコープを確認し、リポジトリの絞り込みを解除してください。

行をクリックすると、そのルールが生成した提案が開きます。

ステータスはルールごとに、次の優先順位で算出されます。

| ステータス | 意味 | 推奨アクション |
| --- | --- | --- |
| **Stale** | 期間中にトリガーされなかった | そのルールがまだ必要かどうかを見直す |
| **Low data** | トリガーされたが、判断するには回数が少なすぎる（5 回未満） | より多くのデータがたまるまで待つ |
| **Noisy** | チームが積極的にダウンボートしている（👎 が 3 件以上、👎 が 👍 より多く、かつトリガー 10 回につき 👎 が少なくとも 1 件） | ルールのキャリブレーションがずれている。書き換えるかスコープを絞る（例：テストを除外する） |
| **Ignored** | 頻繁にトリガーされるが、ほとんど実装されない（20% 以下） | その妥当性を問い直す。チームはそれを重視しているか？ |
| **Healthy** | 上記以外のすべて | アクションは不要 |

**Noisy** と **Ignored** は似ているように見えますが、求められるアクションは異なります。*Ignored* は受動的です。ルールは発火するが誰も実装しない状態であり、それがノイズなのか単なる放置なのかは分かりません。*Noisy* は能動的な反対です。チームが明示的にダウンボートしているため、それがノイズだと分かります。だからこそ、両方に該当するルールは **Noisy** として表示されます。ダウンボートのほうが、より強く、より行動につながるシグナルだからです。

## 提案

すべてのドリルダウンは [Suggestions](/ja/how_to_use/cockpit/suggestions) を開きます。数値の背後にある実際の提案を、フィルター可能なリストとして表示します。
