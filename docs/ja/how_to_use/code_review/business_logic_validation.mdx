## 概要

ビジネスロジック検証は、プルリクエストがタスクで求められている内容を実現しているかを確認します。Kody は PR が参照しているタスクを見つけ、タスク管理ツールから読み込み、すべての要件についてコード上でどの状態にあるかを一覧にします。結果は PR 上の 1 つのコメントとして常に最新の状態に保たれ、GitHub、GitLab、Bitbucket、Azure Repos、Forgejo のいずれでも同じです。

<img src="https://kodus.io/wp-content/uploads/2025/10/business-logic.gif" alt="Example of using business logic validation" />

## 前提条件

- [Plugins](/ja/how_to_use/code_review/plugins) で接続されたタスク管理ツール: Linear、Jira (Atlassian Rovo)、Notion、Git Issues、またはカスタムプラグイン。
- Kody はタスクを ID で**読み取る**だけで、タスクがリンクしているもの (親タスク、サブタスク、添付ドキュメント) も読み取ります。タスクを検索したり、タスク管理ツールに書き込んだりすることはありません。
- タスク管理ツールがなくても、コマンドにタスクのテキストを貼り付けることができます (後述)。

## 有効化

Business Logic はデフォルトで有効です。**Code review → What to review** の **Business Logic** 行、または `kodus-config.yml` で有効・無効を切り替えます:

```yaml
reviewOptions:
  business_logic: true
```

その行の **Business Logic** をクリックすると設定が開きます。行の **⋯** メニューでは、**Edit** で設定を、**Try it** でテストパネルを開きます。

## Kody がタスクを見つける方法

Kody は PR のタイトル、ブランチ名、説明の順にタスクへの参照を探します:

- `PROJ-123` のようなキー (Jira、Linear、およびほとんどのタスク管理ツール)
- `#123` と `owner/repo#123` (Git issues。プルリクエストの番号は無視されます)
- `AB#123` (Azure Boards)
- Linear、Jira、Notion、GitHub/GitLab の issue、Azure の work item へのリンク

参照は、タスク管理ツールがその ID と完全に一致するタスクを返した場合にのみ有効になります。そのため、タイトル内の `UTF-8` や `gpt-5` がタスクと誤認されることはありません。タイトル内の小文字のキー (`feat(kod-10)`) は、タスク管理ツールにそのチームやプロジェクトが存在する場合に有効になります。Linear のプロジェクト ID (`P-KOD-1`) は有効になりません。

Kody はタスクがリンクしているものも読み取ります:

- **親タスク** (Linear の sub-issue、Jira のサブタスク、ClickUp のサブタスク): PR は、このタスクのタイトルが対象とする親タスクの要件と照合されます。「親を参照」とだけ書かれた sub-issue もチェックされます。
- **サブタスク**: いずれかのサブタスクが実現する要件は CHECK MANUALLY ("Delivered by KOD-20") として表示され、不足として扱われることはありません。
- **タスクに添付されたドキュメント** (Linear docs): 受け入れ基準を含め、タスクの一部として読み取られます。

- **"Closes PROJ-1"**、またはタイトルやブランチ内のキー: PR はタスク全体と照合されます。
- **"Part of PROJ-1"**: PR はタスクの一部を実現するものです。不足分は一覧に表示されますが、マージ前に対応すべきものとしては扱われません。
- 説明文の **"Refs PROJ-1"**、**"see PROJ-1"**、**"related to PROJ-1"**: 言及です。PR が他のタスクを挙げていない場合にのみ、PR 自身のタスクとしてチェックされます。
- 1 つの PR につき**最大 3 つのタスク**がチェックされ、タスクごとに 1 セクションになります。それ以上を記載した PR (リリースやマージなど) はスキップされます。

## 5 つの状態

| 状態 | 意味 | 修正が必要か |
|---|---|---|
| **MET** | diff で実装されています。 | いいえ |
| **PARTIAL** | 要件の一部が実装されています。 | いいえ (表示のみ): 半分できているかどうかは判断の問題で、実行ごとに変わる可能性があります |
| **MISSING** | この PR の diff に根拠がない、または PR が依存しているコードがそれを行っていません。 | はい |
| **CHECK MANUALLY** | 視覚やフローに関する要件、リポジトリを読んでも Kody が確信を持てない要件、または読み込めないほど大きなファイルにある可能性がある要件。 | 対象外 |
| **NOT IN TASK** | タスクで求められていない変更。 | いいえ (表示のみ) |

各行には根拠となるファイルと行が示され、何を変更すべきかが書かれています。

### ギャップを表示する前に

ギャップは作成者に作業のやり直しを求めるものなので、Kody は各ギャップをコードに照らして確認します:

- **タスクに書かれているとおりの要件。** タスクが一切触れていない入力やエッジケース (負の金額、別のコードパス、言及されていないフォーマット) によって行が PARTIAL になることはありません。変更後に起こること (PR がキューに入れたメッセージを既存のジョブが送信すること、PR が埋めたシリアライザーをルートが使うこと) によっても同様です。
- **diff だけでなく、PR が呼び出すコード。** ルールが PR から呼び出されるが変更されていないコード (バリデーター、ヘルパー、レスポンスを組み立てる mapper) にある場合、Kody は何かを表示する前に PR の head 時点のリポジトリでそれを読みます。MISSING、PARTIAL、CHECK MANUALLY のすべての行についても同じことを行います。行が MET になるのは Kody が読んだファイルと行がある場合のみで、diff の外ですでにコードに存在することが示されます。行が MISSING になるのは、Kody が PR の依存するコードを読み、ルールが欠けている行を示した場合のみです。リポジトリで判断できないものは元の状態のままです。
- **別の場所に属する作業。** サブタスクが実現する要件や、チームのガイダンスでここではチェックしないとされている要件は CHECK MANUALLY のままで、不足として再判定されることはありません。

## プルリクエスト上での動作

- Kody は**最初のレビュー**で PR をチェックします。その後は、誰かが `@kody -v business-logic` とコメントしたとき、または `@kody review --force` を実行したときに再チェックします。**Re-check** は、何かが不足している間の push のたび (修正すれば誰かが依頼しなくてもコメントが更新されます)、または push のたびに設定することもできます。どちらも push ごとに検証が 1 回増えます。
- `@kody -v business-logic` でいつでも再チェックできます。**同じコメントが編集され**、Kody が 2 つ目のコメントを投稿することはありません。
- タスクを満たしている PR には、1 行のコメント ("✅ 4 of 4 met") と手動で確認すべき項目が投稿され、チェック済みであることが作成者にわかります。こうした場合にコメントしないようにするには、**Comment when every requirement is met** をオフにします。
- どのプラットフォームでもコメントがシグナルです。Kody は check や status を書き込まないため、それ自体でマージをブロックすることはありません。コメントのヘッダーに、修正が必要な項目が示されます。

### コメントへの返信

Business Logic のコメントに返信し、`@kody` をメンションします。Kody がコメントを返信として扱うのは、そのコメントのスレッド内 (GitLab、Bitbucket、Azure Repos) に投稿されたとき、コメントを引用したとき、または要件、その状態 (MISSING、PARTIAL)、タスク ID を挙げたときです。それ以外のコメントはチャットに回されます。

- **異議を唱える**: 「`useDrag.ts` で対応済みです」。Kody は指摘された箇所を再チェックし、MET にするか、何を確認したかを説明したうえで状態を維持します。
- **指摘を受け入れる** (PR の作成者以外の人。GitHub ではリポジトリへの書き込み権限を持つ人、GitLab ではリポジトリで Developer 以上の権限を持つ人、Bitbucket・Azure Repos・Forgejo ではプラットフォームが返す組織のメンバー): 「キーボードでの並べ替えはスコープ外のため SAA-102 に移しました」。Kody は SAA-102 が存在することを確認し、その行を受け入れた人とともに **ACCEPTED** にします。その行は修正対象から外れます。この判断は、Kody が要件を少し違う言い回しで書いた場合も含め、タスクの本文が変わらない限り以降の再チェックでも維持されます。タスクが編集された場合は、もう一度受け入れる必要があります。

## Kody がコメントしない場合

Kody は作成者が何か対処できる場合にのみコメントします:

| 状況 | PR 上の動作 |
|---|---|
| タスクにタイトルしかない | 受け入れ基準を求めるコメント |
| `SAA-999` は存在しないが、SAA がタスク管理ツールのチームである | タイプミスの可能性を指摘し、最も近い実在のタスクを示すコメント。**Ask for a task** がオンの場合、修正されるまで未解決のままになります |
| タスクが参照されていない、またはどのタスク管理ツールにもない ID のみ (タイトル内の `UTF-8`) | 何もしない。**Ask for a task** がオンの場合、タスクを求めるコメント (bot の PR には投稿しません) |
| GitHub の issue だが、接続されているのは Linear のみ | 何もしない。管理者には設定ページに件数が表示されます。**Ask for a task** がオンの場合、どのタスク管理ツールが読み取れないかを伝えるコメント |
| タスク管理ツールがダウンしている、またはトークンの有効期限が切れている | 何もしない。オーナーに通知され、タスク管理ツールが応答した時点で Kody が再チェックします (最初の失敗から最大 1 日間) |

スキップの理由はすべて記録され、Business Logic の設定ページに表示されます。

## オンデマンド実行

PR に (コードの行ではなく) コメントします:

- `@kody -v business-logic`: PR が参照するタスクを再チェック
- `@kody -v business-logic PROJ-123` またはタスクへのリンク: そのタスクと照合
- `@kody -v business-logic` の後に要件をテキストで記述: 書いた内容と照合 (タスク管理ツールは不要)

## 設定

**Code review → What to review** を開き、**Business Logic** (または **⋯ → Edit**) をクリックします。すべての設定はグローバルに設定でき、リポジトリやディレクトリごとに上書きできます。

- **Task source**: 接続されているすべてのタスク管理ツール (ClickUp などのカスタムタスクプラグインを含む)、または 1 つのプラグイン。カスタムプラグインの場合は、ID で 1 つのタスクを読み取るツールを選択します。読み取り専用のツールのみが表示されます。ページ右側に固定された **Try it** (この設定の編集権限が必要) を使うと、タスクのみの場合は Kody がそこから何を読み取るかが表示され、プルリクエストの場合は画面上の設定 (保存済みかどうかを問わず) でチェック全体を投稿せずに実行します。**Post to the pull request** は、表示された結果を再実行せずに、テストごとに 1 回だけ投稿します。テスト後にプルリクエストへ新しいコミットがあった場合は投稿が拒否されるので、先にテストを再実行してください。
- **Custom task id format** (任意): Kody が自動では見つけられない ID のための正規表現。`T(\d{4})` は `T1234` をタスク 1234 として読み取ります。`SAA-96`、`#12`、`AB#8`、`CU-…` のようなキーとタスク管理ツールのリンクはこの設定がなくても見つかります。ブランチ名の `sc-123` のような小文字のキーも同様です。タイトルや説明文の小文字のキーは、Linear または Jira にそのチームやプロジェクトがある場合にのみ有効です。それ以外のツールでは形式を設定してください。形式が取り出した数字は、Git Issues がタスクソースの場合にのみ Git の issue として読まれます。接続されているすべてのツールを使う設定では、`T1234` がリポジトリの issue #1234 になることはありません。
- **Where acceptance criteria live**: 自動検出、説明内の見出しの下、またはカスタムフィールド。そのフィールドがないタスクは説明から読み取られます。
- **Ask for a task when the PR references none**: Kody はスキップする代わりに、PR がどのタスクに対応するかを尋ねる (またはタイプミスを指摘する) コメントを投稿します。Dependabot や Renovate などの bot が作成した PR には何もしません。タスク管理ツールのダウンは対象外です。
- **Re-check**: リクエスト時のみ (デフォルト)、何かが不足している間の push のたび、または push のたび。
- **Skipped pull requests**: コードレビューがスキップする PR はここでもスキップされます。無視するキーワードを含むタイトル (`ignoredTitleKeywords`、たとえば `wip`) と、`runOnDraft` がオフの場合のドラフトです。`@kody -v business-logic` のコメントは常に実行されます。
- **Team guidance**: Kody が判断するときに従うメモ。たとえば「フィーチャーフラグは、フラグが存在しデフォルトでオフになっていれば実装済みとみなす」。判定の形式を変えたり、Kody に要件を作り出させたりすることはできません。

`kodus-config.yml` での同じ設定:

```yaml
businessLogic:
  taskSource: 'auto'
  criteriaLocation: 'heading'
  criteriaHeading: 'Acceptance criteria'
  commentWhenMet: true
  recheckOn: 'request' # request | failing | push
  requireTask: false
```

## CLI から

コーディングエージェントは PR を作成する前に自分の作業をチェックできます:

```bash
kodus pr business-validation --task-id AB#8
kodus pr business-validation --task-id AB#8 --format json
```

ローカルの変更をタスクと照合し、要件ごとに 1 行と状態を出力します。`--format json` (または `--agent`) を指定すると、エージェントが処理できるよう同じ判定を構造化して出力します。プルリクエストには何も投稿されません。

## Cockpit

**Cockpit → Delivered as asked** には、タスクを満たした PR の割合、タスクにない変更、開発者が Kody に同意した頻度、そしてコードを書いたのが誰か (人かコーディングエージェントか。コミットの作成者と `Co-Authored-By` トレーラーから判定) とチームごとの内訳が表示されます。Cockpit のリポジトリ選択に従い、他のタブと同様に **Organization → Cockpit** で非表示にできます。
