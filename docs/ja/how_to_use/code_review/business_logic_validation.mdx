## 概要

ビジネスロジック検証は、プルリクエストがタスクで求められている内容を実現しているかを確認します。Kody は PR が参照しているタスクを見つけ、タスク管理ツールから読み込み、すべての要件についてコード上でどの状態にあるかを一覧にします。結果は PR 上の1つのコメントとして常に最新の状態に保たれ、GitHub、GitLab、Bitbucket、Azure Repos、Forgejo のいずれでも同じです。

**Code review → What to review → Business Logic** で初期設定はオンです。タスクを自動取得するには [Plugins](/ja/how_to_use/code_review/plugins) でトラッカーを接続してください。レビューコマンドに要件を直接渡すこともできます。

タスクの一部を実装した PR では、コメントは次のようになります。

> **Kody · Business Logic**
>
> **#291 · Ticket SLA badge** — 修正が必要: 不足している要件2件
>
> | | 要件 | この PR |
> |---|---|---|
> | ✅ **MET** | チケットのヘッダーに、SLA の残り時間を示すバッジが表示される。 | `TicketPanel.tsx:40` · ヘッダーにバッジが表示され、"SLA Xh Ym" と表示されます。 |
> | ❌ **MISSING** | 残り時間が1時間未満になるとバッジが赤くなる。 | `SlaBadge.tsx:14` · バッジは常に "info" のトーンです。**Do:** 60分未満で danger のトーンに切り替えてください。 |
> | ❌ **MISSING** | 解決済みのチケットにはバッジを表示しない。 | `TicketPanel.tsx:40` · ステータスに関係なく表示されます。**Do:** チケットが解決済みのときは非表示にしてください。 |

修正後は、同じコメントが "All requirements met" と "✅ 3 of 3 met" になり、前回のチェック結果がその下に残ります。

## 前提条件

- [Plugins](/ja/how_to_use/code_review/plugins) で接続されたタスク管理ツール: Linear、Jira (Atlassian Rovo)、Notion、Git Issues、またはカスタムプラグイン。
- Kody はタスク管理ツールから**読み取る**だけです。対象は、PR が ID で指定したタスクと、そのタスクがリンクしているもの (親タスク、サブタスク、添付ドキュメント) です。書き込みは一切行わず、タスクとして扱うのは、タスク管理ツールがその ID のタスクを返した場合のみです。
- タスク管理ツールがなくても、コマンドにタスクのテキストを貼り付けることができます (後述)。

## 有効化

Business Logic はデフォルトで有効です。**Code review → What to review** の **Business Logic** 行、または `kodus-config.yml` で有効・無効を切り替えます。

```yaml
reviewOptions:
  business_logic: true
```

その行の **Business Logic** をクリックすると設定が開きます。行の **⋯** メニューでは、**Edit** で設定を、**Try it** でテストパネルを開いた状態の設定を開けます。

## Kody がタスクを見つける方法

Kody は PR のタイトル、ブランチ名、説明の順にタスクへの参照を探します。

- `PROJ-123` のようなキー (Jira、Linear、およびほとんどのタスク管理ツール)
- `#123` と `owner/repo#123` (Git issues。プルリクエストの番号は無視されます)
- `AB#123` (Azure Boards)
- Linear、Jira、Notion、GitHub/GitLab の issue、Azure の work item へのリンク

参照は、タスク管理ツールがその ID と完全に一致するタスクを返した場合にのみ有効になります。そのため、タイトル内の `UTF-8` や `gpt-5` がタスクと誤認されることはありません。タイトル内の小文字のキー (`feat(kod-10)`) は、タスク管理ツールにそのチームやプロジェクトが存在する場合に有効になります。Linear のプロジェクト ID (`P-KOD-1`) は有効になりません。

Kody はタスクがリンクしているものも読み取ります。

- **親タスク** (Linear の sub-issue、Jira のサブタスク、ClickUp のサブタスク): PR は、このタスクのタイトルが対象とする親タスクの要件と照合されます。「親を参照」とだけ書かれた sub-issue もチェックされます。
- **サブタスク**: いずれかのサブタスクが実現する要件は CHECK MANUALLY ("Delivered by KOD-20") として表示され、不足として扱われることはありません。
- **タスクに添付されたドキュメント** (Linear docs): 受け入れ基準を含め、タスクの一部として読み取られます。

### PR でのタスクの示し方

- **"Closes PROJ-1"** (fixes、resolves、implements、completes も同様)、またはタイトルやブランチ内のキー: PR はタスク全体と照合されます。
- **"Part of PROJ-1"**: PR はタスクの一部を実現するものです。不足分は一覧に表示されますが、マージ前に対応すべきものとしては扱われません。
- **"Refs PROJ-1"**、**"see PROJ-1"**、**"related to PROJ-1"**、または説明文中のキーのみの記載: 言及です。PR が他のタスクを挙げていない場合にのみ、PR 自身のタスクとしてチェックされます。説明文中の `#123` だけの記載がタスクとして読まれることはありません。`Closes #123` と書いてください (PR が他に何も挙げていない場合は `Refs #123` も有効です)。
- 1つの PR につき**最大3つ**の参照が読み取られ、1つの参照につき1セクションになります。ID とリンクはタスク管理ツールが確認する前にカウントされるため、それ以上を記載した PR (リリースやマージなど) はスキップされます。

## 5つの状態

| 状態 | 意味 | 修正が必要か |
|---|---|---|
| **MET** | diff で実装されています。 | いいえ |
| **PARTIAL** | 要件の一部が実装されています。 | いいえ (表示のみ): 半分できているかどうかは判断の問題で、実行ごとに変わる可能性があります |
| **MISSING** | この PR の diff に根拠がない、または PR が依存しているコードがそれを行っていません。 | はい |
| **CHECK MANUALLY** | 視覚やフローに関する要件、リポジトリを読んでも Kody が確信を持てない要件、または読み込めないほど大きな PR の一部にある可能性がある要件。 | 対象外 |
| **NOT IN TASK** | タスクで求められていない変更。 | いいえ (表示のみ) |

各行には根拠となるファイルと行が示され、何を変更すべきかが書かれています。レビュアーによる受け入れは **ACCEPTED** として表示されます (後述)。diff 全体がタスク以外の作業を行っている場合、コメントにその旨が示され、PR がタスクの一部であると述べていない限り、それは修正が必要な項目になります。

### ギャップを表示する前に

ギャップは作成者に作業のやり直しを求めるものなので、Kody は各ギャップをコードに照らして確認します。

- **タスクに書かれているとおりの要件。** タスクが一切触れていない入力やエッジケース (負の金額、別のコードパス、言及されていないフォーマット) によって行が PARTIAL になることはありません。変更後に起こること (PR がキューに入れたメッセージを既存のジョブが送信すること、PR が埋めたシリアライザーをルートが使うこと) によっても同様です。
- **diff だけでなく、PR が呼び出すコード。** ルールが PR から呼び出されるが変更されていないコード (バリデーター、ヘルパー、レスポンスを組み立てる mapper) にある場合、Kody は何かを表示する前に PR の head 時点のリポジトリでそれを読みます。MISSING、CHECK MANUALLY、PARTIAL の行についても、その順に最大8行まで同じことを行います。視覚的な要件は再度読み込みません。それを確定できるファイルがないためです。行が MET になるのは Kody が読んだファイルと行がある場合のみで、diff の外ですでにコードに存在することが示されます。行が MISSING になるのは、Kody が PR の依存するコードを読み、ルールが欠けている行を示した場合のみです。リポジトリで判断できないものは元の状態のままです。
- **別の場所に属する作業。** サブタスクが実現する要件や、チームのガイダンスでここではチェックしないとされている要件は CHECK MANUALLY のままで、不足として再判定されることはありません。

## プルリクエスト上での動作

- Kody は**最初のレビュー**で PR をチェックします。何も投稿せずにスキップしたレビュー (タスクが参照されていない、タスク管理ツールがダウンしているなど) はカウントされず、次のレビューで再試行されます。PR のチェックが済んだ後は、誰かが `@kody -v business-logic` とコメントしたとき、または `@kody review --force` を実行したときに再チェックします。**Re-check after a push** を **While something is missing** に設定すると、誰も依頼しなくても修正でコメントが更新されます。**On every push** に設定することもできます。どちらも push ごとに検証が1回増えます。
- `@kody -v business-logic` でいつでも再チェックできます。**同じコメントが編集され**、Kody が2つ目のコメントを投稿することはありません。
- タスクを満たしている PR には、短いコメント ("✅ 4 of 4 met") と手動で確認すべき項目が投稿され、チェック済みであることが作成者にわかります。こうした場合にコメントしないようにするには、**Comment when every requirement is met** をオフにします。
- どのプラットフォームでもコメントがシグナルです。Kody は check や status を書き込まないため、それ自体でマージをブロックすることはありません。コメントのヘッダーに、修正が必要な項目が示されます。

### コメントへの返信

Business Logic のコメントに返信し、`@kody` をメンションします。Kody がコメントを返信として扱うのは、そのコメントのスレッド内 (GitLab、Bitbucket、Azure Repos) に投稿されたとき、コメントを引用したとき、または要件、コメントに書かれたとおりの状態 (MISSING、PARTIAL)、タスク ID を挙げたときです。それ以外のコメントはチャットに回されます。

- **異議を唱える**: 「`useDrag.ts` で対応済みです」。Kody は指摘された箇所を再チェックし、MET にするか、何を確認したかを説明したうえで状態を維持します。
- **指摘を受け入れる** (PR の作成者以外の人。GitHub ではリポジトリへの書き込み権限を持つ人、GitLab ではリポジトリで Developer 以上の権限を持つ人、Bitbucket・Azure Repos・Forgejo ではプラットフォームが返す組織のメンバー): 「キーボードでの並べ替えはスコープ外のため SAA-102 に移しました」。Kody は SAA-102 が存在することを確認し、その行を受け入れた人とともに **ACCEPTED** にします。その行は修正対象から外れます。この判断は、Kody が要件を少し違う言い回しで書いた場合も含め、タスクの本文が変わらない限り以降の再チェックでも維持されます。タスクが編集された場合は、以前とまったく同じ文言の要件のみが判断を維持します。

Kody の返答:

| 返信 | Kody |
|---|---|
| レビュアーが受け入れ、SAA-102 に移す | "Got it. SAA-102 exists, I marked “Keyboard reordering” as accepted by @rafa and updated the table above. Nothing is left to merge." (または "Other requirements are still listed to merge.") |
| PR の作成者が受け入れようとする | "The pull request's author can't accept its own requirements: ask a reviewer to. If the code already covers it, say where and I'll re-check." |
| 上記の権限を持たない人 | "Only someone with write access to the repository can accept a requirement…" |
| Kody がコメントした人の権限を確認できない | "I couldn't check your access to the repository, so nothing was accepted. Reply again in a moment." |
| 移動先のタスクが存在しない | "I couldn't find SAA-102 in the task tracker, so nothing was accepted. Check the id and reply again." |

## Kody がコメントしない場合

Kody は作成者が何か対処できる場合にのみコメントします。

| 状況 | PR 上の動作 |
|---|---|
| タスクにタイトルしかない、または照合するには情報が少なすぎる | 受け入れ基準を求めるコメント |
| `SAA-999` は存在しないが、SAA がタスク管理ツールのチームである | タイプミスの可能性を指摘し、最も近い実在のタスクを示すコメント。**Ask for a task** がオンの場合、修正されるまで未解決のままになります |
| タスクが参照されていない、またはどのタスク管理ツールにもない ID のみ (タイトル内の `UTF-8`) | 何もしない。**Ask for a task** がオンの場合、タスクを求めるコメント (bot の PR には投稿しません) |
| GitHub の issue だが、接続されているのは Linear のみ | 何もしない。管理者には設定ページに件数が表示されます。**Ask for a task** がオンの場合、どのタスク管理ツールが読み取れないかを伝えるコメント |
| タスク管理ツールがダウンしている、またはトークンの有効期限が切れている | 何もしない。オーナーに通知され、タスク管理ツールが応答した時点で Kody が再チェックします (最初の失敗から最大1日間) |

スキップの理由はすべて記録されます。Business Logic の設定ページの上部には、Kody が動作中か (過去30日間にチェックした PR、最後に読み取ったタスク)、タスク管理ツールが応答しないため一時停止中かが表示され、読み取れなかった PR が理由別にカウントされます。理由は、タスクが存在しない、参照のタイプミス、タスク管理ツールが応答しなかった、その参照を読み取れる接続済みのタスク管理ツールがない、タスクの情報が少なすぎる、のいずれかです。

## オンデマンド実行

PR に (コードの行ではなく) コメントします。

- `@kody -v business-logic`: PR が参照するタスクを再チェック
- `@kody -v business-logic PROJ-123` またはタスクへのリンク: そのタスクと照合
- `@kody -v business-logic` の後に要件をテキストで記述 (40文字以上): 書いた内容と照合 (タスク管理ツールは不要)

## 設定

**Code review → What to review** を開き、**Business Logic** (または **⋯ → Edit**) をクリックします。すべての設定はグローバルに設定でき、リポジトリやディレクトリごとに上書きできます。

- **Task source**: 接続されているすべてのタスク管理ツール、または1つのプラグイン。**Every connected tracker** では、Kody は Linear、Jira、Notion、Git Issues に加え、名前からタスク管理ツールであることがわかるカスタムプラグイン (Jira、Linear、Notion、ClickUp) を読み取ります。Azure DevOps など、それ以外のカスタムプラグインは、選択した場合にのみ読み取られます。カスタムプラグインの場合は、ID で1つのタスクを読み取るツールを選択します。読み取り専用のツールのみが表示されます。ページ右側に固定された **Try it** (この設定の編集権限が必要) を使うと、タスクのみの場合は Kody がそこから何を読み取るかが表示され、プルリクエストの場合は画面上の設定 (保存済みかどうかを問わず) でチェック全体を投稿せずに実行します。**Post to the pull request** は、表示された結果を再実行せずに、テストごとに1回だけ投稿します。テスト後にプルリクエストへコミットがあった場合、または30分が経過した場合は投稿が拒否されるので、先にテストを再実行してください。
- **Custom task id format** (任意): Kody が自動では見つけられない ID のための正規表現。`T(\d{4})` は `T1234` をタスク 1234 として読み取ります。`SAA-96`、`#12`、`AB#8`、`CU-…` のようなキーとタスク管理ツールのリンクはこの設定がなくても見つかります。ブランチ名の `sc-123` のような小文字のキーも同様です。タイトルや説明文の小文字のキーは、Linear または Jira にそのチームやプロジェクトがある場合にのみ有効です。それ以外のタスク管理ツールでは形式を設定してください。形式が取り出した数字は、Git Issues がタスクソースの場合にのみ Git の issue として読まれます。接続されているすべてのタスク管理ツールを使う設定では、`T1234` がリポジトリの issue #1234 になることはありません。形式は最大200文字で、`(a+)+` のように実行に時間がかかる可能性があるものは Kody が破棄します。
- **Requirements → Where acceptance criteria live**: 自動検出 (受け入れ基準のフィールド、チェックリスト、または説明内のリスト)、説明内の見出しの下、またはカスタムフィールド。そのフィールドがないタスクは説明から読み取られます。**Under a heading in the description** を `Acceptance criteria` に設定すると、次のタスクは3つの箇条書きと照合され、その上の段落は背景情報として扱われます。

  ```markdown
  Agents should see at a glance how much time is left on a ticket's SLA.

  ## Acceptance criteria
  - The ticket header shows a badge with the remaining SLA time.
  - The badge turns red when less than 1 hour is left.
  - Resolved tickets show no badge.
  ```
- **On the pull request → Comment when every requirement is met** (デフォルトでオン): タスクを満たした PR には短いコメントが付きます。オフにするとコメントは付きませんが、手動で確認すべき項目、PARTIAL、タスクにない変更がある PR には引き続きコメントが付き、PR にすでにあるコメントも更新されます。
- **On the pull request → Ask for a task when the PR references none**: Kody はスキップする代わりに、PR がどのタスクに対応するかを尋ねるコメントを投稿し、タイプミスのように見える参照は修正されるまで未解決のままになります。Dependabot や Renovate などの bot が作成した PR には何もしません。タスク管理ツールのダウンは対象外です。
- **On the pull request → Re-check after a push**: **Only on request** (デフォルト)、**While something is missing**、または **On every push**。各チェックはレビューと同じく組織のモデルで実行されるため (**Code review → Routing** の **Other task models** にある **Business Rules** で別のモデルを指定できます)、**On every push** では push ごとに検証1回分のコストがかかります。
- **Skipped pull requests**: Business Logic は、コードレビューがスキップする PR をスキップします。無視するキーワードを含むタイトル (`ignoredTitleKeywords`、たとえば `wip`) と、`runOnDraft` がオフの場合のドラフトです。これらは **Code review → General** で設定します。`@kody -v business-logic` のコメントは常に実行されます。
- **Requirements → Team guidance**: Kody が判断するときに従うメモで、最大2,000文字。たとえば「フィーチャーフラグは、フラグが存在しデフォルトでオフになっていれば実装済みとみなす」。判定の形式を変えたり、Kody に要件を作り出させたりすることはできません。

### よくある設定

| チーム | 設定 |
|---|---|
| チェックは欲しいがノイズは不要 (デフォルト) | リクエスト時に再チェック、**Comment when every requirement is met** をオン |
| すべての PR がタスクを実装すべき | **Ask for a task** をオン、**Re-check after a push** を **While something is missing** に設定: タスクのない PR にはタスクを求め、修正のたびにコメントが更新され、満たされるまで続きます |
| 不足点だけ知りたい | **Comment when every requirement is met** をオフ |
| 領域ごとにタスク管理ツールが異なるモノレポ | **Task source** と **Where acceptance criteria live** をディレクトリごとに設定 |

`kodus-config.yml` での同じ設定 (**Code review → General** で **Prefer kodus-config.yml settings** がオンの場合に読み取られます):

```yaml
businessLogic:
  taskSource: 'auto'              # or a plugin's integration id
  taskSourceTool: 'get_ticket'    # custom plugin only: the tool that reads one task by id
  taskIdPattern: 'T(\d{4})'       # optional: ids Kody doesn't find on its own
  criteriaLocation: 'heading'     # auto | heading | field
  criteriaHeading: 'Acceptance criteria'
  # criteriaField: 'Acceptance Criteria'   # with criteriaLocation: 'field'
  teamGuidance: 'Feature flags count as implemented when the flag exists and defaults to off.'
  commentWhenMet: true
  recheckOn: 'request'            # request | failing | push
  requireTask: false
```

## CLI から

コーディングエージェントは PR を作成する前に自分の作業をチェックできます。

```bash
kodus pr business-validation --task-id AB#8
kodus pr business-validation --task-id AB#8 --format json
```

ローカルの変更をタスクと照合し、要件ごとに1行と状態を出力します。`--format json` (または `--agent`) を指定すると、エージェントが処理できるよう同じ判定を構造化して出力します。プルリクエストには何も投稿されません。

タスクは `--task-id` または `--task-url` で指定します (両方は指定できません)。チェック対象の変更は、ファイルパス、`--staged`、`--commit <sha>`、`--branch <name>` のいずれか1つで選択します。いずれも指定しない場合は、追跡対象ファイルのステージ済みおよび未ステージの変更をチェックします。

## Cockpit

**Cockpit → Delivered as asked** (Teams および Enterprise プラン) には、タスクを満たした PR の割合 (**Met their task**)、タスクにない変更を含む PR の割合、開発者が Kody に同意した頻度 (**Findings accepted**)、読み取れるタスクがない PR の割合、コードを書いたのが誰か (人かコーディングエージェントか。コミットの作成者と `Co-Authored-By` トレーラーから判定) による内訳、最も多く不足している要件の種類、そして組織に複数のチームがある場合はチームごとの表が表示されます。Cockpit のリポジトリ選択と期間に従い、他のタブと同様に **Organization → Cockpit visibility** で非表示にできます。
