リンクされたリポジトリを使うと、プルリクエストのレビュー中に Kody が組織内の他のリポジトリを**読み取り専用のコンテキスト**として参照できます。これがないと、レビューが見られるのは、PR の head でチェックアウトされたレビュー対象のリポジトリだけです。別のリポジトリにあるもの（呼び出しているサービス、インポートしているライブラリなど）は見えません。

レビュー対象のリポジトリごとに、接続済みのリポジトリを最大 3 つリンクできます。

リンクには方向があり、リポジトリごとに設定します。`frontend → backend-api` をリンクすると、Kody は `frontend` のレビュー時に `backend-api` を参照できます。両方で確認が必要なら逆方向のリンクも追加します。

## どんなときに必要か

どれもよくある状況で、単一リポジトリのレビューでは見えない3つのケースです。

1. **producer/consumer の契約の破壊。** バックエンドが API のフィールド名を変更したのに、フロントエンドが古い名前を読み続けている。producer が追加した enum の値を、どの consumer も処理していない。writer と reader が、同じキャッシュキーを別々の方法で導出している。契約が2つのリポジトリに分かれていて、何もそれを保証していません。

2. **自分のリポジトリが依存しているコードが、自分のリポジトリにない。** vendor された社内パッケージ、ビルド時に取得される共有ライブラリ、git submodule。レビューは*パッケージを取得しない*ため、ビルド時の依存は、エージェントが辿れない import になります。git submodule を取得するのは、その submodule が PR のベースブランチですでに宣言されていて、同じ Git ホスト上にあり、別の submodule の内側にネストされていない場合に限られ、制限時間内でのみ行われます。それ以外の submodule は、レビュー中は空のディレクトリです。正規の型、ルール、クライアントがそのようなリポジトリにある場合は、それをリンクすることで、読み取れるようになります。

3. **同じビジネスルールがチャネルやサービスごとに再実装されている。** 価格、在庫の可否、バリデーション、注文ステータスの遷移など、正規の場所に一度だけ存在し、あちこちに「だいたい」コピーされているもの。正規のリポジトリをリンクすれば、エージェントは推測ではなく、正のソースと比較できます。

<Note>
**この機能がなくても、レビューがすでに見ているもの:** PR の head コミットにおける、レビュー対象リポジトリ全体（diff だけではありません）と、PR の説明。そのチェックアウト内のどのファイルでも、grep して読み取れます。見えないのは、他のリポジトリ、インストール済みの依存関係、取得しない submodule です。
</Note>

リンクされたリポジトリは、コードの外にある契約は**カバーしません**。たとえば、サードパーティ API のバリデーション規則は、どのリンク先リポジトリからも見つけられません。

## 得られるもの

具体例を挙げます。フロントエンドの PR が、次のエラーハンドリングを追加したとします。

```ts
const isNotApproved =
    error.response?.data?.error === 'INTEGRATION_NOT_APPROVED';
```

バックエンドをリンクしておくと、Kody はその契約の反対側を確認し、PR に次のようにコメントします。

> **Bug · medium** — [cross-repo] フロントエンドは `error.response?.data?.error` が `INTEGRATION_NOT_APPROVED` かどうかを確認していますが、バックエンドの `sendError`（`src/api/response.ts`）は、コードを `message` フィールドで返します。not-approved の分岐は決して一致せず、ユーザーには常に汎用のエラートーストが表示されます。代わりに `data.message` を読んでください。

レビューのサマリーには、参照したものも表示されます: **Additional context used:** `org/backend-api@main`。

### 指摘が付く場所

- すべてのコメントは、**あなたの PR の diff** の行に付きます。リンク先リポジトリのコードは、`[cross-repo]` タグ付きで、相手側のファイル名とともに、コメント内に根拠として引用されます。Kody が、リンク先リポジトリにコメントしたり、指摘を登録したり、変更したりすることはありません。
- 指摘が挙げられるのは、相手側のファイルから確認できた根拠がある場合のみです。証拠のない「このリテラルはバックエンドと一致していなければならない」という指摘は出力されません。
- **Additional context used** の行は、レビュー中にリンク先リポジトリが実際に読み取られた場合にのみ表示されます。行がない場合は、参照されていません（その理由は後述）。

## 仕組み

リンクされたリポジトリを持つリポジトリのプルリクエストが境界面に触れると、Kody のレビューエージェントは、自分のリポジトリを grep するのと同じ要領で、リンクされたリポジトリを検索して読み取り、契約の両側が今も一致しているかを検証できます。リンクされたリポジトリは遅延取得され、エージェントが最初に読み取るときにのみフェッチされます。[カスタムエージェント](/ja/how_to_use/code_review/custom_agents)も同じリンクを使用しますが、それは、そのエージェント自身の指示がレビューを求めている内容の根拠としてのみです。

### このパスを有効にする条件

リンクを設定するだけでは十分ではありません。レビューの前に、軽量で決定的なチェックが、PR の diff の**追加行**を走査し、*境界面*が見つかった場合にのみ、リポジトリ横断のツールを有効にします。

- 文字列リテラル（コード、イベント名、パスのセグメント、ヘッダー名）
- エクスポートされたシンボル（`export function/const/class/type/interface/enum`）
- enum、type、interface のメンバー
- オブジェクト / ペイロード / DTO のフィールドキー
- status、state、エラーコードのような識別子（`status`、`code`、`errorCode`、`kind`、`event`、`key` など）
- 契約のようなファイルパス（`dto/`、`schema/`、`api/`、`types/`、`clients/`、`openapi`、`proto` など）

このチェックは寛容です。文字列リテラル、プロパティキー、エクスポートのいずれかを含む追加行が1行あれば十分です。コードの削除のみ、import の並べ替え、コメントの編集、プライベートなヘルパーの名前変更だけの diff は、これらのどれにも該当しないため、リンクされたリポジトリはフェッチされず、レビューは単一リポジトリのレビューとまったく同じように実行されます。これは意図的なものです。何も見つけられない diff では、このパスをオフに保ちます。

### 何も表示されないとき

リンクされたリポジトリを持つリポジトリの PR に `Additional context used` の行が**ない**場合、可能性の高い順に、次のいずれかが起きています。

1. diff に境界面がなかった（ゲートがオフのまま。リファクタリングでは想定どおりです）。
2. ゲートはオンだったが、エージェントが結論に至るためにリンクされたリポジトリを必要としなかった。
3. リンクされたリポジトリを取得できなかった（権限、タイムアウト）。レビューはそれなしで続行されます。
4. リンクされたリポジトリがこの Kodus 組織に接続されていない、または組織のプランにこの機能が含まれていない。リンクは無視されます。

最初の2つは、機能が設計どおりに動作している状態です。リンクが正しく設定されているかを確認するには、共有リテラル、DTO フィールド、エクスポートされた型を*実際に*変更する PR を開いてください。それによってゲートが有効になり、エージェントにリポジトリをまたいで確認する理由が生まれます。

<Info>
- リンクできるのは、**同じ Kodus 組織にすでに接続されている**リポジトリのみです（Kody は既存の Git 連携を再利用するため、追加のトークンは不要です）。
- 1つのリポジトリにつき、リンクできるのは**最大3つ**です。`kodus-config.yml` では、3つ目より後のエントリは破棄されます。
- アクセスは読み取り専用です。Kody が、リンクされたリポジトリにプッシュしたり、コメントしたり、変更したりすることはありません。
- リンクされたリポジトリを取得できない場合（権限、タイムアウト）、レビューはそれなしで通常どおり続行されます。
</Info>

## リンクされたリポジトリの追加

### Web アプリで

サイドバーの **Code review** グループ上部にあるスコープピッカーでリポジトリを選択し、**Code review → Linked repositories** を開きます。このページが存在するのは、リポジトリスコープのみです。**Add repository** をクリックし、**Add linked repository** ダイアログでリポジトリを選択し（接続済みのリポジトリのみ表示されます）、**Save settings** をクリックします。リンクをクリックすると、任意の2つのフィールド、**Instructions**（最大500文字）と **Branch / ref pin** が開きます。これらについては後述します。リンクは、その行の **X** で削除できます。リンクが3つになると、**Add repository** は無効になります。

### `kodus-config.yml` で

`linkedRepositories` は設定ファイルのキーでもあるため、リンクを、他のレビュー設定と並べてバージョン管理に置けます。

```yaml
linkedRepositories:
  - repository: "org/backend-api"
    instructions: "REST API this frontend consumes"
    ref: main   # optional pin; omit for the same-branch cascade
```

- `repository`（必須）— 組織に接続されているリポジトリのフルネーム（`owner/repo`）。
- `instructions`、`ref` — Web アプリのフィールドと同じ意味です（後述）。

ファイルと Web 設定の関係は、通常の[設定ファイルのルール](/ja/how_to_use/code_review/configs/general#設定の優先度)に従います。ファイルが読み取られるのは、リポジトリで **Prefer kodus-config.yml settings**（**Code review → General**）がオンの場合のみで、リポジトリの**デフォルトブランチ**から読み取られ、ファイルの `linkedRepositories` リストが、そのリポジトリの Web のリストを**置き換えます**（リストはマージされません。ファイルの `linkedRepositories: []` は、この機能をオフにします）。プランの要件は、リンクをどこで宣言しても適用されます。

### Instructions

このリンクが**何のためのもので、どこを見ればよいか**をレビューエージェントに伝える、自由記述のヒントです。なくても Kody は動作しますが、適切な指示があると、リポジトリ横断のパスが速く、正確になります。エージェントがリンク先をゼロから探索するか、関連するコードに直行するかの違いです。

適切な指示は、関係と、要となるパスを具体的に示します。

```text
REST API this dashboard consumes. Error responses are built by
src/api/response.ts — check error codes against it.
```

```text
Shared order state machine. Status enums live in
src/domain/order-status.ts; we must handle every value it defines.
```

リンクされたライブラリや submodule の場合（上記のケース2）は、そのコードがこのリポジトリに*ない*ことと、エージェントが何と照合すべきかを書きます。

```text
Canonical library of business rules, types and clients. Consumed here as a
git submodule, so its source is not in this repo. Validation rules live in
src/rules/, API clients in src/clients/ — check field names and status
values against them.
```

効果の薄い指示は、自明なこと（「バックエンドのリポジトリ」）を繰り返すだけで、何も加えません。

<Note>
リポジトリ横断のパスが探すのは、**境界をまたいだ不一致**です。つまり、片側のフィールド名、キー、エンコーディング、ステータス値が、もう片側が生成する、または期待するものと一致していないケースです。正規のライブラリをリンクすれば、盲点はなくなります（エージェントがそれを読めるようになります）が、それだけで、「正規の実装がすでに存在するのに、この PR はより弱い実装を再実装している」とレビューが指摘するようにはなりません。そのチェックが必要な場合は、[Kody Rule](/ja/how_to_use/code_review/configs/kody_rules) として記述し、指示で正規の実装の場所を示してください。
</Note>

### Ref pin（ブランチの選択）

Kody が、リンクされたリポジトリのどのブランチ（"ref"）を読み取るかを制御します。**ほとんどのチームは空のままにします**。その場合、Kody は、あなたの PR のブランチと同じ名前のブランチが存在すればそれを読み取り（複数リポジトリにまたがる連携した変更が、マージ前に互いに見えるように）、存在しなければデフォルトブランチにフォールバックします。

解決順序の全体は次のとおりです。Kody は、取得できた最初のものを使用するため、存在しないピンは、次のステップに進みます。

1. **PR の説明での上書き** — レビュー対象の PR のタイトルまたは説明に、リンクされたリポジトリのブランチや PR を記載します（例: `org/backend-api#123`、PR の URL、`org/backend-api@feature-x`）。1回限りで、最優先です。すでにリンクされているリポジトリにのみ適用されます。
2. **設定の `ref` ピン**（このフィールド）。設定されている場合。
3. **一致するブランチのオープンな PR** — リンクされたリポジトリで、head ブランチがあなたの PR の head ブランチと一致する、オープンなプルリクエスト。
4. リンクされたリポジトリの**同名のブランチ**。
5. リンクされたリポジトリの**デフォルトブランチ**（その後、`main`/`master` にフォールバック）。

ステップ3〜4は、複数リポジトリにまたがる機能開発の足並みをそろえるためのものです。レビューは、まだその変更を含まないデフォルトブランチではなく、マージ*前*の対になる変更を確認できます。

安定したブランチに対して決定的なレビューを行いたい場合は、**ref pin**（例: `main`、`develop`、`release/2.x`）を設定してください。たとえば、無関係な作業でリポジトリ間にブランチ名が使い回されていて、同名ブランチの一致によって誤ったものが選ばれてしまう場合です。1回限りのケースでは、PR の説明での上書きが、ピンよりも優先されます。

<Tip>
submodule の場合、追跡しているものがライブラリのデフォルトブランチより遅れているなら、`ref` を、リポジトリが実際に追跡しているコミットまたはブランチに固定してください。そうしないと、まだ取り込んでいないコードと比較されることがあります。
</Tip>

リンクされたリポジトリが読み取られると、**Additional context used** の行に、実際に使用された ref が表示されます。例を交えた手順については、[リンクされたリポジトリの使い方](/ja/knowledge_base/how-to-use-linked-repositories-in-code-review)を参照してください。
