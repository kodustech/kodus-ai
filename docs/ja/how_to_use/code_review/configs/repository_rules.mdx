<Info>
リポジトリルールは常に同期されます。オンにする設定はありません。リポジトリ内で Kody Rules になるのはこれらのファイルだけです。コーディングエージェント向けに書かれた指示（`CLAUDE.md`、`AGENTS.md`、`.cursor/rules`）は別に扱われます。<a href="/ja/how_to_use/code_review/configs/rules_file_detection">コーディングエージェント向け指示</a> を参照してください。
</Info>

## 使い方

以下のテンプレートに沿ったマークダウンファイルをリポジトリに置きます。Kody はそれをルールとしてインポートし、ルールはファイルに追従します。ファイルを編集するとルールが変わり、ファイルを削除するとルールも削除されます。

ファイルは LLM による変換なしで **そのまま** インポートされます。フロントマターは記述どおりに読み込まれ、マークダウン本文は記述したとおりにルールの指示になり、悪い例と良い例は本文からインポートされます。1 つのファイルから 1 つのルールが作成されます。

- **自動：** ルールファイルは、接続済みのすべてのリポジトリで同期されます。
- **マージ時：** ルールファイルを追加・変更・リネーム・削除するプルリクエストがマージされると、ルールが作成・更新・削除されます。[集中設定](/ja/how_to_use/code_review/configs/centralized_config) リポジトリのプルリクエストは同期されません。
- **今すぐインポート：** すでにリポジトリにあるファイルは、リポジトリの **Code review → Kody Rules → Configuration** を開き、**Import rule files now** をクリックします。デフォルトブランチ上のすべてのルールファイルを読み込みます。
- **アプリ内：** 同期されたルールは、リポジトリの **Kody Rules** ページに、**Auto-sync** のオリジンと、ソースとしてのファイルパス付きで表示されます。

新しいルールは有効な状態で追加されます。**Kody knowledge approval** がオンの場合は **Pending review** に入ります。

ファイルが信頼できる唯一の情報源です。ルールのテキスト、パス、重大度、ステータスは同期のたびにファイルの内容で置き換えられるため、アプリ上のルールではなくファイルを変更してください。アプリで一時停止したルールは、そのファイルが次に同期されたときに再び有効になります。

## ファイルの場所

ルールファイルは、リポジトリのルートまたは任意のサブディレクトリにある、以下のいずれかの場所に配置します。

- `.kody/rules/`
- `rules/**/*.md`
- `.rules/` と `docs/coding-standards/`（テンプレートに沿ったファイルのみ）

ルールのスコープは、ファイルの場所ではなく `path` で決まります。`services/billing/.kody/rules/` にある `path` のないルールも、すべてのファイルに適用されます。

## ルールテンプレート

````markdown
---
title: "<rule name>"
scope: "file"            # "file" or "pull-request"
path: []                 # list of globs. example: ["**/*.ts", "apps/web/**"]
severity_min: "high"     # "low", "medium", "high", "critical"
enabled: true            # optional
---

## Instructions
Describe what to review and how to decide. Be direct and objective.
- Focus on security, performance and public contract impacts.
- Give team preferences or patterns when applicable.
- If it's a PR rule, explain what to consider in the changeset.

## Examples

### Bad example
```lang
// paste here a short counter-example that violates the rule
```

### Good example
```lang
// paste here a short example that follows the rule
```
````

### フィールド

必須なのは、空でない `title` と空でない本文だけです。どちらかが欠けているファイルはスキップされます。

| フィールド | 説明 | 値 | デフォルト |
|-------|-------------|--------|---------|
| `title` | アプリに表示されるルール名 | 任意の文字列 | 必須 |
| `scope` | **Per file** または **Per PR** | `"file"` または `"pull-request"` | `"file"` |
| `path` | ルールを適用するファイル。**いずれか**のグロブに一致するファイルで実行されます。`pull-request` ルールでは使用されません | グロブ、またはグロブのリスト | `**/*`（すべてのファイル） |
| `severity_min` | ルールの重大度 | `"low"`、`"medium"`、`"high"`、`"critical"` | `"medium"` |
| `enabled` | `false` にするとファイルはスキップされます。そこからインポート済みのルールは削除されません | boolean | `true` |

<Note>
  `severity` は `severity_min` のエイリアスとして受け付けられます。4 つのレベル以外の値は `"medium"` にフォールバックし、`"pull-request"` 以外の `scope` は `"file"` として扱われます。それ以外のフロントマターキーは無視されます。
</Note>

悪い例と良い例は、見出しに "bad" または "good" を含むもの（たとえば `### Bad example`）から取得されます。そのような見出しの下にあるフェンス付きコードブロックは、すべて例になります。

## ルールの例

### ファイルレベルルール

````markdown
---
title: "Avoid console.log in production code"
scope: "file"
path: ["src/**/*.ts", "src/**/*.tsx"]
severity_min: "medium"
---

## Instructions
Check for console.log statements in production TypeScript/JavaScript files.
- Console logs should not appear in production code
- Use proper logging libraries instead
- Allow console.log only in development utilities

## Examples

### Bad example
```typescript
function processUser(user: User) {
  console.log('Processing user:', user.id);
  return user.process();
}
```

### Good example
```typescript
import { logger } from './logger';

function processUser(user: User) {
  logger.info('Processing user:', user.id);
  return user.process();
}
```
````

### プルリクエストレベルルール

````markdown
---
title: "New API endpoints must have tests"
scope: "pull-request"
severity_min: "high"
---

## Instructions
When new API endpoints are added, ensure corresponding tests are included in the PR.
- Check for new route definitions in controllers
- Verify test files exist for new endpoints
- Ensure both positive and negative test cases

## Examples

### Bad example
Added new endpoint `/api/users/profile` but no test file included in the PR.

### Good example
Added new endpoint `/api/users/profile` with corresponding test file `tests/api/users/profile.test.ts` that covers success and error cases.
````

## ファイルが同期されなくなる場合

- **ファイルがテンプレートに沿っていない。** フロントマター、`title`、本文のいずれかがないファイルはスキップされます。そのファイルからすでにルールがインポートされている場合、ルールは最後のテキストとステータスを保持し、ルールのサイドパネルに、ファイルが同期されなくなったという警告が表示されます。ファイルが再び解析できるようになると、警告は消えます。
- **ファイルを同期の対象外にする。** ファイルの最初または最後の 10 行以内に `@kody-ignore` を追加します。そのルールは次回の同期で削除されます。
- **ファイルのインポートを止める。** `enabled: false` にすると、そのファイルはインポートされなくなります。すでにあるルールは削除も一時停止もされません。それにはファイルを削除するか、`@kody-ignore` を使ってください。

## セルフホストのログ

セルフホストのデプロイでは、ログから次のマーカーを検索します。

- `[kody-rules-sync]`：同期ごとのサマリー。インポート、スキップ（理由付き）、削除されたファイルが記録されます。
- `[kody-rules-eval]`：レビュー中に、変更されたファイルに対してどのルール（uuid とタイトル）が選ばれたかが記録されます。

アプリ上では有効なのに、期待するファイルの `[kody-rules-eval]` に一度も現れないルールがある場合は、その **Path** を確認してください。ルールはパスに一致するファイルでしか実行されません。

## ルールの上限

Free プランと、ライセンスのないセルフホストインスタンスでは、ファイル由来のルールを含め、有効なルールは最大 10 個までです。[ルールの上限](/ja/how_to_use/code_review/configs/kody_rules#ルールの上限) を参照してください。
