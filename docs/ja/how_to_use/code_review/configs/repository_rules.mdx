<Info>
リポジトリルールは常に同期されます。オンにする設定はありません。リポジトリ内で Kody ルールになるのはこれらのファイルだけです。コーディングエージェント向けに書かれた指示（`CLAUDE.md`、`AGENTS.md`、`.cursor/rules`）は別に扱われます。<a href="/ja/how_to_use/code_review/configs/rules_file_detection">コーディングエージェント向け指示</a> を参照してください。
</Info>

## 使い方
リポジトリに直接カスタム Kody ルールを作成するには、特定のディレクトリに構造化されたマークダウンファイルを配置します。これにより、コードと並行してルールをバージョン管理し、チーム全体で共有できます。

<Info>
リポジトリのルールファイルは **そのまま**（LLM 変換なしで）インポートされます。フロントマターはそのまま解析され、マークダウン本文は記述したとおりにルールの指示になり（識別子・書式・文言は保持されます）、悪い例／良い例も構造を保ってインポートされます。1 つのファイルから 1 つのルールが作成されます。テンプレートとして解析できないファイル（フロントマター、`title`、または本文が無いもの）はスキップされ、同期のログに記録されます。そこから何かが生成されることはありません。
</Info>

### 同期
- **自動検出**：リポジトリルールは接続済みのすべてのリポジトリで検出・同期されます。有効化する必要はありません
- **今すぐインポート**：リポジトリの **Kody Rules → Configuration** シートにある **Import rule files now** で、デフォルトブランチ上のすべてのルールファイルを読み込みます
- **Webアプリケーション**：同期されたルールは、そのリポジトリの **Code review → Kody Rules** ページに **Auto-sync** のオリジン付きで表示されます（変換が停止される前にコーディングエージェント向けファイルからインポートされたルールには、代わりに **Agent file** と表示されます）
- **リアルタイム更新**：プルリクエストがデフォルトブランチにマージされるとルールファイルの変更が同期されます

## ファイルの場所

ルールファイルを以下のいずれかのディレクトリ（リポジトリのルートまたは任意のサブディレクトリ）に配置してください：
- `.kody/rules/**/*.md`
- `rules/**/*.md`
- `.rules/**` と `docs/coding-standards/**`（テンプレートに沿ったファイルのみ）

## ルールテンプレート

各ルールファイルはこの正確なテンプレート構造に従う必要があります：

```markdown
---
title: "<ルール名>"
scope: "file"            # "file" または "pull-request"
path: []                 # glob のリスト。例：["**/*.ts", "apps/web/**"]
severity_min: "high"     # "low", "medium", "high", "critical"
languages: []            # オプション。例：["jsts", "go", "php", "ruby", "java", "csharp", "dart", "kotlin", "rust"]
buckets: []              # オプション。例：["style-conventions", "error-handling", "security"]
uuid: ""                 # オプション。安定したルール ID に使用
enabled: true            # オプション
---

## 指示
何をレビューするかとどのように判断するかを説明します。直接的で客観的に。
- セキュリティ、パフォーマンス、パブリックコントラクトへの影響に焦点を当てます。
- 該当する場合はチームの設定やパターンを提供します。
- PR ルールの場合は、変更セットで何を考慮するかを説明します。

## 例

### 悪い例
\`\`\`lang
// ルールに違反する短い反例をここに貼り付け
\`\`\`

### 良い例  
\`\`\`lang
// ルールに従う短い例をここに貼り付け
\`\`\`
```
## テンプレートフィールド

### 必須フィールド

厳密に必須なのは 2 つだけです：空でない `title` と、空でないルール本文。どちらかが欠けている
ファイルは丸ごとスキップされます。

| フィールド | 説明 | 値 |
|-------|-------------|---------|
| `title` | インターフェースに表示されるルール名 | 任意の説明的な文字列 |

### デフォルト値のあるフィールド

それ以外はすべて任意です — 省略するとデフォルトが適用されます。

| フィールド | 説明 | 値 | デフォルト |
|-------|-------------|---------|---------|
| `scope` | ルールの分析スコープ | `"file"` または `"pull-request"` | `"file"` |
| `path` | ルールを適用するパス。**いずれか**のグロブに一致するファイルで発火します | グロブパターンの配列 | `**/*`（すべてのファイル） |
| `severity_min` | 最小の重大度レベル | `"low"`、`"medium"`、`"high"`、`"critical"` | `"medium"` |
| `enabled` | `false` にするとこのファイルはインポートされません（既にインポート済みのルールは削除されません） | boolean | `true` |
| `uuid` | 安定したルール識別子 — ファイル名を変更してもプラットフォーム上で同じルールを維持します | string | なし |
| `languages`、`buckets` | 参考用のメタデータ | — | — |

<Note>
  `severity` は `severity_min` のエイリアスとして受け付けられます（打ち間違えやすく、意図が
  明確なため）。4 つのレベル以外の値は `"medium"` にフォールバックし、`"pull-request"` 以外の
  `scope` は `"file"` として扱われます。
</Note>

## ルールの例

### ファイルレベルルールの例
```markdown
---
title: "本番コードで console.log を使用しない"
scope: "file"
path: ["src/**/*.ts", "src/**/*.tsx"]
severity_min: "medium"
languages: ["jsts"]
buckets: ["style-conventions"]
enabled: true
---

## 指示
本番 TypeScript/JavaScript ファイルで console.log ステートメントを確認します。
- console.log は本番コードに含まれるべきではありません
- 代わりに適切なログライブラリを使用してください
- console.log は開発ユーティリティのみに許可します

## 例

### 悪い例
\`\`\`typescript
function processUser(user: User) {
  console.log('Processing user:', user.id);
  return user.process();
}
\`\`\`

### 良い例
\`\`\`typescript
import { logger } from './logger';

function processUser(user: User) {
  logger.info('Processing user:', user.id);
  return user.process();
}
\`\`\`
```

### プルリクエストレベルルールの例
```markdown
---
title: "新しい API エンドポイントにはテストが必要"
scope: "pull-request"
path: ["**/*"]
severity_min: "high"
buckets: ["testing"]
enabled: true
---

## 指示
新しい API エンドポイントが追加された場合、対応するテストが PR に含まれていることを確認します。
- コントローラーの新しいルート定義を確認します
- 新しいエンドポイントのテストファイルが存在することを確認します
- 正常系と異常系の両方のテストケースを確認します

## 例

### 悪い例
新しいエンドポイント `/api/users/profile` が追加されたが、PR にテストファイルが含まれていない。

### 良い例
新しいエンドポイント `/api/users/profile` が追加され、成功とエラーのケースをカバーする対応するテストファイル `tests/api/users/profile.test.ts` が含まれている。
```

## セットアップ要件

1. **ルールファイルを作成する**：テンプレートに沿った `.md` ファイルを `.kody/rules/**` または `rules/**` に配置します。`.rules/**` と `docs/coding-standards/**` にあるテンプレートに沿ったファイルもインポートされます。
2. **マージする**：ルールファイルは、それを追加・変更・リネーム・削除するプルリクエストがデフォルトブランチにマージされたときに同期されます。ファイルを削除するとそのルールも削除されます。
3. **既存のファイル**：デフォルトブランチにすでにあるルールファイルをインポートするには、リポジトリの **Kody Rules → Configuration** シートで **Import rule files now** を使います。

新しいルールは有効な状態で追加されます。**Kody knowledge approval** がオンの場合は **Pending review** に入ります。

<Tip>
ルールファイルをリポジトリに残したまま同期しないようにするには、ファイル内のどこかに `@kody-ignore` を追加します。既存のルールは次回の同期で削除されます。
</Tip>

## 同期とルール評価の確認（セルフホスト）

セルフホストのデプロイでは、API のログに grep しやすいマーカーが出力されます：

- `[kody-rules-sync]` — 実行ごとの同期サマリー：どのファイルがインポート・スキップ（理由付き）・削除されたか。
- `[kody-rules-eval]` — レビュー中のファイル単位の評価トレース：レビュー対象ファイルごとに、どのルール（uuid + タイトル）がプロンプトに選ばれたか。

```bash
docker logs kodus_api 2>&1 | grep "kody-rules-sync"
docker logs kodus_api 2>&1 | grep "kody-rules-eval"
```

UI 上では有効なのに、期待するファイルの `[kody-rules-eval]` に一度も現れないルールがある場合は、その **Path** グロブを確認してください — ルールはパスに一致するファイルでしか実行されません。

## ルールの上限

クラウドの **Free** プランの組織（またはサブスクリプションがキャンセル済み・期限切れの組織）と、**有効なライセンスなし**で稼働しているセルフホストインスタンス（Community Edition）は、1 回のレビューで最大 **10 個の有効なルール**（古い順）までしか評価しません。上限を超えたルールは **Locked** としてリストに残り、すべての PR でスキップされます。**Code review → Kody Rules** のバナーに、スキップされているルールの数が表示されます。有料のクラウドプランとライセンス済みのセルフホストにはこの上限はありません。11 個目以降のルールが発火しない場合は、この上限が原因です。
