---
title: "レビューの方向付け（フォーカス）"
description: "PR コメントまたは CLI から、単発のレビューディレクティブでプルリクエストの特定の領域に Kody の注意を向けます"
---

**レビューディレクティブ** を使うと、その 1 回のレビューで Kody がどこを最も深く分析すべきかを指示できます。設定を変更する代わりに、レビューを起動するときに短い指示を添えます。たとえば「認証とセッションのロジックに集中して」と伝えると、Kody は該当する変更コードに最も厳しい分析を集中させます。

<Note>
  ディレクティブは **一時的** です。その 1 回のレビュー実行にのみ適用され、設定には保存されず、今後のレビューには影響しません。Kody の挙動を恒久的に変えたい場合は、代わりにカテゴリの指示と Kody のパーソナリティ（[Instructions & Personality](/ja/how_to_use/code_review/configs/custom_prompts)）または [Kody Rules](/ja/how_to_use/code_review/configs/kody_rules) を使ってください。
</Note>

## いつ使うか

- PR が多数のファイルに触れているが、特にリスクの高い 1 つの領域（認証、決済、マイグレーション）が気になるとき。
- 特定の変更の呼び出し元と呼び出し先を Kody に辿らせ、より厳しく精査させたいとき。
- レビューを再実行する際、設定を編集せずに注意を向けたいとき。

## フィルターではなく優先度

これが最も重要なポイントです。

<Warning>
  ディレクティブは **フィルターではなく優先度** を設定します。Kody はフォーカス領域を優先しますが、diff の **他の箇所** で気づいた具体的なバグ、セキュリティ、パフォーマンスの問題も引き続き報告します。フォーカス外の指摘を抑え込むことはなく、PR の残りを未確認のまま承認することもありません。
</Warning>

ディレクティブは *「ここを最も重点的に見て」* と伝えるものであり、*「ここだけ見て」* ではありません。

## 起動方法

<Tabs>
  <Tab title="PR / MR コメント">
    プルリクエストのコメントで、レビューコマンドの直後にフォーカステキストを書きます。

    ```text
    @kody review focus on the auth and session logic
    ```

    `start-review` も使え、`--force` と組み合わせられます。

    ```text
    @kody start-review focus on the new database migration
    @kody review --force focus on error handling in the webhook parser
    ```

    <Note>
      `--force` は、Kody が通常スキップする場合（「前回のレビュー以降に新しいコミットがない」）でもレビューを再実行します。フォーカスディレクティブの有無にかかわらず、前回の実行を失敗させた原因を修正した後にあらためてレビューを実行したり、レビュー済みの PR に更新後の設定を適用したりする際に使ってください。
    </Note>

    <Note>
      ディレクティブとして使われるのは、コマンドの後の **最初の 1 行のみ** です。以降の行は無視されるため、フォーカスは 1 行にまとめてください。
    </Note>

    GitHub、GitLab、Azure DevOps、Bitbucket、Forgejo で動作します。
  </Tab>
  <Tab title="CLI">
    レビュー実行時に `--focus` フラグを渡します。

    ```bash
    kodus review --focus "the auth and session logic"
    ```

    コマンド全体は [CLI コマンドリファレンス](/ja/how_to_use/cli/commands) を参照してください。
  </Tab>
</Tabs>

## Heavy mode

<Badge color="yellow" size="sm">ベータ版</Badge>

Teams、Enterprise、および Cloud ワークスペースのトライアルで利用できます。セルフホストでは有効な Teams または Enterprise ライセンスが必要です。CLI では認証済みのワークスペースを使います。未認証のトライアルレビューは Balanced で実行されます。

フォーカスディレクティブは Kody に *どこを* 重点的に見るかを伝えます。`--heavy` は *より広く* 見ることを伝えます。通常のレビューと並行して、9 つの専門レビュアーがそれぞれ diff 全体を読み、1 種類の欠陥だけを探します。

- 言っていることとやっていることが違うコード（名前、計測、結果）
- 人に届くテキスト（メッセージ、コメント、翻訳）とコードの食い違い
- 不正な状態、壊れた不変条件、競合状態
- 境界、インデックス、順序についての前提
- シークレットと認証情報：比較、正規化、フォールバック値
- 変更された契約に呼び出し側が追従していない
- カバーしている振る舞いが壊れても通ってしまうテスト
- レスポンス、ログ、エラーメッセージへのデータ漏えい
- 互いに食い違う 2 つの変更ファイル

専門レビュアーの指摘はすべて、投稿される前にメインレビューの指摘と同じ検証を通り、その後いつもどおりの重複排除と重大度の判定を経ます。そのため、根拠のない推測は他の指摘と同様に取り除かれます。

### デフォルトで Heavy に、または 1 回のレビューだけ

**Code review → Routing** で、リポジトリのレビューの実行方法を選びます。**Balanced**（デフォルト。メインレビューのみ）または **Heavy** です。[リスク評価](/ja/how_to_use/code_review/configs/risk) がオンの場合は、リスクの結果によってプルリクエストのレビューのモードが決まります。この設定は、自動レビュー、`@kody review`、`kodus review` に適用されます。`kodus review` は、リスクの結果ではなく、設定のみからモードを取得します。コマンドにフラグを付けると、そのレビューに限り設定を上書きします。

```text
@kody review --heavy
@kody review --heavy focus on the payment reconciliation logic
@kody review --balanced
kodus review --heavy
kodus review --balanced
```

`--heavy` は Balanced に設定されたリポジトリで heavy レビューを実行し、`--balanced` は Heavy に設定されたリポジトリで balanced レビューを実行します。1 つのコマンドに両方を付けた場合は `--heavy` が優先されます。

どちらのフラグも、コマンドラインのどこに置いても構いません（フォーカステキストの前でも後でも）。いずれの場合もディレクティブからは取り除かれるため、`@kody review focus on the retry logic --heavy` は "the retry logic" にフォーカスします。

フラグは任意の順序で組み合わせられます。`@kody review --heavy --force` は強制の heavy レビューを実行します。Kody がすでにレビューしたプルリクエストで、前回のレビューと異なるモードを指定すると、それ以降のコミットだけでなく、プルリクエスト全体をレビューします。

ダッシュは必須です。ダッシュなしの `heavy` や `balanced` はディレクティブのテキストとして読まれるため、`@kody review heavy checkout path` はフラグを有効にせず、"heavy checkout path" にフォーカスします。

### 期待できること

- Heavy を含まないプランではレビューが Balanced で実行され、Kody が切り替えを知らせます。
- **カテゴリ設定はそのまま適用されます。** オフにしたカテゴリの専門レビュアーは実行されません（7 つが Bug、2 つが Security）。Kody Rules とカスタムエージェントは通常どおり実行されます。
- **Heavy のモデルで実行されます。** Global スコープの **Code review → Routing** には、**Heavy model** と **Balanced model** があります。Heavy のモデルが未設定の場合、heavy レビューは組織のデフォルトモデルを使います。リポジトリまたはディレクトリの **Code review model override** は、両方のモードで使われます。
- **コストも時間も増えます。** 30 件のプルリクエストでの評価では、同じモデルの Balanced と比べて、heavy レビューはプルリクエストあたり最大で約 2 倍の時間と、約 2.5 倍のモデルコストがかかりました。実際の問題はプルリクエスト 2 件につき約 1 件多く見つかり、実際の問題ではないコメントはプルリクエストあたり約 1 件多く投稿されました。自分のモデルキー（BYOK）の場合、追加のコストはプロバイダーの請求に含まれ、同時実行数の上限が低いプロバイダーでは呼び出しが待たされることがあります。
- **リポジトリにアクセスできない場合**（サンドボックスなし）、専門レビュアーは、その場合のメインレビューと同様に diff だけを読みます。
- レビューモードのバッジとタイムラインの **Specialist Agents** については、[プルリクエスト一覧](/ja/how_to_use/reviews/pull_requests)を参照してください。

<Tip>
  見落としのコストが高いリポジトリ（決済サービス、認証モジュールなど）では Heavy をレビューモードに設定するか、リスクの高い単発の変更で `--heavy` を指定してください。
</Tip>

## 良いディレクティブの書き方

- **判定ではなく領域を具体的に。**「バグを見つけて」より「キューコンシューマの並行処理に集中して」の方が有効です。
- **結果ではなくコードを名指しする。** モジュール、フロー、関心事を指し示します（「リトライロジック」「レポートサービスの SQL」）。
- **短く。** ディレクティブは **最大 500 文字** で、コメントの最初の 1 行のみが読まれます。

<AccordionGroup>
  <Accordion title="良い例">
    - `@kody review focus on the authentication and token-refresh flow`
    - `@kody review focus on the new Stripe webhook handling`
    - `kodus review --focus "race conditions in the background worker"`
  </Accordion>
  <Accordion title="弱い例">
    - `@kody review please be thorough` — 優先すべき領域がありません。
    - `@kody review only comment on file X` — ディレクティブはフィルターではありません。ファイルを絞るには、代わりに [Ignored files](/ja/how_to_use/code_review/configs/general) を使ってください。
  </Accordion>
</AccordionGroup>

## 注意点と制限

- **長さ：** ディレクティブは 500 文字で切り詰められます。
- **最初の 1 行のみ：** PR コメントでは、コマンド後の最初の 1 行だけがディレクティブになります。
- **設計上、信頼しない：** PR にコメントできる人なら誰でもディレクティブを渡せるため、使用前にテキストはサニタイズされます（制御文字と山括弧を除去）。これはフォーカスを変えるものではなく、テキストが Kody の内部プロンプトを改ざんするのを防ぐだけです。
- **保存されない：** リポジトリや組織の設定には何も書き込まれません。
