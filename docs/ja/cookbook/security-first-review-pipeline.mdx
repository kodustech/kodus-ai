## セキュリティに特化したパイプラインが必要な理由

一般的なコードレビューは、スタイルやバグを検出します。しかし、SQL インジェクション、ハードコードされたシークレット、安全でない認証パターンといったセキュリティ脆弱性には、指摘を重大なブロッカーとして扱う専用のルールが必要です。

このクックブックでは、既存のレビューの上にセキュリティファーストのレイヤーを設定します。

## ステップ1 — セキュリティ分析を有効にする

**Code review → What to review** で **Security** カテゴリがオンになっていることを確認します。または `kodus-config.yml` で設定します（リポジトリで **Prefer kodus-config.yml settings** がオンの場合にのみ読み込まれます）。

```yaml
reviewOptions:
  security: true
```

これで Kodus の組み込みセキュリティチェックが有効になります。以下のルールは、その上にチーム固有のセキュリティポリシーを追加します。

## ステップ2 — OWASP に焦点を当てたルールを作成する

各ルールは **Code review → Kody Rules** で作成します。**Review Rules** タブで **New rule** をクリックし、以下のとおりにフィールドを入力します。

### SQL インジェクションの防止

```
Rule name: No raw SQL queries
Execution mode: Per file
Path: **/*.ts, **/*.js, **/*.py
Severity: Critical
Instructions:
  Flag any use of string concatenation or template literals
  to build SQL queries. Look for patterns like:
  - `query("SELECT ... " + variable)`
  - `query(\`SELECT ... ${variable}\`)`
  - `execute(f"SELECT ... {variable}")`
  Must use parameterized queries or an ORM instead.
```

### ハードコードされたシークレットの検出

```
Rule name: No hardcoded secrets or credentials
Execution mode: Per file
Path: **/*
Severity: Critical
Instructions:
  Flag any string that looks like an API key, password,
  token, or secret in fileDiff. Patterns to catch:
  - Variables named *_KEY, *_SECRET, *_TOKEN, *_PASSWORD
    assigned to string literals
  - Strings matching patterns like "sk_live_", "ghp_",
    "AKIA", "Bearer " followed by a long string
  - Connection strings with embedded passwords
  Secrets must come from environment variables or a vault.
```

### 認証のバイパス

```
Rule name: Auth middleware must not be skipped
Execution mode: Per PR
Severity: Critical
Instructions:
  Check pr_files_diff for any route or controller that
  handles user data without auth middleware. Look for:
  - New routes without @UseGuards, @Authenticated,
    or equivalent decorators
  - Middleware bypass patterns like skipAuth: true
  - Public endpoints that access user-specific data
  Reference @file:src/shared/auth/guards/auth.guard.ts for the
  approved auth patterns.
```

### XSS の防止

```
Rule name: No dangerouslySetInnerHTML without sanitization
Execution mode: Per file
Path: **/*.tsx, **/*.jsx
Severity: Critical
Instructions:
  Flag any use of dangerouslySetInnerHTML in fileDiff.
  If used, verify the input is sanitized with DOMPurify
  or an equivalent library. Unsanitized HTML injection
  is a critical XSS vulnerability.
```

## ステップ3 — セキュリティの Memories を教える

あらゆる場所に適用される、永続的な規約を作成します。

```
@kody remember: all user input must be validated and sanitized
before use. Never trust client-side data.
```

```
@kody remember: all API endpoints that handle sensitive data
must use HTTPS only and include rate limiting.
```

```
@kody remember: error messages must never expose stack traces,
internal paths, or database details to the client.
```

## ステップ4 — ゼロトレランスのために設定する

セキュリティルールでは、重大な指摘がブロックし、決してフィルターで除外されないようにしたいはずです。

1. **Code review → General → Review feedback** で **Request changes on critical issues** をオンにします（接続しているプロバイダーがすべて GitLab の場合は利用できません）。Kody は Critical のインラインコメントを投稿すると、レビューを Request Changes に設定します
2. セキュリティルールを **Critical** 重要度に設定します
3. **Code review → What to review** で、**Apply the threshold to Kody Rules** はデフォルトのオフのままにします。そうすると、**Minimum severity to post** の値にかかわらず、ルールはどの重要度でも投稿されます

Request changes はインラインコメントに連動するため、**Per file** ルールによって設定されます。認証ミドルウェアのルールのような **Per PR** ルールは、プルリクエストコメントを 1 件投稿するだけで、これを設定しません。

## チェックリスト

- [ ] **Security** カテゴリがオンになっている
- [ ] SQL インジェクションのルールが、DB とやり取りするすべてのコードをカバーしている
- [ ] シークレット検出のルールが、すべてのファイルタイプをカバーしている
- [ ] 認証バイパスのルールが、実際の認証パターンを参照している
- [ ] XSS のルールが、すべてのフロントエンドコンポーネントファイルをカバーしている
- [ ] セキュリティの Memories が、一般的なセキュアコーディングの原則を教えている
- [ ] **Request changes on critical issues** がオンで、**Apply the threshold to Kody Rules** がオフになっている
- [ ] テスト PR でルールが正しく動作することを確認した

ルールの設定の詳細は [Kody Rules](/ja/how_to_use/code_review/configs/kody_rules) を参照してください。
