## このガイドが重要な理由

どのエンジニアリングチームにも、どこかに「ベストプラクティス」の文書があります。問題は、IDE の提案はそれを読まず、レビュアーは細かな点を忘れ、文書の権威が少しずつ失われていくことです。このガイドでは、ハンドブックを能動的なガードレールに変えます。Kody がすべてのプルリクエストでそれらのルールを徹底し、ずれが生じた節を指し示します。

2 つの構成要素を使います。

- [Kody Rules](/ja/how_to_use/code_review/configs/kody_rules) – 方針の各項目が、ハンドブックを参照するファイルレベルまたは PR レベルのチェックになります。
- [カスタムエージェント](/ja/how_to_use/code_review/custom_agents) – ハンドブックを doc としてリンクし、すべての指摘が適用するルールを引用します。

## 事前チェックリスト

- **Code review → Kody Rules** を編集する権限がある。
- ハンドブックがリポジトリ内にある（例：`docs/engineering-standards.md`）。別のパスにある場合は適宜読み替えてください。
- どのトピックをファイルレベル（コントローラー、設定）で評価し、どれを PR レベル（フィーチャーフラグ、ロールアウトの説明、アーキテクチャ）で評価するかがわかっている。

<Callout icon="layers">
  ハンドブックはバージョン管理下に置いてください。ルールとエージェントはプルリクエストのターゲットブランチからハンドブックを読むため、すべての編集は、オーナーが承認するプルリクエストを経由します。
</Callout>

## フェーズ1 – ルールにしやすいポリシーパックを整える

1. `docs/engineering-standards.md` のような markdown ファイルを作成するか、既存のものを再利用します。
2. 内容を、短くチェック可能な箇条書きに整理します。

```md
# Engineering Standards

## Error handling
- Never swallow errors.
- Do not log PII or secrets.
- External requests must have a timeout and retry policy.

## Architecture
- No direct cross-module imports from `domain/*` into `web/*`.
- New endpoints must include tracing fields (e.g., requestId) and structured logs.
- Feature flags are mandatory for risky changes.
```

<Tip>
  各項目は原子的にしてください。ルールが発火したとき、何を直すべきかについて議論の余地がないようにします。
</Tip>

## フェーズ2 – すべてのルールを実際の文書に向ける

各 instructions にスニペットを貼り付けるのではなく、実際のハンドブックを参照します。

```text
Use @file:docs/engineering-standards.md (Architecture section) as the policy source.
Only flag code that clearly violates those bullets. If the section is missing, say so.
```

- ドメイン固有のポリシーパックには、別のファイルパスに差し替えます（例：`@file:docs/mobile.md`）。
- ファイルの一部だけが必要ですか？ `@file:docs/engineering-standards.md#L40-L72` のように行アンカーを付けると、ルールはその節だけを読み込みます。

<Callout icon="link">
  参照を 1 つにしておけば、すべてが同期されます。ハンドブックを 1 回更新するだけで、すべてのルールが最新版を適用します。
</Callout>

## フェーズ3 – 各節を Kody Rules に変換する

サイドバーで **Code review → Kody Rules** を開きます。**Review Rules** タブで **New rule** をクリックし、ポリシーの各節を適切な実行モードとパスに対応付けます。

| ポリシーの節         | 実行モード | パスの例                       | 重要度 |
| ---------------------- | -------------- | ---------------------------------- | -------- |
| Error handling         | Per file       | `backend/**/*.ts`                  | High     |
| Architecture           | Per PR         | 該当なし                     | Critical |
| Logging & tracing      | Per file       | `web/apps/**/controllers/**/*.ts`  | Medium   |
| Security / PII         | Per file       | `**/*`                             | Critical |

### ファイルレベルの例

```
Rule name: Enforce tracing fields on new endpoints
Execution mode: Per file
Path: web/apps/**/controllers/**/*.ts
Severity: High
Instructions:
  Compare fileDiff with Architecture → New endpoints in @file:docs/engineering-standards.md.
  Flag handlers that lack requestId tracing AND structured log statements.
  Quote the diff chunk that violates the policy.
```

### PR レベルの例

```
Rule name: Require feature flags for risky changes
Execution mode: Per PR
Severity: Critical
Instructions:
  Scan pr_files_diff for routes/services/domain files that add major functionality.
  If no feature flag file is touched, cite “Architecture → Feature flags are mandatory” and request the rollout plan.
```

<Info>
  ルールは変数（ファイルごとの `fileDiff`、PR ごとの `pr_files_diff` とその他の `pr_*` 変数）とファイル参照を理解します。一覧は [Kody Rules ガイド](/ja/how_to_use/code_review/configs/kody_rules) を参照してください。
</Info>

## フェーズ4 – または、ハンドブックをカスタムエージェントに渡す

カスタムエージェントは、リンクされた doc としてハンドブックを読み、すべての指摘の根拠となるルールを引用する必要があります。ターゲットブランチの doc にない引用は破棄されます。カスタムエージェントはベータ版で、Teams プランと Enterprise プラン、およびトライアル期間中に利用できます。セルフホストの Kodus では `BETA_FEATURES=true` も必要です。

<Steps>
  <Step title="エージェントを作成する">
    **Code review → What to review → Custom agents** で **New agent → Templates → Blank** をクリックします。名前を **Engineering standards** にします。
  </Step>
  <Step title="ハンドブックをリンクする">
    **Files & knowledge → Skills & docs** で **Add skill or doc → Add by path** をクリックし、`docs/engineering-standards.md` を入力します。doc はレビューのたびに全体が読み込まれるため、短く保ってください。長いハンドブックは、参照ファイルを持つスキルにするほうが適しています。
  </Step>
  <Step title="instructions を書く">
    ```text
    Flag changes that break a rule in docs/engineering-standards.md.
    Quote the rule you apply. Ignore tests and generated code.
    ```
  </Step>
  <Step title="試してから、オンにする">
    ルールに違反するプルリクエストで **Try it** を実行します。各コメントは、引用された箇条書きとともに、ルールを **Rule** (`docs/engineering-standards.md`) として引用します。
  </Step>
</Steps>

予算と検出の詳細は [Skills, docs and tools](/ja/how_to_use/code_review/custom_agents_knowledge_and_tools) を参照してください。

## フェーズ5 – テストし、観察し、維持する

<AccordionGroup>
  <Accordion title="検証用の PR を用意する">
    各節に違反する使い捨ての PR を作成し、Kody にレビューさせます（開始されていなければ `@kody start-review` とコメントします）。インラインコメントと PR レベルのコメントが正しい箇条書きを引用していることを確認します。エージェントは `@kody -v engineering-standards` でオンデマンドに実行できます。
  </Accordion>
  <Accordion title="ノイズと重要度を調整する">
    ロールアウト中は、各ルールがどのくらいの頻度で発火するかを観察します。シグナルが期待に合うまで、ファイルの glob を絞り込み、除外を追加し、または重要度を調整します。
  </Accordion>
  <Accordion title="文書とルールを一緒に更新する">
    ハンドブックを変更するときは常に、同じ PR で markdown と関連するルールまたはエージェントの instructions を更新し、レビュアーがパイプライン全体を検証できるようにします。
  </Accordion>
</AccordionGroup>

## クイックチェックリスト

- [ ] `docs/engineering-standards.md` が、スキャンしやすい箇条書きで存在する。
- [ ] すべてのルールが `@file` でポリシーパックを参照しており、最新のテキストを読む。
- [ ] ファイルレベルと PR レベルの Kody Rules が、重要な節をカバーしている。
- [ ] 任意：カスタムエージェントがハンドブックに従い、それを引用する。
- [ ] 広く展開する前に、ドライラン PR でインラインコメントと PR サマリーを確認した。
