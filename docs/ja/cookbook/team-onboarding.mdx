## 概要

新しいチームが Kodus を使い始めるまでには、約 30 分かかります。このガイドでは、最初の PR からチームが価値を得られるよう、セットアップの全体を順に説明します。

## ステップ1 — ワークスペースを作成して設定する

1. [kodus.io](https://kodus.io) でサインアップするか、セルフホストのインスタンスにアクセスします
2. チーム用の新しいワークスペースを作成します
3. Git プロバイダー（GitHub、GitLab、Bitbucket、Azure Repos、Forgejo）を接続します
4. 監視するリポジトリを選択します

セットアップガイドは、投稿する最小の重要度、コーディングエージェント instructions のスイッチ（ステップ3）、Kody の最初のレビュー用のプルリクエストへと続きます。

## ステップ2 — レビューのベースラインを設定する

Kodus は妥当なデフォルト設定で始まるため、異なる部分だけをカスタマイズします。ベースラインは、Web アプリの **Code review → What to review**（カテゴリと **Minimum severity to post**）で設定するか、各リポジトリのルートにあるデフォルトブランチの `kodus-config.yml` で管理できます。Kody がこのファイルを読み込むのは、リポジトリの **Code review → General** で **Prefer kodus-config.yml settings** をオンにした後だけです。

```yaml
# kodus-config.yml — these are the defaults
reviewOptions:
  bug: true
  security: true
  performance: true
  business_logic: true

suggestionControl:
  severityLevelFilter: medium
  applyFiltersToKodyRules: false

automatedReviewActive: true
```

これで、妥当な重要度のしきい値を持つ自動レビューが有効になります。1 週間後にフィードバックに基づいて調整してください。

## ステップ3 — コーディングエージェント向けにすでに書いた instructions を使う

チームがすでに Cursor、Copilot、Claude、または `AGENTS.md` の instructions を管理している場合：

1. サイドバーの **Code review** グループ上部にあるスコープピッカーで **Global** またはリポジトリを選び、**What to review** を開いて **Coding-agent instructions** をオンにします
2. Kody は、各プルリクエストの変更ファイルに該当する instruction ファイルを読み、それらに違反する変更を指摘します
3. すべてのレビューで徹底したい規約は、`.kody/rules` 内のルールファイルとして書きます

instruction ファイルが Kody Rules に変換されることはないため、レビューポリシーが気づかないうちに変わることはありません。

## ステップ4 — 上位 5 つの規約を教える

初日からすべてをエンコードしようとしないでください。チームが最もよく議論する 5 つの規約から始めます。

```
@kody remember: we use camelCase for variables and PascalCase for types.
```

```
@kody remember: all API responses use the standard envelope format
{ data, error, meta }.
```

```
@kody remember: we prefer composition over inheritance.
Use interfaces and dependency injection.
```

```
@kody remember: every public function must have JSDoc with
@param and @returns descriptions.
```

```
@kody remember: database queries go through the repository layer only.
No direct DB access from services or controllers.
```

これらは、Kody が以降のレビューで使う Memories になります。**Kody knowledge approval** がオンの場合、それぞれが誰かに承認されるまで **Pending review** で待機します。

## ステップ5 — 2〜3 個の重要なルールを作成する

決して起きてはならないことのルールを追加します。**Code review → Kody Rules** の **Review Rules** タブで **New rule** をクリックします。

```
Rule name: No console.log in production code
Execution mode: Per file
Path: src/**/*.ts
Severity: High
Instructions: Flag any console.log, console.warn, or console.error
in fileDiff. Use the project logger instead.
Exclude test files (*.spec.ts, *.test.ts).
```

```
Rule name: No hardcoded API URLs
Execution mode: Per file
Path: src/**/*.ts
Severity: Critical
Instructions: Flag any hardcoded URL (http:// or https://)
in fileDiff that looks like an API endpoint.
URLs must come from environment variables or config files.
```

## ステップ6 — タスク管理を接続する（任意ですが推奨）

**Plugins**（サイドバー内）で Atlassian Rovo（Jira）、Linear、Notion、または Git Issues を接続し、[ビジネスロジック検証](/ja/how_to_use/code_review/business_logic_validation)を有効にします。これにより、Kodus は PR がタスクの記述どおりに実装しているかを確認できます。

## ステップ7 — パイロット PR を実行する

テスト PR を開いて、次を確認します。

- [ ] PR に Kodus のコメントが表示される
- [ ] 提案が的確で、重要度が適切である
- [ ] カスタムルールが、発火すべきときに発火する
- [ ] Memories がレビューのコンテキストに反映されている

## ステップ8 — 1 週間後にフィードバックを集める

1 週間レビューを行ったら、チームに確認します。

- 提案が多すぎますか？ → **Code review → What to review** で **Minimum severity to post** を上げます（`kodus-config.yml` では `severityLevelFilter`）
- ルールがノイズになりすぎていますか？ → ファイルパスを絞り込むか、除外を追加します
- 重要なパターンが抜けていますか？ → 新しいルールまたは Memories を追加します
- 自動生成されるルールが欲しいですか？ → スコープピッカーでリポジトリを選び、**Code review → Kody Rules** を開いて **Configuration** をクリックし、**Generate from past reviews** をオンにすると、Kody がレビュアーのコメントからルールの下書きを作成します。クラウドのトライアル外では、これには [BYOK](/ja/how_to_use/byok) が必要です

## ヒント

- 初日からルールを詰め込みすぎないでください。小さく始めて、育てていきます
- ルールとして形式化する前に、会話を通じてチームに自然に Kody を教えてもらいます
- 最初の数件の PR では `@kody start-review` を使い、チームが Kodus の動作を確認できるようにします
- Kody が学習した内容を確認したい場合は、**Kody knowledge approval**（**Code review → Kody Rules → Configuration**）をオンにします

セットアップの完全なガイドは [クイックスタート](/ja/how_to_use/quickstart) を参照してください。
