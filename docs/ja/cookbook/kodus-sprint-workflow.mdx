## 多くのスプリントワークフローにあるギャップ

チームは要件を Jira、Linear、Notion で管理し、開発者はそれを PR で実装します。しかし、PR が受け入れ基準をすべて満たしているかを体系的に確認する人はおらず、QA がステージングでギャップを見つけて初めて気づきます。

このクックブックでは、[ビジネスロジック検証](/ja/how_to_use/code_review/business_logic_validation)でこのループを閉じます。Kody が各 PR を、それが参照するタスクに照らして確認します。

## ワークフロー

```
Task created (Jira, Linear, Notion)
    ↓
Developer implements → Opens PR that references the task
    ↓
Kodus, on the PR's first review:
  1. Finds the task in the PR title, branch or description
  2. Reads it from the connected tracker
  3. Lists every requirement and where it stands in the code
    ↓
Developer addresses the gaps → Re-checks with @kody -v business-logic
    ↓
Merge with confidence
```

## ステップ1 — タスクトラッカーを接続する

サイドバーで **Plugins** を開き、使用しているツールを接続します。

- **Atlassian Rovo** — Jira 用
- **Linear**
- **Notion**
- **Git Issues** — リポジトリ自身のトラッカーにある issue 用

その他のトラッカーは[カスタムプラグイン](/ja/cookbook/custom-plugin-install)で利用できます。Kody はタスクを ID で読み取るだけで、トラッカーに書き込むことはありません。

## ステップ2 — Business Logic がオンになっていることを確認する

デフォルトでオンです。オン／オフは **Code review → What to review** の **Business Logic** 行、または `kodus-config.yml` で切り替えます（リポジトリで **Prefer kodus-config.yml settings** がオンの場合にのみ読み込まれます）。

```yaml
reviewOptions:
  business_logic: true
```

## ステップ3 — 良い受け入れ基準を書く

Kody がどこまで確認できるかは、タスクの内容によって決まります。

| タスク | Kody の動作 |
|------|----------------|
| 受け入れ基準：基準フィールド、チェックリスト、または説明内のリスト | 各要件を確認し、ファイルと行を引用する |
| 説明のみで、リストなし | 説明に書かれた動作を確認する |
| タイトルのみ | 確認しない。受け入れ基準を求めるコメントを投稿する |

**Jira/Linear タスクのテンプレート：**

```
## Description
Brief context about what needs to change and why.

## Acceptance Criteria
1. Users with role "admin" can delete any comment
2. Users can only edit their own comments within 24 hours
3. Deleted comments show "[removed]" placeholder
4. Audit log records who deleted what and when
5. API returns 403 for unauthorized delete attempts
```

基準が見出しの下やカスタムフィールドにある場合は、Business Logic の設定で **Where acceptance criteria live** を設定します。

## ステップ4 — PR にタスクを明記させる

Kody は、PR のタイトル、ブランチ名、説明の順にタスクを探します。`KC-1292`、`#123`、`AB#123` のようなキー、またはタスクへのリンクが対象です。「Closes KC-1292」はタスク全体に対して PR を確認します。「Part of KC-1292」は一部分を確認し、不足しているものをブロッカー扱いせずに一覧にします。

必須にするには、**Code review → What to review → Business Logic** を開き、**Ask for a task when the PR references none** をオンにします。すると Kody は、その PR がどのタスクのものかを尋ねるコメントを投稿します。Dependabot などのボット PR は対象外です。

## ステップ5 — PR の変更に合わせて再確認する

Kody は PR の最初のレビューで確認します。その後は、次のようにコメントします。

```
@kody -v business-logic
```

Kody は新しいコメントを投稿せず、自分の 1 件のコメントを編集します。特定のタスクに対して確認するには、そのリンクまたは ID を追加します：`@kody -v business-logic https://kodustech.atlassian.net/browse/KC-1292`

依頼せずに再確認させるには、**Re-check after a push** を **While something is missing** に設定します。プッシュのたびに、すべての要件が満たされるまで再確認します。

## ステップ6 — チームの規約を教える

Business Logic の設定にある **Team guidance** には、Kody が判断するときに従うメモを記述します。

```
Requirements the ticket marks as out of scope are not missing.
Feature flags count as implemented when the flag exists and defaults to off.
```

PR の作成者ではなくレビュアーが、Kody のコメントに Kody をメンションして返信することで、ギャップを承認することもできます。たとえば「@kody Out of scope, moved to SAA-102」のようにします。Kody はそのタスクが存在することを確認し、要件を承認済みとしてマークします。承認できる人については [コメントへの返信](/ja/how_to_use/code_review/business_logic_validation#コメントへの返信) を参照してください。

## 結果

セットアップ後は、スプリント内のすべての PR に次の 2 つが付きます。

1. **コード品質レビュー** — セキュリティ、パフォーマンス、スタイル（標準の Kodus）
2. **ビジネスロジック検証** — 各要件を、満たしている・一部・不足・手動で確認、のいずれかで表示し、タスクが求めていない変更も示します

QA が見つけるギャップが減り、スプリントデモはより順調に進み、「それは終わっていると思っていた」ということはまれになります。

## ヒント

- チームに番号付きの受け入れ基準を書くよう促します。最も良い検証が得られます
- `@kody -v business-logic` は、レビュー時だけでなく開発中にも実行します
- 段階的に提供する場合は、PR の説明に「Part of KC-1292」と書いて、Kody が残りをブロッカーとして扱わないようにします

詳細は [ビジネスロジック検証](/ja/how_to_use/code_review/business_logic_validation) を参照してください。
