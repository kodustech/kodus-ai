## 課題

モノレポでは、パッケージごとに基準が異なります。React のフロントエンドはコンポーネントのパターンを重視し、NestJS のバックエンドは依存性注入を重視し、共有ライブラリは API の安定性を重視します。画一的なレビューでは機能しません。

## 戦略の概要

Kodus は、モノレポに自然に対応する 3 つの設定レベルをサポートしています。

| レベル | 適用対象 | 例 |
|-------|-----------|---------|
| **Global** | すべてのリポジトリ | 「`.env` ファイルをコミットしない」 |
| **Repository** | そのモノレポ | 「Conventional Commits を使う」 |
| **Directory** | 特定のパッケージ | 「React コンポーネントは PascalCase を使う」 |

## ステップ1 — パッケージをマッピングする

モノレポ内の個別の領域と、それぞれのレビューのニーズを洗い出します。

```
monorepo/
├── apps/
│   ├── web/          → React rules, component patterns
│   ├── api/          → NestJS rules, architecture boundaries
│   └── mobile/       → React Native rules
├── libs/
│   ├── shared/       → API stability, breaking change detection
│   └── ui/           → Design system compliance
└── infra/            → Terraform/IaC rules
```

## ステップ2 — ディレクトリスコープを作成する

**Code review** グループの上部にあるスコープピッカーでモノレポを選び、もう一度ピッカーを開いて **Add directory scope** を選びます。**Select directories** で、レビュー設定を共有する 1 つ以上のパッケージフォルダーを選び、**Add directory scope** をクリックします。各ディレクトリスコープは、ピッカー内でリポジトリの下にインデントされて表示されます。それを選ぶと設定できます。

各ディレクトリスコープには、それぞれ次の設定を持たせられます。
- **Kody Rules**（ファイルレベルと PR レベル）
- **What to review**（有効にするカテゴリと、投稿する最小の重要度）
- **Custom agents**（リポジトリのものに追加されます）
- **Ignored files**（**General** 内）

プルリクエストは、設定済みのあるディレクトリに触れ、ほかの設定済みディレクトリには触れない場合に、そのディレクトリの設定を使います。プルリクエストが設定をどう選ぶかは [ディレクトリレベルの設定](/ja/how_to_use/code_review/configs/directory_level) を参照してください。

## ステップ3 — 的を絞ったルールを書く

**Code review → Kody Rules** の **Review Rules** タブで **New rule** をクリックします。ディレクトリスコープで作成したルールには **Path** がなく、そのディレクトリスコープの設定でレビューされるプルリクエストのすべてのファイルに適用されます。2 つ以上のディレクトリスコープに触れる、またはどれにも触れないプルリクエストは、リポジトリの設定でレビューされ、**すべての**ディレクトリスコープのルールがそのすべてのファイルに適用されます。そのような場合でも成り立つように、たとえば instructions にフォルダー名を明記して、ディレクトリのルールを書いてください。[ルール継承](/ja/how_to_use/code_review/configs/rules_inheritance) を参照してください。パッケージの一部を対象にするには、リポジトリスコープで **Path** の glob を指定してルールを作成します。

### フロントエンドのルール（スコープ：モノレポ、パスあり）

```
Rule name: React components must use design system tokens
Execution mode: Per file
Path: apps/web/src/components/**/*.tsx
Severity: High
Instructions:
  Check fileDiff for hardcoded colors, spacing, or font sizes.
  Components must import tokens from @file:libs/ui/src/tokens.ts.
  Flag any hex color, pixel value, or font-size not from the token file.
```

### バックエンドのルール（スコープ：`apps/api/` ディレクトリ）

```
Rule name: Domain layer must not import from infrastructure
Execution mode: Per file
Severity: Critical
Instructions:
  In files under apps/api/src/domain, check fileDiff for any import from
  "../infrastructure", "../../infrastructure", or any path containing
  "/infrastructure/". Domain modules must only depend on other
  domain modules and shared interfaces.
```

### 共有ライブラリのルール（スコープ：`libs/shared/` ディレクトリ）

```
Rule name: Public API changes require changeset
Execution mode: Per PR
Severity: High
Instructions:
  If pr_files_diff modifies any file in libs/shared/src/index.ts
  or adds/removes exports, check that a changeset file exists
  in the .changeset/ directory. If missing, flag it as a
  potential breaking change without documentation.
```

## ステップ4 — 横断的な規約には Memories を使う

規約によっては、あらゆる場所に適用されます。それらは Memories として教えます。

```
@kody remember: in this monorepo, all packages use ESM imports.
CommonJS require() is not allowed anywhere.
```

```
@kody remember: shared libs must maintain backward compatibility.
Any breaking change requires a major version bump and a changeset.
```

## ステップ5 — ディレクトリごとに重要度のしきい値を設定する

トラフィックの多いパッケージには、より厳しいフィルターが必要な場合があります。スコープピッカーでディレクトリを選び、**What to review** を開いて **Minimum severity to post** を設定します。

- **apps/web/** — **Medium**（フロントエンドは動きが速い）
- **libs/shared/** — **Low/All**（安定性が重要）
- **infra/** — **High**（件数は少なく、重要なものだけ）

しきい値が Kody Rules に適用されるのは、**Apply the threshold to Kody Rules** がオンの場合だけです。

## ステップ6 — 生成されたパスを無視する

ノイズを避けるため、モノレポ固有の除外を追加します。**Code review → General → Review scope** の **Ignored files** で **Edit** をクリックするか、`kodus-config.yml` で設定します（リポジトリで **Prefer kodus-config.yml settings** がオンの場合にのみ読み込まれます）。

```yaml
ignorePaths:
  - "**/node_modules/**"
  - "**/dist/**"
  - "**/build/**"
  - "**/*.generated.ts"
  - "**/prisma/migrations/**"
  - "**/coverage/**"
```

## ヒント

- ディレクトリごとに 2〜3 個のルールから始め、チームが実際にレビューで指摘する内容に基づいて広げていきます
- ルール継承を使います。組織レベルのルールでセキュリティを、リポジトリレベルで規約を、ディレクトリレベルでアーキテクチャをカバーします
- あるパッケージでルールが頻繁に発火しすぎるのに、ほかの場所では妥当な場合は、その **Path** を絞り込むか、ルールを書き直します。**Override and disable for this scope** は、継承されたルールを一覧で無効としてマークするだけで、レビューではそのルールが引き続き適用されます

ディレクトリスコープの詳細は [ディレクトリレベルの設定](/ja/how_to_use/code_review/configs/directory_level) を、ルール継承については [ルール継承](/ja/how_to_use/code_review/configs/rules_inheritance) を参照してください。
