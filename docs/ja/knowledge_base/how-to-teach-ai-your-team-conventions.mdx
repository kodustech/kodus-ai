どのチームにも、明文化されていない文脈があります。技術の好み、命名規則、アーキテクチャ上の決定、移行の詳細などです。それらを最初にすべて文書化する代わりに、自然な会話を通じて Kody に教えることで、今後のレビューがより的確になり、繰り返される的外れな提案もなくなります。

## 仕組み

PR コメントで Kody に何かを覚えるよう頼むと、Kody はそれを**メモリ**として保存します。コードベースの文脈やチームの好みを述べただけの場合、Kody は保存を提案し、あなたが了承すると保存します。メモリは、その後のコードレビューや会話で高優先度のコンテキストとして使われます。

### 明示的に教える

Kody に直接、何かを覚えるよう伝えます。

```
@kody remember: this repo mirrors a third-party API, so some payload fields intentionally stay snake_case.
```

```
@kody please remember: this service follows hexagonal architecture and keeps adapters at the edge.
```

### 規約を述べる

規約を述べるか、提案が当てはまらない理由を説明すると、Kody はそれをメモリとして保存することを提案します。`@kody yes` と返信すると保存されます。例：

```
@kody this repo mirrors a third-party API, so some payload fields intentionally stay snake_case.
```

```
@kody in this service, tests usually live next to the implementation files rather than in a central test folder.
```

```
@kody the billing module is mid-migration, so prefer incremental fixes over broad refactors.
```

## Kody が保存しないもの

Kody は、何をメモリにするかを選別します。

- 一時的な指示（「今すぐ直して」「今日はこれをスキップして」）
- 質問（「期限はいつ？」）
- デバッグ中のやり取り（「エラーが出ています」）
- 実行可能な情報を含まない曖昧な発言
- 1 つの PR やタスクに限定されたリクエスト

## メモリのスコープ

各メモリは特定のレベルで適用されます。

| スコープ | 例 |
|-------|---------|
| **Directory** | 「`src/components/ui` では、必ずデザインシステムのトークンを使用する」 |
| **Repository** | 「このリポジトリはヘキサゴナルアーキテクチャを採用している」 |
| **Organization** | 「すべてのリポジトリで ESLint の flat config を使用する」 |

## 承認ワークフロー

Kody が作成したメモリを有効になる前にレビューしたい場合は、**Code review → Kody Rules** を開き、**Configuration** をクリックして、**Kody knowledge approval** をオンにします。新しいメモリ（と Kody が生成したルール）は、**Approve** または **Discard** するまで **Pending review** セクションで待機します。**New memory** で自分で書いたメモリはすぐに有効になります。

## メモリの管理

**Code review → Kody Rules** → **Memories** タブで、メモリの表示、編集、削除ができます。**New memory** で手動でメモリを作成することもできます。

詳細については、[Kody Rules — メモリ](/ja/how_to_use/code_review/configs/kody_rules#memories)を参照してください。
