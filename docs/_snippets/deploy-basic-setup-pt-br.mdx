## Requisitos do Sistema

<AccordionGroup>
  <Accordion title="Hardware Recomendado">
    Dimensionado para o modo de sandbox `local` padrão (kodus-graph + contexto
    cross-file rodam dentro do container worker).

    - **CPU**: 2+ núcleos (4+ recomendado para repos acima de ~100k LOC)
    - **RAM**: 8GB+ (16GB recomendado ao rodar o sandbox `local` em repos grandes)
    - **Armazenamento**: 60GB+ de espaço livre (o Postgres guarda o cache do AST graph;
      cresce com a quantidade de repos e o volume de PRs)
  </Accordion>
  <Accordion title="Software Necessário">
    - **Docker** (última versão estável) com o plugin Compose
    - **Nome de domínio ou IP fixo** se você quer receber webhooks de
      provedores Git na nuvem (GitHub.com, GitLab.com, etc.)
  </Accordion>
  <Accordion title="Portas Necessárias">
    Publicadas no host pelo arquivo Compose do instalador.

    - **3000** — Kodus Web App (`WEB_PORT`)
    - **3001** — API
    - **3332** — Webhooks (`API_WEBHOOKS_PORT`)
    - **3101** — MCP Manager (`API_MCP_MANAGER_PORT`), _só se `API_MCP_SERVER_ENABLED=true`_
    - **15692** — métricas Prometheus do RabbitMQ

    PostgreSQL (5432), MongoDB (27017) e RabbitMQ (5672 AMQP, 15672 painel de
    gerenciamento) são publicados em portas aleatórias do host. Os containers
    chegam neles pelas redes do Docker; rode `docker compose port <service> <port>`
    para descobrir a porta no host.
  </Accordion>
  <Accordion title="Serviços">
    O que `./scripts/install.sh` sobe, com base no seu `.env`.

    **Core (sempre ligados):**
    - `api` — backend principal
    - `worker` — jobs de code review
    - `webhooks` — receptor de webhooks dos provedores Git
    - `kodus-web` — frontend Next.js
    - `db_kodus_postgres`, `db_kodus_mongodb`, `rabbitmq` —
      infraestrutura local. Defina `USE_LOCAL_DB=false` /
      `USE_LOCAL_RABBITMQ=false` para apontar para instâncias gerenciadas. Os
      containers continuam subindo como dependências, mas o Kodus não os usa.

    **Opcionais:**
    - `kodus-mcp-manager` — broker do Model Context Protocol. Habilite
      com `API_MCP_SERVER_ENABLED=true`. Veja [MCP Manager](/pt-BR/how_to_deploy/deploy_kodus/mcp_manager).
    - `worker-analytics` — ingestão do Cockpit (métricas DORA, classificador
      de PRs). **Exclusivo do self-hosted Enterprise.** Fica atrás do profile
      `analytics` do Compose, então o instalador não o inicia.
      Veja [Analytics Worker](/pt-BR/how_to_deploy/deploy_kodus/analytics_worker).
  </Accordion>
</AccordionGroup>

<Note>
  O code review usa um AST graph + contexto cross-file que roda em um
  sandbox — `local` (padrão, roda dentro do worker) ou `e2b` (sandbox remoto
  pago). Veja [Sandbox & AST Graph](/pt-BR/how_to_deploy/deploy_kodus/sandbox)
  para entender os modos, o comportamento de cache e quando escolher cada um.
</Note>

<Note>
  Na instalação, as imagens precisam estar disponíveis nos registries ou mirrors, ou já carregadas no host. Em uma implantação interna, use serviços Git e endpoints de modelos acessíveis na sua rede. Serviços externos opcionais precisam de acesso aos próprios endpoints.
</Note>

## Configuração de Domínio (Opcional)

O provedor Git precisa alcançar a URL do webhook via HTTPS. O instalador exige pelo menos uma URL HTTPS de webhook, inclusive quando Kodus e Git estão em rede privada. O app web precisa estar acessível aos usuários, inclusive quando o navegador voltar do login ou do provedor Git.

Recomendamos configurar dois subdomínios:
- Um para a aplicação web, ex.: `kodus-web.seudominio.com`.
- Um para a API, ex.: `kodus-api.seudominio.com`.

Os webhooks são tratados por um serviço separado (porta 3332). Você pode:
- Usar um subdomínio dedicado para webhooks, ex.: `kodus-webhooks.seudominio.com`, ou
- Continuar usando o domínio da API e rotear `/github/webhook`, `/gitlab/webhook`, etc. para o serviço de webhooks no seu proxy reverso.

Os dois subdomínios devem ter registros DNS A apontando para o endereço IP do seu servidor. O [proxy reverso](/pt-BR/how_to_deploy/deploy_kodus/reverse_proxy) roteia cada subdomínio para o serviço interno correto.


## Configuração

<Steps>
  <Step title="Clone o repositório do instalador">
    ```bash
    git clone https://github.com/kodustech/kodus-installer.git
    cd kodus-installer
    ```
  </Step>
  <Step title="Copie o arquivo de ambiente de exemplo">
    ```bash
    cp .env.example .env
    ```
  </Step>
  <Step title="Gere chaves seguras para as variáveis de ambiente obrigatórias">
    ```bash
    ./scripts/generate-secrets.sh
    ```

    <Warning>
      Rode uma única vez, antes da primeira instalação. Rodar de novo substitui todos os segredos do `.env`, incluindo as senhas dos bancos de dados e a `API_CRYPTO_KEY`, e os dados existentes deixam de funcionar.
    </Warning>
  </Step>
  <Step title="Edite o arquivo de ambiente">
    Edite o `.env` com seus valores usando seu editor de texto preferido. 
    ```bash
    nano .env
    ```

    Adicione `IMAGE_TAG=<version>` para fixar a release que você instala, por exemplo `IMAGE_TAG=2.2.11`. Sem isso, o instalador usa `latest`. As versões de release estão listadas na [página de releases do kodus-ai](https://github.com/kodustech/kodus-ai/releases) como _Self-Hosted Release_.

    Veja [Configuração das Variáveis de Ambiente](/pt-BR/how_to_deploy/deploy_kodus/generic_vm#configuração-das-variáveis-de-ambiente) para instruções detalhadas.
  </Step>

  <Step title="Execute o instalador">
    ```bash
    ./scripts/validate-env.sh
    ./scripts/install.sh
    ```

    O `validate-env.sh` confere o `.env` contra o schema. O `install.sh` se recusa a iniciar até que as variáveis obrigatórias estejam definidas e pelo menos uma URL de webhook de Git seja válida. O container `api` roda as migrations e os seeds do banco de dados quando inicia.
  </Step>
  <Step title="Verifique a instalação">
  Quando o instalador terminar, os serviços estão rodando. Confira com:
  ```bash
  ./scripts/doctor.sh
  ```

  A primeira linha diz se os reviews estão rodando. Cada problema listado depois dela mostra o que você perde e como corrigir. Adicione `--verbose` para ver todas as verificações.
  </Step>
  <Step title="Acesse a interface web">
    Quando você acessar a interface web pela primeira vez, vai precisar:

1. **Criar sua conta de administrador** - Será o primeiro usuário, com acesso total ao sistema
2. **Conectar um provedor de LLM** - O Kodus é bring-your-own-key, e nenhum review roda sem um modelo. Abra **AI providers** na barra lateral, ou defina o modelo no `.env` (veja [Configuração do Provedor de LLM](/pt-BR/how_to_deploy/deploy_kodus/generic_vm#configuração-do-provedor-de-llm))
3. **Configurar seu provedor Git** - Conecte GitHub, GitLab, Bitbucket, Azure DevOps ou Forgejo seguindo as instruções na tela
4. **Selecionar repositórios** para análise - Escolha quais repositórios de código o Kody vai revisar

<Info>
  Para etapas detalhadas do processo de configuração inicial, consulte nosso [Guia de Início Rápido](/pt-BR/how_to_use/quickstart).
</Info>
  </Step>
</Steps>
