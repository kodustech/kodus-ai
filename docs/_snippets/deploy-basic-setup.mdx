## System Requirements

<AccordionGroup>
  <Accordion title="Recommended Hardware">
    Sized for the default `local` sandbox mode (kodus-graph + cross-file
    context run inside the worker container).

    - **CPU**: 2+ cores (4+ recommended for repos above ~100k LOC)
    - **RAM**: 8GB+ (16GB recommended when running the `local` sandbox on large repos)
    - **Storage**: 60GB+ free space (Postgres holds the AST graph cache;
      grows with repo count and PR volume)
  </Accordion>
  <Accordion title="Required Software">
    - **Docker** (latest stable) with the Compose plugin
    - **Domain name or fixed IP** if you want to receive Git webhooks
      from cloud providers (GitHub.com, GitLab.com, etc.)
  </Accordion>
  <Accordion title="Required Ports">
    Published on the host by the installer's Compose file.

    - **3000** — Kodus Web App (`WEB_PORT`)
    - **3001** — API
    - **3332** — Webhooks (`API_WEBHOOKS_PORT`)
    - **3101** — MCP Manager (`API_MCP_MANAGER_PORT`), _only if `API_MCP_SERVER_ENABLED=true`_
    - **15692** — RabbitMQ Prometheus metrics

    PostgreSQL (5432), MongoDB (27017) and RabbitMQ (5672 AMQP, 15672
    management UI) are published on random host ports. Containers reach them
    over the Docker networks; run `docker compose port <service> <port>` to
    find the host port.
  </Accordion>
  <Accordion title="Services">
    What `./scripts/install.sh` brings up, based on your `.env`.

    **Core (always on):**
    - `api` — main backend
    - `worker` — code-review jobs
    - `webhooks` — Git provider webhook receiver
    - `kodus-web` — Next.js frontend
    - `db_kodus_postgres`, `db_kodus_mongodb`, `rabbitmq` — local
      infrastructure. Set `USE_LOCAL_DB=false` /
      `USE_LOCAL_RABBITMQ=false` to point at managed instances. The
      containers still start as dependencies, but Kodus does not use them.

    **Optional:**
    - `kodus-mcp-manager` — Model Context Protocol broker. Enable with
      `API_MCP_SERVER_ENABLED=true`. See [MCP Manager](/en/how_to_deploy/deploy_kodus/mcp_manager).
    - `worker-analytics` — Cockpit ingestion (DORA metrics, PR
      classifier). **Self-hosted Enterprise only.** Behind the `analytics`
      Compose profile, so the installer does not start it.
      See [Analytics Worker](/en/how_to_deploy/deploy_kodus/analytics_worker).
  </Accordion>
</AccordionGroup>

<Note>
  Code review uses an AST graph + cross-file context that runs in a
  sandbox — `local` (default, runs inside the worker) or `e2b` (paid
  remote sandbox). See [Sandbox & AST Graph](/en/how_to_deploy/deploy_kodus/sandbox)
  for the modes, caching behavior, and when to pick each.
</Note>

<Note>
  Install-time images must be available from their registries or mirrors, or already loaded on the host. For an internal deployment, use Git and model endpoints reachable on your network. Optional external services need access to their own endpoints.
</Note>

## Domain Name Setup (Optional)

Your Git provider must be able to reach the webhook URL over HTTPS. The installer requires at least one HTTPS webhook URL, including when both Kodus and Git run on a private network. The web app must be reachable by its users and by their browsers when they return from sign-in or a Git provider.

We recommend setting up two subdomains:
- One for the Web Application, e.g., `kodus-web.yourdomain.com`.
- One for the API, e.g., `kodus-api.yourdomain.com`.

Webhooks are handled by a separate service (port 3332). You can either:
- Use a dedicated webhooks subdomain, e.g., `kodus-webhooks.yourdomain.com`, or
- Keep using the API domain and route `/github/webhook`, `/gitlab/webhook`, etc. to the webhooks service in your reverse proxy.

Both subdomains should have DNS A records pointing to your server's IP address. The [reverse proxy](/en/how_to_deploy/deploy_kodus/reverse_proxy) routes each subdomain to the right internal service.


## Setup

<Steps>
  <Step title="Clone the installer repository">
    ```bash
    git clone https://github.com/kodustech/kodus-installer.git
    cd kodus-installer
    ```
  </Step>
  <Step title="Copy the example environment file">
    ```bash
    cp .env.example .env
    ```
  </Step>
  <Step title="Generate secure keys for the required environment variables">
    ```bash
    ./scripts/generate-secrets.sh
    ```

    <Warning>
      Run it once, before the first install. Running it again replaces every secret in `.env`, including the database passwords and `API_CRYPTO_KEY`, and the existing data stops working.
    </Warning>
  </Step>
  <Step title="Edit the environment file">
    Edit `.env` with your values using your preferred text editor. 
    ```bash
    nano .env
    ```

    Add `IMAGE_TAG=<version>` to pin the release you install, for example `IMAGE_TAG=2.2.11`. Without it the installer uses `latest`. Release versions are listed on the [kodus-ai releases page](https://github.com/kodustech/kodus-ai/releases) as _Self-Hosted Release_.

    See [Environment Variables Configuration](/en/how_to_deploy/deploy_kodus/generic_vm#environment-variables-configuration) for detailed instructions.
  </Step>

  <Step title="Run the installer">
    ```bash
    ./scripts/validate-env.sh
    ./scripts/install.sh
    ```

    `validate-env.sh` checks `.env` against the schema. `install.sh` refuses to start until the required variables are set and at least one Git webhook URL is valid. The `api` container runs database migrations and seeds when it starts.
  </Step>
  <Step title="Verify the installation">
  When the installer finishes, the services are running. Check them with:
  ```bash
  ./scripts/doctor.sh
  ```

  The first line says whether reviews are running. Each problem after it lists what you lose and how to fix it. Add `--verbose` to see every check.
  </Step>
  <Step title="Access the web interface">
    Once you access the web interface for the first time, you'll need to:

1. **Create your admin account** - This will be the first user with full system access
2. **Connect an LLM provider** - Kodus is bring-your-own-key, and no review runs without a model. Open **AI providers** in the sidebar, or set the model in `.env` (see [LLM Provider Configuration](/en/how_to_deploy/deploy_kodus/generic_vm#llm-provider-configuration))
3. **Configure your Git provider** - Connect GitHub, GitLab, Bitbucket, Azure DevOps or Forgejo following the on-screen instructions
4. **Select repositories** for analysis - Choose which code repositories Kody will review

<Info>
  For detailed steps on the initial configuration process, refer to our [Getting
  Started Guide](/en/how_to_use/quickstart).
</Info>
  </Step>
</Steps>
