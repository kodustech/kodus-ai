当您保存仓库选择时，Kody 通常会按仓库自动创建 service hook。这需要项目上的 **Edit subscriptions** 权限（Project Administrators 拥有该权限）。本页面介绍自动注册未发生时采用的**手动设置**路径。**Repositories** 页面会列出该仓库及原因。

<Note>
  Webhook URL 必须能到达 Webhooks 服务（端口 3332）。仅当您的反向代理将 `/.../webhook` 路径转发到 Webhooks 服务时，才能使用 API 域名。
</Note>

## Azure Repos webhook URL 需要签名令牌

与 GitHub、GitLab、Bitbucket 和 Forgejo 不同，Azure Repos webhook 请求**必须包含加密的 `token` 查询参数**。Kodus 对每个到达的请求验证此令牌，没有令牌的调用会被 `403 Unauthorized` 拒绝。该令牌由您在自托管设置中已配置的两个环境变量派生：

- `CODE_MANAGEMENT_SECRET` — 32 字节的加密密钥（十六进制编码）。
- `CODE_MANAGEMENT_WEBHOOK_TOKEN` — 密钥加密的明文。

所以 Azure webhook URL 形式如下：

```
https://kodus-api.yourdomain.com/azure-repos/webhook?token=<generated>
```

`<generated>` 值由使用 AES-256-CBC 以 `CODE_MANAGEMENT_SECRET` 加密 `CODE_MANAGEMENT_WEBHOOK_TOKEN` 产生，格式为 `<ivHex>:<cipherHex>`。

<Note>
  当 Kody 通过 UI 驱动的集成流程为您创建 webhook 时，会自动生成此令牌。仅当您在 Azure DevOps 中手动注册 webhook 时，才需要手动生成。
</Note>

## 生成 webhook 令牌

选择适合您环境的选项。两个选项都使用您的 Kodus 堆栈已配置的环境变量 — 您**不需要**克隆仓库。

### 选项 A — 在运行中的 Kodus 容器内（推荐）

对已运行的 `api` 容器执行。环境变量已经在作用域内：

```bash
docker compose exec api node -e "
const crypto = require('crypto');
const key = Buffer.from(process.env.CODE_MANAGEMENT_SECRET, 'hex');
const iv = crypto.randomBytes(16);
const c = crypto.createCipheriv('aes-256-cbc', key, iv);
let e = c.update(process.env.CODE_MANAGEMENT_WEBHOOK_TOKEN, 'utf8', 'hex');
e += c.final('hex');
console.log(iv.toString('hex') + ':' + e);
"
```

输出就是您粘贴到 webhook URL 上作为 `?token=...` 的值。示例：

```
8f3c1a4b9e2d6f8a1c3e5f7091a4b7c2:d1e9a23c78...
```

### 选项 B — 本地使用 Node（无 Docker）

如果您的 Kodus 堆栈未运行，或您想在另一台机器上生成令牌，请导出两个环境变量后运行：

```bash
export CODE_MANAGEMENT_SECRET="<same value as in your .env>"
export CODE_MANAGEMENT_WEBHOOK_TOKEN="<same value as in your .env>"

node -e "
const crypto = require('crypto');
const key = Buffer.from(process.env.CODE_MANAGEMENT_SECRET, 'hex');
const iv = crypto.randomBytes(16);
const c = crypto.createCipheriv('aes-256-cbc', key, iv);
let e = c.update(process.env.CODE_MANAGEMENT_WEBHOOK_TOKEN, 'utf8', 'hex');
e += c.final('hex');
console.log(iv.toString('hex') + ':' + e);
"
```

<Warning>
  两个环境变量的值必须与您的 Kodus API 容器正在使用的**完全一致**。密钥不匹配会产生看起来有效、但 Kodus 会以 `403 Unauthorized` 拒绝的令牌。
</Warning>

<Tip>
  令牌不会过期 — 您可以在您组织的每个 Azure Repos webhook 上重复使用同一个生成的值。仅在轮换 `CODE_MANAGEMENT_SECRET` 或 `CODE_MANAGEMENT_WEBHOOK_TOKEN` 时才需要重新生成。
</Tip>

## 在 Azure DevOps 中创建 webhook 订阅

1. 导航到您的 Azure DevOps 项目。
2. 单击左下角的 **Project settings**。
3. 在 **General** 下，选择 **Service hooks**。
4. 单击 **+ Create subscription**。
5. 配置 webhook：

   - **Service：** **Web Hooks**
   - **Trigger on this type of event：** 选择一个受支持的事件（见下文）
   - **URL：** 您的 Kodus Azure Repos webhook URL，附加令牌：

     ```
     https://kodus-api.yourdomain.com/azure-repos/webhook?token=<generated>
     ```

   - **Filters**（可选）：如果需要，按仓库或分支过滤。
   - **Action：** 向给定的 URL 发送 POST 请求。

6. 单击 **Finish**。

每个事件类型需要创建一个订阅。以下三个是 Kody 自己创建、且审查所需要的：

- `git.pullrequest.created` — Pull request created
- `git.pullrequest.updated` — Pull request updated
- `ms.vss-code.git-pullrequest-comment-event` — Pull request commented

Kodus 还接受 `git.pullrequest.merge.attempted` — Pull request merge attempted — 但审查并不需要它。

<Note>
  确保该 URL 可以从 Azure DevOps 访问，并在端口 3332 上（直接或通过您的反向代理）接受到达的 POST 请求。
</Note>

## 故障排除

<AccordionGroup>
  <Accordion title="Azure 发送了 webhook 但 Kodus 返回 403">
    `?token=` 值缺失、被截断，或者是用与运行中 API 所使用的不同的 `CODE_MANAGEMENT_SECRET` / `CODE_MANAGEMENT_WEBHOOK_TOKEN` 生成的。请使用**选项 A** 重新生成令牌（可保证使用容器实际使用的环境变量产生），并在 Azure 中更新订阅 URL。
  </Accordion>

  <Accordion title="Webhook 从未到达">
    Azure DevOps 对失败的投递只会重试有限的次数。查看 **Service hooks** 页面 — 成功的投递会显示绿色勾号。如果投递因连接错误失败，请验证 URL 从公网可达，并且您的反向代理将 `/.../webhook` 路径转发到端口 3332。
  </Accordion>

  <Accordion title="一个事件有效但其他无效">
    每个事件类型在 Azure DevOps 中都需要自己的订阅。如果您只创建了 "Pull request created"，更新和评论将不会触发审查。
  </Accordion>

  <Accordion title="Kodus 返回 400 Unrecognized event">
    令牌已被接受，但请求正文中没有 `eventType`。Azure DevOps service hook 总是会发送它，因此是其他东西在向该 URL 发送请求，例如手动测试请求。
  </Accordion>
</AccordionGroup>
