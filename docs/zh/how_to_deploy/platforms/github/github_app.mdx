如果您想通过 GitHub App 运行 Kody，需要创建一个 GitHub App。此应用使 Kody 能够与您的仓库交互、管理拉取请求并接收 webhooks。

<Note>如果您想为平台用户启用“使用 GitHub 登录”，那是单独的 OAuth App 流程，不会干扰 GitHub App 的权限。本指南专注于功能集成。参见 <a href="/zh/how_to_deploy/platforms/github/github_oauth">GitHub OAuth App</a>。</Note>

## 先决条件

准备好您的应用域名：

- **WEB_DOMAIN**：您的前端 URL（例如 `https://app.yourdomain.com` 或 `http://localhost:3000`）。请在 `.env` 中将 `NEXTAUTH_URL` 和 `API_FRONTEND_URL` 设置为同一个 URL。
- **WEBHOOK_DOMAIN**：能到达 webhooks 服务的公共 URL（例如 `https://kodus-webhooks.yourdomain.com`）。仅当您的 API 域名的反向代理将 `/github/webhook` 转发到该服务时，才能使用 API 域名。

## 步骤 1：创建 GitHub App

1. 在 GitHub 上，转到 **Settings** > **Developer Settings** > **GitHub Apps**
2. 点击 **New GitHub App**
3. 根据您的偏好填写基本信息（Name、Homepage URL）

## 步骤 2：配置回调和设置 URL

这一步对于确保安装和重定向正常工作至关重要。填写以下字段，将 `WEB_DOMAIN` 替换为您的实际 URL：

- **Callback URL**：
  ```
  WEB_DOMAIN/api/auth/callback/github
  ```
  此 URL 用于完成授权流程。
  请保持其上的 **Allow wildcard matching** 为勾选状态：当有人连接该应用时，GitHub 会确认其有权访问该安装，并将其送回 `WEB_DOMAIN/api/auth/callback/github/installation`，即此 URL 的子目录。如果您关闭了通配符匹配，请将该 URL 添加为第二个 Callback URL。Kodus 使用 `API_FRONTEND_URL` 构建该返回 URL；当 `API_FRONTEND_URL` 为空时则使用 `NEXTAUTH_URL`，因此它必须与您的 Web URL 一致。安装器的 `.env.example` 将 `API_FRONTEND_URL` 设置为 `http://localhost:3000`；请修改它。

- **Setup URL**：
  ```
  WEB_DOMAIN/setup/github
  ```

- 勾选选项：**Redirect on update**
  这确保安装应用后，用户被重定向回 Kodus 以完成设置。

## 步骤 3：配置 Webhook

Webhook 通知 Kodus 关于拉取请求中的事件。

<Note>
  Webhook 由独立服务处理（端口 3332）。如果这里使用 API 域名，请确保反向代理将 `/github/webhook` 转发到 webhooks 服务；否则请使用专用的 webhooks 域名。
</Note>

- **Webhook URL**：
  ```
  WEBHOOK_DOMAIN/github/webhook
  ```

- 确保 **Active** 选项已勾选
- 将 **Secret** 留空

## 步骤 4：设置权限并订阅事件

在 **Repository permissions** 下，设置：

| Permission | Access |
| --- | --- |
| Contents | 只读 |
| Pull requests | 读写 |
| Issues | 读写 |
| Checks | 读写 |
| Commit statuses | 只读 |
| Metadata | 只读 |

在 **Organization permissions** 下，将 **Members** 设置为 **Read-only**。Kody 用它来列出组织的成员，例如在 **Repositories** 中的 PR 作者筛选器里。

只有需要提交仓库文件的功能才需要 Contents 写权限；读取代码只需只读权限。Commit statuses 设为只读，是为了把您的 CI 结果用作审查依据；没有它，Kody 只能看到 check runs。将 App 安装到目标仓库，并在已有安装上批准新请求的权限。

在 **Subscribe to events** 下，选择：

- **Pull request**
- **Pull request review comment**
- **Issue comment**
- **Push**
- **Repository**（可选）：当 [Review every repository](/zh/how_to_use/code_review/configs/review_all_repositories) 开启时，让 Kody 在 GitHub 报告后，立即为在应用安装之后创建、且安装范围为所有仓库的新仓库完成设置。

Kody 会忽略其他事件。GitHub 仍然会收到 `200` 响应。

### Merge queue

Kody 只对 merge queue 分支（`gh-readonly-queue/...`）上的 **Push** 采取行动，并忽略其他所有 push。GitHub 的 merge queue 会在该分支上测试每个排队的 PR。在该 push 上，Kody 会把 PR 最近一次已完成的 `Kody Code Review` 结果复制到队列提交上，因此在使用 merge queue 时该检查仍可保持为必需项。不会运行新的审查，除 **Checks** 外也不需要其他权限。如果 PR 没有已完成的 Kody 审查，该检查会失败，队列会移除该 PR；参阅[故障排除](/zh/how_to_use/code_review/troubleshooting)。

## 步骤 5：收集凭据并添加到 .env

现在您需要获取 GitHub 生成的凭据并将其添加到您的 Kodus 环境变量中。

### App ID

在应用 "About" 页面的顶部，复制 **App ID**。

添加到您的 `.env`：
```
API_GITHUB_APP_ID=your_app_id_here
```

### Client ID

在同一页面上，复制 **Client ID**。

添加到您的 `.env`：
```
GLOBAL_GITHUB_CLIENT_ID=your_client_id_here
```

### Client Secret

转到 **Client secrets** 部分并点击 **Generate a new client secret**。

复制生成的值。

添加到您的 `.env`：
```
API_GITHUB_CLIENT_SECRET=your_client_secret_here
```

### Private Key

滚动到页面底部并点击 **Generate a private key**。

这将下载一个 `.pem` 文件。使用文本编辑器打开此文件并复制整个内容。

添加到您的 `.env`：
```
API_GITHUB_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY----- ..."
```

Kodus 接受带换行的密钥，也接受单行形式（各行之间用 `\n` 连接）。

### Installation URL

打开您的 GitHub App，点击 **Install App**。从浏览器地址栏复制 URL（形如 `https://github.com/apps/<app-slug>/installations/new`）。

添加到您的 `.env`：
```
WEB_GITHUB_INSTALL_URL="https://github.com/apps/your-app/installations/new"
```

## 环境变量摘要

最后，您的配置文件应包含：

```bash
API_GITHUB_APP_ID=123456
GLOBAL_GITHUB_CLIENT_ID=Iv1.example123
API_GITHUB_CLIENT_SECRET=example_secret_123
API_GITHUB_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY----- ..."
WEB_GITHUB_INSTALL_URL="https://github.com/apps/your-app/installations/new"
```

在 GitHub 上点击 **Save Changes** 并重启您的 Kodus 应用程序以应用更改。

## 验证连接

Webhook URL 必须到达 webhooks 服务，而不是前端登录页。仅凭 `200` 或 `307` 响应并不能证明投递正确；有关能够证明这一点的请求，请参阅[如何修复 webhook 问题](/zh/knowledge_base/how-to-fix-webhook-issues)。

保持 **Redirect on update** 开启。安装或修改仓库访问范围后，请完成通过 **Setup URL** 返回 Kodus 的浏览器往返流程。成功的 `ping` 或被忽略的 `installation` 事件不会创建 Kodus 集成。

在 Kodus 中，打开侧边栏的 **Repositories**，确认目标仓库已列出。然后打开一个测试 pull request，并同时检查 GitHub 的投递响应以及 Kodus 的 webhooks 和 worker 日志。

如果连接缺失：

- 执行连接的人必须能够在 GitHub 上看到该安装，例如组织所有者。否则 Kodus 会拒绝该链接。
- 一个安装只能关联一个 Kodus 组织。将其连接到第二个组织会被拒绝。
- 请在 10 分钟内于同一个浏览器中开始并完成连接。超过该时间后 GitHub 的授权会过期，您需要重新开始。
- 检查安装的仓库访问范围、已批准的权限、Setup URL、Callback URL 以及代理路由。

[GitHub 注册参考](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app)。
