## 为什么这份指南很重要

每个工程团队都有一份“最佳实践”文档。问题在于，IDE 的建议不会读它，审阅者会忘记其中的细节，文档也会慢慢失去权威。这份指南把你的手册变成主动护栏，让 Kody 在每个 pull request 上执行这些规则，并指出发生偏离的章节。

我们将使用两个构建块：

- [Kody Rules](/zh/how_to_use/code_review/configs/kody_rules) – 每条策略要点变成引用该手册的文件级或 PR 级检查。
- [自定义 agent](/zh/how_to_use/code_review/custom_agents) – 手册作为文档链接，每条发现都会引用所应用的规则。

## 前置检查清单

- 你有权限编辑 **Code review → Kody Rules**。
- 手册存放在仓库中（例如 `docs/engineering-standards.md`）。如果你的手册位于其他路径，请相应调整。
- 你清楚哪些主题应在文件级评估（控制器、配置），哪些应在 PR 级评估（feature flag、发布说明、架构）。

<Callout icon="layers">
  请将手册置于版本控制之下。规则和 agent 从 pull request 的目标分支读取它，因此每次修改都会经过 pull request，并由负责人签字确认。
</Callout>

## 阶段 1 – 整理出适合规则的策略集

1. 创建或复用一个 markdown 文件，例如 `docs/engineering-standards.md`。
2. 把内容组织成简短、可检查的要点：

```md
# Engineering Standards

## Error handling
- Never swallow errors.
- Do not log PII or secrets.
- External requests must have a timeout and retry policy.

## Architecture
- No direct cross-module imports from `domain/*` into `web/*`.
- New endpoints must include tracing fields (e.g., requestId) and structured logs.
- Feature flags are mandatory for risky changes.
```

<Tip>
  让每条要点都是原子的。规则触发时，对于需要改什么，应当毫无争议。
</Tip>

## 阶段 2 – 让每条规则都指向真实文档

引用实际的手册，而不是在每条指令中粘贴片段。

```text
Use @file:docs/engineering-standards.md (Architecture section) as the policy source.
Only flag code that clearly violates those bullets. If the section is missing, say so.
```

- 针对特定领域的策略集，换成其他文件路径（例如 `@file:docs/mobile.md`）。
- 只需要文件的一部分？附加行锚点，例如 `@file:docs/engineering-standards.md#L40-L72`，让规则只读取该部分。

<Callout icon="link">
  一处引用让一切保持同步。更新一次手册，每条规则就会执行最新版本。
</Callout>

## 阶段 3 – 把章节转化为 Kody Rules

在侧边栏中打开 **Code review → Kody Rules**。在 **Review Rules** 标签页点击 **New rule**，把每个策略章节对应到合适的执行模式和路径。

| 策略章节         | 执行模式 | 路径示例                       | 严重级别 |
| ---------------------- | -------------- | ---------------------------------- | -------- |
| 错误处理         | Per file       | `backend/**/*.ts`                  | High     |
| 架构           | Per PR         | 不适用                     | Critical |
| 日志与追踪      | Per file       | `web/apps/**/controllers/**/*.ts`  | Medium   |
| 安全 / PII         | Per file       | `**/*`                             | Critical |

### 文件级示例

```
Rule name: Enforce tracing fields on new endpoints
Execution mode: Per file
Path: web/apps/**/controllers/**/*.ts
Severity: High
Instructions:
  Compare fileDiff with Architecture → New endpoints in @file:docs/engineering-standards.md.
  Flag handlers that lack requestId tracing AND structured log statements.
  Quote the diff chunk that violates the policy.
```

### PR 级示例

```
Rule name: Require feature flags for risky changes
Execution mode: Per PR
Severity: Critical
Instructions:
  Scan pr_files_diff for routes/services/domain files that add major functionality.
  If no feature flag file is touched, cite “Architecture → Feature flags are mandatory” and request the rollout plan.
```

<Info>
  规则支持变量（每个文件的 `fileDiff`，以及每个 PR 的 `pr_files_diff` 和其他 `pr_*` 变量）和文件引用。完整列表请参阅 [Kody Rules 指南](/zh/how_to_use/code_review/configs/kody_rules)。
</Info>

## 阶段 4 – 或者把手册交给自定义 agent

自定义 agent 把手册作为链接文档来读取，并且必须引用每条发现背后的规则。如果引用内容不在目标分支上的文档中，该发现会被丢弃。自定义 agent 处于 beta 阶段，适用于 Teams 和 Enterprise 套餐以及试用期间；自托管 Kodus 还需要 `BETA_FEATURES=true`。

<Steps>
  <Step title="创建 agent">
    在 **Code review → What to review → Custom agents** 中，点击 **New agent → Templates → Blank**。将其命名为 **Engineering standards**。
  </Step>
  <Step title="链接手册">
    在 **Files & knowledge → Skills & docs** 下，点击 **Add skill or doc → Add by path** 并输入 `docs/engineering-standards.md`。文档在每次审查时都会完整加载，因此请保持简短。较长的手册更适合做成带参考文件的 skill。
  </Step>
  <Step title="编写指令">
    ```text
    Flag changes that break a rule in docs/engineering-standards.md.
    Quote the rule you apply. Ignore tests and generated code.
    ```
  </Step>
  <Step title="试一试，然后启用">
    在一个违反规则的 pull request 上运行 **Try it**。每条评论都会以 **Rule** (`docs/engineering-standards.md`) 的形式引用该规则，并附上引用的要点。
  </Step>
</Steps>

有关预算和检测，请参阅[技能、文档和工具](/zh/how_to_use/code_review/custom_agents_knowledge_and_tools)。

## 阶段 5 – 测试、观察并保持更新

<AccordionGroup>
  <Accordion title="创建验证用 PR">
    创建一个违反每个章节的临时 PR，让 Kody 审查它（如果尚未开始，评论 `@kody start-review`）。检查行内评论和 PR 级评论是否引用了正确的要点。可用 `@kody -v engineering-standards` 按需运行该 agent。
  </Accordion>
  <Accordion title="调整噪声和严重级别">
    在推广期间，观察每条规则的触发频率。收紧文件 glob、添加排除项或调整严重级别，直到信号达到预期。
  </Accordion>
  <Accordion title="同时更新文档和规则">
    每当手册变更时，在同一个 PR 中更新 markdown 以及相关规则或 agent 指令，让审阅者可以验证整条流水线。
  </Accordion>
</AccordionGroup>

## 快速检查清单

- [ ] `docs/engineering-standards.md` 存在，且要点便于扫读。
- [ ] 每条规则都用 `@file` 引用策略集，因此读取的是最新文本。
- [ ] 文件级和 PR 级 Kody Rules 覆盖了你的关键章节。
- [ ] 可选：一个遵循并引用手册的自定义 agent。
- [ ] 在大范围推广之前，已用试运行 PR 确认行内评论和 PR 摘要。
