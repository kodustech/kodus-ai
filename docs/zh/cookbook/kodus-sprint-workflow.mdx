## 大多数 sprint 工作流中的缺口

团队在 Jira、Linear 或 Notion 中跟踪需求。开发者在 PR 中实现它们。但没有人系统地检查 PR 是否真的覆盖了所有验收标准，直到 QA 在预发布环境中发现缺口。

本 cookbook 通过[业务逻辑验证](/zh/how_to_use/code_review/business_logic_validation)来闭合这个环路：Kody 对照每个 PR 所引用的任务进行检查。

## 工作流

```
Task created (Jira, Linear, Notion)
    ↓
Developer implements → Opens PR that references the task
    ↓
Kodus, on the PR's first review:
  1. Finds the task in the PR title, branch or description
  2. Reads it from the connected tracker
  3. Lists every requirement and where it stands in the code
    ↓
Developer addresses the gaps → Re-checks with @kody -v business-logic
    ↓
Merge with confidence
```

## 步骤 1 — 连接你的任务跟踪器

在侧边栏中打开 **Plugins** 并连接你的工具：

- **Atlassian Rovo** — 用于 Jira
- **Linear**
- **Notion**
- **Git Issues** — 用于仓库自带跟踪器中的 issue

其他任何跟踪器都可以通过[自定义插件](/zh/cookbook/custom-plugin-install)使用。Kody 只按 id 读取任务，绝不会写入你的跟踪器。

## 步骤 2 — 确认 Business Logic 已开启

它默认是开启的。可以在 **Code review → What to review** 的 **Business Logic** 行中开启或关闭，也可以在 `kodus-config.yml` 中设置（仅当该仓库开启 **Prefer kodus-config.yml settings** 时才会读取）：

```yaml
reviewOptions:
  business_logic: true
```

## 步骤 3 — 编写好的验收标准

Kody 能检查多少取决于任务本身：

| 任务 | Kody 的做法 |
|------|----------------|
| 验收标准：标准字段、检查清单，或描述中的列表 | 检查每条需求，并引用文件和行号 |
| 有描述，但没有列表 | 检查描述中陈述的行为 |
| 只有标题 | 不检查。它会评论要求提供验收标准 |

**Jira/Linear 任务模板：**

```
## Description
Brief context about what needs to change and why.

## Acceptance Criteria
1. Users with role "admin" can delete any comment
2. Users can only edit their own comments within 24 hours
3. Deleted comments show "[removed]" placeholder
4. Audit log records who deleted what and when
5. API returns 403 for unauthorized delete attempts
```

如果你的标准位于某个标题之下或自定义字段中，请在 Business Logic 设置中配置 **Where acceptance criteria live**。

## 步骤 4 — 让 PR 写明它的任务

Kody 会依次在 PR 标题、分支名和描述中查找任务：类似 `KC-1292`、`#123`、`AB#123` 的 key，或指向任务的链接。“Closes KC-1292” 会对照整个任务检查 PR。“Part of KC-1292” 检查其中一部分，并列出缺失的内容，但不把它们视为阻碍。

如需强制要求，请打开 **Code review → What to review → Business Logic** 并开启 **Ask for a task when the PR references none**。之后 Kody 会评论询问该 PR 对应哪个任务。Dependabot 等机器人 PR 不受影响。

## 步骤 5 — PR 变化时重新检查

Kody 在 PR 的首次审查时进行检查。之后，请评论：

```
@kody -v business-logic
```

Kody 会编辑它的那一条评论，而不是发布新评论。要对照特定任务检查，请附上它的链接或 id：`@kody -v business-logic https://kodustech.atlassian.net/browse/KC-1292`。

如果想不用手动要求就重新检查，请把 **Re-check after a push** 设为 **While something is missing**：每次推送都会重新检查，直到每条需求都得到满足。

## 步骤 6 — 传授团队约定

在 Business Logic 设置中，**Team guidance** 保存 Kody 在判断时遵循的备注：

```
Requirements the ticket marks as out of scope are not missing.
Feature flags count as implemented when the flag exists and defaults to off.
```

审阅者（而不是 PR 作者）也可以通过回复 Kody 的评论并提及 Kody 来接受一个缺口，例如 “@kody Out of scope, moved to SAA-102”。Kody 会确认该任务存在，并把该需求标记为已接受。谁可以接受，请参阅[回复评论](/zh/how_to_use/code_review/business_logic_validation#回复评论)。

## 结果

设置完成后，你 sprint 中的每个 PR 都会得到：

1. **代码质量审查** — 安全、性能、风格（标准 Kodus）
2. **业务逻辑验证** — 每条需求显示为已满足、部分满足、缺失或需手动检查，另外还会列出任务没有要求的变更

QA 发现的缺口更少，sprint 演示更顺利，“我以为那个做完了”也会变得罕见。

## 提示

- 鼓励团队编写带编号的验收标准 — 这样得到的验证效果最好
- 在开发过程中就运行 `@kody -v business-logic`，而不只是在审查时
- 对于分阶段交付，请在 PR 描述中写 “Part of KC-1292”，这样 Kody 不会把其余部分视为阻碍

详情请参阅[业务逻辑验证](/zh/how_to_use/code_review/business_logic_validation)。
