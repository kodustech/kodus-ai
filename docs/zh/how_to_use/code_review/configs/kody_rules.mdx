## 在哪里找到

在 **Code review** 分组顶部的作用域选择器中选择 **Global**、某个仓库或某个目录，然后打开 **Kody Rules**。您在该页面上创建或更改的所有内容都应用于您选择的作用域。各作用域如何组合，请参阅[规则继承](/zh/how_to_use/code_review/configs/rules_inheritance)。

页面标题栏有三个操作：

- **Configuration**：为该作用域创建和批准规则与记忆的方式。
- **Discovery**：[规则库](/zh/how_to_use/code_review/configs/rules_library)。显示在 **Review Rules** 标签页上。
- **New rule**（在 **Memories** 标签页上为 **New memory**）。

## 两种类型

<Tabs>
  <Tab title="审查规则">
    在代码审查期间运行并将违规报告为建议的检查。

    - **Per file** 规则对每个变更文件运行一次，并以行内评论的形式给出。
    - **Per PR** 规则对整个拉取请求运行一次，并发布一条 PR 评论。
    - 每条规则都有严重性，并且可以限定路径。
  </Tab>

  <Tab title="记忆">
    Kody 在代码审查和与 Kody 的对话中作为高优先级上下文使用的背景知识。记忆描述您的代码库是如何工作的；它不是检查，也没有严重性。

    - 通过在 PR 评论中与 Kody 对话，或使用 **New memory** 创建。
    - 作用域可限定为目录、仓库或整个组织。
  </Tab>
</Tabs>

## 创建审查规则

在 **Review Rules** 标签页中，点击 **New rule**（列表为空时为 **Write a rule**）。

| 字段 | 作用 |
|-------|--------------|
| **Rule name** | 最多 300 个字符。 |
| **Execution mode** | **Per file** 或 **Per PR**。 |
| **Path** | 把 **Per file** 规则限定到匹配文件的 glob。多个 glob 用逗号分隔；匹配其中任意一个的文件都会被检查。留空表示所有文件。**Per PR** 规则不使用该字段，在目录作用域下也不可编辑，因为此时规则属于该目录作用域（何时生效请参阅[规则继承](/zh/how_to_use/code_review/configs/rules_inheritance)）。 |
| **Instructions** | Kody 应该检查什么以及如何判断。必填。新建规则时可以 **Start with a popular template**。**Variables** 菜单会插入 `fileDiff` 或 `pr_title` 之类的名称，可用于引用 Kody 看到的 diff 和 PR 详情。 |
| **Severity** | **Critical**、**High**（默认）、**Medium** 或 **Low**。 |
| **Advanced settings** | **Inheritable**（默认开启）和 **Code examples**：一个 **Bad example** 和一个 **Good example**。 |

严重性决定发现如何标注。低于某个严重性的发现是否发布，则在[严重性阈值](/zh/how_to_use/code_review/configs/suggestion_control#对-kody-rules-应用阈值)中设置。

### Kody 看到什么

- **Per file：** 该文件的 diff、文件其余部分（在足够小时），以及 PR 标题和描述（前 1,000 个字符）。
- **Per PR：** PR 标题和描述（前 1,000 个字符）、变更文件列表以及每个文件的 diff。在非常大的 PR 上，超出 diff 预算的文件只按名称列出。

Kody 只会报告拉取请求新增或修改的行上的违规。指令中指明了语言的规则（"在 Ruby 文件中，……"）会限定为该语言的文件，Kody 在您保存规则时判断这一点。

### 在规则中引用文件

在指令中按路径提及文件，例如 `@file:docs/architecture.md`，Kody 在判断规则时就会获得其内容。

- Kody 在您保存规则时查找文件引用。编辑器旁边的状态会显示它们何时解析完成，以及任何无法读取的文件。
- 文件从拉取请求的目标分支读取。
- 使用仓库中的真实路径，而不是占位符。

### 示例

<Tabs>
  <Tab title="Per file">
    - **Rule name：** 避免在循环终止条件中使用相等运算符
    - **Path：** `src/**/*.ts`
    - **Severity：** Critical
    - **Instructions：** 在循环条件中使用 `==` 或 `!=`，如果永远不会命中确切值，可能导致无限循环。

    **Bad example**

    ```typescript
    // Infinite if the increment is not exactly 1
    for (let i = 0; i != 10; i += 2) {
      console.log(i);
    }
    ```

    **Good example**

    ```typescript
    for (let i = 0; i < 10; i += 2) {
      console.log(i);
    }
    ```
  </Tab>

  <Tab title="Per PR">
    - **Rule name：** 新路由必须注册
    - **Execution mode：** Per PR
    - **Instructions：** 当 PR 向控制器添加路由时，检查它是否也已添加到 `@file:routes.json`。

    Per PR 规则还可以检查的其他内容：

    - PR 描述说明了添加或移除了什么。
    - 每个变更的 service 文件在 PR 中都有对应的测试文件。
    - PR 变更的文件数不超过设定的数量。
  </Tab>
</Tabs>

## 添加规则的其他方式

- **[规则库](/zh/how_to_use/code_review/configs/rules_library)：** 通过 **Discovery** 添加现成的规则和规则包。
- **[代码库规则](/zh/how_to_use/code_review/configs/repository_rules)：** 在您的仓库的 `.kody/rules` 中，每条规则一个 markdown 文件。
- **[全局规则源](/zh/how_to_use/code_review/configs/global_rule_sources)：** 把标准仓库中的规则文件导入为全局规则。
- **[自动规则生成](/zh/how_to_use/code_review/learning/kody_rules_generation)：** Kody 根据审查者过去的评论起草规则。
- **在审查讨论串中：** 让 Kody 创建、更改或移除规则，例如 `@kody update this rule to ignore test files`。以这种方式创建的规则显示 **MCP/Agent** 来源，并在 **Pending review** 中等待。

## 规则列表

列表显示所选作用域的规则，以及从更高作用域继承的规则。点击某一行会在侧边面板中打开该规则，其中有 **Pause** 或 **Resume**、**Edit**（没有编辑权限时为 **View**）和删除。

使用筛选器旁边的表格或卡片视图开关；该选择会保存在您的浏览器中。搜索会查找标题、路径、指令和示例（按 `/` 聚焦）。列表上方的严重性标签按严重性筛选。

**Filters** 让您按最近更新、严重性或名称排序，显示或隐藏继承的规则和 **Disabled Rules**，并按来源、按 **Has sync errors**（所引用文件无法读取的规则）或按 **Paused only** 筛选。

### Origin

| 来源 | 规则来自哪里 |
|--------|--------------------------|
| **Manual** | 在应用中编写。 |
| **Library** | 从规则库添加。 |
| **Auto-sync** | 仓库中的规则文件，保持同步。 |
| **Kody-generated** | 根据过去的审查起草。 |
| **Onboarding** | 在引导期间建议。 |
| **MCP/Agent** | 通过 Kodus MCP 工具创建：由 Kody 在审查讨论串中创建，或由 MCP 客户端创建。 |
| **CLI** | 使用 Kodus CLI 创建。 |
| **Agent file** | 在这些文件不再变成规则之前，从编码代理文件导入。已冻结。参见[编码代理指令](/zh/how_to_use/code_review/configs/rules_file_detection#从编码代理文件导入的规则)。 |

### Status

| 状态 | 含义 |
|--------|---------|
| **Active** | 在每个新 PR 上检查。 |
| **Paused** | 保留在列表中，在每个 PR 上跳过。 |
| **Paused by Kody** | 被 **Pause ignored and noisy rules** 暂停。 |
| **Locked** | 因 Free 套餐限制而跳过（见下文）。 |
| **Disabled** | 为该作用域标记为禁用的继承规则。审查仍会应用它；请参阅[规则继承](/zh/how_to_use/code_review/configs/rules_inheritance)。 |
| **Pending add**、**Pending edit**、**Pending delete** | 变更正在[集中式配置](/zh/how_to_use/code_review/configs/centralized_config)拉取请求中等待。 |

### 批量操作

在 **Review Rules** 标签页中，勾选规则（或 **Select all visible**），即可一起 **Pause**、**Resume** 或 **Delete**。只能选择当前作用域的规则，不能选择继承的规则。

### 影响与使用情况

侧边面板会显示最近 30 天的 **Impact** 区块：规则触发了多少次、在多少个拉取请求上触发，以及最近的建议。在 Cockpit 可用的地方（Teams 和 Enterprise 套餐以及试用），它还会显示有多少建议被采纳，以及点赞和点踩反馈，表格会多出 **Usage** 列。需要关注的规则会带有标签：

- **Stale：** 最近 30 天没有触发。
- **Ignored：** 至少触发了 5 次，且其建议被采纳的比例不超过 20%。
- **Noisy：** 至少触发了 5 次，至少有 3 个点踩，点踩多于点赞，且点踩占其建议的至少 10%。

### Pause ignored and noisy rules

在 Teams 和 Enterprise 套餐上，**Configuration → Pause ignored and noisy rules** 会每天一次暂停该作用域中最近 30 天结果为 **Ignored** 或 **Noisy** 的有效规则，包括手工编写的规则。它们会显示 **Paused by Kody** 以及背后的数据。管理员会收到通知，并且可以随时 **Resume** 规则；恢复之后，只统计它之后标记的内容。通过[集中式配置](/zh/how_to_use/code_review/configs/centralized_config)管理的规则不会被暂停。默认关闭。

## 规则限制

云端 **Free** 套餐的组织（或订阅已取消或已过期的组织）以及没有有效许可证的自托管实例，每次审查最多运行 **10 条有效规则**，最早创建的优先。这 10 条把 Global、仓库和目录规则合在一起计算，记忆也计入。超出限制的规则会以 **Locked** 保留在列表中，在每个 PR 上都会被跳过，页面上的横幅会说明有多少条。付费云端套餐和已授权的自托管实例没有限制。

## 记忆

记忆是 Kody 记在心里的简短陈述：您的系统如何工作、团队已经决定了什么。记忆帮助 Kody 避免重复对您的仓库做出错误假设。

- 记忆会被添加到代码审查和与 Kody 对话的上下文中。
- 当 Kody 即将保存一条记忆时，它会检查现有记忆，然后创建它、作为重复项跳过它，或更新一条现有记忆。

### 创建记忆

**在 PR 评论中。** 让 Kody 记住某件事，它就会保存下来：

```
@kody remember: this repo mirrors a third-party API, so some payload fields intentionally stay snake_case.
```

当您只是陈述上下文或团队偏好时，Kody 会提出保存并等待。回复 `@kody yes` 即可保存：

```
@kody in this service, tests usually live next to implementation files rather than in a central test folder.
```

当 Kody 保存或更新记忆时，它会回复一个指向应用中该记忆的链接。

<Info>
  Kody 不会保存临时性指令（"现在修复这个"）、调试闲聊、问题、含糊的陈述，或仅适用于某个任务或 PR 的请求。
</Info>

**在应用中。** 选择作用域，打开 **Memories** 标签页，点击 **New memory**（列表为空时为 **Add a memory**），填写 **Memory name** 和 **Instructions**，然后点击 **Create memory**。

### 记忆作用域

| 作用域 | 适用于 |
|-------|------------|
| **Directory** | 已配置目录中的文件。在 PR 评论中创建的记忆也可以限定到某个路径，例如 `src/components/**`。 |
| **Repository** | 整个仓库。 |
| **Organization**（作用域选择器中的 **Global**） | 组织中的每个仓库。 |

## 批准

默认情况下，根据过去的审查生成的规则、在引导期间建议的规则以及 Kody 保存的记忆，在创建后立即生效。若要先审核它们，请打开 **Configuration** 并开启 **Kody knowledge approval**。

开启批准后，这些内容会在 **Pending review** 中等待，直到被批准：

- 根据过去的审查生成或在引导期间建议的规则；
- Kody 在审查讨论串中保存的记忆；
- 从仓库的规则文件同步的规则。通过[全局规则源](/zh/how_to_use/code_review/configs/global_rule_sources)导入的规则会立即生效。

通过 Kodus MCP 工具创建的规则（包括 Kody 在审查讨论串中创建的规则）无论设置如何，都始终在 **Pending review** 中等待。您手工编写、从规则库添加或使用 CLI 创建的规则会立即生效。

### Pending review

**Review Rules** 和 **Memories** 标签页上的徽标显示待审数量。**Pending review** 部分（"Rules and memories awaiting approval."）将它们一起列出，每一项标记为 **Rule**、**Memory** 或 **Update**：

- **新规则和记忆：** **Approve** 以激活，或 **Discard** 以拒绝。
- **更新：** 对现有项目的建议变更，以 diff 形式显示。**Update existing** 应用它，**Create new instead** 保留原项目并把建议作为单独的项目添加，**Discard** 拒绝它。

选择多项并使用 **Bulk actions**（**Approve N**、**Create as new (N)**、**Discard N**）一次性处理它们。
