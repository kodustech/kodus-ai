两项设置决定 Kody 报告什么以及如何表述。两者都可以在 Global、Repository 和 Directory 范围设置。

| 设置 | 位置 | 控制内容 |
| --- | --- | --- |
| **Instructions** | **Code review → What to review**，位于 Bug、Performance 和 Security 行 | Kody 在该类别中查找什么。 |
| **Personality instructions** | **Code review → What Kody writes**，位于 **Kody's personality** | 每条建议的语气和长度。 |

## 类别指令

[What to review](/zh/how_to_use/code_review/configs/what_to_review) 上每个已开启的 **Bug**、**Performance** 和 **Security** 行都有一个 **Instructions** 按钮，点击后会打开一个编辑器（*What counts as a bug issue* 等）。

- 编辑器显示 Kody 的默认文本。在您更改之前，标签显示 **Kody's default**，更改后显示 **Custom**。
- **Reset to default** 会恢复默认值。清空文本效果相同。
- 上限为 2000 个字符。
- 类别关闭时该按钮会被隐藏。Business Logic 在这里没有指令。

Kody 会把您的文本添加到它针对该类别的准则中。写明您的技术栈以及对您重要的模式：

```text
Focus on SQL injection and missing authorization checks in our API
handlers. Treat unvalidated user input reaching a query as a finding.
```

## Personality instructions

**Kody's personality** 中的 **Personality instructions** 编辑器（上限 2000 个字符，提供 **Reset to default**）设定 Kody 在每条建议中的语气。它叠加在每个类别的指令之上。

- Kody 的默认设置把每条建议控制在两个短句：影响，以及要修改什么。当您自己编写时，该限制不再适用，因此请说明您希望建议有多长。
- 无论您写什么，有些规则始终成立：Kody 不会重复建议的标题，不会在文本中放入代码块（因为修复会单独显示），也不会添加行号。
- 它适用于除确定性扫描器发现之外的每条建议。自定义代理自己的写作指令会取代它，用于该代理的发现。

```text
Be direct. State the impact in one sentence, then the change to make.
Write in the second person and skip pleasantries.
```

## 外部引用

类别指令、个性指令和[摘要指令](/zh/how_to_use/code_review/configs/pr_summary)都可以指向文件。保存后，Kody 会检测这些引用，并在之后的审查中读取这些文件。编辑器下方的状态指示器会显示处理何时完成。

- `@file:path/to/file.ts` — 被审查仓库中的文件。添加 `#L10-L50` 可指定行范围。
- `@file:repo-name:path/to/file.ts` — 另一个仓库中的文件。

诸如"遵循 CONTRIBUTING.md 中的准则"之类的提及也会被检测到。请使用精确的路径，以便 Kody 找到正确的文件。

## 在 `kodus-config.yml` 中设置

相同的字段可在 `v2PromptOverrides` 下使用：

```yaml
v2PromptOverrides:
    generation:
        main: |
            Tone and length for every suggestion.
    categories:
        descriptions:
            bug: |
                What Kody should look for in the Bug category.
            performance: |
                What Kody should look for in the Performance category.
            security: |
                What Kody should look for in the Security category.
```

该文件还接受另一个应用中没有任何页面可编辑的分组：Kody 用来对发现分级的严重级别标准。

```yaml
v2PromptOverrides:
    severity:
        flags:
            critical: |
                What counts as critical.
            high: |
                What counts as high.
            medium: |
                What counts as medium.
            low: |
                What counts as low.
```

<Warning>
  这会改变 Kody 如何*分类*发现，而不仅仅是如何措辞。糟糕的标准可能悄悄地压低或抬高每次审查中的严重级别。请从
  [`default-kodus-config.yml`](https://github.com/kodustech/kodus-ai/blob/main/default-kodus-config.yml)
  中的默认值开始，而不是从零编写标准。
</Warning>

<Note>
  `default-kodus-config.yml` 还包含一个 `v2PromptOverrides.level` 分组。它会被接受但被忽略；只有 `categories.descriptions`、`severity.flags` 和 `generation.main` 会进入审查。
</Note>

只有开启 **Prefer kodus-config.yml settings** 后，才会读取该文件。参见[通用设置](/zh/how_to_use/code_review/configs/general#config-priority)。

## 提示

- **结合您的具体情况。** "关注我们 Java 服务中的空指针解引用和 DAO 层中未关闭的连接"比"查找 bug"效果更好。
- **让各类别保持分离。** 不要在 Bug、Security 和 Performance 中重复相同的指令。
- **描述模式，而不是单个示例。** 像某一处确切的字符串拼接这样的示例，可能会把 Kody 标记的内容缩窄到那种形态。
- **从一项设置开始。** 先用默认设置运行一周，记录误报或漏报，只修改与之相关的指令。

## 常见问题

<AccordionGroup>
  <Accordion title="这些设置适用于所有仓库吗？">
    在 Global 设置时，它们适用于每个没有自己取值的仓库。仓库或目录可以覆盖它们。
  </Accordion>

  <Accordion title="更改它们时，现有的拉取请求会怎样？">
    更改只影响新的审查。评论 `@kody review --force` 可用新文本审查现有拉取请求的全部内容。没有 `--force` 时，审查命令只涵盖上次审查以来的提交。
  </Accordion>

  <Accordion title="审查噪音太多。我应该改什么？">
    在 What to review 上提高 **Minimum severity to post**（参见[严重性阈值](/zh/how_to_use/code_review/configs/suggestion_control)），然后让类别指令更具体。
  </Accordion>

  <Accordion title="Kody 漏掉了它本该发现的问题。">
    检查该类别是否已开启，以及发现的严重级别是否低于您的阈值。使用 **Reset to default** 查看是否是您的指令把审查范围缩得太窄。
  </Accordion>

  <Accordion title="类别指令和个性指令有什么区别？">
    类别指令控制 Kody 在每个类别中分析什么。个性指令控制每条发现如何措辞。您可以分别更改它们。
  </Accordion>
</AccordionGroup>
