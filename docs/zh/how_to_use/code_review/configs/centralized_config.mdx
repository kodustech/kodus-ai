---
title: "集中式配置"
description: "将所有代码审查配置和 Kody Rules 作为代码保存在单个代码库中。每次合并后自动同步；通过 UI 或 CLI 控制发布。"
---

集中式配置让您将所有代码审查设置和所有 Kody Rules 保存在**一个代码库**中，而不是在 Web UI 中按代码库分别编辑。每次更改都通过该代码库上的拉取请求进行，为您的审查配置提供版本历史、评审和回滚能力。

适用场景：

- 跨多个代码库管理审查行为的单一真实来源。
- 配置即代码：历史记录、PR 评审、回滚、CI 校验。
- 在整个组织中保持一致的 Kody Rules（审查规则和记忆）。
- 基于 CLI 或 CI 的配置变更。

## 工作原理

1. 选择一个代码库作为集中式配置源。它必须是 Kodus 中已选择的代码库之一。
2. 在 UI 中（在 Global 作用域下的 **Code review → General** → **Configure centralized config**）启用集中式配置并指向该代码库。
3. 选择**初始同步方式**：
   - `pr` — Kodus 使用您当前的有效设置和规则打开初始化 PR。
   - `manual` — Kodus 生成文件；您的团队下载并自行打开 PR。
4. 首次合并后，集中式代码库上后续的每次合并都会自动将变更传播到 Kodus。

Kody 不会审查集中式代码库本身的拉取请求。

集中式代码库通过其文件夹结构镜像 Kodus 的作用域层级（全局 → 代码库 → 目录）。

## 代码库结构

集中式代码库使用文件夹路径将文件映射到各个作用域。结构同时覆盖审查设置（`kodus-config.yml`）和 Kody Rules（`.kody-rules/`）。

<Note>
代码库名称任意 — 选择适合您组织的即可。下方示例使用 `kodus-config` 作为约定。
</Note>

```
kodus-config/
├── kodus-config.yml                      ← global settings
├── .kody-rules/
│   ├── review/                           ← global review rules
│   │   └── require-tests-for-endpoints.yml
│   └── memories/                         ← global memories
│       └── logging-convention.yml
│
├── backend-api/                          ← matches a Kodus repository
│   ├── kodus-config.yml                  ← repository-level overrides
│   ├── .kody-rules/
│   │   ├── review/
│   │   │   └── no-raw-sql.yml
│   │   └── memories/
│   │       └── auth-module-layout.yml
│   │
│   └── src%2Fauth/                       ← a directory scope for src/auth
│       ├── kodus-config.yml              ← directory-level overrides
│       └── .kody-rules/
│           ├── review/
│           └── memories/
│
└── frontend-web/
    └── kodus-config.yml
```

规则：

- 集中式代码库**根目录**下的 `kodus-config.yml` 适用于全局。
- 顶层文件夹的名称若与某个 Kodus 代码库匹配（如 `backend-api/`），则该文件夹下的文件作用于该代码库。在 GitLab 上，名称是完整路径，因此文件夹是嵌套的：`group/project/`。
- 目录作用域是代码库文件夹内的一个文件夹，以其覆盖的路径命名。将每个 `/` 写成 `%2F`，多个路径用 `&` 连接：`src%2Fauth`，或对于包含两个文件夹的作用域写成 `apps%2Fweb&apps%2Fdocs`。更深的嵌套路径（如 `backend-api/src/auth/`）会被跳过。
- `.kody-rules/review/` 下的规则成为**审查规则**；`.kody-rules/memories/` 下的规则成为**记忆**。

任何没有对应作用域的文件在同步时会被忽略。

从集中式代码库中删除文件，会在下次同步时移除该文件所定义的内容：删除规则文件会删除该规则，删除之前某次同步已应用的 `kodus-config.yml` 会清除该作用域的设置。

## 配置文件

每个 `kodus-config.yml` 使用与按代码库的 `kodus-config.yml` 相同的结构，详见[通用设置](/zh/how_to_use/code_review/configs/general)。字段作用于该文件所在文件夹的层级，并遵循通常的继承规则（参见[配置继承与覆盖](/zh/how_to_use/code_review/configs/inheritance_overrides)）。与代码库自己的文件不同，这些文件还可以包含 `customMessages`（参见[自定义消息](/zh/how_to_use/code_review/configs/custom_messages)）。

[自定义代理](/zh/how_to_use/code_review/custom_agents)以及与之关联的技能和文档不属于集中式配置。它们在应用中配置，这些文件中的 `customAgents` 和 `knowledge` 键会被忽略。

最小示例：

```yaml
version: 2.0
reviewOptions:
  bug: true
  security: true
  performance: true
  business_logic: true
suggestionControl:
  severityLevelFilter: medium
  applyFiltersToKodyRules: false
ignorePaths:
  - yarn.lock
  - package-lock.json
automatedReviewActive: true
```

## Kody Rules 文件

每条规则是 `.kody-rules/review/`（标准规则）或 `.kody-rules/memories/`（记忆）下的一个 `.yml` 或 `.yaml` 文件。文件名任意，但 Kodus 通过文件路径关联规则：重命名或移动文件会在下次同步时删除旧规则并创建新规则。`title` 和 `rule` 是必需的；缺少它们或未通过校验的文件会被跳过，同步会报告失败，并且在文件修复之前不会删除已移除的规则。

审查规则示例（`.kody-rules/review/require-tests-for-endpoints.yml`）：

```yaml
title: Require tests for new endpoints
rule: |
  Every new HTTP endpoint handler must include at least one integration test
  that exercises the happy path and one common failure mode.
severity: high
scope: pull-request
path: apps/api/**
examples:
  - snippet: |
      // endpoint added with matching *.spec.ts
    isCorrect: true
  - snippet: |
      // endpoint added with no test file touched in the PR
    isCorrect: false
inheritance:
  inheritable: true
  exclude: []
  include: []
```

已暂停的规则以 `enabled: false` 写入。

完整字段参考请见 [Kody Rules 概述](/zh/how_to_use/code_review/configs/kody_rules)，`inheritance.inheritable`、`exclude` 和 `include` 的行为请见[规则继承](/zh/how_to_use/code_review/configs/rules_inheritance)。

## UI 工作流

在侧边栏中，在 **Code review** 分组顶部的作用域选择器中选择 **Global**，然后
打开 **Code review → General**：

1. 点击页面标题栏中的 **Configure centralized config**（会打开 **Centralized Config**
   对话框）。
2. 打开 **Enable centralized config**。
3. 选择源代码库（**Selected repository**）。
4. 选择 **Initial Sync Method**：
   - Automatic (Create PR now)
   - Manual (Sync later)
5. 点击 **Initialize** 并确认状态。

启用后，对话框会显示源代码库以及以下按钮：

- **Sync Now** 应用集中式代码库的当前内容。
- **Download** 保存配置包（见下文）。
- **Save Changes** 保存您在对话框中所做的更改，例如关闭 **Enable centralized config**。

启用期间无法更改源代码库。要使用另一个代码库，请关闭 **Enable centralized config**，点击 **Save Changes**，然后重新启用。

## 启用后的 Web UI 行为

集中式代码库是真实来源。Web UI 会相应反映：

- Global、代码库和目录作用域的**代码审查设置**在 Web UI 中仍可编辑。每个页面都会显示一条横幅 — "Centralized config is enabled. Changes on this page are saved immediately and proposed through pull requests in the `<repo>` repository. Synchronization reapplies the configuration from that repository." — 当存在已打开的拉取请求时还会显示 **View active pull request**。**Save settings** 会立即在 Kodus 中应用该变更，并在集中式代码库上打开一个包含相同变更的拉取请求。如果该拉取请求未合并就被关闭，下次同步会用代码库中的版本覆盖已保存的设置。该拉取请求打开期间所做的后续更改会添加到其中。您也可以直接编辑集中式代码库中的文件。
- **Kody Rules** 的工作方式不同。创建或编辑规则不会直接修改它：Kodus 会在集中式代码库上打开一个包含建议变更的拉取请求，PR 合并后变更才会生效。

### UI 中的规则与仓库中的规则共存

启用集中式配置**不会**清除之前在 Web UI 中创建的规则，代码库也不必包含它们。两种来源向同一份有效规则池供给：

- 从集中式代码库导入的规则以 `SYNCED` 状态持久化。
- 启用之前在 Web UI 中创建的规则与它们共存，并保持有效。
- 审查时，Kodus 从数据库加载**所有有效规则**，无论其来源。仅存在于 UI 中的规则与仅存在于代码库中的规则被完全同等地应用。
- 状态为 `PENDING_ADD` 的规则（通过 UI/CLI 创建，或由 `init` 导出，且其 PR 尚未合并）会被**排除**在审查之外，直到 PR 被合并且状态转为 `SYNCED`。Kody Rules 列表将 `PENDING_ADD`、`PENDING_EDIT` 和 `PENDING_DELETE` 显示为 **Pending add**、**Pending edit** 和 **Pending delete**。
- 使用 `pr` 方式的 `init` 会把每条尚无文件的现有规则放入初始化 PR 并标记为 `PENDING_ADD`，因此这些规则在该 PR 合并之前不会在审查中运行。

实际情况：如果您手动搭建集中式代码库，而其中缺少一条您已在 UI 中创建的规则，那条规则仍会继续生效 — 只是没有在代码库中进行版本管理。要将其纳入版本管理，请在 UI 中编辑它一次（这会打开一个 PR），或使用 `init` 让 Kodus 将每条现有规则打包进初始化 PR。当 UI 中的规则仍然存在时，请不要手动把规则文件复制到代码库中：同步按文件路径匹配规则，因此该文件会变成一条标题相同的第二条规则。

## 同步状态

每个来自集中式配置的规则通过状态跟踪其生命周期：

| 状态 | 含义 |
|---|---|
| `SYNCED` | Kodus 中的规则与集中式代码库中的文件一致。 |
| `PENDING_ADD` | 通过 UI/CLI 新建了规则并打开了 PR；默认分支上尚无该文件。 |
| `PENDING_EDIT` | 通过 UI/CLI 提出了编辑并打开了 PR；现有文件尚未更新。 |
| `PENDING_DELETE` | 通过 UI/CLI 提出了删除并打开了 PR；文件仍存在于默认分支。 |

对应 PR 合并后，`PENDING_ADD` 和 `PENDING_EDIT` 会变为 `SYNCED`；`PENDING_DELETE` 规则会被删除。如果 Kodus 打开的拉取请求未合并就被关闭，建议的新规则会被拒绝，建议的编辑或删除会被丢弃。

## 下载配置包

在 **Centralized Config** 对话框中点击 **Download**，即可获得一个 ZIP 包，其中包含反映当前设置和规则的 `kodus-config.yml` 文件和 `.kody-rules/` 目录结构。

适用场景：

- 审计已生成的配置。
- 与其他团队共享设置产物。
- 发布前保留本地备份。
- 在 `manual` 模式下初始化集中式代码库。

## 禁用集中式配置

禁用集中式配置会清除所选的源代码库，所有代码库恢复到标准的非集中式行为（通过 Web UI 编辑设置，可选的按代码库 `kodus-config.yml`）。

已同步进来的规则和设置保留在 Kodus 中 — 禁用时不会被删除。

## CLI

使用以下命令在终端工作流和 CI 脚本中管理集中式配置。

### 前置条件

- 已开启 **Allow repository configuration via CLI** 的团队密钥（**Organization → CLI keys → Configure**）。
- Kodus 中至少选择了一个代码库。

在运行 CLI 的环境中设置 `KODUS_TEAM_KEY`。

### 查看状态

```bash
kodus config centralized status
```

### 初始化集中式配置

```bash
kodus config centralized init [owner/repo] --sync-option <pr|manual>
```

说明：

- `--sync-option` 默认为 `pr`。
- 使用 `.` 表示当前目录所在的代码库。
- 在交互式终端中省略代码库时，CLI 会提示选择。
- 非交互式环境下必须提供代码库。

示例：

```bash
kodus config centralized init kodustech/kodus-config --sync-option pr
kodus config centralized init kodustech/kodus-config --sync-option manual
```

### 运行同步

```bash
kodus config centralized sync
```

### 禁用集中式配置

```bash
kodus config centralized disable
```

### 下载配置 ZIP

```bash
kodus config centralized download --out ./centralized-config.zip
```

说明：

- `--out` 是必需的。
- 输出是包含生成的配置文件和 `.kody-rules/` 目录结构的 ZIP 包。

### JSON 输出

所有集中式命令都支持通过 `--json` 输出结构化结果。

```bash
kodus config centralized status --json
kodus config centralized init kodustech/kodus-config --sync-option pr --json
kodus config centralized sync --json
kodus config centralized disable --json
kodus config centralized download --out ./centralized-config.zip --json
```
