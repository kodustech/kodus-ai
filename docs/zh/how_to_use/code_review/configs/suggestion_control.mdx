严重性阈值决定 Kody 的**哪些**发现会被发布。打开 **Code review → What to review**;相关设置位于 **Minimum severity to post** 卡片中。它们可以在全局、代码库和目录范围设置。请参阅[配置继承与覆盖](/zh/how_to_use/code_review/configs/inheritance_overrides)。

## Minimum severity to post

Kody 会为每条发现分配严重性,只发布达到或高于你在滑块上所选级别的发现。默认值为 **Medium**。Kody 仍然会发现较低严重性的问题,只是不会对它们发表评论。

| 级别 | 典型发现 |
| --- | --- |
| **Low/All** | 维护性和外观上的不一致、轻微的冗余工作、错误或具有误导性的日志行。 |
| **Medium**(默认) | 影响有限的缺陷:错误的指标或消息、孤立的请求失败、常规的无效输入处理、有限的安全弱点、仅阻碍开发的 lint 或 CI 失败。 |
| **High** | 对有效输入而言,受支持的路径变得不可用、关键的持久化效果失败、数据被错误销毁,或席位、配额上限等准入控制被绕过。 |
| **Critical** | 存在可行的路径导致身份验证绕过、大范围的未授权管理、攻击者可控的代码执行,或排队中的工作发生系统性丢失。 |

<Tip>
  大型 PR 上噪音过多,通常是严重性的问题,而不是数量的问题。在尝试其他手段之前先调到
  **High** —— 你会保留所有真正的 bug,只丢掉吹毛求疵的部分。
  参见[如何减少代码审查噪音](/zh/knowledge_base/how-to-reduce-code-review-noise)。
</Tip>

来自[编码代理指令](/zh/how_to_use/code_review/configs/rules_file_detection)的发现与其他发现一样遵循该阈值。确定性发现(beta)会以任意严重性发布。自行设置了最低严重性的自定义智能体则使用它自己的设置。

## 对 Kody Rules 应用阈值

同一卡片中的一个开关,**默认关闭**。

- **关闭** —— [Kody Rules](/zh/how_to_use/code_review/configs/kody_rules) 的发现会**绕过**严重性阈值。团队自己编写的规则,无论被判定为何种严重性,都始终会被报告。
- **开启** —— Kody Rules 与其他发现一样,经过相同的阈值。

除非你的规则产生的噪音多于信号,否则请保持关闭。Kody Rule 的意义正在于:团队已经认定这件事很重要。

<Note>
  在 `kodus-config.yml` 中,这些设置位于 `suggestionControl` 之下:

  ```yaml
  suggestionControl:
      severityLevelFilter: 'medium' # low | medium | high | critical
      applyFiltersToKodyRules: false
  ```

  只有开启 **Prefer kodus-config.yml settings** 后才会读取该文件。请参阅
  [General](/zh/how_to_use/code_review/configs/general#config-priority)。
</Note>

## 减少噪音的其他方式

阈值是一把钝刀。当你需要更有针对性的手段时:

- **Ignored files** —— 跳过生成代码、锁文件和 vendored 目录。请参阅
  [General](/zh/how_to_use/code_review/configs/general#ignored-files)。
- **Categories** —— 通过 [What to review](/zh/how_to_use/code_review/configs/what_to_review)
  上对应的开关,关闭整个类别(例如 Performance)。
- **目录级配置** —— 在 monorepo 中按文件夹设置更严格或更宽松的阈值。请参阅
  [目录级设置](/zh/how_to_use/code_review/configs/directory_level)。
- **Kody Rules** —— 写下团队真正在意的东西,让信号来自你们的标准,
  而不是泛泛的建议。
