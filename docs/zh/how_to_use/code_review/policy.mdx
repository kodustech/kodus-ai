## 建议与阻塞

- **建议:** 默认情况下,Kody 发布不会阻塞 PR 的评论。由您决定采纳哪些。
- **对关键问题请求更改(可选):** 当 Kody 发现关键问题时,会将它在 PR 上的审查设为 Request Changes。只有关键发现才会这样做。一旦这些发现被解决,Kody 就会撤回该请求,即使是在它不批准的 PR 上。该设置位于 **Code review → General → Review feedback**。当 GitLab 是您唯一连接的提供方时,该设置不可用。
- **自动批准 PR(可选):** 当审查结果干净时,Kody 会批准该 PR。它从不合并。配合批准策略时,只有符合某个策略的 PR 才会被批准。请参阅[自动批准](/zh/how_to_use/code_review/configs/auto_approve)。

<Note>
  仅当您的团队就阈值达成一致并有强大的 CI 时,才开启阻塞行为。
</Note>

## 什么不会阻塞

- **Kody Code Review 检查**(GitHub App 和 Forgejo)用于报告审查已运行。存在未处理的建议时它也会通过,只有在审查本身无法运行时才会失败。必需检查能保证审查已经发生;它不会因为 Kody 的发现而阻止合并。
- **Business Logic** 会发布一条评论,不产生检查或状态。请参阅[业务逻辑验证](/zh/how_to_use/code_review/business_logic_validation)。
- **Risk assessment** 和 **routing** 会改变 Kody 的审查方式,以及它是否可以批准。它们不会阻止合并。请参阅[风险评估](/zh/how_to_use/code_review/configs/risk)和 [Routing](/zh/how_to_use/code_review/configs/routing)。

## 何时开启请求更改

- 安全敏感区域,关键问题绝不能发布。
- 性能热点,其中回归成本高昂。
- 具有明确编码标准和稳定审查规则的代码库。

## 何时开启自动批准

- 文档或测试等小型、低风险的更改。如果只希望部分 PR 符合条件,请添加批准策略。
- 具有高测试覆盖率和可靠 CI 的团队。

## 人工决策始终很重要

Kody 加速反馈,但不取代人工判断。您的团队决定采用哪些建议以及何时合并。
