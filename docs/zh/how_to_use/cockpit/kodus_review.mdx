title: "Kodus Review"
description: "衡量 Kodus 审查的有效性，并据此采取行动"
---

**Kodus Review** 标签页回答一个问题：*您的团队是否在根据 Kodus 的建议采取行动？*

与 Productivity 标签页（衡量部署频率、PR cycle time 等通用交付指标）不同，Kodus Review 关注的是 Kodus 本身：有多少建议被实施、哪些类别和规则被采纳或被忽略，以及团队在哪些地方提出了异议。

每个图表和表格都遵循页面顶部的**仓库**和**日期范围**筛选器。基于建议的数字涵盖在该范围内**关闭**的 pull request；审查运行的数字（**PRs processed** 和 **Review processing outcomes**）则涵盖在该范围内运行的审查。点击某个类别条形或规则，即可在 [Suggestions](/zh/how_to_use/cockpit/suggestions) 中打开其背后的建议；点击某个仓库行，可让整个 Cockpit 聚焦到该仓库。

## 摘要卡片

| 卡片 | 含义 |
| --- | --- |
| **Implementation rate** | 在该周期内，团队实施的已发送建议的百分比，下方附有数量 |
| **Suggestions sent** | 在该周期内关闭的 PR 上已发送的建议，不含被排除在比率之外的建议（参见 [Not measured](#实施率)） |
| **PRs processed** | 在该周期内至少有一次已完成审查运行（无论成功、失败还是被跳过）的 pull request，以及与上一周期相比的变化（有审查运行数据时显示） |
| **Negative vote rate** | 反应中为 👎 的占比，以及与上一周期相比的趋势。反应少于 10 个时，显示原始计数而不是比率 |
| **Critical suggestions not yet addressed** | 在该周期内关闭的 PR 上，已发送但未被实施的 critical 建议。它同时统计已合并的 PR 和未合并即关闭的 PR，尽管卡片的页脚写的是 "on merged PRs"。实施检查无法判断的建议不会被计入。点击它会跳转到 **Implementation rate by category**，查看哪些主题被忽略 |

有审查运行数据时，卡片之后会有一个 **Review processing outcomes** 图表。它显示 **Reviews processed**（每一次审查运行，因此审查了两次的 PR 会计两次）与上一周期的对比，以及以 **Success**、**Error**（包括带错误结束的运行）或 **Skipped** 结束的运行的每周构成。旁边的列表给出每种结果的数量、占比，以及与上一周期相比的百分点变化。

## 实施率

核心指标。当一条建议在 PR 关闭时的最终状态为 **Implemented** 或 **Partially implemented** 时，即计为**已实施**。

```
Implementation rate = implemented suggestions ÷ sent suggestions
```

范围规则——所有实施率图表均适用：

- 只有**已发送**的建议才会被计入（即实际作为 PR 评论发布的建议）。Kodus 在评论前过滤掉的草稿建议永远不会被计入。
- 建议归属于 **PR 关闭的那一周**，因为只有在 PR 关闭之后，实施状态才最终确定。
- 最近一次实施检查**无法判断**的建议会被排除在比率之外，而不是被计为未实施。这发生在模型调用失败、其回答无法读取或不完整、文件的变更过大而无法放入模型，或只有整个 PR 的 diff 可用时。每周图表会说明有多少被排除，[Suggestions](/zh/how_to_use/cockpit/suggestions) 则在 **Not measured** 状态下列出它们。投票和 Kody Rule 触发仍会统计每一条已发送的建议。

### 逐周对比

每周图表展示趋势，并提供一个切换选项：

- **Overall**：单条实施率折线。
- **By severity**：每个严重程度（critical / high / medium / low）一条折线，从而可以查看更高严重程度的建议是否更容易被实施。没有任何判定的一周会显示为空缺，而不是 0%。

### 按类别和按严重程度

- **Implementation rate by category**：每个建议类别的已发送数与已实施数。点击某个条形可打开按该类别筛选的 Suggestions。
- **Implementation rate by severity**：每个严重程度级别的实施率。预期应呈递减梯度（critical 比 low 实施得更多）。如果看起来持平或倒挂，则说明严重程度并未引导团队行动。

<Warning>
  **严重程度图表上的 "All / Kodus only" 切换很重要。** Kody Rule 携带的是*您*在规则上设置的严重程度，而不是 Kodus 的风险评估。将两者混合会扭曲校准读数：例如，一批采纳率很高的 medium 级 Kody Rules，可能会让 Kodus 看起来低估了 medium 级别。切换到 **Kodus only**，即可查看 Kodus 自身的严重程度校准。基于少于 5 条建议构建的条形会被淡化并标记 `*`：来自寥寥几条建议的 0% 或 100% 并不是真实信号。
</Warning>

## 负面反馈

反馈来自 Kodus 建议评论上的 👍 / 👎 反应，统计的是该周期内关闭的 PR 上的建议。

- **Negative vote rate**（摘要卡片）：`👎 ÷ (👍 + 👎)`，以及与上一周期相比的趋势。越低越好。
- **Negative feedback (👎)** 有两个视图：**By category** 显示团队最不认同的地方（点击某个类别可打开其建议），**Trend** 显示 👎 的逐周变化。带有大量 👎 的类别是重新调优或禁用的候选项。

## 仓库 — 健康状况

按仓库列出的表格，带有搜索框。列：**Repository**、**PRs reviewed**（在该周期内关闭且至少获得一条已发送建议的 PR）、**Suggestions**、**Impl. rate**、**👍 / 👎**，以及 **Weakest category**：该仓库中实施率最低的类别，仅统计至少有 5 条建议的类别。它展示了 Kodus 在哪些地方被采纳，又在哪些地方被忽略。

点击某一行会将整个 Cockpit 聚焦到该仓库（与在仓库筛选器中选择它的效果相同）。

## Kody Rules — 健康状况

展示每条 Kody Rule 在该周期内的表现。列：**Rule**、**Scope**（Global、Repo 或 Folder）、**Triggers**、**Impl. rate**、**👍 / 👎** 和 **Status**。**All / Healthy / Noisy / Ignored / Stale** 标签可筛选该表，搜索框可按名称查找规则。表格列出组织中所有激活的规则。仓库选择器会筛选触发次数，因此不属于所选仓库的规则也可能显示为 **Stale**。激活的 memory 不会产生规则触发，也可能显示为 **Stale**。根据该状态决定是否保留规则前，请检查规则的作用域并清除仓库筛选。

点击某一行会打开该规则产生的建议。

状态按规则计算，并依照以下优先级顺序：

| 状态 | 含义 | 建议操作 |
| --- | --- | --- |
| **Stale** | 在该周期内没有任何触发 | 重新评估该规则是否仍有必要 |
| **Low data** | 有触发，但次数过少（少于 5 次）而无法判断 | 等待更多数据 |
| **Noisy** | 团队主动给它投反对票（≥ 3 个 👎、👎 多于 👍，且每 10 次触发至少有一个 👎） | 该规则校准有误：重写或限定其范围（例如排除测试） |
| **Ignored** | 触发很多次但几乎没有被实施（≤ 20%） | 质疑其相关性：团队是否真的在意它？ |
| **Healthy** | 其他所有情况 | 无需操作 |

**Noisy** 与 **Ignored** 看起来相似，但需要采取的行动不同。*Ignored* 是被动的：规则触发了但没人实施，您无法判断它是噪音还是单纯被忽视。*Noisy* 是主动的异议：团队明确给它投了反对票，所以您知道它就是噪音。这就是为什么一条同时符合两者的规则会显示为 **Noisy**：反对票是更强、更可执行的信号。

## Suggestions

每一次深入查看都会打开 [Suggestions](/zh/how_to_use/cockpit/suggestions)：一个可筛选的列表，展示数字背后的实际建议。
