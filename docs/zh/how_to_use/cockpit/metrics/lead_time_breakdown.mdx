## 什么是交付时间细分

交付时间细分将从 PR 的第一次提交到其关闭的时间拆分为三个阶段：编码时间、拾取时间和审查时间。它显示您的工作流在哪里变慢。

在 Cockpit 中，它是 **Productivity** 标签页上的 **Lead Time Breakdown** 图表：每周一个堆叠条形，以小时为单位显示 **Coding Time**、**Pickup Time** 和 **Review Time**。点击图表下方的名称可隐藏或显示该阶段。

## 我们如何计算

```
Coding Time = (Last Commit Time) - (First Commit Time)
Pickup Time = (PR Opened Time) - (Last Commit Time)
Review Time = (PR Closed Time) - (PR Opened Time)
```

- **Coding Time**：从 PR 的第一次提交到最后一次提交，包括在 PR 打开之后推送的提交。
- **Pickup Time**：从最后一次提交到 PR 被打开。对于在打开之后又有新提交的 PR，该值为负数。
- **Review Time**：从 PR 被打开到其被关闭（无论是否合并）。

对于每一周，每个阶段都是该周关闭的 PR 的第 75 百分位数（P75），因此异常长的离群值不会扭曲它。某个阶段的值恰好为零的 PR（例如只有一次提交的 PR 的编码时间）会被排除在该阶段的 P75 之外。只有在 PR 打开之前 30 天内提交的提交才会被计入，因为变基分支上更早的提交通常属于其他工作。没有提交数据的 PR 会被排除。

第一次提交之前的时间（规划、设计）和关闭之后的时间（部署）不会被计入。

## 为什么重要

了解时间花在哪里，可以帮助您优化流程中正确的部分：

- **Coding Time**：显示开发效率
- **Pickup Time**：揭示从完成代码到请求审查之间的工作流瓶颈
- **Review Time**：指示审查过程的有效性

## 如何改进

### 减少编码时间
- 在工作开始之前明确需求
- 将大型功能分解为可管理的部分
- 针对复杂问题结对编程

### 减少拾取时间
- 完成代码后立即打开 PR
- 自动化 PR 的创建和设置
- 定义代码何时准备好进行审查

### 减少审查时间
- 为审查者设定清晰的期望
- 使用自动化检查在审查前捕获问题
- 在团队中分摊审查工作量
- 及时响应审查评论
- 保持 PR 较小
