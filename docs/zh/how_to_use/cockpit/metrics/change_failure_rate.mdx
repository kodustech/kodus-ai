## 什么是 Bug 比率

Bug 比率是已关闭的 pull request 中属于 bug 修复的百分比。它显示您的交付中有多少用于修复问题，而不是构建功能。

在 Cockpit 中，它是 **Productivity** 标签页上的 **Bug Ratio** 卡片。它不是 DORA 的变更失败率：它统计的是 bug 修复 PR，而不是失败的部署。

## 我们如何计算

后台作业会让 AI 模型**仅根据标题**将每个 pull request 分类为 **Bug Fix**、**Feature**、**Refactor** 或 **Test**。不会使用 PR 描述、标签和 diff，也没有任何需要配置的内容。

```
Bug Ratio = (PRs classified as Bug Fix) ÷ (PRs closed in the range) × 100
```

范围是在 Cockpit 顶部选择的日期范围，已关闭的 PR 指已合并或未合并即关闭。尚未被分类的 PR 会计入总数，但不计为 bug 修复。例如，如果 15 个 PR 中有 3 个被分类为 bug 修复，则您的 Bug 比率为 20%。

当所选范围和上一周期的比率均为 0% 时，卡片会显示 **Once we have enough data, your metrics will appear here.**，而不是 0%。

## 读懂卡片

卡片显示百分比、一个级别徽章，以及相同长度的上一周期的值和百分比变化（越低越好）。无论选择了哪个范围，页脚都显示 "Last 2 weeks was …"；该数字对应的是上一周期。将鼠标悬停在徽章上可查看各级别：

| Bug 比率 | 级别 |
| --- | --- |
| 低于 5% | Elite |
| 5% 到 10% | High |
| 10% 到 20% | Fair |
| 高于 20% | Need focus |

## PR 标题为何重要

由于只读取标题，描述性强的标题会给出更准确的比率。

| 良好的 bug 修复标题 | 模糊的标题 |
| --- | --- |
| "Fix: User login fails with invalid credentials" | "Fix stuff" |
| "Resolve issue: API returns 500 error for large requests" | "Update code" |
| "Patch: Fix null pointer exception in user service" | "Improve performance" |

## 如何改进

- 在单元、集成和端到端层面进行更多测试
- 在生产前使用 linter 和静态分析器
- 将大型功能分解为更小的可测试部分
- 使用功能标志进行更安全的部署
- 进行事后审查以防止问题再次发生
