代码审查通常关注安全、性能和代码风格。业务逻辑验证则检查代码是否实现了业务需求。

## 检查内容

Kody 会找到 PR 引用的任务，从任务跟踪工具读取内容，并在一条持续更新的 PR 评论中列出每项需求的实现状态：

| 状态 | 含义 |
|---|---|
| **MET** | PR 的改动已实现该需求。 |
| **PARTIAL** | 仅实现了部分需求。 |
| **MISSING** | PR 的改动中找不到实现依据，或 PR 依赖的代码未实现该需求。 |
| **CHECK MANUALLY** | 涉及视觉效果或操作流程，或者仅凭代码无法判断。 |
| **NOT IN TASK** | 任务未要求此项改动。 |

每行都会引用作为依据的文件和行号，并给出修改建议。

## 使用方法

### 自动验证（默认）

连接任务跟踪工具，并在 **Code review → What to review** 中开启 **Business Logic**（默认开启）。如果 PR 标题、分支名或描述引用了任务，Kody 会在第一次审查时验证。可使用 `PROJ-123` 或任务链接。引用 Git Issue 时，可在标题或分支名中使用 `#123`，或在描述中写 `Closes #123`。之后，你可以要求 Kody 重新检查。开启 **Re-check after a push** 后，每次推送都会重新检查。

### 按需验证

在 PR 的常规评论区留言：

```
@kody -v business-logic https://kodustech.atlassian.net/browse/KC-1292
```

```
@kody -v business-logic
Orders above $500 must issue cashback credits.
Discount codes cannot be combined with loyalty rewards.
Free shipping applies only to domestic orders.
```

如果命令后没有指定任务，Kody 会重新检查 PR 引用的任务。如果提供至少 40 个字符的需求说明，Kody 会按说明检查 PR，无需连接任务跟踪工具。

## 支持的任务来源

在[插件](/zh/how_to_use/code_review/plugins)中连接任务跟踪工具。Kody 只按 ID 读取任务。

| 来源 | 引用方式 |
|--------|-----------------|
| **Linear** | Issue 编号（`TEAM-123`）或链接 |
| **Jira**（Atlassian Rovo） | 工单编号（`PROJ-123`）或链接 |
| **Notion** | 页面链接 |
| **Git Issues** | GitHub、GitLab、Bitbucket 或 Forgejo 上的 `#123`、`owner/repo#123` 或 Issue 链接 |
| **其他跟踪工具**（如 ClickUp） | 使用自定义插件。如果插件名称无法表明它是任务跟踪工具，请将它设为 **Task source**。 |
| **内联需求** | 在 PR 评论中写明需求 |

## 提示

- 在任务中写清验收标准，验证结果会更全面。
- 修复缺口后，再次评论 `@kody -v business-logic`。Kody 会更新原有评论。
- PR 实现整个任务时，写 **Closes PROJ-1**。只实现其中一部分时，写 **Part of PROJ-1**。
- 如果任务只有标题，Kody 会请你补充验收标准。

详见[业务逻辑验证](/zh/how_to_use/code_review/business_logic_validation)。
