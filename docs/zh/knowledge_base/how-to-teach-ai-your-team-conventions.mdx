每个团队都有不成文的上下文 — 技术偏好、命名约定、架构决策、迁移中的特殊情况。你不需要一开始就把这些全部文档化,可以通过自然对话教给 Kody,这样未来的审查会更贴合实际,也能减少那些重复出现的无用建议。

## 工作原理

当你在 PR 评论中让 Kody 记住某些内容时,它会将其保存为**记忆**。当你只是陈述代码库上下文或团队偏好时,Kody 会主动提出保存,并在你同意后保存。这些记忆随后会作为高优先级上下文用于之后的代码审查和对话中。

### 显式教学

直接告诉 Kody 记住某些内容:

```
@kody remember: this repo mirrors a third-party API, so some payload fields intentionally stay snake_case.
```

```
@kody please remember: this service follows hexagonal architecture and keeps adapters at the edge.
```

### 陈述约定

陈述一个约定,或解释某条建议为何不适用,Kody 会主动提出将其保存为记忆。回复 `@kody yes` 即可保存。例如:

```
@kody this repo mirrors a third-party API, so some payload fields intentionally stay snake_case.
```

```
@kody in this service, tests usually live next to the implementation files rather than in a central test folder.
```

```
@kody the billing module is mid-migration, so prefer incremental fixes over broad refactors.
```

## Kody 不会保存的内容

Kody 对成为记忆的内容有选择性:

- 临时指令("立即修复"、"今天跳过")
- 问题("截止日期是什么?")
- 调试对话("我看到一个错误")
- 没有可操作信息的模糊陈述
- 限定于单个 PR 或任务的请求

## 记忆范围

每条记忆应用于特定级别:

| 范围 | 示例 |
|------|------|
| **Directory** | "在 `src/components/ui` 中,始终使用我们的设计系统令牌" |
| **Repository** | "这个代码库使用六边形架构" |
| **Organization** | "所有代码库使用 ESLint flat config" |

## 审批工作流

如果您想在 Kody 创建的记忆生效之前进行审查,请打开 **Code review → Kody Rules**,点击 **Configuration**,并开启 **Kody knowledge approval**。新的记忆(以及 Kody 生成的规则)将在 **Pending review** 部分等待,直到您 **Approve** 或 **Discard** 它们。您使用 **New memory** 编写的记忆会立即生效。

## 管理记忆

前往 **Code review → Kody Rules** → **Memories** 选项卡以查看、编辑或删除记忆。您也可以使用 **New memory** 手动创建记忆。

更多详情,请参阅 [Kody Rules — 记忆](/zh/how_to_use/code_review/configs/kody_rules#记忆)。
