---
title: "如何在代码审查中使用关联代码库获得跨代码库上下文"
description: "关联兄弟代码库,使 Kody 在 PR 触及边界表面时能读取服务间的契约与 API。"
---

当产品拆分在多个代码库中时——例如调用后端 API 的前端,或依赖共享契约包的服务——仅审查单个代码库可能会漏掉边界上的破坏。**关联代码库**(*linked repositories*)在代码审查期间为 Kody 提供这些兄弟代码库的可选、按需上下文。

> **套餐要求:** 关联代码库适用于 **Teams** 和 **Enterprise** 套餐,以及试用期间。Free 套餐不包含跨代码库上下文。自托管需要 Enterprise 许可证。

这与[跨代码库共享编码标准](/zh/knowledge_base/how-to-share-standards-across-repositories)(组织级规则与继承)不同。关联代码库共享的是审查用的**源码上下文**,而不是审查规则。

## 它做什么

对于正在审查的代码库,您可以在同一组织中声明最多 **3 个关联代码库**。审查过程中:

1. Kody 首先检查 PR diff 是否触及任何具有边界特征的内容 — 这是一个快速、固定且不产生成本的检查。
2. 若 diff 看起来触及**契约表面**(DTO、export、字符串字面量、状态键、类 API 路径等),则启用跨代码库工具。
3. 仅当 Kody 真正需要读取或搜索时,才**懒克隆**关联代码库。
4. 发现仍**只锚定在当前审查的 PR 的行上** — 关联代码是证据,不是第二个审查目标。

若未配置任何关联,该功能完全关闭(零额外成本)。

## 在控制台中配置

关联代码库是**按代码库**的,不是全局的。关系是有方向的:`frontend` 上的关联仅在审查 `frontend` 的 PR 时生效。

1. 在侧边栏 **Code review** 分组顶部的范围选择器中,选择一个**具体的代码库**(不是 Global)。
2. 打开 **Linked repositories**(仅在代码库范围下显示)。
3. 点击 **Add repository**,选择已连接到您组织的兄弟代码库。
4. 可选地,点击某个关联进行设置:
   - **Instructions · optional** — 给 Kody 的自由文本提示(例如"此前端消费的 REST API")。
   - **Branch / ref pin · optional** — 分支/标签固定。留空则使用自动 ref 级联(见下)。
5. 点击 **Save settings**。

最多可关联 **3** 个代码库。仅接受已连接到同一组织的代码库。

## 在 `kodus-config.yml` 中配置

也可以在代码库配置文件中声明关联:

```yaml
linkedRepositories:
  - repository: "org/backend-api"
    instructions: "REST API this frontend consumes"
    ref: main   # optional pin; omit for same-branch cascade
```

- `repository`(必填):已连接到组织的代码库全名(`owner/repo`)。
- `instructions`(可选):简短说明关联原因。
- `ref`(可选):固定分支、标签或提交。省略时 Kody 使用 ref 级联。

空的 `linkedRepositories: []` 表示功能关闭。仅当该代码库开启了 **Prefer kodus-config.yml settings**(**Code review → General**)时才会读取该文件,并且其中的列表会替换在 Web 应用中设置的列表。参见[设置参考](/zh/how_to_use/code_review/configs/linked_repositories#在-kodus-config-yml-中)。

## 如何选择 ref

对每个关联代码库,Kody 按以下顺序尝试 ref,并使用第一个成功克隆的:

1. 该代码库的 **PR 描述覆盖**(见下)
2. **配置中的 `ref` 固定**(若已设置)
3. 关联代码库上 head 分支与 PR head 分支匹配的**打开中的 PR**
4. 关联代码库上的 **PR head 分支名**
5. 关联代码库的**默认分支**
6. 回退:`main`,然后 `master`

这使跨服务存在同名分支时的多代码库功能工作保持对齐,同时在普通 PR 上安全回退。

## 通过 PR 描述覆盖 ref

对于一次性审查(例如对照某个后端 PR 审查),在正在审查的 PR 的**标题或描述**中提及关联代码库。覆盖仅适用于配置中**已经关联**的代码库。

支持的形式:

| 形式 | 含义 |
| --- | --- |
| `owner/repo#123` | 使用该代码库上 PR/MR `#123` 的 head |
| PR/MR URL | 同上,适用于 `github.com`、`bitbucket.org`、`dev.azure.com` 上的 URL,或名称中含 `gitlab` 的主机 |
| `owner/repo@branch` | 在关联代码库上固定该分支 |

示例:

```text
Depends on org/backend-api#842
Also needs org/shared-contracts@feature/new-events
```

每个关联代码库只提及一次。如果有多处提及,`owner/repo@branch` 固定无论出现在哪里,都优先于 PR 引用;同一形式的多处提及中,以最后一处为准。提及**未**关联的代码库会被忽略(不会创建新关联)。

## 何时激活跨代码库上下文(边界门控)

即使已配置关联,Kody **也不会**总是打开兄弟代码库。一个廉价的确定性门控会扫描 PR diff 中的**新增行**,仅在发现**边界表面**时激活,例如:

- 字符串字面量(路径片段、代码、事件名等)
- export(`export function`、类型、类等)
- enum / type / interface
- 对象或 payload 字段键
- status / state / error-code 类标识符
- 类契约路径(`dto`、`schema`、`api`、`client`、`openapi`、`proto` 等)

仅移动或重排非边界代码的内部重构通常保持门控关闭——克隆与边界提示保持空闲。

## Kody 对关联代码库能做什么、不能做什么

**可以:**

- 在门控开启时搜索并读取关联代码库中的文件
- 使用您的 **instructions** 理解关系
- 在当前 PR 的发现中将关联代码作为支持证据引用

**不能 / 不会:**

- 对仅存在于关联代码库中的文件发布审查评论
- 把整个关联代码库当作 PR 来审查
- 关联组织外或未连接到 Kodus 的代码库
- 每个审查代码库使用超过 3 个关联代码库(在 `kodus-config.yml` 中,第三个之后的条目会被丢弃)

## 审查中会显示什么

当 Kody 读取了关联代码库时,它在审查结束时发布的评论会包含 **Additional context used:**,以及它读取的代码库和 ref,例如 `org/backend-api@main` 或它使用的打开中的 PR。没有这一行表示没有读取任何关联代码库。无法获取或未连接到组织的关联会被跳过,审查会在没有它的情况下继续。

## 推荐设置

| 场景 | 从何处关联 | 典型 instructions |
| --- | --- | --- |
| 前端 ↔ 后端 | 前端 → 后端 API 代码库 | "此 UI 依赖的 HTTP/REST 客户端契约" |
| 服务 ↔ 共享契约 | 服务 → contracts/package 代码库 | "共享事件、DTO 与 protobuf" |
| BFF ↔ 多个后端 | BFF → 最多 3 个后端代码库 | 每个服务边界一行简短说明 |

优先使用**窄、有方向**的关联(消费者指向生产者),而不是把所有代码库互相连起来。
