## Por qué esta guía es importante

Todos los equipos de ingeniería tienen en algún lugar un documento de "mejores prácticas". El problema es que las sugerencias del IDE no lo leen, los revisores olvidan los matices y el documento pierde autoridad progresivamente. Esta guía convierte tu manual en reglas activas, para que Kody las aplique en cada pull request y señale la sección que se desvió.

Usaremos dos elementos fundamentales:

- [Kody Rules](/es/how_to_use/code_review/configs/kody_rules) – cada punto de política se convierte en una verificación a nivel de archivo o de PR que referencia el manual.
- [Agentes personalizados](/es/how_to_use/code_review/custom_agents) – el manual se vincula como doc, y cada hallazgo cita la regla que aplica.

## Lista de verificación previa

- Tienes permiso para editar **Code review → Kody Rules**.
- El manual vive en el repositorio (p. ej., `docs/engineering-standards.md`). Si el tuyo está en otra ruta, ajusta en consecuencia.
- Sabes qué temas deben evaluarse a nivel de archivo (controladores, configs) versus a nivel de PR (feature flags, narrativas de despliegue, arquitectura).

<Callout icon="layers">
  Mantén el manual bajo control de versiones. Las reglas y los agentes lo leen de la rama a la que apunta un pull request, así que cada edición pasa por un pull request con responsables que dan su aprobación.
</Callout>

## Fase 1 – Da forma a un paquete de políticas compatible con reglas

1. Crea o reutiliza un archivo markdown como `docs/engineering-standards.md`.
2. Organiza el contenido en puntos cortos y verificables:

```md
# Engineering Standards

## Error handling
- Never swallow errors.
- Do not log PII or secrets.
- External requests must have a timeout and retry policy.

## Architecture
- No direct cross-module imports from `domain/*` into `web/*`.
- New endpoints must include tracing fields (e.g., requestId) and structured logs.
- Feature flags are mandatory for risky changes.
```

<Tip>
  Haz que cada punto sea atómico. Cuando se active una regla, no debe haber debate sobre qué hay que cambiar.
</Tip>

## Fase 2 – Apunta cada regla al documento real

Referencia el manual real en lugar de pegar fragmentos en cada instrucción.

```text
Use @file:docs/engineering-standards.md (Architecture section) as the policy source.
Only flag code that clearly violates those bullets. If the section is missing, say so.
```

- Intercambia otras rutas de archivos para paquetes específicos de dominio (p. ej., `@file:docs/mobile.md`).
- ¿Solo necesitas una parte del archivo? Añade anclas de línea, como `@file:docs/engineering-standards.md#L40-L72`, para que la regla consuma solo esa sección.

<Callout icon="link">
  Una sola referencia mantiene todo sincronizado. Actualiza el manual una vez y cada regla aplica la versión más reciente.
</Callout>

## Fase 3 – Traduce las secciones a Kody Rules

En la barra lateral, abre **Code review → Kody Rules**. En la pestaña **Review Rules**, haz clic en **New rule** y mapea cada sección de política al modo de ejecución y la ruta apropiados.

| Sección de política    | Modo de ejecución | Ejemplo de ruta                    | Severidad |
| ---------------------- | ----------------- | ---------------------------------- | --------- |
| Manejo de errores      | Por archivo       | `backend/**/*.ts`                  | Alta      |
| Arquitectura           | Por PR            | no aplica                          | Crítica   |
| Logging y trazabilidad | Por archivo       | `web/apps/**/controllers/**/*.ts`  | Media     |
| Seguridad / PII        | Por archivo       | `**/*`                             | Crítica   |

### Ejemplo a nivel de archivo

```
Rule name: Enforce tracing fields on new endpoints
Execution mode: Per file
Path: web/apps/**/controllers/**/*.ts
Severity: High
Instructions:
  Compare fileDiff with Architecture → New endpoints in @file:docs/engineering-standards.md.
  Flag handlers that lack requestId tracing AND structured log statements.
  Quote the diff chunk that violates the policy.
```

### Ejemplo a nivel de PR

```
Rule name: Require feature flags for risky changes
Execution mode: Per PR
Severity: Critical
Instructions:
  Scan pr_files_diff for routes/services/domain files that add major functionality.
  If no feature flag file is touched, cite “Architecture → Feature flags are mandatory” and request the rollout plan.
```

<Info>
  Las reglas comprenden variables (`fileDiff` por archivo, `pr_files_diff` y las demás variables `pr_*` por PR) y referencias a archivos. Consulta la lista completa en la [guía de Kody Rules](/es/how_to_use/code_review/configs/kody_rules).
</Info>

## Fase 4 – O entrega el manual a un agente personalizado

Un agente personalizado lee el manual como un doc vinculado y debe citar la regla detrás de cada hallazgo. Una cita que no esté en el doc de la rama de destino se descarta. Los agentes personalizados están en beta, en los planes Teams y Enterprise y durante el trial; Kodus self-hosted también necesita `BETA_FEATURES=true`.

<Steps>
  <Step title="Crea el agente">
    En **Code review → What to review → Custom agents**, haz clic en **New agent → Templates → Blank**. Ponle el nombre **Engineering standards**.
  </Step>
  <Step title="Vincula el manual">
    En **Files & knowledge → Skills & docs**, haz clic en **Add skill or doc → Add by path** e ingresa `docs/engineering-standards.md`. Un doc se carga completo en cada revisión, así que mantenlo corto. Un manual largo funciona mejor como una skill con archivos de referencia.
  </Step>
  <Step title="Escribe las instrucciones">
    ```text
    Flag changes that break a rule in docs/engineering-standards.md.
    Quote the rule you apply. Ignore tests and generated code.
    ```
  </Step>
  <Step title="Pruébalo y luego actívalo">
    Ejecuta **Try it** en un pull request que infrinja una regla. Cada comentario cita la regla como **Rule** (`docs/engineering-standards.md`) con el punto citado.
  </Step>
</Steps>

Consulta [Skills, docs y herramientas](/es/how_to_use/code_review/custom_agents_knowledge_and_tools) para los presupuestos y la detección.

## Fase 5 – Prueba, observa y mantén vivo el sistema

<AccordionGroup>
  <Accordion title="Crea un PR de verificación">
    Crea un PR desechable que infrinja cada sección y deja que Kody lo revise (comenta `@kody start-review` si no ha empezado). Verifica que los comentarios en línea y a nivel de PR citen los puntos correctos. Ejecuta el agente a demanda con `@kody -v engineering-standards`.
  </Accordion>
  <Accordion title="Ajusta el ruido y la severidad">
    Durante el despliegue, observa con qué frecuencia se activa cada regla. Ajusta los globs de archivos, añade exclusiones o modifica la severidad hasta que la señal cumpla las expectativas.
  </Accordion>
  <Accordion title="Actualiza documentación y reglas juntas">
    Cuando el manual cambie, actualiza el markdown y las reglas o instrucciones del agente relacionadas en el mismo PR para que los revisores puedan validar todo el pipeline.
  </Accordion>
</AccordionGroup>

## Lista de verificación rápida

- [ ] `docs/engineering-standards.md` existe con puntos fáciles de analizar.
- [ ] Cada regla referencia el paquete de políticas con `@file`, para que lea el texto más reciente.
- [ ] Kody Rules a nivel de archivo y de PR cubren tus secciones críticas.
- [ ] Opcional: un agente personalizado sigue el manual y lo cita.
- [ ] Un PR de prueba confirmó los comentarios en línea y el resumen del PR antes del despliegue general.
