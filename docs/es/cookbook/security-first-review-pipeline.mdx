## Por qué un pipeline enfocado en seguridad

La revisión de código genérica detecta problemas de estilo y errores. Pero las vulnerabilidades de seguridad — inyección SQL, secretos hardcodeados, patrones de autenticación inseguros — necesitan reglas dedicadas que traten los hallazgos como bloqueadores críticos.

Este cookbook configura una capa de seguridad prioritaria sobre tu revisión existente.

## Paso 1 — Habilita el análisis de seguridad

Asegúrate de que la categoría **Security** esté activada en **Code review → What to review**, o en `kodus-config.yml` (se lee solo cuando **Prefer kodus-config.yml settings** está activado para el repositorio):

```yaml
reviewOptions:
  security: true
```

Esto te da las verificaciones de seguridad integradas de Kodus. Las reglas a continuación añaden las políticas de seguridad específicas de tu equipo por encima.

## Paso 2 — Crea reglas enfocadas en OWASP

Crea cada regla en **Code review → Kody Rules**: en la pestaña **Review Rules**, haz clic en **New rule** y completa los campos como se muestra a continuación.

### Prevención de inyección SQL

```
Rule name: No raw SQL queries
Execution mode: Per file
Path: **/*.ts, **/*.js, **/*.py
Severity: Critical
Instructions:
  Flag any use of string concatenation or template literals
  to build SQL queries. Look for patterns like:
  - `query("SELECT ... " + variable)`
  - `query(\`SELECT ... ${variable}\`)`
  - `execute(f"SELECT ... {variable}")`
  Must use parameterized queries or an ORM instead.
```

### Detección de secretos hardcodeados

```
Rule name: No hardcoded secrets or credentials
Execution mode: Per file
Path: **/*
Severity: Critical
Instructions:
  Flag any string that looks like an API key, password,
  token, or secret in fileDiff. Patterns to catch:
  - Variables named *_KEY, *_SECRET, *_TOKEN, *_PASSWORD
    assigned to string literals
  - Strings matching patterns like "sk_live_", "ghp_",
    "AKIA", "Bearer " followed by a long string
  - Connection strings with embedded passwords
  Secrets must come from environment variables or a vault.
```

### Omisión de autenticación

```
Rule name: Auth middleware must not be skipped
Execution mode: Per PR
Severity: Critical
Instructions:
  Check pr_files_diff for any route or controller that
  handles user data without auth middleware. Look for:
  - New routes without @UseGuards, @Authenticated,
    or equivalent decorators
  - Middleware bypass patterns like skipAuth: true
  - Public endpoints that access user-specific data
  Reference @file:src/shared/auth/guards/auth.guard.ts for the
  approved auth patterns.
```

### Prevención de XSS

```
Rule name: No dangerouslySetInnerHTML without sanitization
Execution mode: Per file
Path: **/*.tsx, **/*.jsx
Severity: Critical
Instructions:
  Flag any use of dangerouslySetInnerHTML in fileDiff.
  If used, verify the input is sanitized with DOMPurify
  or an equivalent library. Unsanitized HTML injection
  is a critical XSS vulnerability.
```

## Paso 3 — Enseña Memorias de seguridad

Crea convenciones persistentes que apliquen en todas partes:

```
@kody remember: all user input must be validated and sanitized
before use. Never trust client-side data.
```

```
@kody remember: all API endpoints that handle sensitive data
must use HTTPS only and include rate limiting.
```

```
@kody remember: error messages must never expose stack traces,
internal paths, or database details to the client.
```

## Paso 4 — Configura para tolerancia cero

Para las reglas de seguridad, querrás que los hallazgos críticos bloqueen y que nunca se filtren:

1. En **Code review → General → Review feedback**, activa **Request changes on critical issues** (no disponible cuando todos los proveedores conectados son GitLab). Kody marca la revisión como Request Changes cuando publica un comentario inline Critical
2. Configura las reglas de seguridad en severidad **Critical**
3. En **Code review → What to review**, deja **Apply the threshold to Kody Rules** desactivado, que es su valor por defecto. Las reglas entonces se publican con cualquier severidad, sea cual sea **Minimum severity to post**

Request changes sigue a los comentarios inline, por lo que lo establecen las reglas **Per file**. Una regla **Per PR**, como la del middleware de autenticación, publica un único comentario en el pull request y no lo establece.

## Lista de verificación

- [ ] Categoría **Security** activada
- [ ] La regla de inyección SQL cubre todo el código que interactúa con BD
- [ ] La regla de detección de secretos cubre todos los tipos de archivo
- [ ] La regla de omisión de auth referencia tus patrones de auth reales
- [ ] La regla de XSS cubre todos los archivos de componentes frontend
- [ ] Las Memorias de seguridad enseñan principios generales de codificación segura
- [ ] **Request changes on critical issues** está activado, y **Apply the threshold to Kody Rules** está desactivado
- [ ] Un PR de prueba confirmó que las reglas se activan correctamente

Para más información sobre la configuración de reglas, consulta [Kody Rules](/es/how_to_use/code_review/configs/kody_rules).
