## El desafío

En un monorepo, distintos paquetes tienen distintos estándares. Tu frontend en React se preocupa por los patrones de componentes, tu backend en NestJS se preocupa por la inyección de dependencias, y tus libs compartidas se preocupan por la estabilidad de la API. Una revisión única para todo no funciona.

## Descripción general de la estrategia

Kodus admite tres niveles de configuración que se mapean de forma natural a un monorepo:

| Nivel | Aplica a | Ejemplo |
|-------|---------|---------|
| **Global** | Todos los repos | "Nunca commitear archivos `.env`" |
| **Repositorio** | El monorepo | "Usar conventional commits" |
| **Directorio** | Un paquete específico | "Los componentes React deben usar PascalCase" |

## Paso 1 — Mapea tus paquetes

Identifica las áreas distintas de tu monorepo y sus necesidades de revisión:

```
monorepo/
├── apps/
│   ├── web/          → React rules, component patterns
│   ├── api/          → NestJS rules, architecture boundaries
│   └── mobile/       → React Native rules
├── libs/
│   ├── shared/       → API stability, breaking change detection
│   └── ui/           → Design system compliance
└── infra/            → Terraform/IaC rules
```

## Paso 2 — Crea alcances de directorio

Elige el monorepo en el selector de alcance en la parte superior del grupo **Code review**, abre el selector otra vez y elige **Add directory scope**. En **Select directories**, elige una o más carpetas de paquetes que compartan la configuración de revisión y luego haz clic en **Add directory scope**. Cada alcance de directorio aparece con sangría bajo el repositorio en el selector; selecciónalo para configurarlo.

Cada alcance de directorio puede tener su propia:
- **Kody Rules** (a nivel de archivo y de PR)
- **What to review** (qué categorías habilitar y la severidad mínima para publicar)
- **Custom agents**, que se suman a los del repositorio
- **Ignored files** (en **General**)

Un pull request usa la configuración de un directorio cuando toca ese directorio configurado y ningún otro directorio configurado. Consulta [Configuración a nivel de directorio](/es/how_to_use/code_review/configs/directory_level) para ver cómo un pull request elige su configuración.

## Paso 3 — Escribe reglas específicas

En **Code review → Kody Rules**, pestaña **Review Rules**, haz clic en **New rule**. Una regla creada en un alcance de directorio no tiene **Path**, así que se aplica a todos los archivos de un pull request revisado con la configuración de ese alcance de directorio. Un pull request que toca dos o más alcances de directorio, o ninguno, se revisa con la configuración del repositorio, y entonces las reglas de **todos** los alcances de directorio se aplican a todos sus archivos. Escribe las reglas de directorio de modo que sigan siendo válidas en ese caso, por ejemplo nombrando la carpeta en las instrucciones. Consulta [Herencia de reglas](/es/how_to_use/code_review/configs/rules_inheritance). Para apuntar a una parte de un paquete, crea la regla en el alcance del repositorio con un glob en **Path**.

### Regla de frontend (alcance: el monorepo, con una ruta)

```
Rule name: React components must use design system tokens
Execution mode: Per file
Path: apps/web/src/components/**/*.tsx
Severity: High
Instructions:
  Check fileDiff for hardcoded colors, spacing, or font sizes.
  Components must import tokens from @file:libs/ui/src/tokens.ts.
  Flag any hex color, pixel value, or font-size not from the token file.
```

### Regla de backend (alcance: el directorio `apps/api/`)

```
Rule name: Domain layer must not import from infrastructure
Execution mode: Per file
Severity: Critical
Instructions:
  In files under apps/api/src/domain, check fileDiff for any import from
  "../infrastructure", "../../infrastructure", or any path containing
  "/infrastructure/". Domain modules must only depend on other
  domain modules and shared interfaces.
```

### Regla de librería compartida (alcance: el directorio `libs/shared/`)

```
Rule name: Public API changes require changeset
Execution mode: Per PR
Severity: High
Instructions:
  If pr_files_diff modifies any file in libs/shared/src/index.ts
  or adds/removes exports, check that a changeset file exists
  in the .changeset/ directory. If missing, flag it as a
  potential breaking change without documentation.
```

## Paso 4 — Usa Memorias para convenciones transversales

Algunas convenciones aplican en todas partes. Enséñalas como Memorias:

```
@kody remember: in this monorepo, all packages use ESM imports.
CommonJS require() is not allowed anywhere.
```

```
@kody remember: shared libs must maintain backward compatibility.
Any breaking change requires a major version bump and a changeset.
```

## Paso 5 — Define el umbral de severidad por directorio

Los paquetes con mucho tráfico pueden necesitar filtros más estrictos. Selecciona el directorio en el selector de alcance, abre **What to review** y define **Minimum severity to post**:

- **apps/web/** — **Medium** (el frontend avanza rápido)
- **libs/shared/** — **Low/All** (la estabilidad importa)
- **infra/** — **High** (menos, pero críticas)

El umbral se aplica a Kody Rules solo cuando **Apply the threshold to Kody Rules** está activado.

## Paso 6 — Ignora rutas generadas

Añade ignorados específicos del monorepo para evitar ruido: en **Code review → General → Review scope**, haz clic en **Edit** bajo **Ignored files**, o defínelos en `kodus-config.yml` (se lee solo cuando **Prefer kodus-config.yml settings** está activado para el repositorio):

```yaml
ignorePaths:
  - "**/node_modules/**"
  - "**/dist/**"
  - "**/build/**"
  - "**/*.generated.ts"
  - "**/prisma/migrations/**"
  - "**/coverage/**"
```

## Consejos

- Comienza con 2-3 reglas por directorio y amplía según lo que tu equipo realmente marque en las revisiones
- Usa la herencia de reglas — las reglas a nivel de organización cubren seguridad, las de repositorio cubren convenciones, las de directorio cubren arquitectura
- Si una regla se activa demasiado en un paquete, limita su **Path** o reescríbela en el ámbito donde se creó.

Para más información sobre alcances de directorio, consulta [Configuración a nivel de directorio](/es/how_to_use/code_review/configs/directory_level). Para la herencia de reglas, consulta [Herencia de reglas](/es/how_to_use/code_review/configs/rules_inheritance).
