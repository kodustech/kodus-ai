---
title: "Cómo crear reglas de revisión de código personalizadas"
description: "Define reglas adaptadas a la arquitectura, los patrones y las preferencias de codificación de tu equipo, que se verifican en cada PR."
---

Cada equipo tiene convenciones que los linters genéricos no cubren: límites de arquitectura, patrones de nomenclatura, requisitos de pruebas o restricciones específicas del negocio. Las reglas de revisión de código personalizadas te permiten codificarlas como verificaciones que Kody ejecuta en cada pull request.

## Crear una regla en Kodus

1. Selecciona **Global** (o un repositorio / directorio) en el selector de alcance en la parte superior del grupo **Code review** de la barra lateral y luego abre **Kody Rules**
2. En la pestaña **Review Rules**, haz clic en **New rule**
3. Configura:
   - **Rule name**: qué verifica la regla (por ejemplo, "Los archivos de servicio deben tener pruebas")
   - **Execution mode**: **Per file** (verifica cada archivo modificado, comenta en línea) o **Per PR** (verifica el PR completo, publica un comentario en el PR)
   - **Path**: patrones glob que limitan una regla Per file a archivos específicos (por ejemplo, `src/services/**/*.ts`); las reglas Per PR no lo usan
   - **Instructions**: qué verificar y cómo decidir
   - **Severity**: Critical, High (el valor por defecto), Medium o Low

En **Advanced settings** puedes agregar un **Bad example** y un **Good example**, que ayudan a Kody a distinguir una infracción de un código que cumple.

## Qué ayuda a que una regla funcione

- **Sé específico.** Nombra el patrón, la ruta y qué cuenta como una infracción.
- **Apunta a tus estándares.** Menciona un archivo por su ruta, como `@file:docs/architecture.md`, y Kody lo lee cuando evalúa la regla. El archivo se lee desde la rama de destino del pull request.
- **Elige el modo correcto.** Usa Per file para lo que puedes ver en un solo archivo, y Per PR para requisitos sobre el pull request como un todo: su descripción, su tamaño o si archivos relacionados cambian juntos.

### Ejemplo: Aplicar una convención de nomenclatura

Puedes crear una regla a nivel de archivo como:

- **Rule name**: "Los componentes de React deben usar nombres de archivo en PascalCase"
- **Path**: `src/components/**/*.tsx`
- **Severity**: High
- **Instructions**: "Marcar cualquier archivo de componente que no siga la nomenclatura PascalCase."

### Ejemplo: Regla de límite de arquitectura

```
Name: Domain layer must not depend on infrastructure
Execution mode: Per PR
Instructions: Flag any import added in src/domain/ that
points to src/infrastructure/. The allowed dependencies are
described in @file:docs/architecture.md.
```

### Ejemplo: Regla de cobertura de pruebas

```
Name: Every service change needs a test change
Execution mode: Per PR
Instructions: For each file modified in src/services/, check that the
PR also changes a matching test file under test/services/.
```

## Más formas de agregar reglas

- **Rules Library**: haz clic en **Discovery** en la página de Kody Rules para agregar reglas y paquetes ya preparados
- **Reglas de repositorio**: mantén una regla por archivo markdown en tu repositorio, en `.kody/rules`
- **Generación automática**: Kody redacta reglas a partir de los comentarios anteriores de tus revisores
- **En un hilo de revisión**: pídele a Kody que cree o cambie una regla, por ejemplo `@kody update this rule to ignore test files`

Para que Kody verifique los pull requests contra `CLAUDE.md`, `AGENTS.md` o las instrucciones de Cursor y Copilot, consulta [Instrucciones para agentes de código](/es/how_to_use/code_review/configs/rules_file_detection).

Para la referencia completa, consulta [Kody Rules](/es/how_to_use/code_review/configs/kody_rules).
