Las revisiones de código típicamente se enfocan en la calidad del código — seguridad, rendimiento, estilo. Pero a menudo omiten la pregunta: **¿este código realmente hace lo que el negocio pidió?** La Validación de Lógica de Negocio cierra esa brecha.

## Qué verifica

Kody encuentra la tarea que referencia un PR, la lee desde tu tracker de tareas y lista cada requisito con su estado en el código. El resultado es un comentario en el PR, que se mantiene actualizado. Cada requisito recibe un estado:

| Estado | Significado |
|---|---|
| **MET** | El diff lo implementa. |
| **PARTIAL** | Parte de lo que dice el requisito está implementada. |
| **MISSING** | No hay evidencia en el diff del PR, o el código del que depende el PR no lo hace. |
| **CHECK MANUALLY** | Un requisito visual o de flujo, o uno que Kody no puede resolver a partir del código. |
| **NOT IN TASK** | Un cambio que la tarea no pide. |

Cada fila cita el archivo y la línea en los que se basa e indica qué cambiar.

## Cómo usarla

### Automático (por defecto)

Con la categoría **Business Logic** activada en **Code review → What to review** (activada por defecto) y un tracker de tareas conectado, Kody verifica el PR en su primera revisión cuando el título, el nombre de la rama o la descripción del PR nombra una tarea: `PROJ-123` o un enlace a la tarea, o `#123` en el título o la rama (`Closes #123` en la descripción). Después vuelve a verificarlo cuando alguien lo pide, o en cada push si activas **Re-check after a push**.

### Bajo demanda

Comenta en el PR (no en una línea de código):

```
@kody -v business-logic https://kodustech.atlassian.net/browse/KC-1292
```

```
@kody -v business-logic
Orders above $500 must issue cashback credits.
Discount codes cannot be combined with loyalty rewards.
Free shipping applies only to domestic orders.
```

Sin una tarea después del comando, Kody vuelve a verificar las tareas que referencia el PR. Con un texto de al menos 40 caracteres, verifica el PR contra lo que escribiste, y no se necesita un tracker.

## Fuentes de tareas compatibles

Conecta un tracker en [Plugins](/es/how_to_use/code_review/plugins). Kody solo lee las tareas por su id.

| Fuente | Cómo referenciar |
|--------|-----------------|
| **Linear** | Clave del issue (`TEAM-123`) o URL del issue |
| **Jira** (Atlassian Rovo) | Clave del issue (`PROJ-123`) o URL del issue |
| **Notion** | URL de la página |
| **Git Issues** | `#123`, `owner/repo#123` o la URL del issue, en GitHub, GitLab, Bitbucket o Forgejo |
| **Otros trackers** (por ejemplo ClickUp) | Mediante un plugin personalizado. Elígelo como **Task source** si su nombre no indica que es un tracker. |
| **En línea** | Escribe los requisitos en el comentario del PR |

## Consejos

- Las tareas con criterios de aceptación explícitos reciben la validación más exhaustiva.
- Después de corregir una brecha, comenta `@kody -v business-logic` de nuevo. Se actualiza el mismo comentario.
- Usa **Closes PROJ-1** cuando el PR entrega la tarea completa y **Part of PROJ-1** cuando entrega una parte.
- Si la tarea solo tiene un título, Kody pide criterios de aceptación en lugar de adivinar.

Para más detalles, consulta [Validación de Lógica de Negocio](/es/how_to_use/code_review/business_logic_validation).
