---
title: "Cómo solucionar problemas de webhook"
description: "Diagnostica y resuelve problemas de entrega de webhooks entre tu proveedor de Git y Kodus."
---

Los webhooks son la forma en que Kodus sabe cuándo se abre, actualiza o comenta un PR. Si no funcionan, las revisiones no se activarán.

Con la GitHub App, los eventos vienen del webhook propio de la App. Con cualquier otra conexión, Kodus crea un webhook en cada repositorio cuando guardas la selección en **Repositories**.

## Revisa primero Repositories

Cuando un proveedor se niega a crear un webhook, **Repositories** muestra una advertencia, **A repository has no webhook** o **N repositories have no webhook**, con cada repositorio y el motivo. Kodus nunca se entera de los pull requests de esos repositorios, así que no se ejecuta ninguna revisión. La causa habitual es una credencial que no puede gestionar webhooks:

### Permisos de webhook por proveedor

| Proveedor | Qué necesita la credencial |
| --- | --- |
| GitHub (token) | Acceso de lectura y escritura a los webhooks del repositorio: `admin:repo_hook`, o **Webhooks: Read and write** en un token fine-grained |
| GitLab | Rol **Maintainer** u **Owner** en el proyecto |
| Bitbucket Cloud | Acceso de admin al repositorio y `read:webhook:bitbucket` y `write:webhook:bitbucket` |
| Bitbucket Data Center | Permiso **Repository admin** |
| Azure DevOps | **Edit subscriptions** en el proyecto (los Project Administrators lo tienen) |
| Forgejo | Acceso de admin al repositorio y el scope `write:repository` |

Corrige el permiso y luego guarda la selección de nuevo (**Save selected repositories**). Con **Review every repository** activado, Kodus reintenta estos repositorios en cada sincronización.

Los rechazos de Azure DevOps aparecen aquí solo con **Review every repository** activado. Con una selección, revisa las suscripciones en **Project settings** → **Service hooks**.

## Revisa la entrega

### GitHub

1. Ve a **Settings** → **Webhooks** de tu repositorio
2. Encuentra el webhook de Kodus
3. Haz clic en él y revisa **Recent Deliveries**
4. Busca entregas fallidas (códigos de estado que no sean 2xx)

Con una GitHub App que creaste para una instancia autoalojada, revisa en su lugar **Advanced** → **Recent Deliveries** en los ajustes de la App.

### GitLab

1. Ve a **Settings** → **Webhooks** de tu proyecto
2. Encuentra el webhook de Kodus
3. Revisa el historial de entregas en busca de errores

### Azure DevOps

Abre **Project settings** → **Service hooks** y revisa el historial de la suscripción.

## Comprueba que la URL llega a Kodus

Los webhooks los maneja un servicio aparte (puerto 3332), no la API ni la app web. Envía una solicitud que el servicio acepte sin un evento real:

```bash
curl -i -X POST https://kodus-webhooks.yourdomain.com/github/webhook \
  -H 'Content-Type: application/json' \
  -H 'X-GitHub-Event: ping' \
  -d '{}'
```

Un `200` con `Webhook ignored (event not supported)` significa que la solicitud llegó al servicio de webhooks. Un `404`, una redirección o una página HTML significa que la URL apunta a la API o a la app web: corrige la URL o tu reverse proxy. Para otros proveedores usa `/gitlab/webhook`, `/bitbucket/webhook` o `/forgejo/webhook`. Azure Repos responde `403 Unauthorized` sin su parámetro `token`, lo que también demuestra que la ruta es correcta.

Un `200` solo significa que el servicio aceptó la solicitud. Kodus descarta los eventos de un repositorio que no está seleccionado en **Repositories**.

## Soluciones comunes

### La URL del webhook es incorrecta o está desactualizada

La URL de cada proveedor viene de su variable de entorno:

| Proveedor | Variable | Ruta |
| --- | --- | --- |
| GitHub | `API_GITHUB_CODE_MANAGEMENT_WEBHOOK` | `/github/webhook` |
| GitLab | `API_GITLAB_CODE_MANAGEMENT_WEBHOOK` | `/gitlab/webhook` |
| Bitbucket | `GLOBAL_BITBUCKET_CODE_MANAGEMENT_WEBHOOK` | `/bitbucket/webhook` |
| Azure DevOps | `GLOBAL_AZURE_REPOS_CODE_MANAGEMENT_WEBHOOK` | `/azure-repos/webhook` |
| Forgejo | `API_FORGEJO_CODE_MANAGEMENT_WEBHOOK` | `/forgejo/webhook` |

Kodus identifica los webhooks existentes por su URL. Después de cambiar la URL, reinicia la API y guarda la selección de nuevo: Kodus crea un webhook nuevo y deja el antiguo en su lugar. Elimina el antiguo en tu proveedor de Git.

### Problemas con el certificado SSL

Los webhooks que Kodus crea en GitHub y GitLab tienen la verificación SSL activada; los otros proveedores usan su propio valor por defecto. Si alojas Kodus por tu cuenta, asegúrate de que tu certificado SSL sea válido; de lo contrario, el proveedor rechaza la entrega.

### Bloqueo del firewall

Si Kodus está detrás de un firewall, asegúrate de que los rangos de IP de tu proveedor de Git puedan alcanzar el endpoint del webhook.

### El webhook fue eliminado

Guardar la selección en **Repositories** (**Add repository** → **Save selected repositories**) registra cualquier webhook que falte. También puedes agregarlo manualmente: [GitHub](/es/how_to_deploy/platforms/github/github_webhook), [GitLab](/es/how_to_deploy/platforms/gitlab/gitlab_webhook), [Bitbucket](/es/how_to_deploy/platforms/bitbucket/bitbucket_webhook), [Azure DevOps](/es/how_to_deploy/platforms/azure_devops/azdevops_webhook) o [Forgejo](/es/how_to_deploy/platforms/forgejo/forgejo_webhook).

## Pruebas

La mayoría de los proveedores de Git te permiten **reenviar** una carga de webhook reciente. Úsalo para probar sin necesidad de crear un nuevo PR.

Autoalojado: ejecuta `./scripts/doctor.sh` desde la carpeta del instalador. Sus verificaciones de Git reportan los repositorios que el token no puede leer ni comentar, los repositorios sin webhook de Kodus, y si la URL del webhook está definida y recibió eventos en los últimos 7 días.
