---
title: "Cómo usar repositorios vinculados para contexto entre repos en la revisión de código"
description: "Vincula repositorios hermanos para que Kody lea contratos y APIs entre servicios cuando un PR toca una superficie de frontera."
---

Cuando tu producto está dividido en varios repositorios — por ejemplo un frontend que llama a una API de backend, o un servicio que depende de un paquete de contratos compartidos — una revisión de un solo repo puede pasar por alto roturas en la frontera. Los **repositorios vinculados** (*linked repositories*) dan a Kody contexto opcional y bajo demanda de esos codebases hermanos durante la revisión de código.

> **Requisito de plan:** Los repositorios vinculados están disponibles en los planes **Teams** y **Enterprise**, y durante el trial. Los planes Free no incluyen contexto entre repositorios. El autoalojado necesita una licencia Enterprise.

Esto es distinto de [compartir estándares de codificación entre repositorios](/es/knowledge_base/how-to-share-standards-across-repositories) (reglas y herencia a nivel de organización). Los repositorios vinculados comparten **contexto de código** para la revisión, no reglas de revisión.

## Qué hace

Para el repositorio en revisión, declaras hasta **3 repositorios vinculados** en la misma organización. Durante la revisión:

1. Kody primero comprueba si el diff del PR toca algo con forma de frontera — una comprobación rápida y fija que no cuesta nada.
2. Si el diff parece tocar una **superficie de contrato** (DTOs, exports, literales de string, claves de estado, rutas con forma de API y similares), se habilitan las herramientas entre repositorios.
3. Los repos vinculados se **clonan de forma lazy** solo cuando Kody realmente necesita leer o buscar en ellos.
4. Los hallazgos siguen **anclados solo a líneas del PR en revisión** — el código vinculado es evidencia, no un segundo objetivo de revisión.

Si no hay vínculos configurados, la función está completamente desactivada (costo extra cero).

## Configurar en el dashboard

Los repositorios vinculados son **por repositorio**, no globales. Las relaciones son direccionales: los vínculos en `frontend` solo aplican al revisar PRs en `frontend`.

1. En el selector de alcance en la parte superior del grupo **Code review** de la barra lateral, elige un **repositorio concreto** (no Global).
2. Abre **Linked repositories** (solo aparece en el alcance de repositorio).
3. Haz clic en **Add repository** y elige repos hermanos ya conectados a tu organización.
4. Opcionalmente, haz clic en un vínculo para definir:
   - **Instructions · optional** — pista en texto libre para Kody (p. ej. “API REST que consume este frontend”).
   - **Branch / ref pin · optional** — fija una rama o tag. Déjalo vacío para usar la cascada automática de refs (abajo).
5. Haz clic en **Save settings**.

Puedes vincular como máximo **3** repositorios. Solo se aceptan repos ya conectados a la misma organización.

## Configurar en `kodus-config.yml`

También puedes declarar vínculos en el archivo de configuración del repositorio:

```yaml
linkedRepositories:
  - repository: "org/backend-api"
    instructions: "REST API this frontend consumes"
    ref: main   # optional pin; omit for same-branch cascade
```

- `repository` (obligatorio): nombre completo de un repo conectado a la organización (`owner/repo`).
- `instructions` (opcional): descripción breve de por qué existe el vínculo.
- `ref` (opcional): fija una rama, tag o commit. Si se omite, Kody usa la cascada de refs.

`linkedRepositories: []` vacío significa que la función está desactivada. El archivo solo se lee cuando **Prefer kodus-config.yml settings** (**Code review → General**) está activado para el repositorio, y su lista reemplaza la definida en la app web. Consulta la [referencia de ajustes](/es/how_to_use/code_review/configs/linked_repositories#en-kodus-config-yml).

## Cómo se elige la ref

Para cada repositorio vinculado, Kody prueba refs en este orden y usa la primera que se clone con éxito:

1. **Override en la descripción del PR** para ese repo (ver abajo)
2. **Pin de `ref` en la config** (si está definido)
3. **PR abierto** en el repo vinculado cuya rama head coincide con la rama head del PR
4. El **nombre de la rama head del PR** en el repo vinculado
5. La **rama por defecto** del repo vinculado
6. Alternativas: `main`, luego `master`

Esto mantiene alineado el trabajo de funcionalidades multi-repo cuando existe el mismo nombre de rama en varios servicios, y a la vez recurre de forma segura a una alternativa en los PRs normales.

## Sobrescribir la ref desde la descripción del PR

Para una revisión puntual (por ejemplo, revisar contra un PR específico del backend), menciona el repo vinculado en el **título o la descripción** del PR en revisión. Los overrides solo aplican a repositorios que **ya están vinculados** en la config.

Formas compatibles:

| Forma | Significado |
| --- | --- |
| `owner/repo#123` | Usa el head del PR/MR `#123` de ese repo |
| URL de PR/MR | Igual que arriba, para una URL en `github.com`, `bitbucket.org`, `dev.azure.com` o un host con `gitlab` en su nombre |
| `owner/repo@branch` | Fija esa rama en el repo vinculado |

Ejemplos:

```text
Depends on org/backend-api#842
Also needs org/shared-contracts@feature/new-events
```

Menciona cada repositorio vinculado una sola vez. Con varias menciones, un pin `owner/repo@branch` gana sobre una referencia a un PR en cualquier lugar donde aparezca, y entre menciones de la misma forma gana la última. Las menciones de repos que **no** están vinculados se ignoran (no crean vínculos nuevos).

## Cuándo se activa el contexto entre repos (boundary gate)

Incluso con vínculos configurados, Kody **no** siempre abre los repos hermanos. Un gate barato y determinista escanea las **líneas añadidas** del diff del PR y se activa solo cuando encuentra **superficie de frontera**, como:

- Literales de string (segmentos de ruta, códigos, nombres de eventos, etc.)
- Exports (`export function`, tipos, clases, …)
- Enums / tipos / interfaces
- Claves de campos de objetos o payloads
- Identificadores con estilo de estado / código de error
- Rutas de archivo con forma de contrato (`dto`, `schema`, `api`, `client`, `openapi`, `proto`, …)

Los refactors internos que solo mueven o reformatean código que no es de frontera suelen mantener el gate apagado, así que los clones y el prompt de frontera quedan inactivos.

## Qué puede y qué no puede hacer Kody con los repos vinculados

**Puede:**

- Buscar y leer archivos en los repositorios vinculados cuando el gate está activo
- Usar tus **instructions** para entender la relación
- Citar código vinculado como evidencia de apoyo en un hallazgo sobre el PR actual

**No puede / no lo hará:**

- Publicar comentarios de revisión en archivos que existen solo en un repositorio vinculado
- Revisar todo el repo vinculado como si fuera el PR
- Vincular repositorios fuera de la organización o que no estén conectados a Kodus
- Usar más de 3 repositorios vinculados por repo en revisión (en `kodus-config.yml`, las entradas después de la tercera se descartan)

## Qué muestra la revisión

Cuando Kody leyó un repositorio vinculado, el comentario que publica al terminar la revisión incluye **Additional context used:** con el repositorio y la ref que leyó, por ejemplo `org/backend-api@main` o el PR abierto que usó. Si no hay esa línea, no se leyó ningún repositorio vinculado. Un vínculo que no se puede obtener o que no está conectado a la organización se omite, y la revisión continúa sin él.

## Configuraciones recomendadas

| Escenario | Vincular desde | Instructions típicas |
| --- | --- | --- |
| Frontend ↔ backend | Frontend → repo de la API de backend | “Contratos del cliente HTTP/REST de los que depende esta UI” |
| Servicio ↔ contratos compartidos | Servicio → repo de contratos/paquete | “Eventos, DTOs y protobufs compartidos” |
| BFF ↔ varios backends | BFF → hasta 3 repos de backend | Una línea corta por cada frontera de servicio |

Prefiere vínculos **estrechos y direccionales** (el consumidor apunta al productor) en lugar de vincular cada repo con todos los demás.
