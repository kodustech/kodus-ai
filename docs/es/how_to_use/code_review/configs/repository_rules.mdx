<Info>
Las Reglas del Repositorio siempre se mantienen sincronizadas: no hay ninguna opción que activar. Son los únicos archivos de un repositorio que se convierten en Kody Rules. Las instrucciones escritas para agentes de código (`CLAUDE.md`, `AGENTS.md`, `.cursor/rules`) se manejan por separado, consulta <a href="/es/how_to_use/code_review/configs/rules_file_detection">Instrucciones para Agentes de Código</a>.
</Info>

## Cómo funciona

Coloca en tu repositorio un archivo markdown con la plantilla de abajo. Kody lo importa como una regla, y la regla sigue al archivo: edita el archivo y la regla cambia, elimínalo y la regla se elimina.

Los archivos se importan **tal cual**, sin conversión con LLM. El frontmatter se lee como está escrito, el cuerpo markdown se convierte en las instrucciones de la regla exactamente como lo escribiste, y los ejemplos Bad y Good se importan desde el cuerpo. Cada archivo produce una regla.

- **Automático:** los archivos de reglas se sincronizan en todos los repositorios conectados.
- **Al fusionar:** cuando se fusiona un pull request que agrega, modifica, renombra o elimina un archivo de reglas, la regla se crea, actualiza o elimina. Los pull requests en un repositorio de [configuración centralizada](/es/how_to_use/code_review/configs/centralized_config) no se sincronizan.
- **Importar ahora:** para los archivos que ya están en el repositorio, abre **Code review → Kody Rules → Configuration** del repositorio y haz clic en **Import rule files now**. Lee todos los archivos de reglas de la rama por defecto.
- **En la aplicación:** las reglas sincronizadas aparecen en la página **Kody Rules** del repositorio con el origen **Auto-sync** y la ruta del archivo como fuente.

Las reglas nuevas quedan activas, o esperan en **Pending review** cuando **Kody knowledge approval** está activado.

El archivo es la fuente de verdad. El texto, la ruta, la severidad y el estado de una regla se reemplazan desde el archivo en cada sincronización, así que cambia el archivo en vez de la regla en la aplicación. Una regla pausada en la aplicación vuelve a quedar activa la próxima vez que se sincroniza su archivo.

## Ubicación de los archivos

Coloca los archivos de reglas en una de estas ubicaciones, en la raíz del repositorio o en cualquier subdirectorio:

- `.kody/rules/`
- `rules/**/*.md`
- `.rules/` y `docs/coding-standards/` (solo los archivos que siguen la plantilla)

El alcance de una regla viene de su `path`, no del lugar donde está el archivo. Una regla en `services/billing/.kody/rules/` sin `path` se aplica igualmente a todos los archivos.

## Plantilla de regla

````markdown
---
title: "<rule name>"
scope: "file"            # "file" or "pull-request"
path: []                 # list of globs. example: ["**/*.ts", "apps/web/**"]
severity_min: "high"     # "low", "medium", "high", "critical"
enabled: true            # optional
---

## Instructions
Describe what to review and how to decide. Be direct and objective.
- Focus on security, performance and public contract impacts.
- Give team preferences or patterns when applicable.
- If it's a PR rule, explain what to consider in the changeset.

## Examples

### Bad example
```lang
// paste here a short counter-example that violates the rule
```

### Good example
```lang
// paste here a short example that follows the rule
```
````

### Campos

Solo se requieren un `title` no vacío y un cuerpo no vacío. Un archivo al que le falte cualquiera de los dos se omite.

| Campo | Descripción | Valores | Por defecto |
|-------|-------------|---------|-------------|
| `title` | Nombre de la regla mostrado en la aplicación | Cualquier cadena | obligatorio |
| `scope` | **Per file** o **Per PR** | `"file"` o `"pull-request"` | `"file"` |
| `path` | Archivos a los que se aplica la regla; se ejecuta sobre los archivos que coincidan con **cualquiera** de los globs. No se usa en las reglas `pull-request` | Un glob o una lista de globs | `**/*` (todos los archivos) |
| `severity_min` | La severidad de la regla | `"low"`, `"medium"`, `"high"`, `"critical"` | `"medium"` |
| `enabled` | `false` omite el archivo. Una regla ya importada desde él no se elimina | boolean | `true` |

<Note>
  `severity` se acepta como alias de `severity_min`. Un valor fuera de los cuatro niveles cae a `"medium"`, y cualquier `scope` distinto de `"pull-request"` se trata como `"file"`. Las demás claves del frontmatter se ignoran.
</Note>

Los ejemplos Bad y Good provienen de los encabezados que contienen "bad" o "good" (por ejemplo `### Bad example`); cada bloque de código delimitado bajo uno de esos encabezados se convierte en un ejemplo.

## Reglas de ejemplo

### Regla a nivel de archivo

````markdown
---
title: "Avoid console.log in production code"
scope: "file"
path: ["src/**/*.ts", "src/**/*.tsx"]
severity_min: "medium"
---

## Instructions
Check for console.log statements in production TypeScript/JavaScript files.
- Console logs should not appear in production code
- Use proper logging libraries instead
- Allow console.log only in development utilities

## Examples

### Bad example
```typescript
function processUser(user: User) {
  console.log('Processing user:', user.id);
  return user.process();
}
```

### Good example
```typescript
import { logger } from './logger';

function processUser(user: User) {
  logger.info('Processing user:', user.id);
  return user.process();
}
```
````

### Regla a nivel de pull request

````markdown
---
title: "New API endpoints must have tests"
scope: "pull-request"
severity_min: "high"
---

## Instructions
When new API endpoints are added, ensure corresponding tests are included in the PR.
- Check for new route definitions in controllers
- Verify test files exist for new endpoints
- Ensure both positive and negative test cases

## Examples

### Bad example
Added new endpoint `/api/users/profile` but no test file included in the PR.

### Good example
Added new endpoint `/api/users/profile` with corresponding test file `tests/api/users/profile.test.ts` that covers success and error cases.
````

## Cuando un archivo deja de sincronizarse

- **El archivo no sigue la plantilla.** Un archivo sin frontmatter, sin `title` o sin cuerpo se omite. Si ya se había importado una regla desde él, la regla conserva su último texto y estado, y el panel lateral de la regla avisa de que su archivo ya no se sincroniza. El aviso desaparece cuando el archivo vuelve a interpretarse correctamente.
- **Mantener un archivo fuera de la sincronización.** Agrega `@kody-ignore` en las primeras o últimas 10 líneas del archivo. Su regla se elimina en la siguiente sincronización.
- **Dejar de importar un archivo.** `enabled: false` detiene la importación del archivo. No elimina ni pausa una regla que ya existe; para eso, elimina el archivo o usa `@kody-ignore`.

## Logs en self-hosted

En despliegues self-hosted, busca estos marcadores en los logs:

- `[kody-rules-sync]`: un resumen de cada sincronización con los archivos importados, omitidos (con el motivo) y eliminados.
- `[kody-rules-eval]`: durante una revisión, qué reglas (uuid y título) se seleccionaron para los archivos modificados.

Si una regla está activa en la aplicación pero nunca aparece en `[kody-rules-eval]` para los archivos que esperas, revisa su **Path**: una regla solo se ejecuta sobre los archivos que coinciden con su ruta.

## Límites de reglas

El plan Free y las instancias self-hosted sin licencia ejecutan como máximo 10 reglas activas, incluidas las reglas provenientes de archivos. Consulta los [límites de reglas](/es/how_to_use/code_review/configs/kody_rules#límites-de-reglas).
