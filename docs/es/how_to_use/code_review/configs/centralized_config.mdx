---
title: "Configuración Centralizada"
description: "Gestiona toda la configuración de code review y las Kody Rules como código en un único repositorio. Los cambios se sincronizan automáticamente tras cada merge; el despliegue se controla desde la UI o el CLI."
---

La Configuración Centralizada te permite mantener cada ajuste de code review y cada Kody Rule en **un único repositorio** en lugar de editarlos por repositorio en la interfaz web. Cada cambio fluye a través de un pull request en ese repositorio, dándote historial de versiones, revisión y rollback sobre tu configuración de revisión.

Úsala cuando quieras:

- Una única fuente de verdad para el comportamiento de revisión a través de muchos repositorios.
- Code-review-as-code: historial, revisión en PR, rollback, validación en CI.
- Kody Rules consistentes (reglas de revisión y memorias) en toda la organización.
- Cambios de configuración gestionados desde el CLI o CI.

## Cómo Funciona

1. Elige un repositorio para almacenar tu configuración centralizada. Debe ser uno de los repositorios seleccionados en Kodus.
2. Habilita la Configuración Centralizada en la UI (**Code review → General** en el alcance Global → **Configure centralized config**) y apúntala a ese repositorio.
3. Elige un **modo de sincronización inicial**:
   - `pr` — Kodus abre el PR de inicialización con tu configuración efectiva actual y las reglas.
   - `manual` — Kodus genera los archivos; tu equipo los descarga y abre el PR.
4. Después del primer merge, cada merge futuro en el repositorio centralizado propaga automáticamente los cambios a Kodus.

Kody no revisa los pull requests del propio repositorio centralizado.

El repositorio centralizado refleja la jerarquía de alcance de Kodus (Global → Repositorio → Directorio) a través de su estructura de carpetas.

## Estructura del Repositorio

El repositorio centralizado usa rutas de carpetas para mapear archivos a alcances. La estructura cubre tanto la configuración de revisión (`kodus-config.yml`) como las Kody Rules (`.kody-rules/`).

<Note>
El nombre del repositorio es arbitrario — elige el que mejor se adapte a tu organización. A continuación se usa `kodus-config` como convención.
</Note>

```
kodus-config/
├── kodus-config.yml                      ← global settings
├── .kody-rules/
│   ├── review/                           ← global review rules
│   │   └── require-tests-for-endpoints.yml
│   └── memories/                         ← global memories
│       └── logging-convention.yml
│
├── backend-api/                          ← matches a Kodus repository
│   ├── kodus-config.yml                  ← repository-level overrides
│   ├── .kody-rules/
│   │   ├── review/
│   │   │   └── no-raw-sql.yml
│   │   └── memories/
│   │       └── auth-module-layout.yml
│   │
│   └── src%2Fauth/                       ← a directory scope for src/auth
│       ├── kodus-config.yml              ← directory-level overrides
│       └── .kody-rules/
│           ├── review/
│           └── memories/
│
└── frontend-web/
    └── kodus-config.yml
```

Reglas:

- Un `kodus-config.yml` en la **raíz** del repositorio centralizado se aplica globalmente.
- Una carpeta de nivel superior cuyo nombre coincida con un repositorio de Kodus (por ejemplo `backend-api/`) limita sus archivos a ese repositorio. En GitLab el nombre es la ruta completa, así que la carpeta está anidada: `group/project/`.
- Un alcance de directorio es una carpeta dentro de la carpeta del repositorio, con el nombre de las rutas que cubre. Escribe cada `/` como `%2F` y une varias rutas con `&`: `src%2Fauth`, o `apps%2Fweb&apps%2Fdocs` para un alcance con dos carpetas. Una ruta anidada más profunda, como `backend-api/src/auth/`, se omite.
- Las reglas bajo `.kody-rules/review/` se convierten en **reglas de revisión**; las reglas bajo `.kody-rules/memories/` se convierten en **memorias**.

Cualquier archivo sin un alcance coincidente se ignora en la sincronización.

Eliminar un archivo del repositorio centralizado elimina lo que definía en la siguiente sincronización: un archivo de regla eliminado borra esa regla, y un `kodus-config.yml` eliminado que una sincronización anterior aplicó borra la configuración de ese alcance.

## Archivos de Configuración

Cada `kodus-config.yml` usa el mismo esquema que el `kodus-config.yml` por repositorio documentado en [Configuración General](/es/how_to_use/code_review/configs/general). Los campos se aplican al nivel de la carpeta donde vive el archivo y siguen las reglas de herencia habituales (ver [Herencia y Overrides de Configuración](/es/how_to_use/code_review/configs/inheritance_overrides)). A diferencia del archivo propio de un repositorio, estos archivos también pueden incluir `customMessages` (ver [Mensajes Personalizados](/es/how_to_use/code_review/configs/custom_messages)).

Los [agentes personalizados](/es/how_to_use/code_review/custom_agents), y los skills y documentos vinculados a ellos, no forman parte de la Configuración Centralizada. Se configuran en la aplicación, y las claves `customAgents` y `knowledge` de estos archivos se ignoran.

Ejemplo mínimo:

```yaml
version: 2.0
reviewOptions:
  bug: true
  security: true
  performance: true
  business_logic: true
suggestionControl:
  severityLevelFilter: medium
  applyFiltersToKodyRules: false
ignorePaths:
  - yarn.lock
  - package-lock.json
automatedReviewActive: true
```

## Archivos de Kody Rules

Cada regla es un único archivo `.yml` o `.yaml` bajo `.kody-rules/review/` (reglas estándar) o `.kody-rules/memories/` (memorias). El nombre del archivo es arbitrario, pero Kodus vincula una regla a la ruta de su archivo: renombrar o mover un archivo elimina la regla anterior y crea una nueva en la siguiente sincronización. `title` y `rule` son obligatorios; un archivo que no los tiene o que no supera la validación se omite, la sincronización reporta el fallo y no elimina las reglas retiradas hasta que se corrija el archivo.

Ejemplo de regla de revisión (`.kody-rules/review/require-tests-for-endpoints.yml`):

```yaml
title: Require tests for new endpoints
rule: |
  Every new HTTP endpoint handler must include at least one integration test
  that exercises the happy path and one common failure mode.
severity: high
scope: pull-request
path: apps/api/**
examples:
  - snippet: |
      // endpoint added with matching *.spec.ts
    isCorrect: true
  - snippet: |
      // endpoint added with no test file touched in the PR
    isCorrect: false
inheritance:
  inheritable: true
  exclude: []
  include: []
```

Una regla en pausa se escribe con `enabled: false`.

Consulta [Descripción General de Kody Rules](/es/how_to_use/code_review/configs/kody_rules) para la referencia completa de campos y [Herencia de Reglas](/es/how_to_use/code_review/configs/rules_inheritance) para entender el comportamiento de `inheritance.inheritable`, `exclude` e `include`.

## Flujo de Trabajo en la UI

En la barra lateral, elige **Global** en el selector de alcance en la parte superior del grupo **Code review** y luego
abre **Code review → General**:

1. Haz clic en **Configure centralized config** en el encabezado de la página (abre el diálogo
   **Centralized Config**).
2. Activa **Enable centralized config**.
3. Selecciona el repositorio fuente (**Selected repository**).
4. Elige el **Método de Sincronización Inicial**:
   - Automático (Crear PR ahora)
   - Manual (Sincronizar más tarde)
5. Haz clic en **Initialize** y confirma el estado.

Una vez habilitada, el diálogo muestra el repositorio fuente y estos botones:

- **Sync Now** aplica el contenido actual del repositorio centralizado.
- **Download** guarda el paquete de configuración (ver más abajo).
- **Save Changes** guarda lo que cambiaste en el diálogo, por ejemplo al desactivar **Enable centralized config**.

El repositorio fuente no se puede cambiar mientras está habilitada. Para usar otro repositorio, desactiva **Enable centralized config**, haz clic en **Save Changes** y vuelve a habilitarla.

## Comportamiento de la Interfaz Web Cuando Está Habilitada

El repositorio centralizado es la fuente de verdad. La interfaz web lo refleja:

- **Los ajustes de code review** en el alcance Global, de repositorio y de directorio siguen siendo editables en la interfaz web. Cada página muestra un banner — "Centralized config is enabled. Changes on this page are saved immediately and proposed through pull requests in the `<repo>` repository. Synchronization reapplies the configuration from that repository." — con **View active pull request** cuando hay uno abierto. **Save settings** aplica el cambio en Kodus de inmediato y abre un pull request con el mismo cambio en el repositorio centralizado. Si ese pull request se cierra sin mergear, la siguiente sincronización restaura la versión del repositorio por encima del ajuste guardado. Los cambios posteriores hechos mientras ese pull request está abierto se añaden a él. También puedes editar los archivos directamente en el repositorio centralizado.
- **Las Kody Rules** funcionan de forma distinta. Crear o editar una regla no la cambia directamente: Kodus abre un pull request en el repositorio centralizado con el cambio propuesto, y el cambio se activa cuando el pull request se mergea.

### Las reglas de la UI y las reglas del repo coexisten

Habilitar la Configuración Centralizada **no** elimina las reglas creadas previamente en la interfaz web, y el repositorio no tiene que contenerlas. Ambas fuentes alimentan el mismo conjunto de reglas activas:

- Las reglas importadas del repositorio centralizado se persisten con estado `SYNCED`.
- Las reglas creadas en la interfaz web antes de habilitarla conviven con ellas y permanecen activas.
- Al momento de la revisión, Kodus carga **todas las reglas activas** de la base de datos sin importar el origen. Una regla que existe solo en la UI se aplica exactamente igual que una regla que existe solo en el repo.
- Las reglas con estado `PENDING_ADD` (creadas desde la UI o el CLI, o exportadas por `init`, con un PR aún no mergeado) están **excluidas** de las revisiones hasta que el PR sea mergeado y el estado pase a `SYNCED`. La lista de Kody Rules muestra `PENDING_ADD`, `PENDING_EDIT` y `PENDING_DELETE` como **Pending add**, **Pending edit** y **Pending delete**.
- `init` con el método `pr` incluye en el PR de inicialización cada regla existente que aún no tiene archivo y la marca como `PENDING_ADD`, por lo que esas reglas no se ejecutan en las revisiones hasta que ese PR se mergee.

En la práctica: si creas el repositorio centralizado manualmente y le falta una regla que ya tenías en la UI, esa regla sigue funcionando — simplemente no queda versionada en el repo. Para llevarla al versionado, edítala una vez desde la UI (lo que abre un PR) o usa `init` para que Kodus empaquete cada regla existente en el PR de inicialización. No copies a mano el archivo de una regla al repositorio mientras la regla de la UI siga existiendo: la sincronización asocia las reglas por la ruta del archivo, así que el archivo se convierte en una segunda regla con el mismo título.

## Estados de Sincronización

Cada regla que proviene de la Configuración Centralizada rastrea su ciclo de vida mediante un estado:

| Estado | Significado |
|---|---|
| `SYNCED` | La regla en Kodus coincide con el archivo en el repositorio centralizado. |
| `PENDING_ADD` | Se creó una nueva regla vía UI/CLI y se abrió un PR; el archivo aún no existe en la rama predeterminada. |
| `PENDING_EDIT` | Se propuso una edición vía UI/CLI y hay un PR abierto; el archivo existente aún no ha sido actualizado. |
| `PENDING_DELETE` | Se propuso una eliminación vía UI/CLI y hay un PR abierto; el archivo todavía existe en la rama predeterminada. |

`PENDING_ADD` y `PENDING_EDIT` pasan a `SYNCED` una vez que el PR correspondiente es mergeado; una regla `PENDING_DELETE` se elimina. Si el pull request abierto por Kodus se cierra sin mergear, una regla nueva propuesta se rechaza y una edición o eliminación propuesta se descarta.

## Descargar Paquete de Configuración

Haz clic en **Download** en el diálogo **Centralized Config** para obtener un ZIP con los archivos `kodus-config.yml` generados y el árbol `.kody-rules/` que reflejan tu configuración y reglas actuales.

Úsalo cuando:

- Audites la configuración generada.
- Compartas artefactos de configuración con otro equipo.
- Mantengas una copia de seguridad local antes de un despliegue.
- Inicialices el repositorio centralizado en modo `manual`.

## Deshabilitar la Configuración Centralizada

Deshabilitar la Configuración Centralizada borra el repositorio fuente seleccionado y devuelve todos los repositorios al comportamiento estándar no centralizado (ajustes editados en la interfaz web, `kodus-config.yml` opcional por repositorio).

Las reglas y ajustes que fueron sincronizados permanecen en Kodus — no se eliminan al deshabilitar.

## CLI

Usa estos comandos para gestionar la Configuración Centralizada desde flujos de trabajo en terminal y scripts de CI.

### Requisitos

- Una clave de equipo con **Allow repository configuration via CLI** activado (**Organization → CLI keys → Configure**).
- Al menos un repositorio seleccionado en Kodus.

Define `KODUS_TEAM_KEY` en el entorno donde ejecutas el CLI.

### Verificar Estado

```bash
kodus config centralized status
```

### Inicializar la Configuración Centralizada

```bash
kodus config centralized init [owner/repo] --sync-option <pr|manual>
```

Notas:

- `--sync-option` tiene como valor predeterminado `pr`.
- Usa `.` para el repositorio del directorio actual.
- Si el repositorio se omite en una terminal interactiva, el CLI solicita la selección.
- En entornos no interactivos, el repositorio debe proporcionarse.

Ejemplos:

```bash
kodus config centralized init kodustech/kodus-config --sync-option pr
kodus config centralized init kodustech/kodus-config --sync-option manual
```

### Ejecutar Sincronización

```bash
kodus config centralized sync
```

### Deshabilitar la Configuración Centralizada

```bash
kodus config centralized disable
```

### Descargar ZIP de Configuración

```bash
kodus config centralized download --out ./centralized-config.zip
```

Notas:

- `--out` es obligatorio.
- La salida es un paquete ZIP con los archivos de configuración generados y el árbol `.kody-rules/`.

### Salida en JSON

Todos los comandos centralizados soportan salida estructurada con `--json`.

```bash
kodus config centralized status --json
kodus config centralized init kodustech/kodus-config --sync-option pr --json
kodus config centralized sync --json
kodus config centralized disable --json
kodus config centralized download --out ./centralized-config.zip --json
```
