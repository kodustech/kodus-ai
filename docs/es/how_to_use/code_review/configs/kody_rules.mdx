## Dónde encontrarlas

Elige **Global**, un repositorio o un directorio en el selector de alcance en la parte superior del grupo **Code review** y luego abre **Kody Rules**. Todo lo que crees o cambies en la página se aplica al alcance que elegiste. Consulta [Herencia de Reglas](/es/how_to_use/code_review/configs/rules_inheritance) para saber cómo se combinan los alcances.

El encabezado tiene tres acciones:

- **Configuration**: cómo se crean y aprueban las reglas y memorias de este alcance.
- **Discovery**: la [Biblioteca de Reglas](/es/how_to_use/code_review/configs/rules_library). Se muestra en la pestaña **Review Rules**.
- **New rule** (o **New memory** en la pestaña **Memories**).

## Dos tipos

<Tabs>
  <Tab title="Reglas de Revisión">
    Comprobaciones que se ejecutan durante la revisión de código y reportan las infracciones como sugerencias.

    - Las reglas **Per file** se ejecutan una vez por cada archivo modificado y comentan en línea.
    - Las reglas **Per PR** se ejecutan una vez para todo el pull request y publican un único comentario de PR.
    - Cada regla tiene una severidad y se puede limitar a rutas.
  </Tab>

  <Tab title="Memorias">
    Conocimiento de fondo que Kody usa como contexto de alta prioridad en las revisiones de código y en las conversaciones con Kody. Una memoria describe cómo funciona tu base de código; no es una comprobación y no tiene severidad.

    - Se crean hablando con Kody en un comentario de PR, o con **New memory**.
    - Con alcance de directorio, repositorio o toda la organización.
  </Tab>
</Tabs>

## Crear una Regla de Revisión

En la pestaña **Review Rules**, haz clic en **New rule** (**Write a rule** cuando la lista está vacía).

| Campo | Qué hace |
|-------|----------|
| **Rule name** | Hasta 300 caracteres. |
| **Execution mode** | **Per file** o **Per PR**. |
| **Path** | Globs que limitan una regla **Per file** a los archivos que coinciden. Separa varios globs con comas; se comprueba un archivo que coincida con cualquiera de ellos. Vacío significa todos los archivos. No lo usan las reglas **Per PR**, y no se puede editar en el alcance de directorio, donde la regla pertenece al alcance de directorio (consulta [Herencia de Reglas](/es/how_to_use/code_review/configs/rules_inheritance) para saber cuándo se aplica). |
| **Instructions** | Qué debe comprobar Kody y cómo decidir. Obligatorio. En una regla nueva puedes **Start with a popular template**. El menú **Variables** inserta nombres como `fileDiff` o `pr_title`, que puedes usar para referirte al diff y a los detalles del PR que ve Kody. |
| **Severity** | **Critical**, **High** (predeterminado), **Medium** o **Low**. |
| **Advanced settings** | **Inheritable** (activado por defecto) y **Code examples**: un **Bad example** y un **Good example**. |

La severidad decide cómo se etiqueta el hallazgo. Si los hallazgos por debajo de una severidad se publican o no se define en [Control de Sugerencias](/es/how_to_use/code_review/configs/suggestion_control#aplicar-el-umbral-a-las-kody-rules).

### Qué ve Kody

- **Per file:** el diff del archivo, el resto del archivo cuando es lo bastante pequeño, y el título y la descripción del PR (primeros 1000 caracteres).
- **Per PR:** el título y la descripción del PR (primeros 1000 caracteres), la lista de archivos modificados y el diff de cada archivo. En PRs muy grandes, los archivos que exceden el presupuesto de diff se listan solo por nombre.

Kody solo reporta infracciones en líneas que el pull request añade o cambia. Una regla cuyas instrucciones nombran un lenguaje ("en archivos Ruby, ...") se limita a los archivos de ese lenguaje, que Kody determina cuando guardas la regla.

### Referenciar archivos en una regla

Menciona un archivo por su ruta en las instrucciones, por ejemplo `@file:docs/architecture.md`, para darle a Kody su contenido cuando juzga la regla.

- Kody encuentra las referencias a archivos cuando guardas la regla. El estado junto al editor muestra cuándo se resuelven, y cualquier archivo que no pudo leer.
- Los archivos se leen de la rama de destino del pull request.
- Usa la ruta real en el repositorio, no un marcador de posición.

### Ejemplos

<Tabs>
  <Tab title="Per file">
    - **Rule name:** Evitar operadores de igualdad en condiciones de terminación de bucles
    - **Path:** `src/**/*.ts`
    - **Severity:** Critical
    - **Instructions:** Usar `==` o `!=` en la condición de un bucle puede causar bucles infinitos cuando nunca se alcanza el valor exacto.

    **Bad example**

    ```typescript
    // Infinite if the increment is not exactly 1
    for (let i = 0; i != 10; i += 2) {
      console.log(i);
    }
    ```

    **Good example**

    ```typescript
    for (let i = 0; i < 10; i += 2) {
      console.log(i);
    }
    ```
  </Tab>

  <Tab title="Per PR">
    - **Rule name:** Las rutas nuevas deben registrarse
    - **Execution mode:** Per PR
    - **Instructions:** Cuando el PR añade una ruta a un controlador, comprueba que también se añada a `@file:routes.json`.

    Otras cosas que una regla Per PR puede comprobar:

    - La descripción del PR indica qué se añadió o se eliminó.
    - Cada archivo de servicio modificado tiene un archivo de prueba correspondiente en el PR.
    - El PR no modifica más de un número determinado de archivos.
  </Tab>
</Tabs>

## Otras formas de añadir reglas

- **[Biblioteca de Reglas](/es/how_to_use/code_review/configs/rules_library):** añade reglas y paquetes ya preparados con **Discovery**.
- **[Reglas de Repositorio](/es/how_to_use/code_review/configs/repository_rules):** mantén una regla por archivo markdown en tu repositorio, en `.kody/rules`.
- **[Fuentes Globales de Reglas](/es/how_to_use/code_review/configs/global_rule_sources):** importa archivos de reglas desde un repositorio de estándares como reglas globales.
- **[Generación Automática de Reglas](/es/how_to_use/code_review/learning/kody_rules_generation):** Kody redacta reglas a partir de comentarios pasados de tus revisores.
- **En un hilo de revisión:** pídele a Kody que cree, cambie o elimine una regla, por ejemplo `@kody update this rule to ignore test files`. Las reglas creadas así muestran el origen **MCP/Agent** y esperan en **Pending review**.

## La lista de reglas

La lista muestra las reglas del alcance seleccionado más las heredadas de alcances superiores. Haz clic en una fila para abrir la regla en un panel lateral, con **Pause** o **Resume**, **Edit** (**View** sin permiso de edición) y eliminar.

Usa el interruptor de vista de tabla o de tarjetas junto a los filtros; la elección se recuerda en tu navegador. La búsqueda mira títulos, rutas, instrucciones y ejemplos (pulsa `/` para enfocarla). Los chips de severidad sobre la lista filtran por severidad.

**Filters** te permite ordenar por actualización reciente, severidad o nombre, mostrar u ocultar las reglas heredadas y **Disabled Rules**, y filtrar por origen, por **Has sync errors** (reglas cuyos archivos referenciados no se pudieron leer) o por **Paused only**.

### Origen

| Origen | De dónde vino la regla |
|--------|------------------------|
| **Manual** | Escrita en la aplicación. |
| **Library** | Añadida desde la Biblioteca de Reglas. |
| **Auto-sync** | Un archivo de reglas en un repositorio, mantenido sincronizado. |
| **Kody-generated** | Redactada a partir de revisiones pasadas. |
| **Onboarding** | Sugerida durante el onboarding. |
| **MCP/Agent** | Creada mediante las herramientas MCP de Kodus: por Kody en un hilo de revisión, o por un cliente MCP. |
| **CLI** | Creada con el CLI de Kodus. |
| **Agent file** | Importada desde un archivo de agente de programación antes de que estos dejaran de convertirse en reglas. Congelada. Consulta [Instrucciones para Agentes de Código](/es/how_to_use/code_review/configs/rules_file_detection#reglas-importadas-desde-archivos-para-agentes-de-código). |

### Estado

| Estado | Significado |
|--------|-------------|
| **Active** | Se comprueba en cada PR nuevo. |
| **Paused** | Se mantiene en la lista, se omite en cada PR. |
| **Paused by Kody** | Pausada por **Pause ignored and noisy rules**. |
| **Locked** | Se omite por el límite del plan Free (abajo). |
| **Disabled** | Regla heredada marcada como deshabilitada para este alcance. Una revisión aún la aplica; consulta [Herencia de Reglas](/es/how_to_use/code_review/configs/rules_inheritance). |
| **Pending add**, **Pending edit**, **Pending delete** | Un cambio en espera en un pull request de [configuración centralizada](/es/how_to_use/code_review/configs/centralized_config). |

### Acciones en lote

En la pestaña **Review Rules**, marca reglas (o **Select all visible**) para **Pause**, **Resume** o **Delete** a la vez. Solo se pueden seleccionar las reglas del alcance actual, no las heredadas.

### Impacto y uso

El panel lateral muestra un bloque **Impact** de los últimos 30 días: cuántas veces se disparó la regla, en cuántos pull requests se disparó y sus sugerencias recientes. Donde Cockpit está disponible (planes Teams y Enterprise, y pruebas), también muestra cuántas sugerencias se implementaron y el feedback de pulgar arriba y pulgar abajo, y la tabla incorpora una columna **Usage**. Un chip marca las reglas que necesitan atención:

- **Stale:** no se disparó en los últimos 30 días.
- **Ignored:** se disparó al menos 5 veces y el 20% o menos de sus sugerencias se implementaron.
- **Noisy:** se disparó al menos 5 veces, con al menos 3 pulgares abajo, más pulgares abajo que arriba, y un pulgar abajo en al menos el 10% de sus sugerencias.

### Pause ignored and noisy rules

En los planes Teams y Enterprise, **Configuration → Pause ignored and noisy rules** pausa, una vez al día, las reglas activas del alcance que resultaron **Ignored** o **Noisy** en los últimos 30 días, incluidas las reglas escritas a mano. Muestran **Paused by Kody** con las cifras que lo respaldan. Los administradores reciben una notificación y pueden **Resume** una regla en cualquier momento; tras un resume, solo cuenta lo que señale después. Las reglas gestionadas mediante una [configuración centralizada](/es/how_to_use/code_review/configs/centralized_config) no se pausan. Está desactivado por defecto.

## Límites de reglas

Las organizaciones en el plan cloud **Free** (o cuya suscripción se canceló o venció) y las instancias self-hosted sin una licencia válida ejecutan como máximo **10 reglas activas** por revisión, las más antiguas primero. Las 10 cuentan juntas las reglas Global, de repositorio y de directorio, y las memorias también cuentan. Las reglas que exceden el límite quedan en la lista como **Locked**, se omiten en cada PR, y un banner en la página indica cuántas son. Los planes cloud de pago y las instancias self-hosted con licencia no tienen límite.

## Memorias

Una memoria es una afirmación corta que Kody tiene en cuenta: cómo funciona tu sistema, qué ha decidido ya el equipo. Las memorias ayudan a Kody a no repetir suposiciones equivocadas sobre tu repositorio.

- Las memorias se añaden al contexto de las revisiones de código y de las conversaciones con Kody.
- Cuando Kody está a punto de guardar una memoria, comprueba las existentes y la crea, la omite por duplicada o actualiza una memoria existente.

### Crear una memoria

**En un comentario de PR.** Pídele a Kody que recuerde algo y lo guarda:

```
@kody remember: this repo mirrors a third-party API, so some payload fields intentionally stay snake_case.
```

Cuando solo expones contexto o una preferencia del equipo, Kody ofrece guardarlo y espera. Responde `@kody yes` para guardarlo:

```
@kody in this service, tests usually live next to implementation files rather than in a central test folder.
```

Cuando Kody guarda o actualiza una memoria, responde con un enlace a ella en la aplicación.

<Info>
  Kody no guarda instrucciones transitorias ("arregla esto ahora"), conversaciones de depuración, preguntas, afirmaciones vagas, ni solicitudes que aplican solo a una tarea o PR.
</Info>

**En la aplicación.** Elige el alcance, abre la pestaña **Memories**, haz clic en **New memory** (**Add a memory** cuando la lista está vacía), completa **Memory name** e **Instructions**, y haz clic en **Create memory**.

### Alcances de las memorias

| Alcance | Se aplica a |
|---------|-------------|
| **Directory** | Los archivos de un directorio configurado. Una memoria creada en un comentario de PR también se puede limitar a una ruta, como `src/components/**`. |
| **Repository** | Todo el repositorio. |
| **Organization** (**Global** en el selector de alcance) | Todos los repositorios de la organización. |

## Aprobación

Por defecto, las reglas generadas a partir de revisiones pasadas, las reglas sugeridas durante el onboarding y las memorias que guarda Kody están activas en cuanto se crean. Para revisarlas primero, abre **Configuration** y activa **Kody knowledge approval**.

Con la aprobación activada, estas esperan en **Pending review** hasta que se aprueban:

- reglas generadas a partir de revisiones pasadas o sugeridas durante el onboarding;
- memorias que Kody guarda en un hilo de revisión;
- reglas sincronizadas desde los archivos de reglas de un repositorio. Las reglas importadas mediante [Fuentes Globales de Reglas](/es/how_to_use/code_review/configs/global_rule_sources) están activas de inmediato.

Una regla creada mediante las herramientas MCP de Kodus, lo que incluye una regla que Kody crea en un hilo de revisión, siempre espera en **Pending review**, sea cual sea el ajuste. Las reglas que escribes a mano, añades desde la biblioteca o creas con el CLI están activas de inmediato.

### Pending review

Un badge en las pestañas **Review Rules** y **Memories** muestra el número de pendientes. La sección **Pending review** ("Rules and memories awaiting approval.") los lista juntos, cada uno marcado como **Rule**, **Memory** o **Update**:

- **Reglas y memorias nuevas:** **Approve** para activar o **Discard** para rechazar.
- **Actualizaciones:** un cambio propuesto a un elemento existente, mostrado como un diff. **Update existing** lo aplica, **Create new instead** conserva el original y añade la propuesta como un elemento separado, **Discard** la rechaza.

Selecciona varios y usa **Bulk actions** (**Approve N**, **Create as new (N)**, **Discard N**) para gestionarlos a la vez.
