## Skills & docs

Las skills y los docs son guías que ya viven en tu repositorio. Kodus no las copia: las lee de la **rama de destino del pull request** en cada revisión, así que los cambios en esa rama se aplican sin volver a los ajustes, y un pull request no puede cambiar la regla que lo evalúa. Una guía también puede venir de otro repositorio, como un repositorio de reglas compartido (consulta **Desde otro repositorio** más abajo).

| | Skill | Doc |
| --- | --- | --- |
| Qué es | Una carpeta con un `SKILL.md` (o un único archivo `.md` de agente) | Una guía en Markdown |
| Cómo la lee el agente | La abre bajo demanda, cuando el cambio la necesita, junto con sus archivos de referencia | La carga completa, en cada revisión |
| Ideal para | Muchas reglas, o reglas para una parte del código | Una guía corta que aplica a todo cambio que revisa el agente |

Los scripts dentro de una skill se muestran al agente como texto y nunca se ejecutan.

### Dónde las encuentra Kodus

Las **skills** se detectan en:

- `.claude/skills/*/SKILL.md`
- `.claude/agents/*.md`
- `.agents/skills/*/SKILL.md`
- `.github/skills/*/SKILL.md`

Un `SKILL.md` empieza con un frontmatter YAML con `name` (hasta 64 caracteres: letras minúsculas, dígitos y guiones simples) y `description` (hasta 1.024 caracteres). Una skill sin ellos aparece como "Not a valid skill", con el motivo. Un `name` que difiere del nombre de la carpeta se lee como el nombre de la carpeta. El agente lee las primeras 500 líneas (unos 5.000 tokens) de `SKILL.md`, recorre el resto cuando lo necesita y abre los demás archivos de la carpeta de la skill, como `references/payments.md` (hasta 200 archivos).

```markdown .claude/skills/ledger-rules/SKILL.md
---
name: ledger-rules
description: How the ledger service records, reverses and reconciles entries.
---

# Ledger rules

- Every write to `entries` goes through `LedgerWriter`; never insert directly.
- A reversal is a new entry, never an UPDATE of the original.

See references/reconciliation.md for the nightly job.
```

Los **docs** se sugieren a partir de `CONTRIBUTING.md`, `ARCHITECTURE.md`, `CONVENTIONS.md`, `STYLEGUIDE.md` y `docs/**/*.md` (hasta 30). También puedes agregar cualquier ruta a mano: un archivo con extensión es un doc; una carpeta (o un `SKILL.md` dentro de una) es una skill.

### Vincularlas

Hay dos lugares para vincular una skill o un doc:

- **En la página del agente**, en **Files & knowledge → Skills & docs**: **Add skill or doc** lista lo que el agente puede seguir, o usa **Add by path**.
- **En la página Skills & docs** (el enlace **Skills & docs** junto a **Custom agents** en What to review): en **Added, and who follows each**, cada skill y doc registrado con una casilla para **Main review** y para cada agente. Vincular a **Main review** le da la guía a la revisión propia de Kody. **Found in the repository** lista lo que Kodus detectó, cada uno con **Add**, y un campo permite agregar cualquier ruta a mano. Los cambios se conservan con **Save**.

En el nivel global, la página Skills & docs solo acepta rutas escritas a mano. Cada repositorio se lee por separado; abre los ajustes de un repositorio para ver si cada ruta existe allí.

### Citados por hallazgos descartados

Cuando las revisiones descartan hallazgos porque citan un archivo que el agente no sigue ("is not a guide linked to this review"), **Skills & docs** del agente muestra ese archivo en **Cited by dropped findings**, con cuántos hallazgos se descartaron. **Follow** lo vincula, desde este repositorio o desde el repositorio donde está. Solo se ofrecen archivos que existen.

### Desde otro repositorio

Es común que un equipo mantenga sus reglas en un repositorio y las aplique en varios. Elígelo en **From** al agregar una skill o un doc en la página de un agente: primero aparecen los repositorios vinculados de este repositorio, y **Other repository…** lista todos los repositorios conectados a Kodus (seleccionados en Git settings). Si el repositorio de reglas no aparece, conéctalo ahí primero.

- Una guía de otro repositorio se lee de la **rama por defecto** de ese repositorio, o de la rama o tag que definas con **Use a branch or tag instead**. Una rama o tag por repositorio. Un pull request nunca la cambia.
- Es solo para agentes personalizados. La revisión principal lee las guías del repositorio revisado y sus instrucciones para agentes de código, no las de otro repositorio, por eso la página Skills & docs no ofrece **Main review** para ella.
- Se carga como una guía del repositorio revisado, en cada revisión, sin sandbox y aunque el cambio no toque el otro repositorio.
- El agente la cita como `owner/repo:path`, y el comentario enlaza el archivo.
- Cuando el repositorio de reglas es privado y el revisado es público, el comentario nombra el archivo sin citar su texto.

Cuando las instrucciones de un agente nombran un repositorio vinculado del que no sigue nada, su página lo indica y ofrece **Browse its rules**. Cuando nombran un archivo de reglas (`.md`, `.mdc`, `.mdx`) que el agente no sigue, la página ofrece **Follow it** para ese archivo, en el repositorio donde las instrucciones lo ubican. Un doc seguido entra completo en el prompt del agente, así que el agente ya no depende de decidir leerlo, y sus hallazgos pueden citarlo.

<Warning>
  Un archivo marcado como **Also a Kody Rules source** ya alimenta las Kody Rules. Vincularlo también a un agente puede hacer que la misma regla comente dos veces.
</Warning>

### Presupuestos

Por agente, y para la revisión principal:

| Límite | Valor |
| --- | --- |
| Skills | 20 |
| Docs | 10 |
| Tokens de docs | 20.000 |

La página Skills & docs avisa cuando un agente o la revisión principal supera un límite. En una revisión, los docs que exceden el presupuesto se recortan u omiten, y la revisión registra un aviso.

### Cómo los usan los hallazgos

Un hallazgo de convención debe **citar** la regla que aplica. La cita puede venir de:

- una guía vinculada al agente
- las propias instrucciones del agente
- los `CLAUDE.md`, `AGENTS.md` y otros archivos para agentes de código del repositorio, cuando **Coding-agent instructions** está activado en What to review

Kodus verifica la cita contra esa fuente tal como está en la rama de destino y descarta el hallazgo cuando la cita no está allí. Un hallazgo que señala código existente como el patrón a seguir se conserva solo cuando el archivo citado contiene el código citado en la rama de destino. El comentario publicado cita la regla:

```markdown
**Rule** (`docs/ledger.md`):
> A reversal is a new entry, never an UPDATE of the original.
```

Una regla de otro repositorio se cita como `owner/repo:path`, con un enlace al archivo en la rama de la que se leyó.

## Plugins (MCP)

Los agentes pueden consultar los plugins instalados en tu workspace: un gestor de tareas, una wiki, el monitoreo. En **Tools → Plugins**, activa un plugin para el agente. Recibe todas las herramientas de lectura; haz clic en **Customize** para elegir las herramientas una por una, y en **Use every tool** para volver atrás.

Solo se ofrecen herramientas de lectura; las de escritura nunca. Un plugin que marca sus herramientas como de solo lectura se toma al pie de la letra. Para uno que no lo hace, una herramienta solo califica cuando su nombre lleva un verbo de lectura (get, list, search, read, find…) y ningún verbo de escritura. Una revisión nunca crea un ticket ni publica un mensaje en nombre de tu equipo.

El agente consulta un plugin cuando el cambio apunta a algo registrado allí, como un ticket en la descripción del pull request, y cita lo que encontró. Consulta [Plugins](/es/how_to_use/code_review/plugins) para instalar uno.

## CLIs del equipo

Un agente puede ejecutar hasta **3** herramientas de línea de comandos de tu equipo: un detector de código duplicado, un verificador de esquemas, un linter interno. Las CLIs solo se ejecutan en el sandbox aislado de E2B, dentro del checkout del repositorio. En cualquier otro sandbox la CLI no se instala y el agente se ejecuta sin ella.

En **Tools → CLIs**, haz clic en **Add CLI**:

| Campo | Notas |
| --- | --- |
| **Name** | Cómo se refieren a ella el agente y los comentarios. |
| **Binary** | Lo que llama el agente, p. ej. `jscpd`. |
| **Install** | Un único comando de gestor de paquetes, fijado a una versión exacta o un digest. Se ejecuta una vez en el sandbox antes de la revisión. |
| **Allowed command prefixes** | Toda llamada debe empezar con uno de estos. Un prefijo nombra un subcomando o flag después del binario, p. ej. `ledgerctl check`. Un token que termina en `/` cubre cualquier ruta debajo de él. |
| **Allowed domains** | Hosts a los que la CLI puede acceder por HTTPS, comparados por nombre exacto. Todo lo demás, incluido HTTP sin TLS, se bloquea. |
| **Usage** | Markdown que lee el agente para saber cuándo y cómo llamarla. |
| **Runs project code** | Actívalo para pruebas, builds o linters que cargan el repositorio. Una CLI así nunca recibe secretos. |
| **Secrets** | Variables de entorno (p. ej. `LEDGER_TOKEN`) definidas solo en el entorno de esta CLI, enmascaradas en su salida, nunca en el prompt. Son de solo escritura: una vez guardadas se muestran como **Stored · hidden**. |

**Reglas de instalación.** Instaladores admitidos: `npm`, `pnpm`, `yarn`, `pip`, `pip3`, `pipx`, `uv`, `go`, `cargo`. Todo paquete debe estar fijado (`tool@1.2.3`, `tool==1.2.3` o `tool@sha256:…`). Se rechazan etiquetas como `@latest`, rangos de versión, URLs, fuentes Git, rutas locales y sintaxis de shell.

<CodeGroup>
```bash npm
npm i -g jscpd@5.4.1
```

```bash pip
pip install sqlfluff==3.2.5
```

```bash go
go install github.com/acme/ledgerctl@v1.4.2
```
</CodeGroup>

**Cómo se ejecutan las llamadas.**

- El agente pasa argumentos, nunca un comando de shell: pipes, redirecciones, globs y variables se pasan literalmente.
- Una llamada que no empieza con un prefijo permitido se rechaza.
- Cada CLI se ejecuta con su propio usuario, con un timeout, un directorio temporal privado y archivos legibles solo por ese usuario. Su salida está limitada, y todo lo que inició o escribió en directorios temporales se elimina después de la llamada.
- Cada paso de una CLI se ejecuta como root a través del proveedor del sandbox, nunca a través del usuario con el que corre la revisión. Ese usuario pierde toda forma de convertirse en root (sudo incluido) antes de descargar el repositorio, así que el código del pull request no puede alcanzar el proceso ni los archivos de una CLI.
- Un sandbox en el que eso no pudo confirmarse no ejecuta ninguna CLI.

**Comandos bloqueados.** En una CLI con secretos, Kodus rechaza, al guardar y al ejecutar, los prefijos y argumentos que listan el entorno (`printenv`, `env`, `set`, `export`, `declare`, cualquier cosa bajo `/proc`), los comandos comunes que imprimen tokens (`auth token`, `auth status --show-token`, `auth:token`, `config get`, `configure get`, `print-access-token`, `get-access-token`), un shell o intérprete como binario (`bash`, `node`, `python`, `npx`, …) y los argumentos que nombran uno de sus secretos como `$NAME` o `${NAME}`. Los argumentos nunca pasan por un shell, así que Kodus nunca los expande.

**Red.** La allowlist se aplica por nombre de host. Las conexiones HTTPS de la CLI pasan por un proxy que reenvía una conexión solo cuando el nombre de servidor que pide está en la lista (nombre exacto, sin subdominios) y que resuelve ese nombre por su cuenta, rechazando direcciones privadas e internas. La CLI no tiene otro acceso a la red: ni DNS, ni HTTP sin TLS, ni otros puertos. Un host permitido sigue recibiendo lo que la CLI le envíe, credenciales incluidas, y la red no distingue una lectura de una escritura. Usa tokens de solo lectura y con el menor privilegio posible, y permite solo hosts de confianza.

**Cómo se guardan los secretos.**

- Un secreto se cifra al guardarse (AES-256-GCM, vinculado a su agente, su CLI y el nombre de la variable) y nunca vuelve al navegador, que muestra **Stored · hidden**.
- Queda vinculado a la CLI para la que se guardó, en ese nivel de ajustes. Cualquier cambio en la CLI (nombre, instalación, binario, prefijos permitidos, dominios permitidos, **Runs project code** o los nombres de sus secretos) vuelve a pedir todos sus secretos, al guardar y en **Try it**. Solo las notas de uso y el timeout pueden cambiar sin eso. Un secreto guardado que ya no puede leerse también hay que escribirlo de nuevo.
- **Try it** usa solo los secretos guardados en el nivel que estás editando, nunca los heredados.
- Un secreto llega solo al proceso de esa CLI, nunca a su instalación, a las otras CLIs ni al prompt del agente.
- En la salida de la CLI, cada secreto se reemplaza por `***`, también cuando se imprime en base64, codificado en URL, en hex o escapado en JSON, antes de que lo vean el agente, **Try it**, un comentario del pull request o un log. El enmascarado no puede reconocer toda transformación (un valor partido o parcial), y por eso se bloquean los comandos anteriores.

Cuando un hallazgo viene de una CLI, el comentario muestra hasta cinco de las líneas de salida de la CLI que nombran el archivo:

````markdown
**Evidence** (`jscpd` output):
```text
- src/billing/invoice.ts [12:1 - 41:2] (29 lines, 212 tokens)
```
````

<Note>
  Si la instalación falla, el agente se ejecuta sin esa CLI y la ejecución registra el aviso. **Try it** lo muestra en **Warnings**.
</Note>

## Reglas de ast-grep

En **Tools → Advanced → Structural search (ast-grep rules)**, dale al agente reglas de [ast-grep](https://ast-grep.github.io), de una de estas formas:

- **Inline**: el YAML de la regla. Separa varias reglas con `---`. Cada una necesita un `id` y una `rule`.
- **Un archivo de reglas**: una sola línea con la ruta de un archivo `.yml` o `.yaml` del repositorio, leído de la rama de destino del pull request.

```yaml
id: no-float-money
language: typescript
message: Parse amounts with Money.parse, never parseFloat
rule:
  pattern: parseFloat($A)
```

Las reglas se ejecutan sobre los archivos cambiados del pull request. Una coincidencia de regla es prueba: un hallazgo que cita una regla que coincidió en ese archivo durante la ejecución omite la verificación de la cita y la verificación del modelo. Las reglas tienen un límite de 64.000 bytes. La ayuda del campo lista las reglas que encontró y reporta una regla sin `id` o sin `rule`.

El agente también tiene búsqueda estructural ad hoc en el repositorio, sin ninguna regla configurada.
