## Qué es el Tiempo de Ciclo del PR

El Tiempo de Ciclo del PR mide cuánto tiempo permanece abierto un pull request: desde que se abre hasta que se cierra. Esta métrica representa la velocidad de revisión y merge de tu proceso de desarrollo.

En el Cockpit, es la tarjeta **PR Cycle Time (p75)** y el gráfico **PR Cycle Time** de la pestaña **Productivity**.

## Cómo lo Calculamos

Rastreamos automáticamente el tiempo entre el momento en que se abre cada pull request y el momento en que se cierra. Partimos de la fecha de apertura del PR y no de su primer commit, porque las ramas con rebase pueden arrastrar commits antiguos que inflarían el número. Para el tiempo dedicado antes de abrir el PR, consulta [Lead Time Breakdown](/es/how_to_use/cockpit/metrics/lead_time_breakdown).

**Lo que Rastreamos:**
- Tiempo desde la apertura del PR hasta su cierre
- PRs cerrados en el rango de fechas seleccionado
- Cuánto tiempo tarda el código en integrarse

**Lo que No Contamos:**
- Tiempo dedicado a planificar, diseñar o programar antes de abrir el PR
- Tiempo después de la fusión (despliegue, adopción por parte del usuario, etc.)
- Cambios fallidos o abandonados

**Cómo se Calcula:**
```
Tiempo de Ciclo del PR = (Hora de Cierre del PR) - (Hora de Apertura del PR)
```

Usamos el percentil 75 (P75) para mostrarte el tiempo de ciclo típico, filtrando los valores atípicos inusualmente largos que podrían distorsionar tu comprensión del rendimiento normal.

## Por qué es Importante

El Tiempo de Ciclo del PR es una métrica crítica que mide la capacidad de tu equipo para completar el trabajo de desarrollo de manera eficiente. Los tiempos de ciclo altos pueden indicar tamaños de lote grandes, procesos de revisión extensos o cuellos de botella en el flujo de trabajo de desarrollo.


## Cómo Mejorar

- Dividir los cambios grandes en PRs más pequeños (200-400 líneas)
- Establecer expectativas y pautas de revisión claras
- Usar verificaciones automatizadas para detectar problemas antes de la revisión
- Distribuir la carga de trabajo de revisión en el equipo
- Obtener retroalimentación temprana durante el desarrollo
- Usar una estrategia de ramas consistente
