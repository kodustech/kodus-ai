## The challenge

In a monorepo, different packages have different standards. Your React frontend cares about component patterns, your NestJS backend cares about dependency injection, and your shared libs care about API stability. A one-size-fits-all review doesn't work.

## Strategy overview

Kodus supports three config levels that map naturally to a monorepo:

| Level | Applies to | Example |
|-------|-----------|---------|
| **Global** | All repos | "Never commit `.env` files" |
| **Repository** | The monorepo | "Use conventional commits" |
| **Directory** | A specific package | "React components must use PascalCase" |

## Step 1 — Map your packages

Identify the distinct areas in your monorepo and their review needs:

```
monorepo/
├── apps/
│   ├── web/          → React rules, component patterns
│   ├── api/          → NestJS rules, architecture boundaries
│   └── mobile/       → React Native rules
├── libs/
│   ├── shared/       → API stability, breaking change detection
│   └── ui/           → Design system compliance
└── infra/            → Terraform/IaC rules
```

## Step 2 — Create directory scopes

Pick the monorepo in the scope picker at the top of the **Code review** group, open the picker again and choose **Add directory scope**. Under **Select directories**, pick one or more package folders that share review settings, then click **Add directory scope**. Each directory scope appears indented under the repository in the picker — pick it to configure it.

Each directory scope can have its own:
- **Kody Rules** (file-level and PR-level)
- **What to review** (which categories to enable, and the minimum severity to post)
- **Custom agents**, added to the repository's
- **Ignored files** (on **General**)

A pull request uses a directory's settings when it touches that configured directory and no other configured one. See [Directory-Level Settings](/en/how_to_use/code_review/configs/directory_level) for how a pull request picks its settings.

## Step 3 — Write targeted rules

On **Code review → Kody Rules**, **Review Rules** tab, click **New rule**. A rule created at a directory scope has no **Path**, so it applies to every file of a pull request reviewed with that directory scope's settings. A pull request that touches two or more directory scopes, or none, is reviewed with the repository's settings, and then the rules of **every** directory scope apply to all its files. Write directory rules so they still hold there, for example by naming the folder in the instructions. See [Rule Inheritance](/en/how_to_use/code_review/configs/rules_inheritance). To target part of a package, create the rule at the repository scope with a **Path** glob.

### Frontend rule (scope: the monorepo, with a path)

```
Rule name: React components must use design system tokens
Execution mode: Per file
Path: apps/web/src/components/**/*.tsx
Severity: High
Instructions:
  Check fileDiff for hardcoded colors, spacing, or font sizes.
  Components must import tokens from @file:libs/ui/src/tokens.ts.
  Flag any hex color, pixel value, or font-size not from the token file.
```

### Backend rule (scope: the `apps/api/` directory)

```
Rule name: Domain layer must not import from infrastructure
Execution mode: Per file
Severity: Critical
Instructions:
  In files under apps/api/src/domain, check fileDiff for any import from
  "../infrastructure", "../../infrastructure", or any path containing
  "/infrastructure/". Domain modules must only depend on other
  domain modules and shared interfaces.
```

### Shared library rule (scope: the `libs/shared/` directory)

```
Rule name: Public API changes require changeset
Execution mode: Per PR
Severity: High
Instructions:
  If pr_files_diff modifies any file in libs/shared/src/index.ts
  or adds/removes exports, check that a changeset file exists
  in the .changeset/ directory. If missing, flag it as a
  potential breaking change without documentation.
```

## Step 4 — Use Memories for cross-cutting conventions

Some conventions apply everywhere. Teach them as Memories:

```
@kody remember: in this monorepo, all packages use ESM imports.
CommonJS require() is not allowed anywhere.
```

```
@kody remember: shared libs must maintain backward compatibility.
Any breaking change requires a major version bump and a changeset.
```

## Step 5 — Set the severity threshold per directory

High-traffic packages might need stricter filters. Pick the directory in the scope picker, open **What to review**, and set **Minimum severity to post**:

- **apps/web/** — **Medium** (frontend moves fast)
- **libs/shared/** — **Low/All** (stability matters)
- **infra/** — **High** (fewer but critical)

The threshold applies to Kody Rules only when **Apply the threshold to Kody Rules** is on.

## Step 6 — Ignore generated paths

Add monorepo-specific ignores to avoid noise: in **Code review → General → Review scope**, click **Edit** under **Ignored files**, or set them in `kodus-config.yml` (read only when **Prefer kodus-config.yml settings** is on for the repository):

```yaml
ignorePaths:
  - "**/node_modules/**"
  - "**/dist/**"
  - "**/build/**"
  - "**/*.generated.ts"
  - "**/prisma/migrations/**"
  - "**/coverage/**"
```

## Tips

- Start with 2-3 rules per directory and expand based on what your team actually flags in reviews
- Use rule inheritance — org-level rules cover security, repo-level covers conventions, directory-level covers architecture
- If a rule fires too often in one package but is valid elsewhere, narrow its **Path** or rewrite it. **Override and disable for this scope** only marks an inherited rule as disabled in the list; a review still applies it

For more on directory scopes, see [Directory-Level Settings](/en/how_to_use/code_review/configs/directory_level). For rule inheritance, see [Rules Inheritance](/en/how_to_use/code_review/configs/rules_inheritance).
