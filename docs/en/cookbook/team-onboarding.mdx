## Overview

Getting a new team up and running with Kodus takes about 30 minutes. This guide walks through the complete setup so your team gets value from the first PR.

## Step 1 — Create and configure the workspace

1. Sign up at [kodus.io](https://kodus.io) or access your self-hosted instance
2. Create a new workspace for your team
3. Connect your Git provider (GitHub, GitLab, Bitbucket, Azure Repos, or Forgejo)
4. Select the repositories to monitor

The setup guide continues with the minimum severity to post, the coding-agent instructions switch (Step 3) and a pull request for Kody's first review.

## Step 2 — Set the review baseline

Kodus starts with sensible defaults, so customize only what differs. You can set the baseline in the web app, in **Code review → What to review** (categories and **Minimum severity to post**), or keep it in a `kodus-config.yml` at the root of each repository, on its default branch. Kody reads that file only after you turn on **Prefer kodus-config.yml settings** in **Code review → General** for the repository.

```yaml
# kodus-config.yml — these are the defaults
reviewOptions:
  bug: true
  security: true
  performance: true
  business_logic: true

suggestionControl:
  severityLevelFilter: medium
  applyFiltersToKodyRules: false

automatedReviewActive: true
```

This gives you automated reviews with a reasonable severity threshold. Adjust after a week based on feedback.

## Step 3 — Use the instructions you already wrote for coding agents

If your team already keeps Cursor, Copilot, Claude or `AGENTS.md` instructions:

1. In the sidebar, pick **Global** or a repository in the scope picker at the top of the **Code review** group, open **What to review**, and turn on **Coding-agent instructions**
2. Kody reads the instruction files that cover each pull request's changed files and points out changes that break them
3. For a convention you want enforced on every review, write it as a rule file in `.kody/rules`

The instruction files are never turned into Kody Rules, so they can't silently change your review policy.

## Step 4 — Teach your top 5 conventions

Don't try to encode everything on day one. Start with the 5 conventions your team argues about most:

```
@kody remember: we use camelCase for variables and PascalCase for types.
```

```
@kody remember: all API responses use the standard envelope format
{ data, error, meta }.
```

```
@kody remember: we prefer composition over inheritance.
Use interfaces and dependency injection.
```

```
@kody remember: every public function must have JSDoc with
@param and @returns descriptions.
```

```
@kody remember: database queries go through the repository layer only.
No direct DB access from services or controllers.
```

These become Memories that Kody uses in later reviews. With **Kody knowledge approval** on, each one waits in **Pending review** until someone approves it.

## Step 5 — Create 2-3 critical rules

Add rules for things that must never happen. In **Code review → Kody Rules**, on the **Review Rules** tab, click **New rule**:

```
Rule name: No console.log in production code
Execution mode: Per file
Path: src/**/*.ts
Severity: High
Instructions: Flag any console.log, console.warn, or console.error
in fileDiff. Use the project logger instead.
Exclude test files (*.spec.ts, *.test.ts).
```

```
Rule name: No hardcoded API URLs
Execution mode: Per file
Path: src/**/*.ts
Severity: Critical
Instructions: Flag any hardcoded URL (http:// or https://)
in fileDiff that looks like an API endpoint.
URLs must come from environment variables or config files.
```

## Step 6 — Connect task management (optional but recommended)

Connect Atlassian Rovo (Jira), Linear, Notion or Git Issues in **Plugins** (in the sidebar) to enable [business logic validation](/en/how_to_use/code_review/business_logic_validation). This lets Kodus check if PRs implement what the tasks describe.

## Step 7 — Run a pilot PR

Open a test PR and verify:

- [ ] Kodus comments appear on the PR
- [ ] Suggestions are relevant and at the right severity
- [ ] Your custom rules fire when they should
- [ ] Memories are reflected in the review context

## Step 8 — Gather feedback after one week

After a week of reviews, check in with the team:

- Are there too many suggestions? → Raise **Minimum severity to post** in **Code review → What to review** (`severityLevelFilter` in `kodus-config.yml`)
- Are rules too noisy? → Narrow the file paths or add exclusions
- Missing important patterns? → Add new rules or Memories
- Want auto-generated rules? → Pick the repository in the scope picker, open **Code review → Kody Rules**, click **Configuration**, and turn on **Generate from past reviews** to have Kody draft rules from your reviewers' comments. On the cloud, outside the trial, this needs [BYOK](/en/how_to_use/byok)

## Tips

- Don't overload with rules on day one — start small and grow
- Let the team teach Kody naturally through conversation before formalizing as rules
- Use `@kody start-review` for the first few PRs so the team sees Kodus in action
- Turn on **Kody knowledge approval** (**Code review → Kody Rules → Configuration**) if you want to review what Kody learns

For the full setup guide, see [Quickstart](/en/how_to_use/quickstart).
