---
title: "What is the difference between Review Rules and Memories"
description: "Understand when to use Review Rules vs Memories in Kody for the best code review results."
---

In the Kody Rules UI, you configure two different things, and knowing when to use each one makes your code reviews more effective.

A useful rule of thumb:

- **Memories** teach Kody how your codebase works so future reviews and suggestions are more relevant.
- **Review Rules** tell Kody what to flag when a PR does not match your standards.

## Review Rules

Review Rules are **checks** that run during code review. Each rule is applied to a file's diff or to the whole PR, and Kody reports a suggestion when the change breaks it.

**Best for:**
- Architecture boundaries ("domain layer must not import infrastructure")
- Code patterns ("avoid `==` in loop conditions")
- PR requirements ("every service file must have a test")
- Requirements about the PR itself, such as its description or size

**How they work:**
- Run per file or per PR (the rule's **Execution mode**)
- Run only during code review
- Can point to a file in the repository with `@file:path/to/file`
- Produce suggestions with severity levels
- Can be limited to paths and be added from the Rules Library

## Memories

Memories are **persistent contextual instructions** that Kody uses in code reviews and in conversations with Kody. They represent the background knowledge Kody should carry about your codebase, conventions, and preferences.

**Best for:**
- Codebase context ("this repo mirrors a third-party API, so some external payload fields intentionally stay snake_case")
- Suggestion preferences ("when suggesting JS utilities here, prefer native methods over Lodash")
- Migration context ("the billing module is mid-migration, so prefer incremental fixes over broad refactors")
- Architectural context ("this service follows hexagonal architecture and keeps adapters at the edge")

**How they work:**
- Added as high-priority context to code reviews and conversations
- Improve future suggestions by grounding Kody in repo-specific context
- Created via conversation (`@kody remember: ...`) or manually with **New memory** on the **Memories** tab of **Code review → Kody Rules**
- Scoped to directory, repository, or organization level
- Kody checks existing memories before saving a new one, and skips duplicates or updates the existing memory

## When to use which

| Scenario | Use |
|----------|-----|
| Check if a test file exists for every service | Review Rule |
| "This repo mirrors an external API, so some response fields intentionally stay snake_case" | Memory |
| PR description must follow a template | Review Rule |
| "Tests in this service usually live next to implementation files, not in a central test folder" | Memory |
| Flag imports that violate architecture layers | Review Rule |
| "The auth module is mid-migration, so prefer incremental changes over broad refactors" | Memory |

## Can I convert between them?

Not directly — there is no convert action in the app. Pending memories appear in the **Pending review** section of **Code review → Kody Rules**, where you can **Approve** or **Discard** them. If a memory needs more structured enforcement with file paths and severity levels, create a Review Rule with **New rule** on the **Review Rules** tab and delete or discard the memory.

For details, see [Kody Rules](/en/how_to_use/code_review/configs/kody_rules).
