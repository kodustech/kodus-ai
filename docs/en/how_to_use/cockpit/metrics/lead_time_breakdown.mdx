## What is Lead Time Breakdown

Lead Time Breakdown splits the time from a PR's first commit to its close into three phases: coding time, pickup time, and review time. It shows where your workflow slows down.

In the Cockpit, it's the **Lead Time Breakdown** chart on the **Productivity** tab: one stacked bar per week, with **Coding Time**, **Pickup Time** and **Review Time** in hours. Click a name under the chart to hide or show that phase.

## How We Calculate It

```
Coding Time = (Last Commit Time) - (First Commit Time)
Pickup Time = (PR Opened Time) - (Last Commit Time)
Review Time = (PR Closed Time) - (PR Opened Time)
```

- **Coding Time**: from the first to the last commit of the PR, including commits pushed after the PR was opened.
- **Pickup Time**: from the last commit until the PR is opened. It is negative for a PR that got new commits after it was opened.
- **Review Time**: from the PR being opened until it is closed, merged or not.

For each week, each phase is the 75th percentile (P75) across the PRs closed that week, so unusually long outliers don't skew it. A PR whose value for a phase is exactly zero, such as the coding time of a single-commit PR, is left out of that phase's P75. Only commits made up to 30 days before the PR was opened count, because older commits on a rebased branch usually belong to other work. A PR with no commit data is left out.

Time before the first commit (planning, design) and after the close (deployment) isn't counted.

## Why It Matters

Understanding where time is spent helps you optimize the right part of your process:

- **Coding Time**: shows development efficiency
- **Pickup Time**: reveals workflow bottlenecks between finishing code and asking for review
- **Review Time**: indicates review process effectiveness

## How to Improve

### Reduce Coding Time
- Make requirements clear before work starts
- Break large features into manageable pieces
- Pair on complex problems

### Reduce Pickup Time
- Open the PR right after finishing the code
- Automate PR creation and setup
- Define when code is ready for review

### Reduce Review Time
- Set clear expectations for reviewers
- Use automated checks to catch issues before review
- Spread review load across the team
- Respond promptly to review comments
- Keep PRs small
