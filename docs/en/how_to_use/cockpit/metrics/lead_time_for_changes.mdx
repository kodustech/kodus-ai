## What is PR Cycle Time

PR Cycle Time measures how long a pull request stays open: from when it is opened until it is closed. It reflects the review-and-merge speed of your process.

In the Cockpit, it's the **PR Cycle Time (p75)** card and the **PR Cycle Time** chart on the **Productivity** tab.

## How We Calculate It

```
PR Cycle Time = (PR Closed Time) - (PR Opened Time)
```

- It starts from the PR's open date, not its first commit, because rebased branches can carry old commits that would inflate the number. For the time before the PR is opened, see [Lead Time Breakdown](/en/how_to_use/cockpit/metrics/lead_time_breakdown).
- It covers PRs closed in the selected date range, merged or closed without merging.
- Time after close (deployment, user adoption) isn't counted.

The card shows the 75th percentile (P75): three quarters of PRs closed faster than this, so unusually long outliers don't skew it. The chart plots the P75 per week, in hours.

## Reading the card

The card shows the P75 in hours and minutes, a level badge, and the value for the previous period of the same length with the percentage change. The footer reads "Last 2 weeks was …" whatever range is selected; the number is for the previous period. Hover the badge to see the levels:

| P75 cycle time | Level |
| --- | --- |
| Less than 48 hours | Elite |
| 48 to 84 hours | High |
| 84 to 160 hours | Fair |
| More than 160 hours | Need focus |

## Why It Matters

High cycle times may indicate large batch sizes, lengthy review processes, or bottlenecks in the workflow.

## How to Improve

- Break large changes into smaller PRs (200-400 lines)
- Set clear review expectations and guidelines
- Use automated checks to catch issues pre-review
- Distribute review workload across the team
- Get early feedback during development
