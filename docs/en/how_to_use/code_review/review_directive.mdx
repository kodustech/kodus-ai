A **review directive** lets you tell Kody where to focus its deepest analysis for a single review. Instead of changing any configuration, you attach a short instruction when you trigger the review — for example, "focus on the auth and session logic" — and Kody spends its hardest analysis on the changed code that matches.

<Note>
  A directive is **ephemeral**: it applies to that one review run only. It is not saved to your settings and does not affect future reviews. To change Kody's behavior permanently, use category instructions and Kody's personality ([Instructions & Personality](/en/how_to_use/code_review/configs/custom_prompts), formerly Custom Prompts) or [Kody Rules](/en/how_to_use/code_review/configs/kody_rules) instead.
</Note>

## When to Use It

- A PR touches many files but you care most about one risky area (auth, payments, a migration).
- You want Kody to trace the callers and callees of a specific change and challenge it harder.
- You're re-running a review and want to steer attention without editing any config.

## Priority, Not a Filter

This is the most important thing to understand:

<Warning>
  A directive sets **priority, not a filter**. Kody prioritizes the focus area, but it still reports any concrete bug, security, or performance issue it notices **elsewhere** in the diff. It never suppresses findings outside the focus, and it never approves the rest of the PR unseen.
</Warning>

Use a directive to say *"look here hardest"* — not *"only look here."*

## How to Trigger It

<Tabs>
  <Tab title="PR / MR Comment">
    Add your focus text right after the review command in a pull request comment:

    ```text
    @kody review focus on the auth and session logic
    ```

    You can also use `start-review`, and combine it with `--force`:

    ```text
    @kody start-review focus on the new database migration
    @kody review --force focus on error handling in the webhook parser
    ```

    <Note>
      `--force` re-runs the review even when Kody would normally skip it ("no new commits since the last review"). Use it — with or without a focus directive — to get a fresh pass after fixing whatever made the previous run fail, or to apply updated settings to an already-reviewed PR.
    </Note>

    <Note>
      Only the **first line** after the command is used as the directive. Everything on later lines is ignored, so keep your focus to a single line.
    </Note>

    Works on GitHub, GitLab, Azure DevOps, Bitbucket, and Forgejo.
  </Tab>
  <Tab title="CLI">
    Pass the `--focus` flag when running a review:

    ```bash
    kodus review --focus "the auth and session logic"
    ```

    See the [CLI commands reference](/en/how_to_use/cli/commands) for the full command surface.
  </Tab>
</Tabs>

## Heavy mode

A focus directive tells Kody *where* to look hardest. `--heavy` tells it to look *wider*: next
to the usual review, nine specialist reviewers each read the whole diff for one kind of defect
only:

- code that says one thing and does another (names, measurements, results)
- text that reaches a person — messages, comments, translations — disagreeing with the code
- invalid state, broken invariants and race conditions
- boundary, index and ordering assumptions
- secrets and identity: comparisons, normalisation, fallbacks
- a changed contract that a caller was not updated for
- tests that would still pass if the behaviour they cover broke
- data leaking into responses, logs and error messages
- two changed files that do not agree with each other

Every finding of a specialist goes through the same verification as the main review's before
anything is posted, then through the usual deduplication and severity, so a guess that does not
hold up is dropped like any other.

### Heavy by default, or for one review

The **Review mode** setting on [Code review → General](/en/how_to_use/code_review/configs/general#review-mode)
picks how every review of a repository runs: **Balanced** (the default, the main review alone) or
**Heavy**. It applies to automatic reviews, to `@kody review` and to `kodus review`. A flag on one
command overrides it for that review:

```text
@kody review --heavy
@kody review --heavy focus on the payment reconciliation logic
@kody review --balanced
kodus review --heavy
kodus review --balanced
```

`--heavy` runs a heavy review on a repository set to Balanced; `--balanced` runs a balanced review
on a repository set to Heavy. If a command carries both, `--heavy` wins.

Either flag can sit anywhere on the command line — before or after your focus text — and it is
stripped from the directive either way, so `@kody review focus on the retry logic --heavy`
focuses on "the retry logic".

<Warning>
  **To combine a flag with `--force`, put `--force` first.** `--force` is only recognized
  immediately after the command word, so `@kody review --force --heavy` runs a forced heavy
  review, while `@kody review --heavy --force` runs a heavy review that is **not** forced. The
  same goes for `--balanced`.
</Warning>

A dash is required: a bare `heavy` or `balanced` is read as directive text, so `@kody review heavy
checkout path` focuses on "heavy checkout path" rather than enabling the flag.

### What to expect

- **Available to everyone**, on Cloud and self-hosted. No opt-in. In the CLI it needs a signed-in team (`kodus auth login`): a trial review runs without it and says so.
- **Your categories still apply.** The specialists of a category you turned off do not run: seven
  of them are Bug, two are Security. Kody Rules and custom agents run as they always do.
- **It runs on the Heavy model.** Under **AI providers → Routing → Code Review**, **Model for
  Heavy** picks the model of heavy reviews and **Model for Balanced** the one of balanced reviews.
  With no Heavy model set, a heavy review uses the organization default. A model set for a
  repository or directory in **Code review → General** runs both modes.
- **It costs more model calls, not much more time.** The specialists run at the same time as the
  main review, so the review takes about as long, but it uses noticeably more tokens. On your own
  model key (BYOK) that is on your provider's bill, and a provider with a low concurrency limit
  may queue the calls.
- **Without repository access** (no sandbox), the specialists read the diff alone, as the main
  review does in that case.
- The pull request list shows a **Heavy** badge on pull requests whose last review ran in heavy
  mode.

<Tip>
  Set Heavy as the review mode of the repositories where missing something is expensive — a
  payments service, an auth module — or ask for it with `--heavy` on a single risky change.
</Tip>

## Writing a Good Directive

- **Be specific about the area, not the verdict.** "focus on concurrency in the queue consumer" works better than "find bugs".
- **Name the code, not the outcome.** Point at a module, flow, or concern ("the retry logic", "the SQL in the reports service").
- **Keep it short.** Directives are capped at **500 characters**; only the first line of a comment is read.

<AccordionGroup>
  <Accordion title="Good examples">
    - `@kody review focus on the authentication and token-refresh flow`
    - `@kody review focus on the new Stripe webhook handling`
    - `kodus review --focus "race conditions in the background worker"`
  </Accordion>
  <Accordion title="Weak examples">
    - `@kody review please be thorough` — no area to prioritize.
    - `@kody review only comment on file X` — a directive is not a filter; use [Ignored files](/en/how_to_use/code_review/configs/general) to scope files instead.
  </Accordion>
</AccordionGroup>

## Notes & Limits

- **Length:** directives are truncated at 500 characters.
- **First line only:** for PR comments, only the first line after the command becomes the directive.
- **Untrusted by design:** because anyone who can comment on the PR can supply a directive, the text is sanitized before use (control characters and angle brackets are stripped). This does not change your focus — it only prevents the text from tampering with Kody's internal prompt.
- **Not persisted:** nothing is written to your repository or organization settings.
