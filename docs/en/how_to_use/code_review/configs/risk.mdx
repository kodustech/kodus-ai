Kody assesses the entire PR. [Routing](/en/how_to_use/code_review/configs/routing) and risk-conditioned custom agents use the result to decide how to review. When [automatic approval](/en/how_to_use/code_review/configs/auto_approve) is on, the result can also hold approval.

## Enable risk assessment

1. Open **Code review → Risk assessment**.
2. Turn on **Risk assessment** and click **Save settings**.

Risk assessment starts off. Kody can assess risk while automatic approval is off.

## Results

- **Risk found:** the PR falls under at least one enabled [risk rule](#risk-rules). Risk-conditioned agents may run, Routing uses its risk-found mode, and automatic approval is blocked. The approval comment names the rules.
- **No risk found:** Routing uses its no-risk mode. Approval still needs a clean review and a matching policy.
- **Unavailable:** Routing uses the configured default review mode. Automatic approval is blocked, and agents that require confirmed risk do not run automatically. The approval comment says why, for example when the Git provider did not return the diff of a code file.

With assessment off, Routing uses one configured mode for all PRs. Conditional agents do not run without confirmed risk; explicit manual agent commands bypass that condition.

An assessment covers one PR head, title and description. A new commit holds automatic approval until its review. When only the title, the description or the risk settings change, Kody assesses the same commits again before it decides on approval.

## Preview on a PR

**Preview on a PR** opens a side panel. Choose a connected repository and PR number to try the current rules, including unsaved edits. It uses the configured risk-assessment model and does not publish a comment or approve the PR.

## Risk rules

Kody finds risk when a PR falls under an enabled rule. Kodus ships these rules, all on:

- `kodus-security` **Security and permissions:** authentication, authorization, permissions, tenant isolation, input validation, or any check that protects data or actions.
- `kodus-money` **Money, billing and licensing:** payments, prices, charges, credits, invoices, subscriptions or licensing.
- `kodus-data` **Stored data and migrations:** data or schema migrations, deleting or rewriting stored data, or the shape of persisted data and the queries that read or write it.
- `kodus-infrastructure` **Secrets and infrastructure:** secrets, credentials, infrastructure, networking or the runtime environment.
- `kodus-ci-build` **CI, build, release and dependencies:** CI, build, release or deploy configuration, or a dependency or tool version.
- `kodus-shared-contract` **Shared contracts and public interfaces:** what other code, users or integrations rely on, such as the results of a public API, library function or CLI.
- `kodus-concurrency` **Concurrency, retries, queues and caching.**
- `kodus-ai-behavior` **Production prompts and model behavior:** the prompts, model choice or model settings a production feature runs with.
- `kodus-broad-change` **Broad or mixed changes:** a broad rewrite of core paths, or one PR that mixes several consequential changes.

You can turn a Kodus rule off, or edit its name, instructions or file filters. Your edits replace Kodus's version until you click **Reset**; what you leave unchanged follows Kodus's updates. Add your own rules for team context, such as the consequences of changing account permissions or deleting customer data.

A rule has a name, instructions, a switch and optional included/excluded file patterns. The settings keep up to 50 entries, counting your rules and the Kodus rules you changed. A name is up to 120 characters and instructions up to 4,000; in a file, each `id` must be unique. A rule with file filters applies only to the changes in matching files; Kody still assesses the rest of the PR against the other rules.

The assessment reads the diff, the PR title and description, and the bug-fix history of the changed areas. Missing history is unknown information, not evidence of safety.

## YAML

Turn on **Prefer kodus-config.yml settings** in **Code review → General** (repository scope) before using repository configuration files.

```yaml
riskAssessmentActive: true
riskCriteria:
  - id: kodus-shared-contract # A Kodus rule, turned off
    enabled: false
  - id: kodus-ci-build # A Kodus rule, limited to release workflows
    enabled: true
    includedFiles:
      - '.github/workflows/release*.yml'
  - id: access-control
    name: Access control
    enabled: true
    instructions: 'Check whether permission changes expose data across accounts. Distinguish them from equivalent refactors.'
    includedFiles:
      - 'src/access/**'
    excludedFiles:
      - '**/*.test.ts'
```

A Kodus rule is listed by its `id` with only what you change. `riskCriteria: []` applies Kodus's rules as shipped. `kodus config remote risk-rules .` lists the rules in effect, with their ids. To stop assessment, set `riskAssessmentActive: false`.

A configuration that never set **Risk assessment** keeps its existing approval risk behavior until you change this setting. Turning automatic approval on or off does not change the **Risk assessment** switch.
