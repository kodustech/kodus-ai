Two settings shape what Kody reports and how it reads. Both can be set at Global, Repository and Directory scope.

| Setting | Where | What it controls |
| --- | --- | --- |
| **Instructions** | **Code review → What to review**, on the Bug, Performance and Security rows | What Kody looks for in that category. |
| **Personality instructions** | **Code review → What Kody writes**, in **Kody's personality** | The tone and length of every suggestion. |

## Category instructions

Each enabled **Bug**, **Performance** and **Security** row on [What to review](/en/how_to_use/code_review/configs/what_to_review) has an **Instructions** button that opens an editor (*What counts as a bug issue*, and so on).

- The editor shows Kody's default text. The chip reads **Kody's default** until you change it, then **Custom**.
- **Reset to default** restores the default. Clearing the text does the same.
- The limit is 2000 characters.
- The button is hidden while the category is off. Business Logic has no instructions here.

Kody adds your text to its guidelines for that category. Name your stack and the patterns that matter to you:

```text
Focus on SQL injection and missing authorization checks in our API
handlers. Treat unvalidated user input reaching a query as a finding.
```

## Personality instructions

The **Personality instructions** editor in **Kody's personality** (limit 2000 characters, **Reset to default** available) sets how Kody sounds in every suggestion. It applies on top of each category's instructions.

- Kody's default keeps each suggestion to two short sentences: the impact, and what to change. When you write your own, that cap no longer applies, so say how long you want suggestions to be.
- Some rules hold whatever you write: Kody does not repeat the suggestion's title, does not put code blocks in the text because the fix is shown separately, and does not add line numbers.
- It applies to every suggestion except deterministic scanner findings. A custom agent's own writing instructions replace it for that agent's findings.

```text
Be direct. State the impact in one sentence, then the change to make.
Write in the second person and skip pleasantries.
```

## External References

Category instructions, personality instructions and [summary instructions](/en/how_to_use/code_review/configs/pr_summary) can point at files. After you save, Kody detects the references and reads those files in later reviews. A status indicator under the editor shows when processing finishes.

- `@file:path/to/file.ts` — a file in the repository being reviewed. Add `#L10-L50` for a line range.
- `@file:repo-name:path/to/file.ts` — a file in another repository.

Mentions such as "follow the guidelines in CONTRIBUTING.md" are detected too. Use precise paths so Kody finds the right file.

## Setting them in `kodus-config.yml`

The same fields are available under `v2PromptOverrides`:

```yaml
v2PromptOverrides:
    generation:
        main: |
            Tone and length for every suggestion.
    categories:
        descriptions:
            bug: |
                What Kody should look for in the Bug category.
            performance: |
                What Kody should look for in the Performance category.
            security: |
                What Kody should look for in the Security category.
```

The file accepts one more group that no page in the app edits: the severity rubric Kody uses to classify a finding.

```yaml
v2PromptOverrides:
    severity:
        flags:
            critical: |
                What counts as critical.
            high: |
                What counts as high.
            medium: |
                What counts as medium.
            low: |
                What counts as low.
```

<Warning>
  This changes how Kody *classifies* findings, not just how it words them. A bad rubric can quietly mute or inflate severities across every review. Start from the defaults in
  [`default-kodus-config.yml`](https://github.com/kodustech/kodus-ai/blob/main/default-kodus-config.yml)
  rather than writing a rubric from scratch.
</Warning>

<Note>
  `default-kodus-config.yml` also contains a `v2PromptOverrides.level` group. It is accepted but ignored; only `categories.descriptions`, `severity.flags` and `generation.main` reach the review.
</Note>

The file is only read once **Prefer kodus-config.yml settings** is on. See [General](/en/how_to_use/code_review/configs/general#config-priority).

## Tips

- **Be specific to your context.** "Focus on null dereferences in our Java services and unclosed connections in the DAO layer" works better than "look for bugs".
- **Keep categories apart.** Do not repeat the same instruction in Bug, Security and Performance.
- **Describe the pattern, not one example.** An example such as one exact string concatenation can narrow what Kody flags to that shape.
- **Start with one setting.** Run the defaults for a week, note the false positives or misses, and change only the instruction that relates to them.

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="Do these apply to all repositories?">
    Set at Global, they apply to every repository without its own value. A repository or directory can override them.
  </Accordion>

  <Accordion title="What happens to existing pull requests when I change them?">
    Changes affect new reviews only. Comment `@kody review --force` to review the whole of an existing pull request with the new text. Without `--force`, a review command covers only the commits since the last review.
  </Accordion>

  <Accordion title="Reviews are too noisy. What should I change?">
    Raise **Minimum severity to post** on What to review (see [Severity Threshold](/en/how_to_use/code_review/configs/suggestion_control)), then make the category instructions more specific.
  </Accordion>

  <Accordion title="Kody misses an issue it should catch.">
    Check that the category is on and the finding's severity is not below your threshold. Use **Reset to default** to see whether your instruction narrowed the review too much.
  </Accordion>

  <Accordion title="What is the difference between category and personality instructions?">
    Category instructions control what Kody analyzes in each category. Personality instructions control how every finding is worded. You can change them independently.
  </Accordion>
</AccordionGroup>
