---
title: "Severity Threshold"
description: "Control how much feedback Kody posts on a pull request by setting the minimum severity it comments on."
---

The severity threshold decides **which** of Kody's findings get posted. Open **Code review → What to review**; the settings are in the **Minimum severity to post** card. They can be set at Global, Repository and Directory scope. See [Config Inheritance & Overrides](/en/how_to_use/code_review/configs/inheritance_overrides).

## Minimum severity to post

Kody gives every finding a severity and posts only those at or above the level you pick on the slider. The default is **Medium**. Kody still finds lower-severity issues; it does not comment on them.

| Level | Typical findings |
| --- | --- |
| **Low/All** | Maintenance and cosmetic inconsistencies, minor redundant work, a wrong or misleading log line. |
| **Medium** (default) | Bounded defects: wrong metrics or messages, isolated request failures, ordinary invalid-input handling, limited security weaknesses, lint or CI failures that only block development. |
| **High** | A supported path becomes unusable for valid inputs, an essential durable effect fails, data is wrongly destroyed, or an admission control such as a seat or quota cap is bypassed. |
| **Critical** | A concrete route to authentication bypass, broad unauthorized administration, attacker-controlled code execution, or systemic loss of queued work. |

<Tip>
  Too much noise on a big PR is usually a severity problem, not a volume problem. Move to
  **High** before reaching for anything else — you keep every real bug and drop the nitpicks.
  See [Reduce code review noise](/en/knowledge_base/how-to-reduce-code-review-noise).
</Tip>

Findings from [coding-agent instructions](/en/how_to_use/code_review/configs/rules_file_detection) follow the threshold like any other. Deterministic findings (beta) are posted at any severity. A custom agent that sets its own minimum severity uses that instead.

## Apply the threshold to Kody Rules

A switch in the same card, **off by default**.

- **Off** — [Kody Rules](/en/how_to_use/code_review/configs/kody_rules) findings **bypass** the severity threshold. A rule your team wrote is always reported, whatever severity it lands on.
- **On** — Kody Rules go through the same threshold as every other finding.

Leave it off unless your rules produce more noise than signal. The point of a Kody Rule is that your team already decided it matters.

<Note>
  In `kodus-config.yml` these settings live under `suggestionControl`:

  ```yaml
  suggestionControl:
      severityLevelFilter: 'medium' # low | medium | high | critical
      applyFiltersToKodyRules: false
  ```

  The file is only read once **Prefer kodus-config.yml settings** is on. See
  [General](/en/how_to_use/code_review/configs/general#config-priority).
</Note>

## Other ways to cut noise

The threshold is a blunt instrument. When you need something more targeted:

- **Ignored files** — skip generated code, lockfiles and vendored directories. See
  [General](/en/how_to_use/code_review/configs/general#ignored-files).
- **Categories** — turn off a whole category, such as Performance, with its switch on
  [What to review](/en/how_to_use/code_review/configs/what_to_review).
- **Directory-level config** — set a stricter or looser threshold per folder in a monorepo. See
  [Directory-Level Settings](/en/how_to_use/code_review/configs/directory_level).
- **Kody Rules** — write down what your team cares about, so the signal comes from your standards
  instead of generic advice.
