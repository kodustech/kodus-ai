## Overview

Business Logic Validation checks that a pull request delivers what its task asks for. Kody finds the task the PR references, reads it from your task tracker, and lists every requirement with where it stands in the code. The result is one comment on the PR, kept up to date, and the `kody/business-logic` check.

<img src="https://kodus.io/wp-content/uploads/2025/10/business-logic.gif" alt="Example of using business logic validation" />

## Prerequisites

- A task tracker connected in [Plugins](/en/how_to_use/code_review/plugins): Linear, Jira (Atlassian Rovo), Notion, Git Issues, or a custom plugin.
- Kody only **reads** tasks, one at a time, by their id. It never searches, lists or writes to your tracker.
- Without a tracker, you can still paste the task text in the command (see below).

## Turning it on

Business Logic is on by default. Turn it on or off in **Code review → What to review**, on the **Business Logic** row, or in `kodus-config.yml`:

```yaml
reviewOptions:
  business_logic: true
```

Click **Configure** on that row to open the Business Logic settings.

## How Kody finds the task

Kody looks for task references in the PR title, branch name and description, in that order:

- Keys like `PROJ-123` (Jira, Linear and most trackers)
- `#123` and `owner/repo#123` (Git issues; a number that is a pull request is ignored)
- `AB#123` (Azure Boards)
- Links to Linear, Jira, Notion, GitHub/GitLab issues and Azure work items

A reference only counts once the tracker returns a task with that exact id, so `UTF-8` or `gpt-5` in a title are never mistaken for tasks.

- **"Closes PROJ-1"** or a key in the title or branch: the PR is checked against the whole task.
- **"Part of PROJ-1"** or **"Refs PROJ-1"**: the PR delivers a slice. What's missing is listed, but doesn't fail the check.
- **Up to three tasks** are checked per PR, one section each. A PR that states more (a release or a merge) is skipped.

## The five states

| State | Meaning | Fails the check |
|---|---|---|
| **MET** | The diff implements it. | No |
| **PARTIAL** | Part of it is implemented. | Only if you choose |
| **MISSING** | No evidence in this PR diff. | Yes, by default |
| **CHECK MANUALLY** | A visual or flow requirement, one Kody isn't sure about, or one that may live in a file too large to read. | Never |
| **NOT IN TASK** | A change the task doesn't ask for. | Only if you choose |

Every row cites the file and line it is based on, and says what to change.

## On the pull request

- Kody checks the PR on its **first review**. Turn on **Re-check on every push** to check every push instead.
- Re-check any time with `@kody -v business-logic`. The **same comment is edited**; Kody never posts a second one.
- A PR that meets its task gets only the green `kody/business-logic` check. Turn on **Comment when every requirement is met** to get the comment too.
- The check exists on GitHub and Forgejo. Make it required in your branch protection to block merging on a failing check. On GitLab, Bitbucket and Azure Repos the comment is the signal.

### Replying to the comment

Reply to the Business Logic comment and mention `@kody`:

- **Disagree**: "It's covered in `useDrag.ts`". Kody re-checks what you pointed at and either marks it MET or says what it looked at and keeps it.
- **Accept a finding** (reviewers and maintainers only, never the PR author): "Keyboard reordering is out of scope, moved to SAA-102". Kody confirms SAA-102 exists, marks the row **ACCEPTED** with who accepted it, and the check passes if nothing else blocks it. The decision stays on later re-checks.

## When Kody stays quiet

Kody comments only when the author can do something about it:

| Situation | On the PR |
|---|---|
| The task has only a title | A comment asking for acceptance criteria |
| `SAA-999` doesn't exist, but SAA is a team in your tracker | A comment saying it looks like a typo, with the closest real tasks |
| No task referenced | Nothing; the check is skipped |
| A GitHub issue, but only Linear is connected | Nothing; admins see a count on the settings page |
| The tracker is down or its token expired | Nothing; the check is skipped, owners are notified, and Kody re-checks once the tracker answers |

The reason for every skip is recorded and shown on the Business Logic settings page.

## Running on demand

Comment on the PR (not on a line of code):

- `@kody -v business-logic`: re-check the tasks the PR references
- `@kody -v business-logic PROJ-123` or a task link: check against that task
- `@kody -v business-logic` followed by the requirements as text: check against what you wrote, no tracker needed

## Settings

Open **Code review → What to review → Business Logic → Configure**. Every setting can be set globally and overridden per repository or directory.

- **Task source**: every connected tracker, or one plugin. For a custom plugin (for example Azure DevOps), pick the tool that reads one task by its id; only read-only tools are offered. Use **Try it with a real task** to check what Kody reads before saving.
- **Where acceptance criteria live**: detected automatically, under a heading in the description, or in a field (for Jira, the custom field your team fills).
- **What fails the check**: MISSING by default; add PARTIAL and NOT IN TASK if you want.
- **Team guidance**: notes Kody follows when it judges, for example "Feature flags count as implemented when the flag exists and defaults to off". It can't change the verdict format or make Kody invent requirements.

The same settings in `kodus-config.yml`:

```yaml
businessLogic:
  taskSource: 'auto'
  failOn: ['missing']
  criteriaLocation: 'heading'
  criteriaHeading: 'Acceptance criteria'
  commentWhenMet: false
  recheckOnPush: false
```

## From the CLI

A coding agent can check its work before opening the PR:

```bash
kodus pr business-validation --task-id AB#8
kodus pr business-validation --task-id AB#8 --format json
```

It checks your local changes against the task and prints one line per requirement and the status. With `--format json` (or `--agent`) it prints the same verdict structured, for an agent to act on. Nothing is posted to a pull request.

## Cockpit

**Cockpit → Delivered as asked** shows the share of PRs that met their task, changes not in the task, how often developers agreed with Kody, and the split by who wrote the code (people or coding agents, from commit authors and `Co-Authored-By` trailers) and by team.
