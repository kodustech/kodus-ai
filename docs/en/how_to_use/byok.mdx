BYOK (Bring Your Own Key) is the **default way Kodus uses LLMs across every plan**: Free, Teams, and Enterprise. You connect your own provider accounts, add the models you want, and choose which model runs each task. Your provider bills you directly for tokens, and your key is stored encrypted and never shown back in plain text.

BYOK also works on self-hosted Community. Only [Owners](/en/how_to_use/workspace_roles) can manage provider credentials in **AI providers**. Enterprise customers can also use Kodus-managed models under their agreement.

## How BYOK works

BYOK is **provider-first**: you connect a provider once, add the models you want to it, and then choose which of those models runs each of Kody's tasks. Connecting lives on the **AI providers** page (sidebar → **AI providers**), which has two tabs. Choosing models per task lives on **Code review → Routing**, which the **Configure routing** button on the page header opens.

## Connect a provider

<Steps>
  <Step title="Open AI providers">
    In the sidebar, open **AI providers** ([app.kodus.io/byok](https://app.kodus.io/byok)). On a fresh workspace you'll see **Connect your first provider**.
  </Step>

  <Step title="Pick a provider">
    The provider grid is split in two:

    - **Providers** — first-class providers you connect with just an API key (OpenAI, Anthropic, Google, OpenRouter, Novita, Moonshot, Z.ai…).
    - **Custom** — providers you point at your own endpoint or run an arbitrary model on: **OpenAI-compatible**, **Anthropic-compatible**, **Google Vertex AI**, **Amazon Bedrock**, and **Azure OpenAI**. Custom endpoints are marked with a *Custom endpoint* hint.

    A provider you've already connected shows **Connected · N models**.
  </Step>

  <Step title="Add a model">
    Picking a provider opens its add-model form (**Add a … model**). Paste the API key once (reused for every model you add to that provider afterward), then choose the model:

    - If Kodus lists the provider’s models, pick one from the dropdown. For a model that is missing, choose **Type model manually** and enter the exact model ID.
    - Otherwise (custom endpoints, self-hosted, or when platform keys aren't configured), type the exact model ID.

    Custom endpoints (OpenAI-compatible / Anthropic-compatible) also ask for a **Base URL** first, and Azure OpenAI for a **Resource endpoint**. **OpenAI** shows an optional **Base URL** for your own proxy or gateway; leave it empty to call OpenAI directly. Paste the base URL without the endpoint path (no `/chat/completions`). It must use `https://` and resolve to a public address.
  </Step>

  <Step title="Tune advanced settings (optional)">
    In the **Advanced (optional)** card, expand **Advanced settings**: **Thinking / Reasoning**, **Temperature**, **Max output tokens**, **Max input tokens**, and **Max concurrent requests**. Defaults are sensible for most providers — see [Reasoning](/en/how_to_use/byok/model_settings#reasoning-/-extended-thinking) and [Temperature](/en/how_to_use/byok/model_settings#temperature) for the fields Kodus locks or hides per model.
  </Step>

  <Step title="Test and save">
    Click **Test** to check the configuration, or **Test & save** to run the test and save on success. Add as many models to the provider as you want; the key is only pasted once.
  </Step>
</Steps>

<Tip>
  **Add another provider** any time from the Providers tab. Each provider keeps its own key; enabling more models on a connected provider never re-asks for it.
</Tip>

## Test before you save

The **Test** button needs a model chosen first. It sends a minimal real request to that model, built the same way a review builds it, with your key, base URL, temperature, and reasoning setting. A passing test means this exact configuration works, and a failing one returns the provider's message on the spot: a wrong model ID, a restricted key, or an endpoint problem. Google Vertex AI first checks the service account, then makes the same request. Amazon Bedrock without a model only checks the credentials.

Test also checks your tuning against the model's own rules and returns a specific message instead of saving a setting the model would ignore:

- A temperature the model ignores or pins (see [Temperature](/en/how_to_use/byok/model_settings#temperature)).
- Reasoning turned **Off** on a model that always reasons and can't be disabled.

When the test passes but a reasoning override or effort reached no parameter of the request, the result carries a warning saying so.

<Info>
  Because Test uses the real model, a **typo in the model ID is caught at Test time** rather than at your first review: the response comes back `Model not found`.
</Info>

## Edit or remove

On the **Providers** tab, **Edit model** changes a model's settings, **Edit provider** changes the provider's key, and **Remove model** (the trash icon) removes a model. A model that is still the default or fallback, set for a task, used by a repository or directory, or pinned on a custom agent can't be removed. The row lists where it is used, so change those first. Removing your last model disconnects BYOK: Kodus uses the LLM set by environment variables if there is one, and otherwise stops running reviews until you connect a model.

## Routing: which model runs each task

Open **Code review → Routing** at **Global** scope (or **Configure routing** on **AI providers**). The **Models** card sets the defaults for your organization. Only Owners edit it; routing is flat, so every task uses the default until you pick another model for it.

- **Default model**: the one model every task uses unless overridden.
- **Fallback model**: a *different* model Kody re-runs a call on, once, when the task's model fails: a bad or expired key, no credit, access denied, or the provider being down (after its own retries). Without one, the review fails.
- **Risk assessment model**, **Balanced model** and **Heavy model**: the models for [risk assessment](/en/how_to_use/code_review/configs/risk) and for each review mode. **Heavy model** is available on Teams and Enterprise. Each uses the default until you pick one.
- **Other task models** (expand it): **Kody Rules**, **PR Summary**, **Conversation**, **Business Rules**, and **Custom Agents** can each run a different model, for example a cheaper one for summaries. A model that can't do a given task is disabled in that row with a tooltip.

Click **Save settings** to persist, or **Reset** to discard your edits. A **Repository overrides** panel lists the models set for single repositories, directories and custom agents. You set a repository or directory model with the scope picker on **Routing**; see [Routing](/en/how_to_use/code_review/configs/routing).

<Note>
  With a single connected model, routing is fixed to it. Connect a second model to make routing meaningful.
</Note>

## Subscriptions and coding plans

Some providers sell a flat-rate subscription, often called a coding plan, instead of or next to pay-per-token API access. Kodus connects to one the way it connects to any API: with the key and the endpoint the plan gives you. It never signs in with your account on a provider's website or app.

Whether a plan can be used this way is up to the provider, and each one sets its own rules. Before you rely on one:

- **Check its terms.** Some plans allow use only from the provider's own apps, or limit automated use. Providers can change this at any time, and Kodus can't check it for you.
- **Check its limits.** Plans often cap concurrent requests, request windows or monthly use. Set **Max concurrent requests** to match, and add a **Fallback model** on a different provider so reviews don't fail when a cap is hit. See [Concurrency and rate limits](/en/how_to_use/byok/model_settings#concurrency-and-rate-limits).
- **Use the plan's own endpoint.** A plan's key often works only on that plan's endpoint, not on the provider's pay-per-token API. [Kimi and GLM](/en/how_to_use/byok/providers#connecting-kimi-moonshot-and-glm-z-ai) show the difference.

Using a subscription plan is at your own risk. If the provider limits or ends access, reviews behave as with any other provider failure: they move to the **Fallback model** if you set one, and fail if you didn't.

## Kodus credits

If your Kodus Cloud workspace has access to the **Kodus** provider alpha, go to **AI providers** and choose **Kodus** to add a model without an API key. Use **Kodus credits** to add prepaid balance. Model usage is deducted at the listed price per token, and the top-up screen shows the platform fee before you pay.

Use **Configure routing** to choose which tasks run on the model. If the balance runs out, reviews routed to Kodus models pause until you add credits. Models using your own provider keys keep working.

## Advanced settings

Each model's form has an optional **Advanced settings** card: reasoning, temperature, output and input limits, and concurrency. The defaults suit most providers; see [Model settings](/en/how_to_use/byok/model_settings). Two settings are worth knowing before you need them.

### Custom JSON override

For a provider option Kodus has no field for, choose **Custom** in **Thinking / Reasoning** and paste the JSON. See [Custom JSON override](/en/how_to_use/byok/model_settings#custom-json-override).

### Pinning OpenRouter providers

On an OpenRouter model, **OpenRouter routing** pins which upstream providers serve it. See [Pinning OpenRouter providers](/en/how_to_use/byok/providers#pinning-openrouter-providers).

## Best Practices

### Security

<CardGroup cols={2}>
  <Card title="Dedicated Keys" icon="shield-check">
    Create separate API keys for Kodus. Makes usage auditing and key rotation easier.
  </Card>
  <Card title="Regular Rotation" icon="arrows-rotate">
    Rotate keys periodically and update them with **Edit provider** on the **AI providers** page.
  </Card>
  <Card title="Monitor Usage" icon="chart-bar">
    Check your provider dashboards for unusual patterns.
  </Card>
  <Card title="Secure Storage" icon="lock">
    Never commit keys to repositories. Kodus stores them encrypted at rest and in transit.
  </Card>
</CardGroup>

### Routing strategy

- Use a **different provider** for your default and fallback (e.g. Anthropic default, Google fallback). Protects against provider-specific outages.
- Subscriptions with tight concurrency limits (GLM Coding Plan Lite/Pro, Kimi Code Plan) make poor solo configurations — pair them with a pay-per-token fallback so bursty PRs don't starve.
- Route the heavy tasks (code review) to your strongest model and the light ones (summaries, chat) to a cheaper one under **Other task models** on **Code review → Routing**.
