To review a PR with the right context, Kodus parses the entire repository
into an **AST graph** (nodes + edges) and uses it to fetch cross-file
context, validate suggestions, and feed the agent. The parser runs inside
a **sandbox** so it can `git clone`, install dependencies, and execute the
CLI in isolation from the API process.

The same sandbox gives review agents their file tools (search, read file,
list directory) over the checked-out repository, in reviews and in `@kody`
conversations.

This page explains the sandbox modes you can pick from, what the AST
graph is, and how the cache keeps PR-level reviews fast.

## How the AST graph works

Kodus uses [`@kodus/kodus-graph`](https://www.npmjs.com/package/@kodus/kodus-graph),
a CLI that walks a repository and emits a JSON graph (functions, classes,
files, imports, calls). The CLI is **pre-installed in the Kodus images**
(including `kodus-ai-worker`), so there is no extra setup step on `local` mode.

The lifecycle:

1. **When you select a repository** (during setup, or when adding a repo
   later in the UI) — Kodus enqueues an `AstGraphBuild` job that runs
   `kodus-graph parse --all` against the default branch, persists the
   result to Postgres (`ast_graph_*` tables), and marks the repo as
   indexed. This happens in the background — you don't have to wait for
   it to finish before opening PRs.
2. **When a PR is merged into the default branch** — webhook handlers
   enqueue an incremental rebuild that re-parses only the changed files
   and merges the deltas into the cached graph. A merge that changes more
   than 500 files triggers a full rebuild instead.
3. **On every PR review** — Kodus loads the cached graph, parses only
   the files touched by the PR, and feeds the agent a focused subgraph.
   This is the hot path; it never re-parses the whole repo.

The cache is what makes large-repo reviews tractable: the first build
runs once at repo-onboarding, every PR after that reads from Postgres.

## Sandbox modes

The sandbox is selected by `SANDBOX_PROVIDER` in `.env`:

| Mode | What it does | Trade-off |
|---|---|---|
| **`local`** _(installer default)_ | Runs `kodus-graph` inside the `worker` container itself. Bun + the CLI are pre-installed. | No external dependency. Shares the worker container's CPU and memory. |
| **`e2b`** | Spins up a remote [E2B](https://e2b.dev) sandbox per job. Requires `API_E2B_KEY`. | Strong isolation, scales for huge repos. **Paid third-party service.** |
| **`auto`** | Uses `e2b` when `API_E2B_KEY` is set, otherwise `local`. | What you get when `SANDBOX_PROVIDER` is not set. |
| **`null`** | No sandbox. | Reviews see only the diff: no cross-file context and no code graph. |

### Picking a mode

- **You're getting started, want it to "just work"** → `local`. This is
  the installer default and needs zero external accounts.
- **Repos are very large or you want strict isolation** →
  `e2b`. Sign up at [e2b.dev](https://e2b.dev), set `API_E2B_KEY`, switch
  `SANDBOX_PROVIDER=e2b`.

`SANDBOX_PROVIDER=e2b` without `API_E2B_KEY` leaves reviews with no sandbox:
no cross-file context, and no code graph. Setting only `API_E2B_KEY` while
`SANDBOX_PROVIDER=local` keeps the local sandbox.

Set `SANDBOX_PROVIDER=null` to turn the sandbox off. `./scripts/doctor.sh` warns when it is off. If `./scripts/validate-env.sh` rejects `null`, check the allowed values in the installer's `.env.example`. Older installer schemas list `none`, which the worker treats as `auto`.

## Migrating an existing self-hosted install

If you upgraded from a release that predates the AST graph, your
**already-selected repositories** won't have a graph yet — the build only
fires automatically on **new** repo selections. To index them, run the
backfill script bundled with the installer:

```bash
# From the kodus-installer directory, with the stack running:
./scripts/backfill-ast-graph.sh
```

This walks every team in the instance and enqueues an `AstGraphBuild`
job for each selected repo whose graph status is not set, `pending` or
`failed`. Builds run in the background — you can keep using Kodus
while they finish.

The script is **idempotent**: re-running skips repos that are already
`ready`, never re-enqueues `building` jobs, and you can stop and resume
freely.

Common flags:

```bash
./scripts/backfill-ast-graph.sh --org <id>          # restrict to one org
./scripts/backfill-ast-graph.sh --org <id> --team <id>  # one team only
./scripts/backfill-ast-graph.sh --force             # also rebuild ready graphs
./scripts/backfill-ast-graph.sh --limit 50          # cap jobs per team (default: 10)
./scripts/backfill-ast-graph.sh --dry-run           # list teams, enqueue nothing
```

You can watch progress in the worker logs:

```bash
docker compose logs -f worker | grep -i ast-graph
```

## Configuration

```bash
# Default for self-hosted — runs in the worker container.
SANDBOX_PROVIDER=local

# Or use E2B (paid) for stronger isolation.
SANDBOX_PROVIDER=e2b
API_E2B_KEY=your-e2b-api-key
```

Sign up for E2B at [e2b.dev](https://e2b.dev), generate an API key in the
dashboard, then drop it in `.env` and run `./scripts/install.sh` again.

In `local` mode the worker clones the repository with a 120 second budget. A
slow clone of a very large monorepo can exceed it, and the review then runs
without a sandbox. Raise the budget in milliseconds:

```bash
API_SANDBOX_CLONE_TIMEOUT_MS=300000
```

```mermaid
    sandbox_local --> graph[(Postgres • ast_graph_*)]

    graph --> agent[code-review agent]
```

## Resource sizing

The `local` sandbox runs `git clone` and `kodus-graph parse` inside the
`worker` container, so the worker's memory limit applies to them. The Helm
chart sets a `1536Mi` limit on the worker. If the worker is killed for memory
while it builds a graph, raise the limit under `services.worker.resources`, or
use `e2b` to parse off the host.

## Troubleshooting

**Reviews don't include cross-file context (`local` mode):**

Check the worker logs for clone or `kodus-graph` parse errors:

```bash
docker compose logs -f worker | grep -iE "sandbox|kodus-graph"
```

The worker needs network access to your Git provider to clone. `./scripts/doctor.sh` runs a read-only
`git ls-remote` against a selected repository and reports a failure.

**`e2b` jobs hang or fail to start:**

Verify `API_E2B_KEY` is set and valid:

```bash
docker compose exec worker sh -c 'if [ -n "$API_E2B_KEY" ]; then echo "API_E2B_KEY is set"; else echo "API_E2B_KEY is missing"; fi'
```

The E2B dashboard shows live sessions and quota usage.
