TWO DIFFERENT MECHANISMS DID THE WORK, and the run separates them:

  * The two `unused` cases now come back `judged 0` — the judge never emits the
    finding. Those cases got the PR's intent (T6) and the instruction to declare
    what a finding asserts (T7); nothing was retrieved and nothing was refuted.
  * `missing` and `duplicate` still come back `judged 1`. The model still asserts
    it, and the claim checker refutes it against the repository and drops it
    (T8/T9). The drop reason is printed on each replicate.

That split matters: the prompt half is a behavioral change and could move back
on another model or another day; the checker half is deterministic and will not.

HARNESS
    The runner now mirrors the provider's sequence — retrieve declared context,
    judge, then refute each claim — instead of calling the judge alone. Measuring
    only the judge would have measured the prompt and none of the checks this
    issue added. The lookup is built over each case's own `repoFiles`, with the
    same contract as `buildRepoLookup`: it answers `path:line:content` or the
    literal "No matches found.", and never with silence.

    Retrieval (T15) is wired but inert on this corpus: none of the four rules
    carries a `contextNeed`, so every one resolves to `diff-only`. Retrieval
    fixes false NEGATIVES, which a negative corpus cannot show by construction.
