# libs/runtime/environment

The one port for "this app up at this SHA" (docs §5, ADR-002): `EnvironmentRuntime`, which every consumer of a claim (a Run, a setup, an env session, a sandbox, a preview, a suite shard) calls in the runtime-worker. The control plane never talks to a cloud or a machine; the port's implementation sends messages through the hub to the cell. This module is the port, its types and the claim ceilings, plus an in-memory driver.

## Owns
- The port: `environment-runtime.ts` `EnvironmentRuntime` (`acquire`, `probe`, `exec`, `reset`, `release`, and the optional `exploreBrowser`, `snapshotRound`, `renew`, `bake`, `poolTarget`, `progress`, `upload`, `status`), with `AcquireRequest`, `Claim`, `Blocked`, `EnvError`, `ProbeOutcome`, `StepResult`.
- The typed blocker (docs §5): `Blocker.kind` is a `BlockerKind`; the optional `title`, `evidence` (`BlockerEvidenceOfClaim`: `stepId`, `lines`, `proxyLog`, `service`) and `fixes` (`BlockerFixView`) are the shared catalog's card. `typed-blocker.ts` `blockerKindOf` (anything outside `BLOCKER_KINDS` reads `unknown`), `typedBlocker`, `typedBlocked`, applied by the worker's hub client; imported by file path, not from the barrel. The blocker's id, state and seen stay in the setup record; `tried` is not carried on the acquire: the product's blocker card computes it from the setup's learn loop (`libs/runtime/api/application/use-cases/environment-blockers.ts` `triedOn`).
- The health of an environment (`status`, docs §5): `EnvironmentHealth` in `environment-runtime.ts`, computed by `environment-health.ts` `environmentHealthOf` from what is already kept (the setup record's state, image, cell, the week's setup boots, its open blockers), never a cell or cloud call; a blocker kind outside `BLOCKER_KINDS` reads `unknown`. The product API computes the same health for the /mcp/env `env_status` tool from the setup record it reads (`libs/runtime/api/application/env-tools.service.ts`). `UploadRequest` mirrors the protocol's `upload` frame; a cell that cannot take files is `EnvError` `upload_unavailable`.
- Claim ceilings per consumer: `LEASE_TTL_MINUTES`, `HARD_EXPIRY_MINUTES`, `READY_TIMEOUT_MINUTES`, `readyTimeoutMinutes`, `readyDeadlineOf`, `bootTimedOut`.
- Capacity refusals: `isCapacityWait`, `CAPACITY_WAIT_SIGNATURES`; `isolation-blocker.ts` `isolationUnavailable`; the org's daily machine minutes, `machine-minutes.ts` `decideMachineMinutes`, `effectiveMachineMinuteLimit` (the org's own limit lowers the deployment's, never raises it), `claimCeilingSeconds`, `machineMinutesExhausted` (names which limit refused).
- The in-memory driver: `fake-environment-runtime.ts` `FakeEnvironmentRuntime` (scenarios, deterministic clock), used by specs, the fake cell (`apps/runtime/src/fake-cell`) and the worker's dev fake driver.

## Does not own
- The implementation over the hub: `apps/runtime/src/worker/env/hub-environment-runtime.ts` `HubEnvironmentClient`.
- The claim's state transitions and its row: `apps/runtime/src/hub/claims/`. The machine-minute ledger: the hub (`runtime.runtime_machine_org_day`).
- Blocker kinds and the vocabulary of sides and consumers: `libs/runtime/contracts/enums.ts`.

## Rules and limits
- Every wait on a claim comes from its ceiling: the ready timeout is below the hard expiry and the lease never outlives it (`claim-ceilings.spec.ts`); a setup waits for its build until a minute before its ceiling.
- `probe` runs on the observer, outside the VM, and is the only path to a verdict; `exec` runs inside the VM, for setup and internal evidence.
- A claim is never placed on a cell with lower isolation than it asks; the admission reserves the claim's whole ceiling before anything reaches a cell.
- `index.ts` re-exports the fake driver from the barrel, although [`AGENTS.md`](../AGENTS.md) says no barrel re-exports a test double; `testing.ts` exports it too.

## Where new code goes
- A new claim operation: the method on `EnvironmentRuntime` (optional if not every driver has it), `HubEnvironmentClient`, `FakeEnvironmentRuntime`, and the protocol message in `libs/runtime/protocol`.
- A new consumer: `contracts/enums.ts` `CLAIM_CONSUMERS`, then its row in each ceiling table here.

## Tests
- `node node_modules/jest/bin/jest.js --runInBand libs/runtime/environment` (pure).
