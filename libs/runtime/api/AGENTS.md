# libs/runtime/api

The product side of the Runtime, as Nest modules: the composition root that wires the use cases (`application/`) to the adapters (`infrastructure/`) behind the ports of `domain/`. `apps/api` imports `RuntimeApiModule`; `apps/worker` imports `RuntimeTriggerModule` (the PR trigger consumer) and, for external-finding maintenance, `RuntimeApiModule`; `libs/mcp-server` imports `RuntimeApiModule` for the /mcp/env tools. See [`libs/runtime/README.md`](../README.md) "api".

## Owns
- `runtime-api.module.ts` `RuntimeApiModule`: every provider and port binding (Runtime readers on one `RuntimeReadDb`, TypeORM stores of product tables, the Git port and repo token issuer with their dev stubs, BYOK providers, the env-session and preview clients, OpenBao, A2A, the crons) and what it exports.
- `runtime-trigger.module.ts` `RuntimeTriggerModule`: `RuntimeTriggerConsumer` and `RuntimeWebhookReconcilerCron`, so only the product worker subscribes to the trigger queue.
- `index.ts`: the old barrel of `domain/` (budget, cell token, egress, ports, run token, commands) plus `contracts/evidence`.
- `testing.ts`: in-memory doubles of the API's ports (`InMemoryReconciledHeadStore`, `InMemoryRuntimeEnvAuditStore`).

## Does not own
- Routes and DTOs: `apps/api/src/controllers/runtime/`. Rules: `domain/`. Use cases: `application/`. Adapters: `infrastructure/`.

## Rules and limits
- Hexagonal: `domain/` holds rules and ports (no Nest, no driver), `application/` the use cases, `infrastructure/` the adapters ([`AGENTS.md`](../AGENTS.md) "Dependency direction"). Only this folder's modules bind a port to an adapter.
- The API never writes Runtime state: Runtime stores are bound to read-only readers (`ReadOnlyRunProjectionStore`); a decision that changes it goes on the outbox.
- `RuntimeReadDb` is the one pool on the Runtime Postgres; a new reader takes it as its `SqlQuery`.
- The dev Git stub (`RUNTIME_DEV_GIT_STUB_FILE`) is refused in production (`infrastructure/dev-stub-git.adapter.ts`).
- `testing.ts` and `__tests__/fixtures.ts` are never imported by production code.

## Where new code goes
- A new use case: a file in `application/use-cases/`, listed in the module's `useCases`, exported if a controller injects it.
- A new port: its interface and token in `domain/ports.ts` (or a domain file of its area), its adapter in `infrastructure/`, the binding here, and a double in `testing.ts` or `__tests__/fixtures.ts`.

## Tests
- `API_NODE_ENV=test npx jest libs/runtime/api` (the specs are in `__tests__/`; `fixtures.ts` holds the shared doubles, the real RBAC `realAuthorization` and the test seal key).
- Integration specs (`*.integration.spec.ts`) need `RUNTIME_IT_DATABASE_URL` naming a disposable Postgres.
