# libs/runtime-publish/application

The publisher's use cases, in the product worker: one delivery of a `RuntimePublishRequested` checked and published, the sweep that re-drives the final publications the broker lost, and the one-line answer to a `@kody runtime` that started no Run. They see the product only through the ports of `domain/runtime-publish.ports.ts`. The flow, step by step, is [README.md](../README.md) sections 1 to 7.

## Owns
- A delivery, end to end: `publish-runtime-request.use-case.ts` `PublishRuntimeRequestUseCase.execute` (unwrap with `unwrapPublishMessage`, strict schema, `keyMatches`, `shapeProblem`, `resolveTarget`, claim, then the kind's publisher, then the replies; one metric per delivery). `ALERT_REFUSALS` picks the refusals logged as errors with `alert: 'runtime_publish_refused'`.
- The outcomes and errors every publisher shares: `publication-outcome.ts` `RefusalReason`, `PublishOutcome`, `PublishOptions` (`fallback`), `PublicationBusyError`, `PublicationFailedError` (both thrown so the broker retries), `PublishTarget`.
- The PR comment: `comment-publisher.ts` `CommentPublisher.publish` (slot acquired with a bounded wait, `commentOrderOf` against stale phases, edit or create, `createPending` and adoption of Kody's own marked comment with `isOwnComment` and `recoveredCommentRef`).
- The check: `check-publisher.ts` `CheckPublisher.publish` (`checkNameOf` per environment, the `awaiting_approval` run carried to the final key, `MAX_CHECK_CREATE_ATTEMPTS`, the neutral fallback, a commit status when the connection cannot create check runs, skipped at once when the token may not write one, and a late `awaiting_approval` phase skipped once the verdict is on the PR).
- Replies on reproduced review suggestions: `reply-publisher.ts` `ReplyPublisher.publish`, one key per suggestion, also run on a duplicate so a redelivery finishes the leftovers.
- The redrive sweep: `redrive-runtime-publications.use-case.ts` `RedriveRuntimePublicationsUseCase.sweep` (reserve, then the same `execute`, fallback, give up).
- The skipped-trigger answer: `skipped-trigger-reply.ts` `SkippedTriggerReplyPublisher.answer`, bound by `libs/runtime/api/runtime-api.module.ts` under `RUNTIME_SKIPPED_TRIGGER_REPLY_TOKEN` for the trigger use case.

## Does not own
- The rules these call (claims, slot, environment, redrive policy, wording): `domain/`.
- The broker subscription and the cron: `infrastructure/runtime-publish-requested.consumer.ts`, `infrastructure/runtime-publication-redrive.cron.ts`.
- Which Runs ask to publish, and when: the runtime-worker (`apps/runtime/src/worker/run/`).

## Rules and limits
- A refusal returns (the consumer acks it); only a retryable failure throws. A thrown publish releases its claim with the error and the state to keep (`PublicationFailedError.keep`).
- A redrive is a delivery: `sweep` calls `PublishRuntimeRequestUseCase.execute` with the stored request, so it cannot post what a delivery could not.
- An edit that fails with 403, 404 or 410 creates a new comment; any other edit error throws, never a duplicate.
- A marked comment is adopted only when its author is the integration's own (`CommentAuthorPort`); without one, a new comment is posted.
- Logs carry ids and Zod issue paths and codes, never message values; metric labels are `kind` (check, comment, unknown), `outcome` and `reason`.

## Where new code goes
- A new refusal: `RefusalReason` in `publication-outcome.ts`, in `ALERT_REFUSALS` if it can only mean a bug or tampering, and the README's list.
- A new kind of publication: its own publisher class here, called from `PublishRuntimeRequestUseCase.publish`, its key shape in `libs/runtime/run` `publishKey` and `keyMatches`.

## Tests
- `API_NODE_ENV=test npx jest libs/runtime-publish/application` (in-memory stores from `../testing.ts`, no services). `publish-runtime-request.use-case.spec.ts`, `publish-runtime-report.spec.ts` and `redrive-runtime-publications.use-case.spec.ts` cover the cases listed in the README's Tests section.
