# libs/runtime-publish

The product side of a Run's publication: it turns a `RuntimePublishRequested` from the runtime-worker into the PR comment, the "Kody Runtime" check and the replies on review suggestions, posted with the product's Git credentials, which the Runtime never holds. It runs in the product worker (code-review role), and the API reads its stores for the Run page. Its root holds the two Nest modules and the gate that keep the Runtime at zero cost where it is off. The flows (target, refusals, keys, comment slot, check, renderer, redrive, Run page) are in [README.md](README.md).

## Owns
- Whether the product worker loads the Runtime at all: `runtime-feature.ts` `isKodyRuntimeEnabled` (`RUNTIME_ENABLED`, else `RUNTIME_RUN_TOKEN_SECRET`), read by `apps/worker/src/worker.module.ts`.
- The publisher's wiring: `runtime-publish.module.ts` `RuntimePublishModule` binds every port token of `domain/runtime-publish.ports.ts` to a product service or an adapter of `infrastructure/`, and reads `API_FRONTEND_URL` and `RUNTIME_PREVIEW_DOMAIN` once.
- The PR observation gate the webhook handlers take: `runtime-pull-request-gate.module.ts` `RuntimePullRequestGateModule` (global), `pullRequestGateOf` (membership or the environment's own row, `libs/runtime/api/infrastructure/membership-pull-request.gate.ts`).
- In-memory doubles of its stores for specs: `testing.ts` `InMemoryRunTargetStore`, `InMemoryPublicationStore`, `InMemoryCommentSlotStore`.

## Subfolders
- `domain/`: the rules and ports: run target, publication keys and claims, comment slot, environment, redrive policy, the renderer, the Run page view.
- `application/`: the use cases: `PublishRuntimeRequestUseCase` and its comment, check and reply publishers, the redrive sweep, the skipped-trigger reply.
- `infrastructure/`: the broker consumer, the cron, the Postgres stores and models, the product readers and the metrics.

## Does not own
- The message and its keys: `libs/runtime/run` (`RuntimePublishRequestedSchema`, `publishKey`, queue names).
- Writing the Run target: the API, at enqueue (`libs/runtime/api/application/runtime-run-enqueuer.service.ts`). The publisher only reads it.
- Deciding the verdict or the report's fields: the runtime-worker (`apps/runtime/src/worker/run/`) and `libs/runtime/run`.
- The HTTP routes: `apps/api/src/controllers/runtime/` and the use cases in `libs/runtime/api`.

## Rules and limits
- Where to publish comes only from the product's `runtime_run_targets` row, re-checked against the org's integration config; nothing in the Runtime's message names a target.
- Only structured fields reach the PR, through the product's renderer; Runtime free text is refused (`unstructured_body`).
- The Runtime never reads or writes this lib's tables (`runtime_run_targets`, `runtime_publications`, `runtime_pr_comments`, all in the product Postgres).
- Off (`isKodyRuntimeEnabled` false), the worker imports none of these modules: no queue declared, no outbox row, no PR event recorded.
- Production code never imports `testing.ts`; specs in `libs/runtime/api/__tests__` and `apps/runtime/src/e2e` do.
- `runtime_publications` has no retention yet.

## Where new code goes
- A new port the publisher needs from the product: a token and interface in `domain/runtime-publish.ports.ts`, its binding in `RuntimePublishModule`, its adapter in `infrastructure/`.
- A new store method: the domain interface, the Postgres store and the in-memory double in `testing.ts`, with the same semantics, plus a case in the store's integration spec.
- A new route or Run page field: `libs/runtime/api`, reading through `domain/run-publication-view.ts`.

## Tests
- `API_NODE_ENV=test npx jest libs/runtime-publish` (unit, no services).
- Postgres stores: `RUNTIME_IT_DATABASE_URL=postgres://… API_NODE_ENV=test npx jest libs/runtime-publish/infrastructure --runInBand` (skipped without the variable or with `SKIP_INTEGRATION=true`).
