# apps/runtime/src/worker/agent

The runtime-worker's clients of the product's model and planner endpoints, and the Run's test planner driver. It runs in the runtime-worker, inside the Run's `agent:plan` step and the setup's recipe and learn steps: adapters of the `LlmGateway` and `RunPlanClient` ports over the API's `/internal/runtime/*` routes, plus `RuntimeAgent`, which turns the planner's answer into checked probes and tests for the replay. The worker never holds an LLM key or a Git credential; the product does.

## Owns
- The Run's plan: `runtime-agent.ts` `RuntimeAgent.plan`. With a `RunPlanClient` it drives the planner's rounds (`planOnHarness`): shell commands and browser exploration on the base claim as exec steps (`stableStepId`), output redacted and canary-checked before it goes back, the plan checked again with `checkPlanSubmission`. Without one it falls back to the two-turn loop over `LlmGateway` (`planInTwoTurns`).
- The reconnaissance pass: `plan-recon.ts` `reconOnBase` sends each http probe to base once, `reconDoubts` reads what is wrong with it, and one revision round may fix paths and compares, never the expected status (`keepFirstStatuses`).
- Model turns: `llm-gateway.ts` (the `LlmGateway` port, `RecordedLlmGateway` for recorded fixtures), `http-llm-gateway.ts` `HttpLlmGateway` (`/internal/runtime/llm`).
- Planner clients: `http-run-plan.ts` `HttpRunPlanClient` (`/internal/runtime/plan`, planner in the product) and `CanaryGuardedRunPlanClient`; `worker-plan-client.ts` `WorkerRunPlanClient` (planner in this worker, `RUNTIME_PLANNER_HOST=worker`) over `http-model-turn.ts` `HttpModelTurnClient` (`/internal/runtime/model-turn`) and the product's scoped source reads (`PLANNER_SOURCE_PATH`); `model-turn-frames.ts` is the pure SDK framing.
- Setup clients: `http-recipe-author.ts` `HttpRecipeAuthorClient` (Kody writes a missing recipe), `http-setup-repo-tokens.ts` `HttpSetupRepoTokensClient` (fresh sealed download tokens for another boot).
- When a call to the product is sent again: `product-call.ts` `postToProduct`, `neverReached`, `mayHaveReached`.

## Does not own
- The planner itself and the plan's shapes and checks: `libs/runtime/planner`, `libs/runtime/contracts/run-plan`.
- The verdict: `libs/runtime/gate`, `libs/runtime/run`. The agent's words never create a finding; only its probes, replayed on both sides, do.
- Canary vault and the canary-guarded gateway: `worker/canary`. Opening sealed tokens: `worker/secrets`.
- The routes and budgets on the product side: `apps/api/src/controllers/runtime/`, `libs/runtime/api`.
- When the plan step runs and what reuses a plan: `worker/run` (`run-orchestrator.ts`, `plan-reuse.ts`, `early-plan.ts`).

## Rules and limits
- A sealed token is opened only inside the call that sends it, and travels only in the Authorization header ([apps/runtime/AGENTS.md](../../../AGENTS.md) "Secrets", [README "Sealed tokens"](../../../README.md#sealed-tokens)).
- A request the product never received is sent again (`PRODUCT_CONNECT_RETRY_MS`, about two minutes); one that may have reached it is not, unless the product deduplicates it (`resend: 'deduplicated'`, the recipe author's `attempt`). Model turns and planner rounds are billed, so never resent.
- Every round's body and every browser request and result are checked for the Run's canaries before they leave or are kept; a canary is a `CanaryLeakError` that halts the Run.
- A plan that never came is a rejected reason (`noPlanReason`), never "nothing to test".
- Bounds: `RUN_PLAN_LIMITS` (explore commands, rounds, diff), `boundedFiles` (8,000 chars per file, 40,000 in all), `RECON_LIMITS`, bounded streamed product responses (`readRuntimeRpc`).
- Budget errors are `LlmBudgetExceededError`, everything else `LlmUnavailableError`; neither echoes the token.

## Where new code goes
- A new call to the product: its own `http-*.ts` client over `postToProduct`, a port the caller depends on, and the route in `apps/api/src/controllers/runtime/`.
- A new planner input or answer field: `libs/runtime/contracts/run-plan` first (shared with the product's planner), then `RuntimeAgent`.
- A new step inside the plan changes the workflow's step order: see [apps/runtime/AGENTS.md](../../../AGENTS.md) "Workflow code (DBOS)".

## Tests
- `API_NODE_ENV=test npx jest apps/runtime/src/worker/agent` (no services: fake fetch, fake environment). `runtime-agent.harness.spec.ts` covers the planner rounds and browser exploration; `worker-plan-client.spec.ts` the worker-hosted planner through the production gateway.
