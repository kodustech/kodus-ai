# apps/runtime/src/worker

The runtime-worker: consumes the product's Runtime commands from RabbitMQ and runs each Run and environment setup as a DBOS workflow, reaching cells only through the hub over HTTP. Its root files are the process's composition root; the work lives in the subfolders below. See [apps/runtime/README.md](../../README.md) "runtime-worker".

## Owns
- `main.ts` `bootstrap`: loads and validates `WorkerConfig` (`loadWorkerConfig`) before anything connects, starts OpenTelemetry with the release version, and boots the Nest application context.
- `runtime-worker.module.ts` `RuntimeWorkerModule.forConfig`: the one place every provider is built from the validated config (RabbitMQ with `workflow.exchange` checked, never declared; the Postgres pool and schema; locks; stores; the hub client; the Run, setup, session, sandbox and preview services; the evidence store). No import-time side effects.
- `fakeEnvironments` in `runtime-worker.module.ts`: the dev-only in-memory environment (`RUNTIME_ENV_DRIVER=fake`), loaded lazily from `fake-cell/scenarios`; the production image refuses it.
- `workflow-cancellation.ts` `isCancellation`: a DBOS cancellation or ownership conflict, recognized by name or constructor, so callers rethrow it untouched instead of finishing the Run.

## Subfolders
- `agent/`: clients of the product's model and planner endpoints, and the Run's test planner driver (`RuntimeAgent`).
- `canary/`: finds and redacts a Run's canaries at the control plane's boundaries; guards every LLM prompt.
- `commands/`: one handler per product command (Run requested and cancelled, approvals, stop, setup, pool, cell tokens, lessons).
- `consumer/`: the two RabbitMQ subscriptions (Run lane, control lane) and the Run lane's delayed retry.
- `dbos/`: the engine: workflow and queue registration, start/stop/approve, the maintenance tick, the Run's dependencies, durable admission.
- `env/`: the `EnvironmentRuntime` adapter over the hub's internal listener, and the waits around an acquire.
- `env-session/`: the developer's interactive environments and the signed listener the API reaches the worker through.
- `evidence/`: the evidence server of the file store (signed reads, granted uploads, retention).
- `intent/`: the intent phase of a Run's findings and the repository tests that back an `intended`.
- `maintenance/`: the hang detector; reports what stayed past its bound, never acts.
- `persistence/`: read-only queries of the hub's claim, egress and blocker tables.
- `preview/`: preview URLs, one `preview` claim per start.
- `publish/`: `RuntimePublishRequested` to the product, confirmed by the broker.
- `run/`: the Run workflow: boot, plan, replay, verdict, report, publish.
- `sandbox/`: code sandboxes for the review and custom agents, and a closed PR's sessions.
- `secrets/`: opening and sealing tokens bound to a Run or a setup.
- `setup/`: the environment setup workflow: boot the default branch, check health, bake, learn from failures.

## Rules and limits
- Layering, DBOS determinism, secrets and tenant scope: [apps/runtime/AGENTS.md](../../AGENTS.md). The worker never imports `hub/` and reaches the hub only through `env/hub-environment-runtime.ts`.
- A provider the production wiring needs is a required injection, so a lost one fails at boot (see `runtimeCommandHandlersProvider`, `worker/commands`).
- Settings are read only through `shared/config.ts`; a new one goes into `WorkerConfig` and the README table.

## Where new code goes
- A new service or store the worker needs: a provider in `RuntimeWorkerModule.forConfig`, the code in the subfolder of its concern; never a new loose file at this root.
- A new subfolder: its own `AGENTS.md` and a line above.

## Tests
- `API_NODE_ENV=test npx jest apps/runtime/src/worker`. At this root: `runtime-worker.admission-wiring.spec.ts` (the hub and the worker share the org claim cap), `background-diagnostics.spec.ts` (fixed background failure events, no interpolated exception), `workflow-cancellation.spec.ts`.
