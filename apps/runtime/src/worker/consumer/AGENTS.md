# apps/runtime/src/worker/consumer

The runtime-worker's broker entry: two RabbitMQ subscriptions on `workflow.exchange` that unwrap the product's outbox envelope and route each event to its handler in `worker/commands`. It runs in the runtime-worker and is an inbound adapter; it decides nothing about a Run.

## Owns
- `run-request.consumer.ts` `RuntimeCommandConsumer.onMessage`: the Run lane (`workflow.jobs.runtime_run.queue`, channel `channel-runtime-run`): Run requested, cancelled and setup requests. It checks the lane (`isRunLaneEvent`), the routing key and the retry counter before dispatch, and passes the delivery's `messageId` and redelivery flag to the handler.
- `RuntimeCommandConsumer.onControl`: the control lane (`workflow.jobs.runtime_control.queue`, channel `channel-runtime-control`): stop, revoke, approvals, pool. A failed control dispatch is dead-lettered, never retried here.
- `RuntimeCommandConsumer.handle`: unwraps `event_name` and `payload` (a bare body is a Run request), finds the handler by event and dead-letters an unknown event or an `invalid` result with `Nack(false)` and a closed `reason`.
- `runtime-run-retry.ts` `RuntimeRunRetry`: a Run-lane dispatch that throws is republished to `workflow.exchange.runtime_run_retry` with `x-retry-count` + 1 and an exponential `x-delay`, and the original is acked only after the broker confirms; past `RUNTIME_COMMAND_MAX_RETRIES` it is nacked to the dead-letter queue. `deserializeRuntimeCommand` returns poison input to the consumer instead of letting the library log it.

## Does not own
- What each event does, the per-PR lock, supersede and the PR generation fence: `worker/commands` (`run-requested.handler.ts`, `command-handlers.ts`), `shared/admission/pr-admission-store.ts`.
- Starting workflows: `worker/dbos/run-engine.service.ts`.
- The message schemas, queue and routing names: `libs/runtime/run` (`run-messages.ts`), `libs/runtime/contracts/runtime-commands.ts`.

## Rules and limits
- Idempotency is the DBOS workflow id, not a product inbox: a redelivered request starts nothing new. The ack happens only after the handler returned, so after the workflow is durably enqueued.
- A Run command on the control lane, or a control command on the Run lane, is dead-lettered.
- Logs carry closed reasons and counters only: never the payload, the parse error or a header the product left (`x-last-error` is stripped on retry).
- Cancellation stays on the Run lane, ordered with Run requests; stop and approvals never wait behind them.

## Where new code goes
- A new command: a handler in `worker/commands` registered in `runtimeCommandHandlers`, and its event name in the lane set of `libs/runtime/contracts/runtime-commands.ts`. Nothing here changes unless the envelope does.

## Tests
- `API_NODE_ENV=test npx jest apps/runtime/src/worker/consumer` (routing, lanes, retry headers, exhaustion). `testing.ts` `consumerWith` builds a consumer over the real handlers with an in-memory lock.
- `runtime-run-retry.integration.spec.ts` runs against a real RabbitMQ only with `RUNTIME_RETRY_IT_ADMIN_URL` and `RUNTIME_RETRY_IT_MANAGEMENT_URL` (skipped otherwise); `run-retry-ordering.spec.ts` covers the PR generation fence across retries.
