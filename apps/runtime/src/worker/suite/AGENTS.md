# apps/runtime/src/worker/suite

The runtime-worker's side of running a repository's own e2e suite (docs/runtime/e2e-suites.md). The pure rules (balance, parse, classify, select, order) are `libs/runtime/suite`; this folder holds what touches Postgres, the fleet and the environment runtime.

## Owns
- `pg-suite-runs.ts` `PgSuiteRuns`: `runtime_suite_runs` (idempotent `create` by `suiteRunId`, `get`, `latestForPr` for the re-push rule, `finish`: the first conclusion stays, and it stores the run's `classification` (migration 53, `jsonb`) with it), `runtime_suite_shards` (`savePlan`, `shards`) and `runtime_suite_results` (`recordResults`: one row per spec and phase `shard | rerun_pr | rerun_main`, a result reported again replaces the earlier one; `results`). Every read names the organization.
- `pg-suite-baselines.ts` `PgSuiteBaselines`: `runtime_suite_baselines`, unique per (environment, main sha, suite digest). `record` keeps the first complete baseline of a key and lets only a complete one replace an incomplete one; `find` and `findAmong` (nearest ancestor first) answer complete baselines only; every `record` prunes the environment: the newest `BASELINE_KEEP_COMMITS` (50), nothing older than `BASELINE_KEEP_DAYS` (30), and the newest complete baseline is never deleted.
- `pg-suite-spec-stats.ts` `PgSuiteSpecStats`: `runtime_suite_spec_stats`, the duration the next plan balances by (`read` as `SpecStats`). `record` folds only passing specs into an exponential average over about 10 runs (`STATS_WINDOW`), atomically per spec; a failed, skipped or timed-out spec changes nothing. What `record` is given is the wall time a spec cost its shard (`SuiteEngine.wallObservations`: the reported duration plus the shard's per-spec overhead, `perSpecOverheadMs` in `libs/runtime/suite`), because a runner that starts per spec does not count that start in its duration.

- `pg-suite-coverage-maps.ts` `PgSuiteCoverageMaps` (build-plan step 11, migration 55): `runtime_suite_coverage_maps`, per (environment, main sha, suite digest) the files each spec exercised, written by a baseline run (`record`: the first complete map of a key stays, a complete one replaces an incomplete one and nothing else; every `record` prunes the environment to the newest `MAP_KEEP_COMPLETE` (2) complete maps, an incomplete one stays only while newer than the newest complete). `newest` answers the environment's newest complete map whatever its digest: `SuiteService` turns it into the `CoverageMapInput` selection reads (the map's commit is placed in main's history of the run, main's head or the merge base; any other commit cannot be placed and is `map_stale`; its age is the clock minus `finishedAt`, so D12's 20 commits or 3 days applies), and a map of another digest is `map_digest`: a changed spec list is never judged by the old map. The map is the worker's: the product has no reader grant on it; the organization purge covers it. The per-spec flake rate of 9.6 is not stored: nothing in selection or ordering reads it.
- Evidence (build-plan step 18, section 7 and D8, migration 56): `suite-artifacts.ts`. `SuiteEngine` calls the optional `artifacts` keeper (`SuiteArtifactKeeper`) once per shard right after its first pass, for a PR run only, while the shard's claim is still held and before a re-run can overwrite the files, and only when the recipe names `suite.results.artifacts` and a spec of the shard failed. The keeper lists the files under those directories on the host (`ExecArtifactSource`: `find` and `wc`, then `od` in 64 KiB chunks, POSIX and binary-safe, the exec output limit never reached), `planArtifacts` (`libs/runtime/suite`) keeps those of failed specs only, each of a kind the evidence holds (png, webm, zip, log, txt, json) and within its size, all within `SUITE_ARTIFACT_BUDGET_BYTES` (200 MiB, shared by the shards in turn through `SuiteInputs.artifactBudgetBytes`), then each is read, a text one is redacted (`redactPatterns`, then the Run's canaries) and written by the worker under the `suite-artifact` key (`suiteArtifactKey`: `{org}/{suiteRun}/{side}/{derived id}/suite-artifact`, so every store, the TTL and the organization purge treat it like other evidence). A cell never gets a grant for this type. The refs (name, key, content type, bytes) are stored on the spec's result (`PgSuiteRuns.recordArtifacts`, `runtime_suite_results.artifacts`). A canary in an artifact (`SuiteInputs.canaries`: the Run's, passed by the stage) is stored redacted and stops the suite: every first-pass command is stopped, nothing is re-run or judged, the run ends `failed` and the outcome and `SuiteServiceResult` say `leaked`, which makes the Run `halted`. A file that cannot be read or stored is dropped with its reason; a keeper that throws loses the artifacts, never the result. Not done: videos in a format the evidence does not hold (Cypress writes mp4) are dropped, and a spec's artifacts are attributed by its path or file name appearing in the file's path (a tie is no owner).
- What a run cost in machine time (migration 59, `first_pass_ms` and `rerun_ms` on `runtime_suite_runs`): the engine adds the time each host was held, summed over hosts, for the first pass (shards, a baseline) and for the re-runs (PR re-runs, the main host, the fresh host), and stores it with the conclusion; null on a run stored before, never zero. The Run page's "Machine time" and the usage report's lines read it.
- Who turned selection off (migration 58, `off_by`): `PgSuiteSelectionState.turnOff` (a person; a brake already on stays the brake) and `applyMiss` (the shadow check) set it, `reenable` clears it. The settings screen shows a brake as "paused" with Resume, and a person's choice as the switch it is.
- Which changed file reached which spec (`selection.reachedBy`, from `libs/runtime/suite/select.ts`): stored in `runtime_suite_runs.selection` for a first-push selected run, bounded; the Run page's "Why these N specs" reads it.
- The shadow check of selection (build-plan step 19, 6.1 Proof b, D14; migration 57, `pg-suite-shadows.ts`, rules in `libs/runtime/suite/shadow.ts`). `PgSuiteSelectionState` (`runtime_suite_selection_state`, per environment) counts the selected runs a PR plan made (`recordSelected`, atomic; a plan whose run row already exists, a retry, a baseline and a shadow count nothing, and neither does a whole-suite plan) and `SuiteService` asks for a shadow on the 5th selected run, then every 5th up to 50 and every 10th after: `PgSuiteShadows.request` (`runtime_suite_shadows`, one per source run, with the specs the run ran, the files the PR changed and removed). The worker cannot mint the shadow's download tokens, so the product issues it (`RuntimeSuiteShadowRequests` in `libs/runtime/api`) as `runtime.suite.requested` of mode `shadow`: the whole suite on the PR head (selection `shadow`), classified like any PR run, never published (`SuitePublisher` and the service skip it), never in `latestForPr` (the re-push rule) and never cancelled by a newer push. When it ends (`settleShadow`, its own step) the regressions it found in specs the selection skipped (`missesOf`, a `regression_unconfirmed` too) are its `selection_misses`: one miss sets the environment to the whole suite for the next 10 pull requests (`full_prs_left`, each new PR takes one, a re-push of a PR that ran under it stays whole; reason `selection_miss`) and raises `SelectionAlert` (logged in `suite-wiring.ts`); misses are counted per spec, and two among the last ten conclusive shadows (since the last `reenable`) turn selection `off` (reason `selection_off`, never turns itself back on). A shadow that did not finish is inconclusive and counts for nothing; one that already completed changes nothing when asked again. Not done: the metric `runtime.suite.selection_miss`, and the way a person turns selection back on (`PgSuiteSelectionState.reenable` exists; no API or screen calls it: step 17).
- `detached-exec.ts` `runDetached`: a suite command started once, detached, in the claim and polled by short `exec` calls (each under `POLL_TIMEOUT_MS`, 60 s, far under the protocol's 600 s), no protocol change (design decision D3). A wrapper writes the exit status and the log to a state directory; the marker file makes a second start (a replay) do nothing; each poll reads the state (`running`, `exited:<code>`, `dead`), the result files that exist (a path pattern, validated) and the log tail, and hands them to `onPoll`. Outcomes: `finished` (exited; red specs are results), `cancelled` (the caller's `signal` aborted: the command and its children are stopped as at the timeout and what finished is named; a signal already aborted starts nothing), `crashed` (died with result files: the engine keeps them and re-runs the rest once), `timeout` (the shard cap: the command and its children are stopped), `infra` (`no_result_file`, `transport_lost` after 3 lost polls in a row, `start_failed`, `bad_results_glob`, `bad_input`, `service_unsupported`: never a regression). With `service` every call (start, polls, kill, final poll) names the compose service it runs in (`exec.service`); a cell without the `execService` feature answers `exec_service_unavailable` to the start and the shard is `infra/service_unsupported`, never run in another container. Clock and sleep are injected; step ids derive from the key and the poll number.
- The suite's `service` (`suite.service`, `SuiteConfig.service`): the engine runs the command, the clear, the result reads and the coverage read through `execInService` (`suite-environment.ts`), and `SuiteService` gives the artifact source the same scoped environment; the spec listing at the template host runs in that service too (the public service's image may leave the specs out: kr-mono's .dockerignore drops cypress/). `cwd` is relative to the target container's workdir. `suite.image` is refused by the recipe (the environment's compose file holds the services).
- `suite-engine.ts` `SuiteEngine.run(request, inputs)`: the first pass (build-plan step 7). It creates the run (idempotent: a finished run asked again returns its state with `replayed: true` and runs nothing), plans shards from the stored durations (`shardCount`, `balanceSpecs`), asks the fleet for one host per shard (`SuiteHostDemand`, asked again every 45 s while the run lives because a demand row lasts 120 s), waits up to `HOST_WAIT_MS` and spreads the specs over the hosts that came (`spreadOnto`), acquires one `suite` claim per shard (PR side at the PR head, `base` at the main sha for a baseline, bound to `suite:<org>/<run>/<shard>` through `AcquireRequest.suiteRunId` and `shard`), runs the shard's specs with `runDetached`, reads every new result file with a `cat` exec as it appears (JUnit, or Mochawesome for `.json`) and stores each spec's result at once. A crashed runner re-runs what it had not reported once, in the same claim; a second crash is `infra`. A shard that finishes early takes half of the specs of shards whose command has not started (`pending`: a host that boots late, or a refused claim) and runs them in its own claim (`stealPending`); a late claim whose specs were all taken is not waited for and is released when it comes up; the plan is rewritten to who ran what. The shard count's target is cut to 80% of the shard cap and of the time left to `deadlineAt` (`shardTargetMs`). A shard past its timeout is stopped: what finished stays, the rest is `not_run`. A blocked claim or no host at all is `infra` for its specs. It records the durations of passing specs, releases every claim and ends the demand.
- The re-run phase (step 8, `SuiteEngine.rerunPhase`, never for a baseline): specs that never reported (`infra`, `not_run`) run once more on a fresh host (extra shard `FRESH_HOST_SHARD` 62, PR side; what it reports joins the first pass, and a spec that was infra is still listed as class `infra` when it passed there, `unclassified/infra` or `unclassified/not_run` when it did not). Then `planReruns` (mass failure over 25% of the specs that ran: nothing re-runs; the 40-spec budget) and, at the same time, the PR re-run (each failed spec again in the claim of the shard that ran it first, which holds the PR build: no new host, results phase `rerun_pr`, the results directory emptied first) and the main re-run (one template host, extra shard `MAIN_HOST_SHARD` 63, side `base` at `mainSha`, phase `rerun_main`; no ready template, `SuiteTemplates.hasReady`, is `template_missing` and asks for a build; no host in 2 attempts is `no_host`). `classifyFailures` labels every red test (`SuiteOutcome.classification`); the run state follows D4: a `regression` is `failed`; flaky, pre-existing and a recovered infra never fail; anything unconfirmed or unclassified with no regression is `neutral`, `failed` with `suite.gate: strict`. Both extra shards are demand rows of the same suite run (`suite:<org>/<run>/62|63`), so `PgSuiteDemand.status` and `end` cover them; the template host of main is made from the environment's template because the fleet resolves a template by environment, whatever the bound key.
- What the diff reaches (docs 8.2, 9.3): `SuiteService.plan` reads the environment's newest coverage map (also under the shadow brake, and for a retry) and `diffReach` (`libs/runtime/suite/plan.ts`) gives `plan.reach`; it goes to the engine as `SuiteInputs.diffReachedSpecs`, so a failing spec the diff reaches is a `regression` even while main is ahead. With no usable map the reach is only the specs the PR changed itself, and while main is ahead the selection stored on the run carries `reachUnknown` (the structured reason the check renders).
- The baseline (step 9): a `baseline` run is the first pass on main alone (side `base` at `mainSha`, never re-run or classified) and `recordBaseline` stores each spec as it ended under (environment, main sha, `suiteDigestOf`), `complete` only when every spec reported. A PR run reads the baseline of its merge base through `SuiteInputs.mainHistory` (main's commits, head first): `findAmong` from the merge base back, `baseDrift` counted in the history, and the classifier decides whether it is evidence (the exact merge base, the same digest, at most 20 commits behind). With a usable baseline the PR re-run goes first and main only gets the specs the baseline does not already explain (`needsMainRerun`); without one both go at the same time.
- Cancelling (docs section 11): `SuiteInputs.signal` is the workflow step's cancel signal (the Run's, for a stage). Aborted, every command is stopped as at the timeout, a shard still waiting for a host takes no claim, nothing is re-run or classified, claims and demand are released by the cleanup and the run ends `cancelled` (no finding; the first conclusion stays). `suite-canceller.ts` `SuiteCanceller.cancelPullRequest` (called by the cancel of a PR's Runs: a new head keeps its own, a closed PR keeps none) cancels the PR's live CI-mode suite workflows through `PgSuiteRuns.livePullRequestRuns` and `RunEngineService.cancelSuite`; a Run-mode suite goes with its Run's stop. A cancelled workflow runs no further step, so `SuiteService` closes the check inside its own `suite:run` step (`SuitePublisher.finished` with the cancelled state) and, when the cancel fell between the check's opening and the engine, in the catch (`SuitePublisher.cancelled`). A suite still queued (no run row yet) when the cancel arrives is not found and starts; not done. Not done in the engine: `suite.retries.main` 2 (D1), the re-run cap derived from the failed specs (a flat `RERUN_TIMEOUT_MS` of 12 min), `timedOut` of a spec (the parsers do not report it), the JUnit reporter flag the design adds to the command.
- Production wiring (build-plan step 15's predecessor, section 11): `suite-service.ts` `SuiteService.run(cmd, step)` is the body of the DBOS workflow `runtimeSuite` (`runtime-suites` queue, workflow id `suite:<suiteRunId>`, `RunEngineService.startSuite`): step `suite:start` reads the recipe's `suite` block from the environment's setup record (`suite-config.ts` `suiteConfigOf`; none, or a baseline with `baseline: false`, is `off` and no run row) and, for a baseline, marks its request started (`PgSuiteBaselineRequests.markStarted`: the product reads with a read-only role, so the worker answers it); step `suite:run` lists the specs, runs the engine and returns a slim result. The engine is idempotent (a finished run is answered, a claim is acquired by its key, a command starts once), so a step that runs again after a crash finishes what was left; the engine's own I/O is not journalled one call at a time. A run that cannot start (`template_missing`, `no_host`, `list_failed`, `no_repository`, `no_specs`) ends `neutral`. `spec-lister.ts` `TemplateSpecLister` lists main's spec files on a template host (shard `LIST_HOST_SHARD` 61, side `base` at `mainSha`, one `find` under the glob's fixed directory), and `libs/runtime/suite` `specListOf` puts the PR's added and removed files (`changedFiles`, `removedFiles` of the command) on that list; `suite-environment.ts` `bootingAsRuns` makes every suite acquire (shards, the fresh host, main's host, the listing host) carry what the environment's setup recorded, as a Run's claims do: the recipe with Kody's build files (`setup/recipe-for-claim.ts` `recipeForClaimOf`, shared with the Run's handler) and the setup's machine size; without them the shards booted the checkout's own Dockerfile and the egress refused what it fetched. `suiteEnvironment` acquires each claim with a download token of its own (the cell revokes a token once it fetched with it: the command carries `repoToken` and `moreRepoTokens`) and renews each claim as consumer `suite` until it is released; `suite-adapters.ts` `PlacementSuiteDemand` (the demand rows over `PgSuiteDemand`, on the perRun pool placement would choose; no such pool fails every shard at once) and `mainHistoryOf` (the worker holds no Git history: the product counts the commits between the merge base and main with the platform's compare API and sends `mainBehind`, cut at 21; the history is main, that many commits the worker cannot name, then the merge base, so the drift and a baseline's age are real. With no count, a merge base that is not main's head is put one commit behind: a drift of at least one, never zero; a retry carries the drift of its original).
- `coverage-collector.ts` and the baseline's coverage (build-plan step 10, 6.1, D10): `SuiteInputs.coverage` (a baseline only; a PR run ignores it and never sets `NODE_V8_COVERAGE`) makes each shard run its specs one command each, one after the other (a service never sees two specs together), with `NODE_V8_COVERAGE` on a directory of that spec (`coverageDirOf`). When the command ends `collectCoverage` runs `COVERAGE_COLLECT_SCRIPT` (plain Node, on the claim) over the directory: the repository-relative files with a function that ran, from V8 dumps and Istanbul objects, `node_modules` out, then the directory is removed. A spec whose dumps cannot be read has no entry, and `SuiteEngine` records a `CoverageMapRecord` through the optional `maps.record` port: `complete` only when every spec of the suite has its files (a red spec on main keeps what it exercised). Collects what Node processes started by the suite command dump; compose services that are already running are not reached (the claim would have to start them with `NODE_V8_COVERAGE` and a flush hook): not done. `detached-exec.shell` style real-shell spec: `coverage-collector.shell.spec.ts`.
- `testing.ts`: `SuiteClock`, `FakeSuiteEnvironment` (a suite command in fake time), the in-memory twins of the stores (`InMemorySuiteRuns`, `InMemorySuiteSpecStats`, `InMemorySuiteBaselines`; same public methods and rules as the Postgres ones), `FakeSuiteDemand` and `FakeSuiteCell` (acquire, exec and release of a whole suite engine in fake time: each spec ends with the outcome the scenario gives its side and attempt, and the runner's JUnit is real text). Specs only.
- Publishing (build-plan step 15): `suite-publisher.ts` `SuitePublisher` (`started`: the check opened `in_progress` when the suite starts; `finished`: closed with the conclusion of the run's stored state, from the stored results, classification, selection, baseline and drift, so a replay publishes the same thing; a baseline or an environment with no suite publishes nothing). The service calls it in the steps `publish:suite-started` and `publish:suite-final`, which retry like a Run's publish steps; `worker/publish/amqp-suite-publish-requester.ts` writes the message. The run keeps `selection` (how the specs were chosen, set at create from `SuiteInputs.selection`), `baseline_sha` and `base_drift` (migration 54).
- Request path and Run mode (build-plan step 16): the service plans the specs with `planSuiteRun` (a baseline is the whole suite; a retry names its own specs; a PR run reads its earlier finished run from `PgSuiteRuns.latestForPr(…, before)` for the re-push rule and the coverage map from `maps.newest`, absent only where no store is wired), stores the selection on the run (`SuiteInputs.selection`), orders each shard risk-first (`SuiteInputs.order` → `orderBin`), and ends a run whose change reaches no spec `passed` without a shard host. `suite-stage.ts` `SuiteRunStage` is the Run's stage: the Run request's `suite` section becomes the `mode: run` command (`targetId` the Run, key the Run id, the suite run id derived from the Run) and the same `SuiteService.run` runs inside the Run's workflow with the Run's step runner; `suite-wiring.ts` `buildSuiteService` builds the one service both the `runtime.suite` workflow and the stage use. Fail fast (6.1) is wired: the first pass of a PR run feeds each finished spec, in order across shards, to `failFast`; when more than 25% of the first batch is red the engine aborts every shard's command, a shard still waiting for its host takes no claim, the specs that did not run are `not_run` and are not given a fresh host, and the classifier sees the mass failure (no re-run). A baseline, the fresh host and the re-runs are never cut short. By design (D9) the stage runs after the probes, never in parallel, and a Run-mode suite shares the Run's 45 minutes: the stage hands `SuiteService.run` a `deadlineAt` (`SuiteInputs.deadlineAt`), no wait for hosts, command or re-run goes past it and what did not run is `not_run` (neutral, a partly tested Run); long suites belong to CI mode.

## Does not own
- The balance, classification, selection and order rules: `libs/runtime/suite`.
- The hosts a suite runs on and their demand rows: `apps/runtime/src/fleet`, `shared/persistence/cell-directory.ts`.
- The suite commands' schemas (`RuntimeSuiteRequested`, `RuntimeSuiteRetried`): `libs/runtime/contracts/runtime-commands.ts`. `worker/commands` `SuiteRequestedHandler` and `SuiteRetriedHandler` (`worker/commands`) start the workflow through the `SuiteStarter` port.

## Rules and limits
- Tables are migration 51 (`shared/persistence/runtime-schema.ts`); each carries `organization_id`, so the organization purge reaches them and a read is always scoped. The API reads them with the read-only role (`scripts/runtime/runtime-reader-grants.sql`).
- Results hold redacted, bounded errors only; the engine redacts before it stores (docs section 7).
- The start and poll scripts are POSIX `sh` (no `setsid`, no `base64`): the command text goes through a quoted heredoc, the results glob is limited to `[A-Za-z0-9_./*?-]`, relative and without `..`, and the key and the cwd are checked the same way. `detached-exec.shell.spec.ts` runs them in a real shell.
- Stores take a `Pick<Pool, 'query'>` and no clock except the baseline store's injectable `now`.

## Where new code goes
- The re-run phase, the baseline recording and the publisher port: this folder, in later steps of the build plan.
- A new column: a migration at the end of `RUNTIME_MIGRATIONS`, never an edit of 51.

## Tests
- `RUNTIME_IT_DATABASE_URL=postgres://… API_NODE_ENV=test npx jest --config jest.integration.config.ts apps/runtime/src/worker/suite/pg-suite` (real Postgres, opt in).
