# apps/runtime/src/worker/suite

The runtime-worker's side of running a repository's own e2e suite (docs/runtime/e2e-suites.md). The pure rules (balance, parse, classify, select, order) are `libs/runtime/suite`; this folder holds what touches Postgres, the fleet and the environment runtime.

## Owns
- `pg-suite-runs.ts` `PgSuiteRuns`: `runtime_suite_runs` (idempotent `create` by `suiteRunId`, `get`, `latestForPr` for the re-push rule, `finish`: the first conclusion stays, and it stores the run's `classification` (migration 53, `jsonb`) with it), `runtime_suite_shards` (`savePlan`, `shards`) and `runtime_suite_results` (`recordResults`: one row per spec and phase `shard | rerun_pr | rerun_main`, a result reported again replaces the earlier one; `results`). Every read names the organization.
- `pg-suite-baselines.ts` `PgSuiteBaselines`: `runtime_suite_baselines`, unique per (environment, main sha, suite digest). `record` keeps the first complete baseline of a key and lets only a complete one replace an incomplete one; `find` and `findAmong` (nearest ancestor first) answer complete baselines only; every `record` prunes the environment: the newest `BASELINE_KEEP_COMMITS` (50), nothing older than `BASELINE_KEEP_DAYS` (30), and the newest complete baseline is never deleted.
- `pg-suite-spec-stats.ts` `PgSuiteSpecStats`: `runtime_suite_spec_stats`, the duration the next plan balances by (`read` as `SpecStats`). `record` folds only passing specs into an exponential average over about 10 runs (`STATS_WINDOW`), atomically per spec; a failed, skipped or timed-out spec changes nothing.

- `detached-exec.ts` `runDetached`: a suite command started once, detached, in the claim and polled by short `exec` calls (each under `POLL_TIMEOUT_MS`, 60 s, far under the protocol's 600 s), no protocol change (design decision D3). A wrapper writes the exit status and the log to a state directory; the marker file makes a second start (a replay) do nothing; each poll reads the state (`running`, `exited:<code>`, `dead`), the result files that exist (a path pattern, validated) and the log tail, and hands them to `onPoll`. Outcomes: `finished` (exited; red specs are results), `crashed` (died with result files: the engine keeps them and re-runs the rest once), `timeout` (the shard cap: the command and its children are stopped), `infra` (`no_result_file`, `transport_lost` after 3 lost polls in a row, `start_failed`, `bad_results_glob`, `bad_input`: never a regression). Clock and sleep are injected; step ids derive from the key and the poll number.
- `suite-engine.ts` `SuiteEngine.run(request, inputs)`: the first pass (build-plan step 7). It creates the run (idempotent: a finished run asked again returns its state with `replayed: true` and runs nothing), plans shards from the stored durations (`shardCount`, `balanceSpecs`), asks the fleet for one host per shard (`SuiteHostDemand`, asked again every 45 s while the run lives because a demand row lasts 120 s), waits up to `HOST_WAIT_MS` and spreads the specs over the hosts that came (`spreadOnto`), acquires one `suite` claim per shard (PR side at the PR head, `base` at the main sha for a baseline, bound to `suite:<org>/<run>/<shard>` through `AcquireRequest.suiteRunId` and `shard`), runs the shard's specs with `runDetached`, reads every new result file with a `cat` exec as it appears (JUnit, or Mochawesome for `.json`) and stores each spec's result at once. A crashed runner re-runs what it had not reported once, in the same claim; a second crash is `infra`. A shard past its timeout is stopped: what finished stays, the rest is `not_run`. A blocked claim or no host at all is `infra` for its specs. It records the durations of passing specs, releases every claim and ends the demand.
- The re-run phase (step 8, `SuiteEngine.rerunPhase`, never for a baseline): specs that never reported (`infra`, `not_run`) run once more on a fresh host (extra shard `FRESH_HOST_SHARD` 62, PR side; what it reports joins the first pass, and a spec that was infra is still listed as class `infra` when it passed there, `unclassified/infra` or `unclassified/not_run` when it did not). Then `planReruns` (mass failure over 25% of the specs that ran: nothing re-runs; the 40-spec budget) and, at the same time, the PR re-run (each failed spec again in the claim of the shard that ran it first, which holds the PR build: no new host, results phase `rerun_pr`, the results directory emptied first) and the main re-run (one template host, extra shard `MAIN_HOST_SHARD` 63, side `base` at `mainSha`, phase `rerun_main`; no ready template, `SuiteTemplates.hasReady`, is `template_missing` and asks for a build; no host in 2 attempts is `no_host`). `classifyFailures` labels every red test (`SuiteOutcome.classification`); the run state follows D4: a `regression` is `failed`; flaky, pre-existing and a recovered infra never fail; anything unconfirmed or unclassified with no regression is `neutral`, `failed` with `suite.gate: strict`. Both extra shards are demand rows of the same suite run (`suite:<org>/<run>/62|63`), so `PgSuiteDemand.status` and `end` cover them; the template host of main is made from the environment's template because the fleet resolves a template by environment, whatever the bound key.
- The baseline (step 9): a `baseline` run is the first pass on main alone (side `base` at `mainSha`, never re-run or classified) and `recordBaseline` stores each spec as it ended under (environment, main sha, `suiteDigestOf`), `complete` only when every spec reported. A PR run reads the baseline of its merge base through `SuiteInputs.mainHistory` (main's commits, head first): `findAmong` from the merge base back, `baseDrift` counted in the history, and the classifier decides whether it is evidence (the exact merge base, the same digest, at most 20 commits behind). With a usable baseline the PR re-run goes first and main only gets the specs the baseline does not already explain (`needsMainRerun`); without one both go at the same time.
- Not done yet: cancelling a running suite (the workflow's long step has no cancel signal), a real count of main's drift (needs a commit listing from the product), the suite's publication and its Run stage (steps 15 and 16). Not done in the engine: `suite.retries.main` 2 (D1), the re-run cap derived from the failed specs (a flat `RERUN_TIMEOUT_MS` of 12 min), fail fast inside a shard (`runDetached` has no cancel), `timedOut` of a spec (the parsers do not report it), selection and re-push (`select`, `planRepush`), the JUnit reporter flag the design adds to the command.
- Production wiring (build-plan step 15's predecessor, section 11): `suite-service.ts` `SuiteService.run(cmd, step)` is the body of the DBOS workflow `runtimeSuite` (`runtime-suites` queue, workflow id `suite:<suiteRunId>`, `RunEngineService.startSuite`): step `suite:start` reads the recipe's `suite` block from the environment's setup record (`suite-config.ts` `suiteConfigOf`; none, or a baseline with `baseline: false`, is `off` and no run row) and, for a baseline, marks its request started (`PgSuiteBaselineRequests.markStarted`: the product reads with a read-only role, so the worker answers it); step `suite:run` lists the specs, runs the engine and returns a slim result. The engine is idempotent (a finished run is answered, a claim is acquired by its key, a command starts once), so a step that runs again after a crash finishes what was left; the engine's own I/O is not journalled one call at a time. A run that cannot start (`template_missing`, `no_host`, `list_failed`, `no_repository`, `no_specs`) ends `neutral`. `spec-lister.ts` `TemplateSpecLister` lists main's spec files on a template host (shard `LIST_HOST_SHARD` 61, side `base` at `mainSha`, one `find` under the glob's fixed directory), and `libs/runtime/suite` `specListOf` puts the PR's added and removed files (`changedFiles`, `removedFiles` of the command) on that list; `suite-environment.ts` `suiteEnvironment` acquires each claim with a download token of its own (the cell revokes a token once it fetched with it: the command carries `repoToken` and `moreRepoTokens`) and renews each claim as consumer `suite` until it is released; `suite-adapters.ts` `PlacementSuiteDemand` (the demand rows over `PgSuiteDemand`, on the perRun pool placement would choose; no such pool fails every shard at once) and `mainHistoryOf` (the worker holds no Git history: a merge base that is not main's head is put one commit behind, a drift of at least one, never zero).
- `testing.ts`: `SuiteClock`, `FakeSuiteEnvironment` (a suite command in fake time), the in-memory twins of the stores (`InMemorySuiteRuns`, `InMemorySuiteSpecStats`, `InMemorySuiteBaselines`; same public methods and rules as the Postgres ones), `FakeSuiteDemand` and `FakeSuiteCell` (acquire, exec and release of a whole suite engine in fake time: each spec ends with the outcome the scenario gives its side and attempt, and the runner's JUnit is real text). Specs only.
- Publishing (build-plan step 15): `suite-publisher.ts` `SuitePublisher` (`started`: the check opened `in_progress` when the suite starts; `finished`: closed with the conclusion of the run's stored state, from the stored results, classification, selection, baseline and drift, so a replay publishes the same thing; a baseline or an environment with no suite publishes nothing). The service calls it in the steps `publish:suite-started` and `publish:suite-final`, which retry like a Run's publish steps; `worker/publish/amqp-suite-publish-requester.ts` writes the message. The run keeps `selection` (how the specs were chosen, set at create from `SuiteInputs.selection`), `baseline_sha` and `base_drift` (migration 54).

## Does not own
- The balance, classification, selection and order rules: `libs/runtime/suite`.
- The hosts a suite runs on and their demand rows: `apps/runtime/src/fleet`, `shared/persistence/cell-directory.ts`.
- The suite commands' schemas (`RuntimeSuiteRequested`, `RuntimeSuiteRetried`): `libs/runtime/contracts/runtime-commands.ts`. `worker/commands` `SuiteRequestedHandler` and `SuiteRetriedHandler` (`worker/commands`) start the workflow through the `SuiteStarter` port.

## Rules and limits
- Tables are migration 51 (`shared/persistence/runtime-schema.ts`); each carries `organization_id`, so the organization purge reaches them and a read is always scoped. The API reads them with the read-only role (`scripts/runtime/runtime-reader-grants.sql`).
- Results hold redacted, bounded errors only; the engine redacts before it stores (docs section 7).
- The start and poll scripts are POSIX `sh` (no `setsid`, no `base64`): the command text goes through a quoted heredoc, the results glob is limited to `[A-Za-z0-9_./*?-]`, relative and without `..`, and the key and the cwd are checked the same way. `detached-exec.shell.spec.ts` runs them in a real shell.
- Stores take a `Pick<Pool, 'query'>` and no clock except the baseline store's injectable `now`.

## Where new code goes
- The re-run phase, the baseline recording and the publisher port: this folder, in later steps of the build plan.
- A new column: a migration at the end of `RUNTIME_MIGRATIONS`, never an edit of 51.

## Tests
- `RUNTIME_IT_DATABASE_URL=postgres://… API_NODE_ENV=test npx jest --config jest.integration.config.ts apps/runtime/src/worker/suite/pg-suite` (real Postgres, opt in).
